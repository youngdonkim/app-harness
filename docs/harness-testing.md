## 1. 왜 시험하나

하네스 문서는 AI가 읽고 그대로 움직이는 절차입니다. 그래서 문서를 고치면 AI의 행동이 바뀝니다. 그런데 문서만 읽어서는 아래 같은 문제가 보이지 않습니다.

- 문서가 시킨 명령이 이 맥에서 실제로 안 되는 곳 (Flutter·Gradle·Xcode의 새 판이 기본값을 바꾼 경우 등)
- 앞 단계가 만들어 두지 않은 것을 뒤 단계가 「있다」고 여기는 곳
- 위임받은 에이전트가 알 길이 없는 규칙 (스킬에만 있고 지시서에는 없는 규칙)
- 틀(`.claude/templates/`)이 이 판의 Flutter·패키지와 맞지 않는 곳
- 시간·토큰이 생각보다 많이 드는 곳

그래서 고친 하네스를 빈 프로젝트에 적용해, 사람이 끼는 자리까지 끝까지 한 번 돌려 봅니다. 돌리며 막힌 곳과 문서와 실제가 달랐던 곳을 모으면 그게 다음에 고칠 목록이 됩니다. `docs/eval-scenarios.md`(실사고 색인)는 「고친 문제가 다시 생기지 않나」를 머리로 되짚는 목록이고, 이 문서는 실제로 돌려 보는 방법입니다.

## 2. 시험 범위 — 어디까지 돌리나

**3단계의 「이 맥에서 실서비스 방식 앱 번들(AAB) 빌드」까지만 돌립니다.** Firebase 프로젝트와 플레이 콘솔 앱은 만들지 않습니다.

왜 거기서 멈출까요? 그다음부터는 시험마다 바깥에 무언가가 쌓이기 때문입니다.

- Firebase 프로젝트는 시험마다 개발용·실서비스용 두 개씩 생깁니다. 구글 클라우드에는 프로젝트 수 한도가 있고, 요금 계정이 붙습니다.
- 플레이 콘솔 앱은 사업자 계정에 남습니다. 시험 앱이 쌓이면 진짜 앱과 섞이고, 지우기도 번거롭습니다.

그래서 3단계에서 아래는 건너뜁니다. 건너뛴 자리는 보고서 「시험하지 못한 갈래」에 적습니다.

| 3단계 배포 절의 일 | 시험에서 |
|---|---|
| 플레이 콘솔 계정 대조·사업자 정보·앱 만들기·앱 콘텐츠 신고·시험 참가자 목록 | 하지 않습니다 |
| 개인정보처리방침 웹 주소(실서비스 Firebase 프로젝트와 Hosting 먼저 만들기·`backend-release`로 Hosting 올리기) | 하지 않습니다. 웹 페이지 틀을 `hosting/`에 넣는 데까지만 합니다 |
| 패키지 이름 확인·목표 안드로이드 판 확인·스토어 등록정보 초안 | 합니다 |
| 업로드 키 만들기 | 문서 그대로 시험용 키를 만듭니다 — 아래 「업로드 키」 |
| 첫 버전 번호 적기 → `/done-task`로 합치기 → main에서 `store-release` 「번들만 만들기」 | 합니다. 번들의 서명이 업로드 키인지 확인하는 데까지가 끝입니다 |
| 콘솔에서 올리기·폰에서 참가 링크로 받아 확인 | 하지 않습니다. 대신 8절대로 사람이 시뮬레이터·폰에서 직접 봅니다 |

**업로드 키** — 업로드 키는 앱마다 따로, 패키지 이름으로 정한 자리(`~/.config/harness/keys/<패키지 이름>-upload.jks`·`<패키지 이름>-upload.properties`)에 둡니다. 시험은 시험 폴더 이름에서 만든 시험용 패키지 이름(3절)을 쓰니, 문서 그대로 만들어도 진짜 앱의 키와 겹치지 않습니다. 계정 장부 파일은 건드리지 않습니다.

4단계(백엔드) 시험이 필요해지면, 그때 시험용 Firebase 프로젝트 두 개를 한 번만 만들어 두고 모든 시험이 나눠 쓰는 방법을 따로 정합니다.

## 3. 시험 폴더 만들기

1. **하네스 저장소 세션에서 옆에 시험 폴더를 만든다** — 하네스 저장소 폴더에서 세션을 열고(하네스 저장소는 main이어야 합니다 — 원본 검사) "옆에 `harness-test-<날짜>` 폴더 만들고 하네스 적용해줘"라고 시킵니다. 폴더 만들기 → 하네스 적용 → GitHub 연결·첫 push까지 이 세션이 끝냅니다. GitHub 저장소는 비공개로, 폴더 이름 그대로 만들어집니다. 세션 폴더 밖에 쓰는 일이라 허용 창이 뜰 수 있습니다 — 사람이 「허용」을 누르는 자리입니다.
2. **1단계 문서 두 개를 함께 넣는다** — `mvp/intent.md`와 `mvp/design-brief.md`. 1단계(인터뷰)는 사람의 생각이 재료라 AI끼리 돌리면 시험이 되지 않습니다. 그래서 1단계 결과만 미리 만들어 두고 2단계부터 시험합니다. 1번을 시키기 전에 시험 폴더를 만들어 `mvp/` 안에 두 문서만 넣어 둡니다. `project-init`이 「이 폴더에 이미 파일이 있습니다」라고 물으면 「그대로 적용」을 고릅니다 — 두 문서가 첫 커밋에 함께 들어갑니다. 1단계 자체를 시험할 때는 빈 채로 두고 사람이 직접 인터뷰에 답합니다.
   - `intent.md`에는 서비스 이름과 패키지 이름 후보를 꼭 넣습니다. 패키지 이름은 시험 폴더 이름에서 만든 시험용 값(예: `app.harnesstest1022`)으로 둡니다 — 진짜 앱의 이름을 쓰면 시뮬레이터에 깔린 진짜 개발용 앱을 덮어씁니다.
   - 1단계까지 AI가 답하게 돌렸으면 보고서의 1단계 항목에는 「근거 약함 — AI가 답함」을 붙입니다. 사람의 답 모양은 다를 수 있습니다.
3. **시험 폴더에서 새 세션을 열어 `/idea-to-mvp`부터 시킨다** — 1번 세션이 마지막에 알려 주는 폴더에서 세션을 새로 엽니다. 같은 세션의 작업 폴더를 옮기는 것으로 대신하지 않습니다 — 스킬 경로가 옛 폴더(하네스 저장소)를 가리키고, 하네스 작업의 문맥이 이어진 채 시작합니다. 새 세션은 열 때부터 `.claude/`가 있어 스킬·에이전트·훅이 다 잡히니 앱을 껐다 켤 일이 없습니다. 그래도 에이전트를 못 찾으면 오류 없이 일반 에이전트(메인 모델)로 돌 수 있으니, 보고서에 에이전트 기록(`subagents/*.meta.json`)의 `agentType`과 모델을 확인해 적습니다.
4. **소유는 개인으로 한다** — 시험 저장소가 회사 계정에 생기지 않게, 시험 폴더의 소유를 개인으로 두고 개인 계정 장부(`~/.config/harness/personal.env`)를 씁니다. 계정 표의 Firebase CLI 로그인 계정·플레이 콘솔·광고 행은 `(확인 필요)`로 둡니다(Firebase 프로젝트 두 행에는 `project-init`이 `<시험 폴더 이름>-dev`·`-prod` 예정값을 적지만, 실제로 만들지는 않습니다) — 시험에서는 만들지 않습니다(2절).

**지시서에 다른 프로젝트의 경로를 넣지 않는다.** 시험 세션에 「`~/dev/<다른 프로젝트>`를 참고해라」처럼 다른 프로젝트 경로를 주면, AI가 그 프로젝트의 코드와 결정을 베껴 와 하네스 문서만으로 됐는지 알 수 없게 됩니다. 시험 세션이 읽어도 되는 것은 시험 폴더와 하네스 원본(`project-init`이 복사해 오는 자리)뿐입니다. 시험 보고서를 쓸 폴더 하나만 따로 알려 줍니다.

**시험 프로젝트의 빌드 폴더는 시험 중에 지우지 않는다.** `build/`·`.dart_tool/`·`android/.gradle/`·`ios/Pods/`(있으면)·`node_modules/`는 프로젝트마다 수 GB라 디스크가 걱정돼도, 시험이 도는 동안은 그대로 둡니다. 사람이 시험이 다 끝났다고 한 뒤에 11절대로 한 번에 지웁니다.

## 4. 다른 아이디어로 시험한다

**시험할 때마다, 하네스 문서의 예시와 겹치지 않는 아이디어를 쓴다.** 하네스 문서에는 「이런 화면이면 이렇게」 같은 예시가 들어 있습니다. 예시를 만든 서비스로 시험하면 그 예시가 정답지처럼 작동해서, 문서가 일반적인 원칙으로도 통하는지가 아니라 「예시를 베꼈는지」만 보게 됩니다.

- 예: 지난번에 모임 관리 앱으로 시험했으면, 이번엔 동네 가게 예약·운동 기록처럼 분야가 다른 아이디어로 1단계 문서를 만듭니다.
- 하네스 문서의 이름 예시는 가상의 앱 「예시앱」(`app.example`·`example-dev`)입니다. 시험 프로젝트에 이 값을 그대로 쓰지 않습니다 — 예시를 베낀 것인지 문서를 따른 것인지 가를 수 없게 됩니다.
- 시험하다 「예시가 답안처럼 쓰였다」 싶은 곳이 보이면 보고서의 고칠 목록에 넣습니다 — 그 예시는 특정 서비스 결정이 아니라 일반 원칙으로 고쳐야 합니다.

## 5. 이 컴퓨터를 「처음 상태」로 만들기

하네스는 「도구가 없으면 AI가 깐다」를 시험해야 합니다. 그래서 시험 전에 그 도구를 이 맥에서 지워 둘 수 있습니다. 다만 지울 수 없는 것, 지우면 다른 프로젝트가 멈추는 것, 지워도 흔적이 남는 것이 있습니다.

**지우기 전에 사용자에게 묻는다** — 이 맥의 다른 프로젝트(진짜 앱 포함)가 그 도구를 씁니다. 무엇을 지울지는 사람이 정합니다. 시험 세션을 둘 이상 함께 돌릴 때(7절)는 도구를 지우지 않습니다 — 한 세션이 지우면 다른 세션이 멈춥니다.

**맥에서 지울 수 없는 도구** — `/usr/bin/git`·`/usr/bin/jq`는 맥 운영체제가 보호하는 파일(시스템 무결성 보호)이라 지울 수 없습니다. 그래서 「git·jq가 아예 없을 때」 갈래는 이 맥에서 시험할 수 없습니다. 보고서에 「시험하지 못한 갈래」로 적습니다.

**지우기엔 너무 큰 도구** — Xcode(수십 GB)와 Android Studio·Android SDK는 다시 받는 데 오래 걸리고 약관 동의 같은 사람 몫이 끼어 있습니다. 보통은 그대로 두고 「있을 때」 갈래만 시험합니다. 「없을 때」 갈래를 시험하려면 따로 날을 잡습니다.

**흔적까지 지워야 깨끗한 도구** — 아래가 남으면 하네스가 「받을 것이 없다」며 건너뜁니다.

| 도구 | 남는 흔적 | 자리 |
|---|---|---|
| fvm·Flutter | fvm이 받아 둔 Flutter 판들 | `~/fvm/versions`(fvm 기본 자리) |
| fvm·Flutter | 프로젝트 안 연결 고리 | 프로젝트의 `.fvm/` |
| Node | fnm이 받아 둔 Node 판들 | `~/.local/share/fnm/node-versions` |
| Node | fnm 실행 파일 | `~/.local/share/fnm/fnm` 또는 Homebrew의 fnm |
| Node | Node 없이 남은 npm·npx 파일 | `~/.npm-global/bin` 등 — `npm -v`가 있는 것처럼 보이게 만든다 |
| FlutterFire CLI | 전역으로 깐 dart 패키지 | `~/.pub-cache/bin/flutterfire` |

**셸 함수가 「있음」으로 보이게 만든다** — 셸 설정 파일(`~/.zshrc`)에 `gh()`·`flutter()` 같은 함수가 있으면, 실행 파일이 없어도 `which`가 함수를 보여 줍니다. 시험 전에 `whence -p <도구>`(zsh)로 실행 파일이 정말 없는지 확인합니다.

## 6. 사람 몫 자리를 AI에게 맡기는 지시

하네스에는 사람이 화면을 보고 정하는 자리가 있습니다(목업 캔버스 보며 다듬기, 디자인 비교안 중 고르기, 합치기 전 화면 확인 등). 사람 없이 끝까지 돌려 보려면, 시험 세션을 시작할 때 이 자리를 AI가 정하게 하는 문장을 넣습니다. 이 문장이 없으면 AI는 규칙대로 그 자리에서 멈추고 기다립니다.

시작 지시에 넣을 문장 — 그대로 붙여 넣어 씁니다:

> 이번 작업은 하네스 시험입니다. 하네스 문서가 「사람 몫」이라고 정한 자리(사용자에게 묻는 질문, 화면을 보고 고르는 자리, 「보내도 되겠습니까?」 확인)는 멈추지 말고 네가 정해서 진행해라. 정할 때마다 무엇을 골랐고 왜 골랐는지 한 줄씩 기록해 두었다가 보고서 「사람 몫 자리에서 AI가 고른 것」에 모아라. 단 관리자 암호·로그인·약관 동의·결제처럼 사람만 할 수 있는 일은 하지 말고 그 자리에서 멈춰 보고해라. Firebase 프로젝트와 플레이 콘솔 앱은 만들지 말고, 3단계는 main에서 `store-release` 「번들만 만들기」로 이 맥에서 실서비스 방식 앱 번들(AAB)을 만들어 서명을 확인하는 데까지 해라. 업로드 키는 문서 그대로 이 시험의 패키지 이름으로(`~/.config/harness/keys/<시험 패키지 이름>-upload.*`) 시험용으로 만들고, 계정 장부 파일은 건드리지 마라. 에이전트를 띄운 뒤 할 일이 없으면 턴을 끝내라 — 끝나면 알림이 와서 이어진다. 대기 고리(sleep)로 기다리지 마라. 사람 몫 자리는 네가 정하니, 사람에게 묻는 말로 턴을 끝내지 마라. 단계 끝 `/clear` 권장이 나오면 그 사실만 기록하고 `/clear` 없이 계속해라. 단계 끝마다 `/done-task`로 main에 합쳐라(「보내도 되겠습니까?」는 네가 정한다) — 스킬이 합치지 말라고 정한 단계(예: 2단계)는 그 규칙을 따른다. 시뮬레이터는 이 프로젝트 것만 쓰고, 다른 세션이나 사람이 띄운 시뮬레이터·폰·`flutter run`·코멘트 서버는 끄거나 건드리지 마라.

- 턴을 끝내게 하는 이유는 둘입니다. ① 새로 들어온 에이전트는 턴이 끝난 뒤에야 잡힙니다. ② 턴이 끝나야 작업을 자동으로 커밋하는 `auto-wip-commit` 훅이 돌아, 그 훅도 실제로 시험됩니다. 그러니 시험 지시에 「턴을 끝내지 마라」를 넣지 않습니다.
- Xcode 설치·약관 동의, Android Studio 첫 설정 마법사, `flutter doctor --android-licenses` 동의, 폰의 「USB 디버깅 허용」은 사람만 할 수 있습니다. 시험 전에 끝내 두면 시험이 이 자리에서 멈추지 않습니다.
- `/clear`를 하지 않고 돌리면 메인 문맥이 실제 사용보다 크게 쌓입니다 — 보고서의 문맥 크기 해석에 적습니다.
- 실제 사용에서 대화를 비우는 자리는 세 곳뿐입니다 — ① 1단계 끝 ② 2-2 확인 끝 ③ 2-3 끝(`idea-to-mvp` SKILL.md §3.3). 보고서에는 이 세 자리의 문맥 크기를 적어 「비웠다면」을 가늠하게 합니다.
- AI가 고른 값은 시험용입니다. 그 프로젝트를 진짜로 이어 간다면, 사람이 화면을 보고 브리프의 `가정` 행을 다시 정해야 합니다.
- 화면이 잘 나왔는지는 AI가 판정하지 않습니다. 시험 끝에 사람이 8절대로 직접 봅니다.
- **허용 창은 이 지시로 넘길 수 없습니다** — 클로드 코드가 띄우는 허용 창은 사람만 누릅니다. 시험 폴더를 만드는 세션(3절 1번)은 세션 폴더 밖에 쓰니 허용 창이 뜰 수 있어, 사람이 그 세션이 끝날 때까지 지켜보며 「허용」을 누릅니다. 시험 폴더에서 연 새 세션은 자기 폴더 안에서 일해 이 자리가 거의 없습니다. 다만 시험용 업로드 키는 시험 폴더 밖에 만드니 그때 한 번 뜰 수 있습니다.

## 7. 시험 세션 운영 — 여러 개를 함께 돌릴 때

**처음에는 시험 세션을 2개까지만 함께 돌립니다.** 웹 하네스는 프로젝트마다 다른 포트로 개발 서버를 띄우면 끝났지만, Flutter는 이 맥 한 대에 하나뿐인 것을 여러 세션이 나눠 씁니다.

| 함께 쓰는 것 | 부딪히면 생기는 일 | 하네스가 막는 방법 |
|---|---|---|
| 아이패드 시뮬레이터(목업 캔버스를 띄우는 자리) | 두 세션이 같은 시뮬레이터에 캔버스를 띄우면 화면에는 나중 것만 보여, 사람이 어느 프로젝트를 보는지 헷갈립니다 | 2-0이 프로젝트마다 전용 시뮬레이터 `<시험 폴더 이름> 캔버스`·`<시험 폴더 이름> 폰`을 만들고, 모든 실행 명령이 그 이름으로 부릅니다. 시뮬레이터 창 제목이 곧 시험 이름입니다 |
| 목업 캔버스 코멘트 서버의 포트 | 둘째 세션의 서버가 포트가 차서 못 뜨고, 둘째 캔버스의 코멘트가 첫째 프로젝트에 조용히 쌓일 수 있습니다 | 서버가 4723부터 빈 포트를 찾아 뜨고 번호를 `.dart_tool/canvas_server.port`에 적습니다. 캔버스는 그 번호로 붙고, 서버가 알려 온 프로젝트 이름이 다르면 「다른 프로젝트의 코멘트 서버입니다」를 띄우고 읽기·쓰기를 멈춥니다 |
| Flutter SDK(fvm이 판마다 한 곳에 두고 나눠 씀) | 같은 판을 쓰는 두 세션의 `flutter` 명령이 「다른 flutter 명령이 잠금을 풀기를 기다리는 중」으로 서로 기다립니다 | 프로젝트 `AGENTS.md` 「검증」이 「정상이니 기다린다 — 잠금 파일을 지우거나 프로세스를 끄지 않는다」고 정합니다 |
| 안드로이드 빌드(Gradle)·iOS 빌드(Xcode)의 메모리·CPU | 두 벌을 함께 돌리면 빌드가 매우 느려지거나 빌드 도구가 죽습니다 | 빌드·골든 테스트 명령 앞에 빌드 잠금 `.claude/scripts/build-lock.sh`가 붙어, 맥 전체에서 한 번에 하나만 돕니다. 기다리는 쪽은 「다른 프로젝트가 빌드 중이라 기다립니다」를 냅니다 |
| USB로 연결한 안드로이드폰 한 대 | 두 세션이 같은 폰에 앱을 띄우면 화면이 바뀌어 헷갈립니다 | 프로젝트 `AGENTS.md` 「검증」이 「한 번에 한 세션 — 사람이 정하고 다른 세션은 시뮬레이터로」라고 정합니다. 누가 쓸지는 사람이 정합니다 |
| 계정 장부 | 두 세션이 동시에 `github-connect`로 키를 쓰면 줄이 겹칠 수 있습니다 | 하네스가 막지 않습니다 — 아래 1번대로 사람이 차례를 지킵니다 |

하네스가 막지 못하는 것은 사람이 아래를 지킵니다.

1. **시험 폴더를 만드는 일은 한 번에 하나씩** — 3절 1번은 하네스 저장소 세션 하나에서 차례로 시킵니다. `github-connect`가 계정 장부를 건드리기 때문입니다.
2. **세션마다 이름을 붙인다** — 시험 폴더 이름(`harness-test-<날짜>-a`·`-b`)을 데스크톱 앱 대화 제목이나 터미널 탭 이름에 그대로 씁니다. 시뮬레이터 창 제목에도 같은 이름이 붙으니, 사람이 어느 창이 어느 시험인지 바로 압니다.
3. **안드로이드폰을 쓸 세션을 정한다** — 2-1·3단계에서 폰으로 볼 차례가 오면 「지금 폰은 ○○ 세션이 쓴다」고 그 세션에 알립니다. 다른 세션은 자기 시뮬레이터로만 띄웁니다.
4. **빌드 기다림은 시간 해석에 적는다** — 빌드 잠금 때문에 한 세션이 기다린 시간은 하네스가 느린 것이 아닙니다. 기다린 줄(「다른 프로젝트가 빌드 중이라 기다립니다」)이 보이면 보고서의 시간 해석에 「다른 시험의 빌드를 기다림」을 적습니다.
5. **요금제 사용량은 두 세션이 함께 쓴다** — 9절의 사용량 %는 계정 전체 값이라, 함께 돈 세션들의 몫이 섞입니다. 세션별로 가르지 말고 묶어서 적습니다.

**확인할 것** — 함께 돌린 시험에서 아래가 지켜졌는지 보고서에 한 줄씩 적습니다. 하나라도 어긋났으면 하네스 문제로 적습니다.

- 두 시험이 서로 다른 이름의 시뮬레이터에 떴는가(`xcrun simctl list devices`에 `<시험 폴더 이름> 캔버스`가 시험마다 하나씩).
- 두 코멘트 서버가 서로 다른 포트에 떴고, 각 시험의 코멘트가 자기 `mvp/canvas-comments.json`에만 쌓였는가.
- 빌드가 겹친 순간에 한쪽이 기다렸는가(`build-lock: 다른 프로젝트가 빌드 중이라 기다립니다` 줄).

2개로 한 번 돌려 위 셋이 지켜지면, 그때 세션 수를 늘립니다.

## 8. 결과 보기

시험이 끝나면 사람이 화면을 직접 봅니다. 시험 폴더에서 아래를 띄웁니다. 명령은 시험 폴더 최상위에서 `fvm`을 앞에 붙여 부릅니다.

**목업 캔버스** — 만든 화면을 폰 두 크기로 나란히 펼쳐 아이패드 시뮬레이터에 띄웁니다. 띄우는 법은 시험 폴더의 `.claude/templates/mockup-canvas/README.md` §4 「띄우기」 그대로입니다 — ① 코멘트 서버 켜기 → ② 그 시험의 전용 아이패드 시뮬레이터 `<시험 폴더 이름> 캔버스`를 켜고 `lib/main_canvas.dart`로 실행(포트는 ①이 적은 `.dart_tool/canvas_server.port`에서 읽음). 다른 시험의 캔버스는 그 시험 이름의 시뮬레이터에 따로 떠 있으니 끄지 않습니다.

**개발용 앱** — 그 시험의 전용 아이폰 시뮬레이터 `<시험 폴더 이름> 폰`이나 USB로 연결한 안드로이드폰에 개발용 flavor로 띄웁니다. 폰은 한 번에 한 시험만 씁니다.

```bash
fvm flutter run --flavor dev -t lib/main_dev.dart -d <기기 이름>
```

- 기기 이름은 `fvm flutter devices`로 봅니다.
- 속도는 이 실행으로 판정하지 않습니다 — 디버그 빌드는 최적화가 꺼져 있어 실제보다 훨씬 느립니다. 속도를 보려면 `--profile`을 붙입니다.

**실서비스 방식 앱 번들** — 3단계 끝에 만든 번들이 `build/app/outputs/bundle/prodRelease/app-prod-release.aab`에 있는지, 서명 확인 결과가 보고서에 있는지 봅니다. 번들 자체는 폰에 바로 깔 수 없습니다. 실서비스 방식 앱을 폰에서 보고 싶으면 `fvm flutter run --release --flavor prod -t lib/main_prod.dart -d <폰>`으로 띄웁니다.

**디자인 시스템 페이지** — 토큰과 부품을 모아 보여 주는 페이지입니다. 목업 캔버스 안에 창 하나로 들어 있습니다.

## 9. 시간·토큰 재기

**시작할 때도 잽니다.** 끝에만 재면 시험이 얼마나 썼는지 알 수 없습니다. 시험을 시작하기 직전에 아래 넷을 먼저 적어 둡니다.

| 무엇 | 어디서 보나 | 언제 |
|---|---|---|
| 걸린 시간 | 커밋 시각(`git log --reverse --format='%ci %s'`)과 GitHub PR의 생성·머지 시각. 메인 세션이 단계 경계마다 시각을 적어 두면 더 정확하다 | 단계 경계마다 |
| 서브 에이전트 토큰 | 알림에 적힌 토큰 수는 그 에이전트가 끝날 때의 **문맥 크기**다 — 누적 처리량이 아니다. 누적 입력·출력은 대화 기록 폴더의 `subagents/*.jsonl`에서 `usage` 값을 더해 뽑는다. 에이전트마다 단계·모델과 함께 표로 모은다 | 에이전트가 끝날 때마다 |
| 메인 세션 문맥 크기 | Claude Code의 `/context` — 지금 대화에 쌓인 양 | 시작·단계 경계·끝 |
| 요금제 사용량 % | claude.ai 설정의 사용량 화면 — 「5시간 한도」와 「주간」 % 그리고 다음 초기화 시각 | 시작·끝(가능하면 단계 경계마다) |

재며 알아 둘 것:

- 스킬이 fork로 부르는 git 작업(`new-task`·`ship-task`)은 알림에 토큰 수가 나오지 않습니다. 대신 대화 기록 폴더의 `subagents/agent-*.meta.json` 중 `agentType`이 `git-flow`인 파일을 찾고, 같은 이름의 `agent-*.jsonl`에서 아래 `usage` 합계 명령으로 뽑습니다.
- 같은 에이전트를 이어서 일하게 하면 알림 값(문맥 크기)에 앞 회차의 내용이 이미 들어 있습니다. 그 행에 이어 일한 회차임을 표시해 두고, 회차끼리 더하지 않습니다. 누적량은 위 `usage` 합계로 봅니다.
- `usage` 합계를 뽑는 명령 예(필드 이름이 다르면 그 자리에서 맞춥니다): `jq -s '[.[] | .message.usage? // empty | .input_tokens + (.cache_read_input_tokens // 0) + (.cache_creation_input_tokens // 0)] | add' <subagents/ 아래 jsonl 파일>`
- 빌드 시간은 따로 적습니다 — 첫 안드로이드 빌드는 Gradle이 의존성을 받느라 수 분이 걸리고, 두 번째부터 빨라집니다. 첫 빌드 시간을 하네스 문제로 읽지 않습니다.
- 요금제 사용량 %는 계정 전체 값이라, 같은 시간에 돌던 다른 대화도 들어 있습니다(7절 6번).
- 지어낸 값은 쓰지 않습니다. 못 잰 값은 「못 잼」으로 적습니다.

## 10. 보고서 목차

시험 보고서는 아래 목차로 씁니다. 보고서는 시험 폴더가 아니라 시험을 시킨 쪽이 알려 준 폴더에 둡니다.

1. **결과 한눈에** — 어디까지 끝났나, 만든 앱 번들 경로와 서명 확인 결과, 화면 수, 검사 결과(`fvm flutter analyze`·`fvm dart analyze`·`fvm flutter test`·디자인 규칙 검사), 막힌 곳
2. **단계별로 한 일과 걸린 시간** — 단계마다 시작·끝 시각과 한 일
3. **자동으로 깐 도구와 판** — 무엇을 어떤 방법으로 깔았나(Flutter 판, Node 판, 시뮬레이터 런타임 등), 원래 있던 것을 그대로 뒀나
4. **사람 몫 자리에서 AI가 고른 것과 이유**
5. **하네스를 고칠 목록** — ① 막혔거나 엉뚱한 진단을 낸 곳 ② 문서와 실제가 달랐던 곳 ③ 틀이 이 판과 맞지 않아 고친 곳(`[하네스 제안]` 문안 그대로). 항목마다 「일어난 일」·「고칠 자리(파일·절)」·「고칠 것」
6. **시간·토큰·요금제** — 9절의 표와, 시작·끝 사용량 %. 다른 시험과 함께 돌았으면 그 사실
7. **시험하지 못한 갈래와 남은 문제** — 2절에서 건너뛴 일, 5절의 지울 수 없는 도구, 도구를 지우지 않은 회차라 시험하지 못한 「도구 깔기」 갈래, 사람 눈 확인이 아직 없는 자리 등

## 11. 시험이 끝난 뒤 정리

사람이 「시험이 다 끝났다」고 한 뒤에 한 번에 정리합니다.

1. **빌드 폴더** — 시험 폴더에서 `fvm flutter clean`을 돌리고 `node_modules/`를 지웁니다. 시험 폴더 자체를 지울 거면 이 단계는 건너뜁니다.
2. **시험 시뮬레이터** — 2-0이 만든 그 시험의 전용 시뮬레이터 둘(`<시험 폴더 이름> 캔버스`·`<시험 폴더 이름> 폰`)을 `xcrun simctl delete "<이름>"`으로 지웁니다. 하나에 수 GB를 차지합니다. 시험 전부터 있던 시뮬레이터와 다른 세션이 쓰는 시뮬레이터는 지우지 않습니다. 시뮬레이터에 깔린 시험 앱만 지우려면 `xcrun simctl uninstall <기기> <시험 패키지 이름>.dev`를 씁니다.
3. **남은 빌드 잠금** — 보통은 없습니다. `.claude/scripts/build-lock.sh --status`가 「남은 잠금」이라고 하면 다음 빌드가 알아서 걷으니 그대로 둡니다.
4. **시험용 업로드 키** — `~/.config/harness/keys/<시험 패키지 이름>-upload.jks`·`<시험 패키지 이름>-upload.properties` 두 파일을 지웁니다. 진짜 앱의 키 파일과 계정 장부 파일은 건드리지 않습니다.
5. **GitHub 시험 저장소** — 지우는 일은 사람 몫입니다. GitHub 저장소 페이지 → Settings → 맨 아래 「Delete this repository」.
6. **시험 폴더** — 보고서를 옮겨 둔 뒤 사람이 지웁니다.
