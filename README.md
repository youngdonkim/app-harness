# app-harness

혼자 AI로 며칠~몇 주 만에 작동하는 폰 앱을 만들어 시장 반응으로 검증하는 사람(이 문서에서는 **AI 빌더**라고 부릅니다)을 위한 **Claude Code 하네스**입니다. 아이디어를 떠올린 순간부터 MVP(Minimum Viable Product — 가설을 검증할 수 있는 최소한의 작동하는 제품)를 구글 플레이에 내놓고 실제 사용자 반응을 보기까지를 **6단계 한 흐름**으로 안내합니다.

만드는 앱은 한 가지 조합으로 고정돼 있습니다 — **Flutter(Dart) 앱 + Firebase 백엔드, 안드로이드를 먼저 구글 플레이에 냅니다.** 개발은 맥 한 대에서 iOS 시뮬레이터(가상 아이폰·아이패드)와 USB로 연결한 안드로이드폰으로 합니다.

용어가 낯설면 먼저 [§3 이게 무엇인가](#3-이게-무엇인가)를 읽으시면 됩니다.

**설계 원칙**: 빌드는 AI가 거의 공짜로 해 주니 — 팀·투자자에게 보여 주기 위한 무거운 문서는 버리고, 빌더 자신이 뭘 만들고 뭘 안 만들지 정하는 최소 전략 + AI가 정확히 빌드하게 만드는 구체 명세만 남깁니다.

## 1. 두 가지 사용 환경

Claude Code는 두 가지 방식으로 씁니다 — **데스크톱 앱**(대화 화면이 있는 프로그램)과 **인터랙티브 터미널**(터미널에서 `claude`를 실행해 대화하는 방식). 이 문서의 안내는 양쪽 모두에 해당하고, 하네스도 양쪽에서 똑같이 작동합니다. 갈리는 건 **대화를 여는 방법**과 **터미널 명령을 실행하는 방법** 둘뿐입니다.

| | 데스크톱 앱 | 인터랙티브 터미널 |
|---|---|---|
| 대화 한 판을 부르는 말 | 대화 | 세션 |
| 새로 열기 | 앱에서 새 대화를 만들고 작업할 프로젝트 폴더를 고른다 | 터미널에서 프로젝트 폴더로 옮겨 간 뒤 `claude` 실행 |
| 대화 비우기 | `/clear`, 또는 새 대화 열기 | `/clear`, 또는 `claude` 다시 실행 |
| 터미널 명령(git 등) | 직접 칠 일이 거의 없다 — 채팅창에 "~해줘"라고 시키면 Claude가 대신 실행한다 | 직접 쳐도 되고, 채팅창에 시켜도 된다 |

`/idea-to-mvp` 같은 **스킬 호출과 `/clear` 같은 명령은 두 환경에서 똑같이 동작합니다.** 채팅 입력창에 `/`를 치면 뜨는 자동완성 목록에서 고르면 됩니다.

이 문서는 둘을 아울러 **세션**이라고 쓰고, 실제 행동이 갈리는 곳에서만 "터미널이면 A / 데스크톱 앱이면 B"로 나눠 적습니다.

한 가지는 두 환경 모두 같습니다 — **개발 중인 앱을 띄워 두는 터미널**이 따로 하나 있으면 편합니다. Flutter는 앱을 켠 채로 그 터미널에서 `r`(핫 리로드 — 바뀐 코드만 끼워 넣기)·`R`(핫 리스타트 — 처음부터 다시 그리기)을 눌러 고친 화면을 바로 봅니다.

## 2. 빠른 시작 — 이 4개만 순서대로

아래 4단계는 **하네스를 프로젝트에 적용하는 사람**이 하는 일입니다. 하네스가 이미 들어 있는 프로젝트를 받아서 쓰기만 하는 팀원은 아무것도 안 해도 됩니다 — 이 저장소에 접근할 필요조차 없습니다([§5.4](#54-팀원은-무엇을-하나)).

**준비물** — 맥 한 대. Flutter·Android Studio·Node 같은 개발 도구는 2단계 첫머리(2-0 개발환경 준비)에서 AI가 깔고, Xcode 설치와 약관 동의처럼 사람만 할 수 있는 일은 그때 한 단계씩 알려 드립니다. 미리 깔아 둘 것은 없습니다.

**1. 하네스 저장소 내려받기** — 컴퓨터에 **딱 한 번만**

```
git clone https://github.com/youngdonkim/app-harness.git ~/dev/app-harness
```

터미널이면 이 명령을 직접 치고, 데스크톱 앱이면 채팅창에 "이 주소를 `~/dev/app-harness`에 clone해줘"라고 시키면 됩니다.

이 저장소는 공개입니다 — 누구나 내려받아 그대로 쓸 수 있습니다. 하네스 자체를 자기 식으로 고치고 싶을 때만 fork(자기 계정으로 복제한 저장소)를 만듭니다([§5.1](#51-하네스-저장소-내려받기)).

계정은 하네스에 적지 않습니다 — 프로젝트에 적용할 때 물어보고, **그 프로젝트의 `AGENTS.md` 「소유와 계정」 표가 정본**이 됩니다.

→ 자세히: [§5.1](#51-하네스-저장소-내려받기)

**2. 하네스 저장소 폴더에서 세션 열기** — 방금 내려받은 `~/dev/app-harness` 폴더에서

- **터미널이면** 그 폴더로 옮겨 가 `claude`를 실행합니다.

  ```
  cd ~/dev/app-harness
  claude
  ```

- **데스크톱 앱이면** 새 대화를 열고 `app-harness` 폴더를 고릅니다.

**3. 새 프로젝트 만들기** — 방금 열린 Claude Code 채팅창에서, 말로

```
옆에 cafe-booking 폴더 만들고 하네스 적용해줘
```

`cafe-booking` 자리에 새 프로젝트 이름을 씁니다(영문 소문자·숫자·하이픈만 — 이 이름이 GitHub 저장소 이름이 되고, Firebase 프로젝트 ID 예정값 `<이름>-dev`·`<이름>-prod`의 앞부분도 됩니다). Claude가 하네스 저장소 옆(`~/dev/cafe-booking`)에 폴더를 만들고, 하네스를 깔고, GitHub에 저장소를 만들어 첫 push까지 합니다. 세션 폴더 밖에 쓰는 일이라 도중에 허용 창이 뜰 수 있습니다 — 뜨면 「허용」을 누릅니다.

→ 자세히: [§5.2](#52-프로젝트에-적용하기). 이미 파일이 있는 폴더에 얹을 때도 거기에 있습니다.

**4. 새 폴더에서 새 세션 열기** — 끝나면 Claude가 알려 주는 폴더(예: `~/dev/cafe-booking`)에서 2번처럼 세션을 새로 엽니다. 열고 `/idea-to-mvp`를 치거나 "인터뷰 시작하자"라고 하면 1단계가 시작됩니다.

적용이 끝나면 채팅창에서 이 명령들을 씁니다 — 역할은 [§4 들어 있는 것](#4-들어-있는-것) 표에 있습니다.

| 언제 | 명령 |
|---|---|
| 아이디어를 MVP까지 끌고 갈 때 | `/idea-to-mvp` |
| 새 작업을 시작할 때 | `/new-task` |
| 작업을 끝내고 main에 합칠 때 | `/done-task` |
| 잘못된 작업을 되돌릴 때 | `/rewind-task` |
| 화면·색·간격 같은 디자인을 다룰 때 | `/design-system` |
| 백엔드(Firebase)를 실서비스에 올릴 때 | "백엔드 올려줘" (`backend-release`) |
| 앱을 구글 플레이에 올릴 때 | "앱 올려줘" (`store-release`) |

**main에 합치는 것과 출시는 따로입니다.** `/done-task`는 코드를 main에 합칠 뿐 아무 데도 내보내지 않습니다. 실서비스 Firebase 배포와 플레이 올리기는 사람이 "올려줘"라고 할 때만, 메인 세션이 직접 합니다.

## 3. 이게 무엇인가

### 3.1 하네스란

**Claude Code**는 대화하며 코딩을 맡기는 도구입니다. 데스크톱 앱으로도 쓰고, 터미널(컴퓨터에 명령어를 직접 쳐 넣는 검은 창)에서 `claude`를 실행해서도 씁니다([두 가지 사용 환경](#1-두-가지-사용-환경)).

**하네스(harness)**는 원래 말이나 사람에게 씌우는 마구·안전벨트를 뜻합니다. 여기서는 **AI가 정해진 절차와 안전 규칙 안에서 일하도록 잡아 주는 틀**이라는 뜻으로 씁니다. AI에게 매번 "이렇게 해줘"라고 설명하는 대신, 그 절차를 미리 문서와 규칙으로 만들어 두고 AI가 항상 그대로 따르게 하는 것입니다.

이 하네스가 잡아 주는 것은 두 가지입니다.

- **진행 절차** — 아이디어에서 MVP 런치까지 6단계를 순서대로, 마지막 단계의 통과 기준과 함께 진행합니다.
- **안전 규칙** — 코드를 잘못 날리거나 검토 없이 반영하는 일, 다른 계정으로 저장소·Firebase·플레이 앱이 만들어지는 일이 생기지 않게 막고 작업을 자동 저장합니다.

### 3.2 스킬·서브에이전트·훅

이 하네스가 담고 있는 세 종류의 부품입니다.

- **스킬(skill)** — Claude가 특정 작업을 할 때 읽는 **작업 설명서**입니다. 채팅창에서 `/이름` 형태로 직접 불러 씁니다. 예: `/idea-to-mvp`.
- **서브에이전트(subagent)** — 특정 일만 전담하는 **보조 AI**입니다. 본 대화와 따로 떨어져 일하기 때문에, 긴 작업을 맡겨도 본 대화가 지저분해지지 않습니다. 대개 스킬이 알아서 호출하므로 사용자가 직접 부를 일은 적습니다.
- **훅(hook)** — 정해진 순간마다 **자동으로 실행되는 규칙**입니다. 사용자가 부르지 않아도 걸립니다. 예: main 브랜치에 코드를 바로 올리려 하면 막고, 답변이 끝날 때마다 작업 내용을 자동 저장합니다.

이 세 부품 말고 **규칙·설정 파일과 틀**도 하네스에 들어 있습니다 — Claude가 항상 지킬 규칙(`AGENTS.md`), 특정 파일을 다룰 때만 적용되는 세부 규칙(`.claude/rules/`), 훅을 작동시키는 등록 설정(`.claude/settings.json`에 합쳐집니다), 단계마다 프로젝트에 펼쳐 넣는 코드·설정 틀(`.claude/templates/`) 같은 것들입니다. 전체 목록은 [§5.3](#53-프로젝트에-무엇이-생기나)에 있습니다.

### 3.3 어떻게 전해지나 — 파일 복사

이 저장소가 하네스의 **원본(SoT, Source of Truth — 정답이 되는 하나뿐인 출처)**입니다. 하네스 본체는 전부 이 저장소의 `payload/` 아래에 있고, 그 안의 구조가 곧 **프로젝트 루트에 그대로 복사될 모양**입니다 — 이런 걸 미러(mirror, 거울처럼 같은 모양)라고 합니다.

적용은 복사입니다. `/project-init` 스킬이 `payload/`를 프로젝트 루트에 같은 경로로 복사하고, 훅 등록 설정을 프로젝트 설정 파일에 합쳐 넣습니다. 그래서 하네스가 한 번 적용된 프로젝트는 **그 저장소 안에 하네스를 통째로 갖고 있습니다.**

이 방식의 좋은 점은 세 가지입니다.

- 프로젝트를 열면 `.claude/` 안의 파일이 세션 시작 때 읽힙니다 — 따로 켜고 끄는 설정이 없습니다. 스킬 본문은 부를 때, 경로 조건이 있는 rules는 그 파일을 만질 때 그때그때 읽혀서, 고치면 다음 호출부터 바로 반영됩니다. 에이전트 정의는 응답을 한 번 끝낸 다음 턴부터, 훅은 바뀐 다음 명령부터 지금 세션에 잡히고(세션을 연 뒤에 `.claude/`가 처음 생긴 경우만 앱을 껐다 켭니다), `AGENTS.md`는 컴팩션이나 `/clear`부터입니다([§6.3](#63-언제부터-적용되나)).
- 하네스 파일도 프로젝트 저장소에 커밋되니, 팀원은 프로젝트만 내려받으면 하네스까지 같이 받습니다([§5.4](#54-팀원은-무엇을-하나)).
- 어느 버전이 적용됐는지가 파일로 남아, 다음에 동기화할 때 무엇이 바뀌었는지 정확히 가려냅니다([§6.4](#64-적용한-버전이-파일로-남는다)).

## 4. 들어 있는 것

부품의 종류는 [§3.2](#32-스킬서브에이전트훅)에서 설명한 스킬·서브에이전트·훅 세 가지인데, 스킬은 쓰이는 시점에 따라 다시 셋으로 나뉩니다.

- **단계 스킬** — 아이디어에서 MVP까지 가는 **6단계 본줄기를 진행하는 스킬**입니다. 지금은 `idea-to-mvp` 하나뿐이고, 이 하나를 여러 번 불러 단계를 하나씩 밟아 갑니다.
- **출시 스킬** — main의 커밋을 **실서비스로 내보내는 스킬**입니다. 사용자가 "올려줘"라고 할 때만 메인 세션이 직접 부르고, 서브에이전트에 맡기지 않습니다.
- **공통 스킬** — 몇 단계에 있든 **필요할 때마다 꺼내 쓰는 스킬**입니다. 작업을 시작하고 마무리하고 되돌리는 일, 디자인을 다루는 일처럼 단계와 상관없이 계속 반복되는 작업들입니다.

| 종류 | 이름 | 역할 |
|---|---|---|
| 단계 스킬 | `idea-to-mvp` | 6단계: Intent(인터뷰) · Mockup(2-0 개발환경 · 2-1 목업 · 2-2 디자인 개선 · 2-3 개성 입히기 — 대담·혁신·파격 세 판 중 고르기 · 2-4 머무는 공간(선택) — 사용자가 들어가 둘러보는 화면 하나를 따로 깊게) · FrontendBuild(플레이 내부 테스트까지) · BackendBuild(4-0~4-3 — Firebase·로그인·계측) · MarketResearch · MvpLaunch(통과 기준). 2단계부터 실제 앱과 같은 Flutter 코드로 화면을 만들어 목업 캔버스(만든 화면을 폰 두 크기로 나란히 펼쳐 아이패드 시뮬레이터에 띄우는 개발용 앱)에서 보고, 그 코드를 끝까지 이어 짓습니다 |
| 출시 스킬 | `backend-release` | main의 보안 규칙·색인·서버 함수·Hosting 웹 페이지·Remote Config를 실서비스 Firebase에 배포. 맨 앞에서 「실서비스 배포 전 확인」을 돌립니다 |
| 출시 스킬 | `store-release` | main의 커밋으로 실서비스 앱 번들(AAB — 구글이 기기마다 알맞게 쪼개 주는 묶음 파일)을 만들어 구글 플레이 트랙에 올림 — 빌드 번호 올리기·업로드 키 연결·서명 확인·태그 |

| 공통 스킬 | `github-connect` | 이 컴퓨터에서 프로젝트가 GitHub에 올라가게 준비 — git 확인, gh·jq 설치, 토큰(계정 장부 `~/.config/harness/<소유>.env`), 계정 확인, 저장소 생성, 첫 push. 이미 된 단계는 건너뜁니다. 하네스 신규 적용 끝에 자동으로 불리고, "깃헙 연결해줘"로 따로 불러도 됩니다 |
| 공통 스킬 | `new-task` | main 최신화 + 머지가 끝난 옛 작업 브랜치 정리 + 새 작업 브랜치 생성 |
| 공통 스킬 | `done-task` | 합치기 한 흐름 — 안에서 코드 정리(`code-cleanup`) 판단을 먼저 하고, git 절차는 내부 스킬 ship-task에 넘깁니다. 부르는 이름은 done-task 하나입니다 |

| 공통 스킬 | `deep-research` | 질문을 여러 각도로 나눠 병렬 조사 → 주장마다 반박 시도 → 깨지지 않은 것만 출처·검증 상태를 달아 보고 |

| 서브에이전트 | `ux-writing-reviewer` | 화면 문구(`.dart`·`.arb`)와 스토어 등록정보 문구를 UX writing 원칙과 대조해 직접 교정 |
| 서브에이전트 | `delegation-integrator` | 타 코딩 에이전트 연동 조사·설치·테스트·위임 스킬 생성/갱신 |
| 훅 | `no-main-push` | main 브랜치에 바로 올리는 것을 차단 (PR 검토 흐름 강제). 예외는 원격에 main이 아직 없을 때의 첫 push 하나 |
| 훅 | `owner-runner-guard` | 키가 필요한 CLI(gh·Firebase CLI·FlutterFire CLI·fastlane)를 실행기 없이 부르면 차단 — 컴퓨터에 남은 다른 계정 로그인으로 도는 것을 막음 |
| 훅 | `auto-wip-commit` | 응답이 끝날 때마다 작업 브랜치에 진행 중 커밋(wip)을 자동 생성. 이름이 비밀 파일 꼴(`.env`·`*.key`·`*.pem`·`credentials.json` 등)인 파일은 커밋에서 뺌 |

위 표는 부품(스킬·서브에이전트·훅)만 담았고, 함께 복사되는 규칙·설정 파일과 틀은 [§5.3](#53-프로젝트에-무엇이-생기나)에 정리돼 있습니다.

용어 참고 — **PR(Pull Request)**은 "내가 고친 걸 본체에 반영해 달라"고 올리는 제안입니다. **CI(Continuous Integration)**는 그 제안이 반영되기 전에 코드가 깨지지 않았는지 자동으로 검사하는 절차입니다. **wip(work in progress)**는 아직 끝나지 않은 진행 중 상태를 뜻합니다.

## 5. 적용 자세히

빠른 시작에 나온 단계를 하나씩 풀어 설명합니다.

### 5.1 하네스 저장소 내려받기

원본을 자기 컴퓨터에 통째로 내려받습니다(clone — 저장소를 그대로 복제해 오는 git 명령). 컴퓨터에 **한 번만** 하면 됩니다.

```
git clone https://github.com/youngdonkim/app-harness.git ~/dev/app-harness
```

터미널이면 이 명령을 직접 치면 됩니다. 데스크톱 앱이면 아무 대화나 열어 "이 주소를 `~/dev/app-harness`에 clone해줘"라고 시키면 Claude가 대신 실행합니다.

`~/dev/app-harness`가 기본 위치입니다. 다른 곳에 두고 싶으면 경로만 바꾸면 되는데, 그러면 [§5.5](#55-자주-막히는-두-가지)에서 경로를 알려 줄 때 그 경로를 씁니다.

**이 저장소는 공개입니다** — 누구나 fork·clone할 수 있습니다. 위 https 주소면 로그인 없이 받습니다. SSH 키를 등록해 둔 사람은 `git@github.com:youngdonkim/app-harness.git`로 받아도 됩니다.

**내려받아야 하는 사람은 하나뿐입니다** — 하네스 자체를 프로젝트에 적용·동기화하거나 하네스를 고치는 사람. 하네스가 이미 적용된 프로젝트를 받아서 쓰기만 하는 팀원은 이 저장소가 아예 필요 없습니다([§5.4](#54-팀원은-무엇을-하나)).

**소유자가 아닌 사람도 그대로 clone해서 쓸 수 있습니다** — 하네스에는 아무 계정도 적혀 있지 않고, 계정은 프로젝트에 적용할 때 물어봐서 그 프로젝트의 `AGENTS.md` 표에만 남습니다. **하네스 자체를 자기 식으로 고치고 싶을 때만 fork를 만듭니다** — 원본에는 push할 수 없어서입니다. fork 주소는 버전 표시 파일의 `repo=`에 적힙니다([§6.4](#64-적용한-버전이-파일로-남는다)).

### 5.2 프로젝트에 적용하기

**기본 — 하네스 저장소 세션에서 옆 폴더를 만듭니다.** 하네스 저장소 폴더(`~/dev/app-harness`)에서 세션을 열고([§1](#1-두-가지-사용-환경)) 채팅창에 말로 시킵니다.

```
옆에 cafe-booking 폴더 만들고 하네스 적용해줘
```

`/project-init cafe-booking`이라고 쳐도 같습니다. 그러면 `/project-init` 스킬이 이 순서로 돕니다.

1. **폴더 이름 확인** — 영문 소문자·숫자·하이픈만 씁니다. 이 이름이 GitHub 저장소 이름이 됩니다. 다른 글자가 섞이면 바꾼 이름을 제안하고 확인받습니다(「카페 예약」 → `cafe-booking`). 같은 이름의 폴더가 이미 있고 비어 있지 않으면 멈추고 다른 이름을 묻습니다.
2. **폴더 만들기** — 하네스 저장소 옆, 즉 같은 부모 폴더 아래(`~/dev/cafe-booking`)에 만듭니다. 세션 폴더 밖에 쓰는 일이라 클로드 코드가 명령마다 허용 창을 띄울 수 있습니다 — 뜨면 「허용」을 누릅니다.
3. **하네스 깔기** — [§5.3](#53-프로젝트에-무엇이-생기나)의 파일들을 만듭니다. 도중에 **프로젝트 소유(개인/회사/그 밖의 조직)** 하나만 물어봅니다. 소유 답과 함께 서비스별 계정(GitHub·구글 플레이 콘솔·Firebase·광고·AI 키 등)을 물어 `AGENTS.md`의 「소유와 계정」 표를 채웁니다(모르는 항목은 `(확인 필요)` — 그 서비스가 처음 필요해지는 단계에서 채웁니다). 이후 저장소·Firebase 프로젝트·플레이 앱이 전부 그 표의 계정으로만 만들어지도록 확인이 걸립니다. 서비스 이름·한 줄 정의·타겟은 여기서 묻지 않습니다 — `/idea-to-mvp` 1단계가 물어 함께 다듬은 뒤 `AGENTS.md` 상단에 써넣습니다. 앱 패키지 이름(`app.example` 같은 앱의 고유 이름)도 여기서 정하지 않습니다 — 2단계 첫머리(2-0)에서 확인받아 적습니다.
4. **첫 커밋과 GitHub 올리기** — main에 첫 커밋을 하고, 이어서 `github-connect`가 git 확인 → gh·jq 설치 → GitHub 토큰 → 저장소 만들기 → 첫 push까지 합니다. 가입·로그인·권한 창처럼 사람만 되는 일이 나오면 화면 이름·버튼 이름으로 한 단계씩 알려 주고 기다립니다. 이 첫 커밋·첫 push만 main에 바로 들어가는 예외입니다(빈 저장소라 리뷰할 화면도 배포도 없습니다).
5. **새 세션 열기** — 끝나면 Claude가 "이제 `<폴더 경로>`에서 새 세션을 여세요"라고 알려 줍니다. 그 폴더에서 세션을 새로 열고 `/idea-to-mvp`를 치거나 "인터뷰 시작하자"라고 하면 1단계가 시작됩니다. 새 세션은 열 때부터 하네스가 들어 있어 스킬·에이전트·훅이 바로 잡힙니다. 하네스 저장소 세션에서는 1단계를 시작하지 않습니다 — 산출물이 하네스 저장소에 쌓입니다.

그다음부터는 작업마다 `/new-task` → `/done-task` 흐름입니다. 두 번째 동기화부터는 [§6.2](#62-프로젝트에-동기화하기)처럼 그 프로젝트 세션에서 작업 브랜치부터 만들고 시작합니다.

**예외 — 이미 있는 폴더에 얹을 때.** 하네스를 한 번도 안 깐 폴더에 얹으려면, 그 폴더에서 직접 세션을 열고 "하네스 적용해줘"라고 합니다. 이 말은 아직 그 폴더에 스킬 파일이 없어 통하지 않을 수 있습니다 — 그럴 땐 원본 경로를 알려 줍니다.

```
~/dev/app-harness의 payload/.claude/skills/project-init/SKILL.md를 읽고 그대로 실행해줘
```

절차는 위와 같고(폴더 만들기만 빠집니다), GitHub 연결까지 다 끝난 뒤 앱을 한 번 껐다 켜 달라는 안내가 나옵니다. 세션을 연 뒤에 `.claude/` 폴더가 생겨, 새로 깐 스킬·에이전트가 그 세션에는 잡히지 않기 때문입니다(껐다 켜도 대화는 안 날아갑니다).

### 5.3 프로젝트에 무엇이 생기나

`/project-init`이 프로젝트에 만드는 것들입니다. `.github/workflows/ci.yml`까지는 원본 `payload/`에서 같은 경로로 복사돼 오는 것이고, `AGENTS.md`부터는 스킬이 따로 만듭니다.

- **`.claude/skills/`·`.claude/agents/`·`.claude/hooks/`** — 세션을 열 때 등록돼 스킬·서브에이전트·훅이 작동합니다. 스킬 본문은 부를 때마다 읽어서 고치면 다음 호출부터 바로 반영되고, 에이전트 정의는 응답을 한 번 끝낸 다음 턴부터, 훅은 바뀐 다음 명령부터 지금 세션에 잡힙니다([§6.3](#63-언제부터-적용되나)).
- **`.claude/scripts/`** — 실행기 `with-owner.sh`(gh·Firebase CLI·fastlane처럼 키가 필요한 명령을 이 컴퓨터의 계정 장부 키로 돌립니다)와 3단계 내보내기 전 디자인 규칙 검사 `design-check.sh`, 빌드 잠금 `build-lock.sh`(한 맥에서 여러 프로젝트가 돌 때 안드로이드·iOS 빌드와 골든 테스트를 맥 전체에서 한 번에 하나만 돌립니다), 그리고 단계 이름표 `stage-tag.sh`(idea-to-mvp 단계가 끝날 때와 판을 고르기 직전에 지금 모습을 커밋하고 `stage/<이름>` 태그를 붙여 GitHub에 올립니다 — 나중에 그때 모습으로 돌아가 볼 수 있습니다).
- **`.claude/rules/`** — 특정 종류의 파일을 다룰 때만 적용되는 세부 규칙 모음(문서 작성 규칙·보안 기본 규칙).
- **`.claude/templates/`** — 단계마다 프로젝트에 펼쳐 넣는 틀입니다. 앱 뼈대와 Firebase 설정(`firebase/`), 안드로이드 서명(`android-signing/`), 목업 캔버스(`mockup-canvas/`), 견본 지도 부품(`sample-map/`), 개인정보처리방침·계정 삭제 요청 같은 Hosting 웹 페이지(`hosting-site/`), 플레이 올리기 도구(`fastlane/`), 스토어 등록정보 서식(`store-listing.md`), `delegation-integrator`가 쓰는 문서 틀(sources·status).
- **`docs/git-workflow.md`** — 훅과 작업 스킬들이 따르는 git 작업 흐름을 사람이 읽으라고 정리해 둔 문서.
- **`docs/account-check.md`** — 계정 확인 절차와 서비스별 함정. 첫 push·첫 배포·4단계 준비(4-0) 직전에 읽습니다.
- **`.github/workflows/ci.yml`** — `done-task`가 머지 전에 통과를 기다리는 검사. 앱 코드는 형식·정적 분석·테스트·개발용 빌드, 서버 함수는 린트·빌드·테스트, 보안 규칙은 에뮬레이터 안 규칙 테스트를 돌립니다.
- **`.gitignore`** — 원본의 `gitignore.template`에서 만듭니다. Flutter·Firebase 빌드 찌꺼기와 업로드 키(`*.jks`·`key.properties`)·서비스 계정 키 같은 비밀 파일을 git에서 막는 줄이 들어 있습니다. 이미 있으면 빠진 줄만 끝에 덧붙입니다.
- **`AGENTS.md`** — 그 프로젝트의 **규칙 정본**입니다. Claude뿐 아니라 Codex 같은 다른 AI 도구도 읽고, 세션을 열 때 자동으로 읽히며 컴팩션(`/compact`·자동) 때 다시 읽힙니다 — 세션 중에 고친 건 다음 컴팩션이나 `/clear`부터 반영됩니다. 이것만은 그대로 복사되지 않고, 원본의 `AGENTS.md.template`에 소유·계정 답을 채워 만듭니다(서비스 정의 줄은 1단계가, 앱 패키지 이름 줄은 2-0이 채웁니다). 내용은 `<!-- BEGIN:project-rules -->` 마커 구역 안에 들어가고, 빈 자리는 프로젝트가 채워 나갑니다. 이미 있으면 덮어쓰지 않고 우리 구역만 덧붙입니다.
- **`CLAUDE.md`** — 내용이 `@AGENTS.md` 한 줄뿐인 포인터 파일. 규칙은 담지 않습니다. 클로드 코드가 버전·실행 환경에 따라 `AGENTS.md`를 혼자 읽지 못하는 경우가 있어서, 어디서 열어도 규칙이 읽히도록 이 한 줄을 둡니다.
- **`.claude/settings.json`** — 원본의 `settings-hooks.json`에 적힌 훅 등록 내용이 이 파일에 합쳐집니다. 이미 있던 다른 설정은 그대로 둡니다.
- **`.claude/harness-version`** — 지금 적용한 하네스가 어느 버전인지 적어 두는 표시 파일입니다([§6.4](#64-적용한-버전이-파일로-남는다)).
- **`.claude/owner`** — 이 프로젝트의 소유를 한 줄로 적은 선언 파일(`owner=personal` 등). `AGENTS.md`의 소유 문장과 같은 값입니다.
- **계정 장부 `~/.config/harness/<소유>.env`** — 프로젝트 밖, 이 컴퓨터에 만드는 키 자리입니다. 커밋되지 않고 같은 소유의 프로젝트끼리 나눠 씁니다. GitHub 토큰 같은 키 값은 `github-connect`가 채우고, 플레이 서비스 계정 키·업로드 키 같은 키 파일은 같은 폴더의 `keys/`에 두고 장부에는 경로만 적습니다.
- **`mvp/`·`docs/` 폴더** — 단계 산출물과 사람이 읽는 문서가 쌓이는 자리.

이 파일들은 전부 그 프로젝트 저장소의 일부입니다. 신규 적용 때는 첫 커밋으로 main에 들어가고 GitHub에 올라가는 것까지 자동입니다([§5.2](#52-프로젝트에-적용하기)). 그다음 바뀌는 것(동기화 등)은 프로젝트의 git 흐름(작업 브랜치 → PR)으로 합칩니다.

### 5.4 팀원은 무엇을 하나

**하네스 쪽으로는 아무것도 안 해도 됩니다.** 하네스 저장소는 내려받을 필요가 없습니다 — 프로젝트 저장소만 받으면 하네스를 다 씁니다.

프로젝트 저장소를 내려받거나(clone) 당겨오면(pull) `.claude/` 안에 스킬·서브에이전트·훅·설정이 이미 커밋돼 있어서, 세션을 여는 순간 그대로 작동합니다. 개발 도구(Flutter·Android Studio 등)는 각자의 맥에 있어야 하니, 처음이면 2-0 개발환경 준비의 도구 점검만 돌리면 됩니다. 하네스가 개선돼서 프로젝트에 반영되는 일은 [§6](#6-업데이트--새-버전-받기)대로 한 사람이 해 두면 되고, 나머지 팀원은 프로젝트를 당겨오기만 하면 됩니다.

### 5.5 자주 막히는 두 가지

- **하네스 저장소가 main이 아니거나 고치던 내용이 남아 있으면 멈춥니다.** 원본 검사([§6.1](#61-원본-저장소가-깨끗한-main인지-확인하기))에 걸린 것입니다. 하네스 저장소를 main으로 돌리고 정리한 뒤 다시 시킵니다. 예외 경로(이미 있는 폴더에서 연 세션)에서 "하네스 적용해줘"가 통하지 않으면 [§5.2](#52-프로젝트에-적용하기)처럼 원본의 `SKILL.md` 경로를 알려 주면 됩니다.
- **스킬 이름은 짧은 형태로 칩니다.** 입력창 자동완성에 뜨는 이름 그대로 — `/project-init`·`/idea-to-mvp`처럼 씁니다. 데스크톱 앱이든 터미널이든 같습니다.

## 6. 업데이트 — 새 버전 받기

하네스가 개선됐을 때 그걸 프로젝트에 반영하는 방법입니다. 길은 이 하나뿐이고, 세 걸음입니다.

1. 하네스를 맡은 사람이 자기 컴퓨터의 원본이 깨끗한 main 상태인지 확인해 둡니다([§6.1](#61-원본-저장소가-깨끗한-main인지-확인하기)).
2. 프로젝트마다 작업 브랜치부터 만들고 "하네스 동기화해줘"로 옮긴 뒤, `/done-task`로 그 프로젝트의 PR을 만들어 main에 합칩니다([§6.2](#62-프로젝트에-동기화하기)).
3. 나머지 팀원은 프로젝트를 당겨오기만(git pull) 하면 끝입니다.

### 6.1 원본 저장소가 깨끗한 main인지 확인하기

내려받아 둔 하네스 저장소 폴더를 미리 최신으로 당겨올 필요는 없습니다. `/project-init`이 동기화를 시작할 때 원본을 스스로 최신으로 당겨오기 때문입니다.

대신 다음 다섯 중 하나라도 안 맞으면 `/project-init`이 **동기화를 시작하지 않고 그 자리에서 멈춥니다**.

- 찾은 원본이 **이 하네스(Flutter판)** 여야 합니다. 안에 출시 스킬 `store-release`가 있는지로 가립니다 — 폴더 구조가 같은 웹 하네스를 원본으로 잘못 잡으면 프로젝트의 하네스 파일이 전부 웹판으로 덮이기 때문입니다.
- 원본 저장소가 **`main` 브랜치**에 있어야 합니다.
- **커밋 안 된 변경이 없어야** 합니다.
- 원본을 최신으로 당겨오는(pull) 데 **성공해야** 합니다.
- 로컬 원본이 원격 main과 **같은 커밋**이어야 합니다.

동기화 때는 하나를 더 봅니다 — 프로젝트의 버전 표시 파일(`.claude/harness-version`, [§6.4](#64-적용한-버전이-파일로-남는다))에 적힌 원본 주소(`repo=`)가 찾은 원본의 주소와 같은지입니다. 다르면(fork를 쓰던 프로젝트 등) 덮어쓰기 전에 이 원본으로 맞출지 물어봅니다.

멈추는 이유는 **잘못된 원본이 프로젝트로 새어 나가는 걸 막기 위해서**입니다. 원본이 작업 중인 브랜치에 있으면 아직 확정되지 않은 내용이 프로젝트에 그대로 복사될 수 있습니다. 게다가 그 상태로 복사하면 프로젝트에 남는 버전 표시(`.claude/harness-version`, [§6.4](#64-적용한-버전이-파일로-남는다))가 실제로 적용한 내용과 다른 값을 갖게 돼서, 다음 동기화 때 판단이 틀어집니다.

⚠️ **하네스를 직접 고치는 사람은 특히 여기서 자주 걸립니다.** 하네스 저장소를 고치는 중이면 원본 폴더가 작업 브랜치에 가 있는 경우가 많은데, 그 상태로 다른 프로젝트에서 "하네스 동기화해줘"를 돌리거나 하네스 저장소 세션에서 새 프로젝트를 만들면 멈춥니다. 하네스 쪽 작업을 PR로 올려 main에 합치거나([§7.1](#71-새-버전이-만들어지는-흐름)), 원본 폴더에서 `git switch main`으로 돌아간 뒤 다시 동기화하면 됩니다.

### 6.2 프로젝트에 동기화하기

새 버전을 쓸 프로젝트에서, 이 순서로 진행합니다.

```
/clear  →  /new-task 하네스 동기화  →  "하네스 동기화해줘"  →  /clear  →  /done-task
```

1. **`/clear`** — 지금 연 세션의 `AGENTS.md`가 옛 판일 수 있고, 긴 대화가 남아 있으면 동기화 보고가 묻힙니다. 비우고 시작합니다.
2. **`/new-task 하네스 동기화`** — 작업 브랜치부터 만듭니다(그 프로젝트 폴더에서 세션을 엽니다 — [§1](#1-두-가지-사용-환경)). 왜 브랜치를 먼저 만드는지는 바로 아래에 있습니다.
3. **"하네스 동기화해줘"** — `/project-init`이 동기화 모드로 돌면서 프로젝트에 있는 하네스 파일을 최신 원본과 하나씩 비교해 갱신합니다.
4. **`/clear`** — 동기화로 바뀐 `AGENTS.md`는 컴팩션이나 `/clear`부터 반영됩니다([§6.3](#63-언제부터-적용되나)).
5. **`/done-task`** — 갱신된 파일을 커밋하고 PR을 만들어 main에 합칩니다.

**왜 작업 브랜치를 맨 먼저 만드나** — `auto-wip-commit` 훅(턴이 끝날 때마다 바뀐 파일을 알아서 커밋해 두는 자동 저장 장치)은 작업 브랜치에서만 돕니다. main에 있는 채로 동기화하면 바뀐 파일 수십 개가 커밋 안 된 채 쌓이고, 그 상태로 `/new-task`를 부르면 "커밋 안 된 변경이 있다"며 멈춥니다. 브랜치를 먼저 만들면 이 갈림길 자체가 안 생깁니다.

**시작하기 전에 프로젝트 쪽에도 확인하는 조건이 하나 있습니다.** 동기화는 프로젝트에 있는 하네스 파일(`.claude/`·`docs/git-workflow.md`·`docs/account-check.md`·`.github/workflows/ci.yml`)을 최신 원본 내용으로 덮어씁니다. 그래서 `/project-init`은 시작하기 전에 이 자리에 커밋 안 된 변경이 있는지 먼저 보고, 있으면 멈춘 뒤 커밋하거나 되돌려 달라고 물어봅니다. 이 검사는 저 네 자리에만 해당합니다 — 프로젝트의 다른 파일(`lib/` 등)에 커밋 안 된 작업이 남아 있는 건 상관없습니다.

파일별 비교 결과는 이렇게 처리됩니다.

- 같으면 그냥 넘어갑니다.
- 새로 생긴 파일은 복사합니다.
- 달라진 파일은 **최신 원본으로 바꾸는 게 기본입니다.** 다만 프로젝트가 그 파일을 손댄 흔적이 있으면 그냥 덮지 않고, 어디가 다른지 짚어 준 뒤 원본으로 교체할지 손본 걸 유지할지 물어봅니다.

예외가 둘 있습니다.

- **`AGENTS.md`** — 프로젝트마다 고유한 내용(서비스 정의·타겟·계정 표·앱 패키지 이름, 직접 덧붙인 규칙)이 담긴 파일이라 덮어쓰지 않고 **합칩니다** — 원본에서 온 공용 문구와 구조만 비교해 최신으로 맞춘 안을 보여 준 뒤, 확인을 받고 반영합니다. 하네스는 `<!-- BEGIN:project-rules -->` 구역만 관리하고 나머지는 건드리지 않습니다.
- **`.gitignore`** — 프로젝트 파일이라 덮어쓰지 않고, 원본 틀에 새로 생긴 줄만 끝에 덧붙입니다.

**옛 원본에서 넘어오는 첫 동기화** — 버전 표시 파일의 커밋이 이 저장소 이력에 없는 프로젝트(이 저장소가 생기기 전의 하네스를 쓰던 프로젝트)는, 옛 버전과 대조할 수 없어 달라진 파일이 전부 「손본 흔적인지 모름」이 됩니다. 그래서 파일마다 묻기 전에 달라진 파일 목록을 한 번에 보여 주고 「전부 원본으로 교체」와 「하나씩 고르기」 가운데 고르게 합니다. 이때도 `mvp/`·`lib/`·`.claude/owner`와 `AGENTS.md`의 프로젝트 값(계정 표·서비스 정의·앱 패키지 이름)은 건드리지 않습니다.

**다른 세션이 시킨 동기화** — 하네스 저장소 세션이 옆 프로젝트를 맞추라고 시킨 경우처럼 그 자리에 답할 사람이 없으면, 묻지 않아도 되는 것(같은 파일 넘기기·새 파일 복사·그냥 낡은 파일 교체·`.gitignore` 줄 덧붙이기)만 하고, 물어야 할 것은 「확인이 필요한 것」 한 묶음으로 모아 시킨 쪽에 돌려줍니다.

### 6.3 언제부터 적용되나

하네스 파일이 프로젝트 폴더 안에 있어서, 세션이 시작될 때 그 자리에서 읽힙니다. 다만 **지금 열려 있는 세션에 들어오는 시점은 파일마다 다릅니다.**

- **스킬 본문** — 부를 때마다 읽어서 다음 호출부터 바로 반영됩니다.
- **에이전트 정의와 훅** — 세션을 열 때 `.claude/agents/`·`.claude/settings.json`이 있었으면 지금 세션에 잡힙니다. 에이전트는 응답을 한 번 끝낸 다음 턴부터, 훅은 바뀐 다음 명령부터입니다. 하네스 저장소 세션에서 옆 폴더를 만들었으면 그 폴더에서 새 세션을 열 때부터 다 잡힙니다. 예외 경로(하네스 없는 폴더에서 연 세션에 처음 깐 경우)만 세션을 연 뒤에 그 폴더가 생긴 것이라, GitHub 연결까지 끝난 뒤 앱을 한 번 껐다 켜야 합니다(대화는 안 날아갑니다). 바뀔 수 있으니 최신은 공식 문서로 확인합니다.
- **`AGENTS.md`** — 컴팩션이나 `/clear`부터 반영됩니다. 방법은 [§1](#1-두-가지-사용-환경) 표의 '대화 비우기' 행에 있습니다.

### 6.4 적용한 버전이 파일로 남는다

`/project-init`은 하네스를 적용·동기화할 때마다 프로젝트에 `.claude/harness-version`이라는 표시 파일을 남깁니다. 어느 시점의 하네스를 적용했는지 적어 두는 파일입니다.

```
repo=youngdonkim/app-harness
commit=<적용한 하네스 커밋 sha 12자리 이상>
date=<YYYY-MM-DD>
```

이 파일이 쓰이는 곳은 다음 동기화 한 군데뿐입니다([§6.2](#62-프로젝트에-동기화하기)). 프로젝트의 하네스 파일이 원본과 다를 때, 여기 적힌 커밋 시점의 원본과 대조해서 **그냥 낡은 것인지 프로젝트가 일부러 손본 것인지**를 가릅니다. 낡은 것이면 조용히 최신으로 바꾸고, 손본 흔적이면 어떻게 할지 물어봅니다.

## 7. 하네스를 직접 고치는 사람에게

이 저장소 자체를 만들고 고치는 사람을 위한 내용입니다.

### 7.1 새 버전이 만들어지는 흐름

어느 프로젝트에서든 하네스의 개선점 발견 → 이 저장소에서 수정 → PR → 관리자가 main에 합침(merge). merge된 순간부터 [§6](#6-업데이트--새-버전-받기)의 절차로 각 프로젝트에 옮길 수 있습니다.

**프로젝트 안에서는 하네스 사본을 고치지 않습니다.** 프로젝트 세션에서 하네스 문제를 찾으면, AI는 그 프로젝트의 `.claude/`를 고치지 않고 「어느 파일 어느 자리를 무엇으로」 고칠지 붙여 넣을 수 있는 문안(`[하네스 제안]`)으로 넘깁니다. 그 문안을 이 저장소에서 반영한 뒤 동기화하면 프로젝트에도 들어옵니다. 프로젝트에서 바로 고치면 다음 동기화 때 원본으로 덮여 사라집니다.

**웹 하네스(website-harness)와는 따로 갑니다.** 이 저장소는 웹 앱용 하네스에서 갈라져 나와 Flutter용으로 다시 쓴 것이라 구조와 많은 규칙이 같지만, 두 저장소를 맞춰 주는 장치는 없습니다. 웹 하네스에 생긴 개선이 여기에도 쓸모 있으면 사람이 골라 손으로 옮깁니다.

**서브 에이전트도 프로젝트 규칙을 자동으로 받습니다.** 일반형이든 `.claude/agents/`의 커스텀이든, 서브 에이전트는 프로젝트 `CLAUDE.md`와 그 한 줄이 펼쳐 오는 `AGENTS.md`를 그대로 받습니다. 그래서 에이전트 파일에 공통 규칙을 다시 적지 않습니다 — 적는 건 공통 규칙을 덮어쓰는 선언뿐입니다. 예를 들어 `git-flow` 에이전트에는 "위임 원칙은 메인 세션용이고 너는 그 위임을 받은 실행자다"라고만 적혀 있습니다.

**이 저장소 자체도 하네스 사용자입니다.** 루트의 `.claude/`에 `payload/`와 같은 스킬·서브에이전트·훅이 적용돼 있어서, 하네스를 고치는 작업도 `/new-task`·`/done-task`로 합니다. main에 바로 올리는 것도 `no-main-push` 훅에 막혀 관리자든 기여자든 반드시 PR을 거칩니다. 만드는 앱이 없는 저장소라서 규칙도 범용 작업 원칙뿐이고, 규칙은 루트 `AGENTS.md` 한 곳에 두고 `CLAUDE.md`는 그 파일을 가리키는 한 줄만 남겨 두었습니다.

### 7.2 버전 번호 정책

버전 번호를 따로 매기지 않습니다. 커밋할 때마다 자동으로 생기는 고유 값(커밋 해시)이 버전 역할을 해서, 커밋 하나하나가 전부 새 버전으로 인식됩니다. 프로젝트에 적용된 버전을 기록하는 `.claude/harness-version`에도 이 커밋 값이 그대로 들어갑니다([§6.4](#64-적용한-버전이-파일로-남는다)). 만든 사람이 직접 매일 써 보면서 바로바로 고치는 중이라 이렇게 해 두었습니다(이런 방식을 "도그푸딩"이라고 부릅니다). 나중에 다른 사람들에게 정식으로 배포할 때는 버전 번호를 정해 관리하는 방식으로 바꿀 것입니다.

### 7.3 저장소 구조

```
README.md
AGENTS.md                             # 규칙 정본 — 어느 AI 도구가 읽어도 지켜야 하는 규칙 (저장소 규칙·글쓰기 원칙·작업 원칙)
CLAUDE.md                             # @AGENTS.md 한 줄 — 클로드 코드가 위 파일을 읽게 하는 포인터
docs/harness-testing.md               # 하네스 시험하는 법 — 시험 폴더·시험 범위·시험 세션 운영·시간과 토큰 재기
docs/eval-scenarios.md                # 실사고 재현 색인 — 스킬·에이전트·rules를 크게 고칠 때 되짚는다
docs/design-notes.md                  # 설계 노트 — 지시 문서에서 덜어 낸 설계 이유가 옮겨 가는 자리
docs/harness-plan-*.md                # 큰 개편 때 쓴 계획서 — 이력 문서라 고치지 않는다
.claude/                              # 이 저장소에 적용된 하네스 — payload/.claude/와 같은 내용
payload/                              # 프로젝트 루트의 미러 — 이 구조 그대로 프로젝트에 복사된다
payload/.claude/skills/               # 단계 스킬·출시 스킬·공통 스킬
payload/.claude/agents/               # 서브에이전트
payload/.claude/hooks/                # 훅 스크립트
payload/.claude/scripts/              # 실행기 with-owner.sh(계정 장부 키로 gh·Firebase CLI·fastlane을 돌림)·디자인 규칙 검사 design-check.sh·빌드 잠금 build-lock.sh·단계 이름표 stage-tag.sh
payload/.claude/rules/                # 특정 파일을 다룰 때만 적용되는 세부 규칙
payload/.claude/templates/            # 앱 뼈대·Firebase·서명·목업 캔버스·견본 지도·Hosting 웹 페이지·fastlane·스토어 등록정보 틀, delegation-integrator 문서 틀
payload/docs/git-workflow.md          # 훅·done-task가 참조하는 작업 흐름 문서
payload/docs/account-check.md         # 계정 확인 절차·서비스별 함정 — 첫 push·첫 배포·4-0 직전에 읽는 온디맨드 문서
payload/.github/workflows/ci.yml      # done-task가 머지 전 통과를 기다리는 검사(앱·서버 함수·보안 규칙)
payload/.claude/settings-hooks.json   # (예외) 복사 아님 — 훅 등록 원본, 프로젝트 설정 파일에 합쳐 넣는 내용
payload/AGENTS.md.template            # (예외) 복사 아님 — 소유·계정 답을 채워 프로젝트 AGENTS.md를 만드는 틀
payload/gitignore.template            # (예외) 복사 아님 — 프로젝트 .gitignore의 원본. 없으면 이 내용으로 만들고, 있으면 빠진 줄만 덧붙인다
```

`payload/` 아래 구조가 곧 프로젝트 루트에 놓일 모양입니다. 여기에 파일을 더하면 그게 그대로 프로젝트로 갑니다. **예외는 끝의 세 파일뿐**입니다 — 그대로 놓이는 파일이 아니라서 복사에서 빠지고, 하나는 병합 원본, 하나는 가공할 틀, 하나는 줄 단위로 덧붙이는 원본으로 쓰입니다. 그래서 이 셋만 `payload/` 안에서 자리가 특별합니다.

`ci.yml`은 앱 코드(`pubspec.yaml`)가 아직 없는 프로젝트에서는 자동으로 통과 처리되고, 앱 코드가 생기는 순간부터 실제 검사가 돌기 시작합니다. 서버 함수(`functions/`)와 보안 규칙도 같은 방식입니다. 그래서 앱이 없는 이 저장소에서도 CI가 통과합니다.

하네스 문서와 틀의 예시 값은 특정 제품이 아니라 가상의 앱 「예시앱」(`app.example`·`example-dev`·`example-prod`)으로 씁니다. 공개 저장소에 제품 이름이 남지 않게 하고, 시험할 때 예시가 정답지처럼 쓰이는 것도 막기 위해서입니다.

### 7.4 시험 세션 운영

하네스를 고친 뒤에는 옆에 시험 프로젝트를 만들어 실제로 돌려 봅니다. 방법은 [`docs/harness-testing.md`](docs/harness-testing.md)에 있고, 줄기는 이렇습니다.

1. **시험 범위** — 3단계의 「이 맥에서 실서비스 방식 앱 번들(AAB) 빌드」까지만 돌립니다. Firebase 프로젝트와 플레이 콘솔 앱은 만들지 않습니다.
2. **동시에 돌리는 시험 세션은 처음엔 2개까지** — Flutter 개발은 아이패드 시뮬레이터·목업 캔버스 코멘트 서버·안드로이드 빌드 도구·USB로 연결한 폰처럼 맥 한 대에 하나뿐인 것을 나눠 씁니다. 하네스는 프로젝트 이름을 붙인 전용 시뮬레이터, 빈 포트를 찾아 뜨는 코멘트 서버, 맥 전체에서 무거운 빌드를 하나씩 돌리는 빌드 잠금으로 이 충돌을 막습니다. 폰을 어느 세션이 쓸지는 사람이 정합니다. 2개로 돌려 이 장치들이 지켜지는 것을 확인한 뒤에 늘립니다.
3. **시험 폴더와 시험 저장소는 시험이 끝나면 사람이 정리합니다** — GitHub 저장소 삭제는 사람 몫입니다.
