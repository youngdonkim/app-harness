# 보안 기준

규칙마다 **근거 등급**을 붙였습니다. 나중에 뒤집고 싶을 때 어디를 다시 봐야 하는지 보이게 하려는 것입니다.

| 표시 | 뜻 | 뒤집으려면 |
|---|---|---|
| **[공식]** | Firebase·플레이 공식 문서가 시키거나 금지한 것 | 공식 문서가 바뀌었는지 확인 |
| **[우리 결정]** | 맞고 틀림이 없고 우리가 골라 정한 것 | 팀이 다시 정하면 됨 |
| **[이전 앱 교훈]** | 이전 앱에서 확인한 교훈 — 실제로 겪어서 아는 것 | 같은 일이 다시 생기는지 확인 |

## 1부 — 밖에서 닿는 위협

**앱 파일은 누구나 내려받아 뜯어볼 수 있습니다.** 플레이에 올린 앱 묶음(AAB·APK)은 풀어서 안의 문자열·설정 파일·코드를 읽을 수 있고, 앱이 보내는 요청은 가로채 고쳐 보낼 수 있습니다. 「앱 화면에 그 버튼이 없으니 그런 요청은 안 온다」는 막는 수단이 아닙니다. **[공식]**

**시험 트랙과 개발용 앱도 밖에 나간 앱입니다.** 내부 테스트·비공개 테스트 트랙의 앱도, 개발용 Firebase 프로젝트도 인터넷에 열려 있습니다. 「내부 베타라 안전하다」는 가정은 위협 모델과 맞지 않습니다. 개발용과 실서비스용은 같은 보안 규칙 파일을 씁니다. **[우리 결정]**

### 적용 범위

- **없음** (서버 데이터·로그인·업로드가 없는 앱) → 1부의 비밀값·로그 항목만.
- **있음** (사용자 데이터·로그인·업로드·서버 함수) → 2단계 개발환경 준비(앱 코드가 생기는 자리)부터 이 문서 전체. 기능이 늘면 그때 해당 항목을 더 지킵니다.

### 앱 안에 두면 안 되는 것 **[공식]**

- **앱에 넣는 값은 공개된 값입니다.** 앱에 들어가도 되는 것은 Firebase 설정 파일(`firebase_options_*.dart`·`google-services.json`·`GoogleService-Info.plist`)과 공개용 앱 키(지도 SDK 키 등 — 콘솔에서 패키지 이름·서명 지문으로 쓰임새를 묶어 둔 것)뿐입니다. Firebase 설정값은 「이 앱이 어느 프로젝트에 붙나」를 가리키는 식별값이라 git에도 올립니다. 막는 일은 보안 규칙과 App Check가 합니다.
- **비밀값은 절대 앱에 넣지 않습니다** — AI 제공사 키, 결제 비밀값, 외부 서비스의 비밀 키, 서비스 계정 키(관리자 권한 열쇠). `--dart-define`이나 `.env` 자산 파일로 넣어도 앱 묶음 안에 그대로 남습니다. 그런 일은 서버 함수로 옮기고, 키는 서버 함수 비밀값(Secret Manager — 구글 클라우드의 비밀값 금고)에 프로젝트마다 둡니다(2부).

### 영역별 기준

- **로그인·세션** — 세션(로그인 상태)은 Firebase Authentication이 기기에 저장하고 갱신합니다. 앱이 토큰을 따로 꺼내 저장하거나 서버로 보내 직접 검증하지 않습니다. 권한 판단은 앱이 아니라 보안 규칙과 서버 함수가 합니다. **[공식]**
- **기기 저장소** — shared_preferences(기기 안 작은 저장소)는 암호화되지 않습니다. 토큰·비밀번호·개인정보를 넣지 않습니다. 꼭 기기에 둬야 하는 민감한 값은 운영체제의 보안 저장소(안드로이드 키스토어·iOS 키체인)를 쓰는 패키지로 둡니다. **[공식]**
- **로그** — `print`·`debugPrint`·Crashlytics 로그·서버 함수 로그(`logger`)에 토큰·비밀값·이메일·전화번호·위치를 남기지 않습니다. 오류를 남길 때는 사용자 ID 정도로 충분합니다. 계측 이벤트의 매개변수에도 개인정보를 넣지 않습니다(분석 서비스 정책 위반). **[공식]**
- **딥링크(앱 안의 특정 화면을 여는 링크)로 들어온 값** — 링크는 누구나 만들어 보낼 수 있습니다. 경로·질의 값을 그대로 믿지 않고, 화면이 쓰기 전에 형식을 검사하고, 그 값으로 남의 데이터를 열거나 무언가를 쓰는 동작을 바로 하지 않습니다(사용자가 화면에서 한 번 더 누르게 합니다). 앱 링크용 확인 파일(`assetlinks.json`)로 우리 도메인의 링크만 우리 앱이 열게 합니다. **[공식]**
- **업로드** — 크기·형식(MIME)·확장자를 Storage 규칙에서 막고, 경로로 소유자를 가릅니다(2부). 앱의 검사는 사용자 안내용일 뿐입니다. **[공식]**
- **오류 메시지** — 사용자 화면에 서버 함수의 내부 오류(스택·질의·내부 ID)를 그대로 보이지 않습니다. 서버 함수는 정해진 오류 코드만 돌려주고, 앱의 `AppError` 네 갈래로 바꿔 보입니다. **[우리 결정]**
- **개발용 기능** — 상태 흉내·「개발」 띠 같은 개발용 기능은 `lib/dev/`에만 두고 개발용 진입점에서만 부릅니다. 실서비스 진입점이 `lib/dev/`에 닿으면 검사(`tool/check_firebase_config.dart`)가 실패합니다. **[우리 결정]**

### 평문 비밀값 금지 **[우리 결정]**

**키 파일·비밀번호는 평문으로 적지 않습니다** — 코드·주석·문서·워크플로 파일·커밋 메시지 어디에도. 업로드 키 비밀번호(`storePassword=`·`keyPassword=`), PEM 개인 키 머리줄, 서비스 계정 키 JSON의 `private_key`가 대표적입니다. 감시 훅이 커밋 때 이런 줄을 찾아 막습니다. 키 파일(`*.jks`·`*.keystore`·서비스 계정 JSON)은 이 컴퓨터의 계정 장부 폴더(`~/.config/harness/` 안 `keys/`)에 두고, 장부에는 경로만 적습니다. 예시 파일은 값 자리를 `<…>`로 비워 둡니다.

**권한(누가 무엇을 할 수 있나)은 1부에 없습니다 — 2부입니다.** 앱에서는 화면마다 검사하는 것이 아니라 **보안 규칙과 서버 함수가 판정**합니다.

## 2부 — Firebase 권한

전제: **Flutter 앱 + Firebase(Authentication·Firestore·Storage·Cloud Functions·App Check)** 고정 스택입니다.

### 보안 규칙이 사실상 유일한 벽입니다 **[공식]**

앱은 서버를 거치지 않고 기기에서 Firestore·Storage에 바로 붙습니다. 그래서 요청마다 허락·거부를 판정하는 것은 **보안 규칙**(`firestore.rules`·`storage.rules`)뿐입니다. 반대로 **서버 함수와 관리자 SDK(Admin SDK)는 보안 규칙을 거치지 않습니다** — 서버 함수 안에서는 함수가 직접 권한을 확인해야 합니다(아래 「서버 함수」).

### 기본은 전부 거부 — 컬렉션마다 명시적으로 엽니다 **[우리 결정]**

규칙 파일은 맨 끝의 「위에 없는 경로는 전부 거부」로 시작하고, 새 컬렉션·경로는 `match`를 열어 필요한 동작만 허락합니다.

이유는 **실수의 방향**입니다.

- 기본 거부 → 실수하면 **「안 보인다」** → 바로 티가 납니다.
- 기본 허용 → 실수하면 **「다 보인다」** → 아무도 모릅니다.

번거로운 것이 요점입니다. 컬렉션을 열 때마다 「이거 정말 열어도 되나?」를 한 번 묻게 됩니다.

### 규칙 모양 **[공식 + 우리 결정]**

**이 규칙들은 어겨도 오류가 나지 않습니다. 조용히 열려 있을 뿐이라 아무도 모릅니다** — 그래서 규칙으로 정해 둡니다.

| # | 규칙 | 어기면 |
|---|---|---|
| ① | `allow write`로 묶지 않고 `create`·`update`·`delete`를 나눠 씁니다 | 만들기만 열려던 것이 지우기까지 열립니다 |
| ② | `create`는 소유자 필드 = `request.auth.uid`를 확인합니다 | 남의 이름으로 문서를 만듭니다 |
| ③ | `update`는 소유자 필드를 바꾸지 못하게 합니다 | 남의 문서를 제 것으로 가져갑니다 |
| ④ | 들어오는 필드를 `keys().hasOnly([...])`로 고정하고, 값의 형식(`is string` 등)과 길이를 봅니다 | 아무 필드나 끼워 넣습니다(관리자 표시·거대한 값) |
| ⑤ | 보호 필드는 앱의 쓰기를 막습니다(아래) | 사용자가 결제 상태·포인트를 고칩니다 |
| ⑥ | 「로그인했으면 누구나」(`request.auth != null`)만으로 남의 데이터를 열지 않습니다 | 가입만 하면 전부 보입니다 |
| ⑦ | 규칙은 거름망이 아닙니다 — 질의는 규칙과 같은 조건을 직접 적습니다 | 질의 전체가 권한 오류로 실패합니다 |

**⑦은 공식 문서가 분명히 적어 둔 동작입니다.** 질의 결과 중 읽을 권한이 없는 문서가 하나라도 나올 수 있으면 질의 전체가 거부됩니다. 규칙이 읽을 수 있는 문서만 골라 주지 않습니다.

### 규칙은 신분이 아니라 권한 이름으로 묻습니다 **[우리 결정]**

```
allow update: if isRole('operator');            // ❌ 문에 신분을 쓴다
allow update: if can('reports.resolve');         // ✅ 문에 권한을 쓴다
```

지금은 둘이 똑같이 동작합니다. 갈리는 건 나중에 「검토자도 신고를 처리한다」가 될 때입니다 — 신분을 쓴 규칙은 **전부** 고쳐야 하고, 권한을 쓴 규칙은 **판정 함수 하나만** 고치면 됩니다.

**역할은 사용자가 고칠 수 없는 자리에 둡니다.** 사용자 정의 클레임(custom claims — 서버가 로그인 토큰에 붙이는 값, `request.auth.token.<이름>`)이나 서버 함수만 쓰는 보호 필드에 둡니다. 사용자가 직접 쓸 수 있는 문서 필드로 권한을 판단하지 않습니다. 사용자 정의 클레임은 관리자 SDK로만 붙일 수 있습니다. **[공식]**

역할을 실제로 만드는 절차는 `idea-to-mvp` 스킬의 4-2 문서에 있습니다.

### 보호 필드 **[이전 앱 교훈]**

결제·구독 상태·포인트·카운터·역할처럼 **사용자가 직접 바꾸면 안 되는 필드**입니다.

1. 보안 규칙으로 앱의 쓰기를 막고(`createsNone`·`changesNone`), **서버 함수만** 씁니다.
2. **카운터는 서버 한 곳에서만** 올리고 내립니다. 앱과 서버가 둘 다 올리면 숫자가 두 번 셉니다.
3. **규칙·보호 필드 표(`backend-build.md`)·규칙 테스트를 한 커밋에서 함께 고칩니다.** 하나만 바뀌면 실서비스 배포 전 확인에서 멈춥니다.
4. 보호 필드마다 「앱이 바꾸려 하면 거부된다」 규칙 테스트를 둡니다.

### 웹 폼 컬렉션은 서버 함수만 쓴다 **[이전 앱 교훈]**

Hosting 웹 페이지의 폼(계정 삭제 요청 등)은 HTTP 서버 함수로 받고, 그 함수가 관리자 권한으로 컬렉션에 씁니다. 컬렉션은 클라이언트(앱·웹)의 읽기·쓰기를 전부 막습니다. 값의 형식·길이 검사는 함수 안에서 합니다.

### Storage 규칙 **[공식]**

- 경로에 소유자를 넣고(`users/{uid}/…`), 쓰기는 본인 경로에만 허락합니다.
- 형식(`request.resource.contentType`)과 크기(`request.resource.size`)를 규칙에서 막습니다.
- 「로그인한 누구나 읽기」와 「본인만 읽기」를 파일 종류마다 정하고, 경로를 나눕니다.

### 규칙은 파일로만 고치고, 테스트로 고정합니다 **[공식 + 우리 결정]**

- **콘솔의 규칙 편집기에서 고치지 않습니다.** CLI로 배포하면 저장소의 파일이 콘솔의 규칙을 덮어씁니다(공식 동작). 콘솔에서 고친 것은 다음 배포에서 말없이 사라집니다.
- **규칙을 바꾸면 규칙 테스트(`rules-test/`)도 같은 커밋에서 바꿉니다.** 거부되어야 하는 경우를 허락되는 경우보다 많이 둡니다. 규칙 테스트는 CI에서만 에뮬레이터(`demo-`로 시작하는 가짜 프로젝트)로 돕니다.

### 서버 함수 **[공식]**

- **함수 안에서 직접 권한을 확인합니다** — 서버 함수는 보안 규칙을 거치지 않습니다. 호출형 함수는 `request.auth`가 없으면 거부하고, 앱이 인자로 보낸 사용자 ID를 믿지 않고 `request.auth.uid`를 씁니다. 인자는 형식·길이를 검사합니다.
- **앱이 부르는 함수는 호출형(callable)으로** — 주소만 알면 누구나 부를 수 있는 HTTP 함수(`onRequest`)는 결제사 웹훅처럼 밖에서 오는 요청에만 쓰고, 보내는 쪽 서명을 확인합니다.
- **비밀값은 `defineSecret`으로 정의해 쓰는 함수에만 묶습니다.** 값은 `firebase functions:secrets:set <이름> --project dev|prod`로 프로젝트마다 따로 넣습니다. 예전 방식 `functions.config()`는 폐기 예정이라 쓰지 않습니다. 비밀값을 화면에 내는 `functions:secrets:access`는 감시 훅이 막습니다.
- **트리거 함수는 두 번 돌아도 결과가 같게 짭니다** — Firestore 트리거는 「적어도 한 번」 전달되고 순서가 보장되지 않습니다. 보호 필드·카운터를 고치는 트리거는 특히 그렇습니다.

### App Check — 앱에서는 처음부터 켜고, 서버 쪽 강제는 단계적으로 **[공식 + 이전 앱 교훈]**

App Check는 「이 요청이 진짜 우리 앱에서 왔나」를 확인합니다. 안드로이드는 Play Integrity, iOS는 App Attest, 개발용 앱은 디버그 공급자(기기 첫 실행 때 로그에 뜨는 디버그 토큰을 **개발용 프로젝트** 콘솔에 등록)를 씁니다.

1. **앱에서는 처음부터 켭니다** — 토큰을 보내기만 하고, 서버는 아직 막지 않습니다.
2. **콘솔에서 「확인된 요청 비율」을 먼저 봅니다** — 강제를 켜는 순간 확인되지 않은 요청은 전부 거부됩니다. 옛 판 앱과 설정이 덜 된 기기가 한꺼번에 막히지 않는지 숫자로 봅니다.
3. **비율이 충분히 높아지면 Firestore → Storage → 서버 함수 순서로 강제를 켭니다.** 콘솔에서 켠 강제는 반영까지 시간이 걸립니다(공식 문서 기준 최대 십여 분). 호출형 함수는 함수 옵션 `enforceAppCheck: true`로 켭니다.
4. **App Check는 로그인도 보안 규칙도 대신하지 않습니다** — 「진짜 앱」이라도 사용자는 남의 데이터를 노릴 수 있습니다. 규칙은 그대로 다 지킵니다.

실서비스의 강제를 켜는 것은 실서비스 설정을 바꾸는 일이라, 사용자에게 비율 숫자를 보여 확인받은 뒤 합니다.

### 하지 말 것 **[①~⑥ 공식 · ⑦~⑩ 우리 결정·이전 앱 교훈]**

| # | 하지 말 것 | 어기면 |
|---|---|---|
| ① | 비밀값·서비스 계정 키를 앱에 넣기(`--dart-define`·자산 파일 포함) | 앱을 풀면 그대로 나옵니다 |
| ② | 보안 규칙 없이(또는 시험용 「누구나 허용」 규칙으로) 컬렉션 열어 두기 | 설정 파일 값만으로 전부 읽고 씁니다 |
| ③ | 서버 함수 안에서 앱이 보낸 사용자 ID·역할을 믿기 | 남인 척 부릅니다 — 함수는 규칙을 거치지 않습니다 |
| ④ | 사용자가 쓸 수 있는 문서 필드로 권한 판단하기 | 사용자가 자기 권한을 올립니다 |
| ⑤ | 콘솔에서 규칙 고치기 | 다음 배포에서 말없이 덮어써집니다 |
| ⑥ | `functions.config()`로 비밀값 다루기 | 폐기 예정 방식입니다 — `defineSecret`을 씁니다 |
| ⑦ | 개발용 프로젝트에서만 규칙을 느슨하게 두기 | 개발용도 인터넷에 열려 있고, 실서비스로 옮길 때 차이를 놓칩니다 |
| ⑧ | 앱과 서버 함수가 함께 카운터 올리기 | 숫자가 두 번 셉니다 |
| ⑨ | App Check 강제를 숫자 확인 없이 처음부터 켜기 | 옛 판 앱과 설정이 덜 된 기기가 한꺼번에 막힙니다 |
| ⑩ | 실서비스 데이터를 AI가 지우기(`firestore:delete --project prod`·정리 스크립트) | 되돌릴 수 없습니다 — 사람 몫이고 감시 훅이 막습니다 |

### 앱 코드 검사는 겹쳐 쌓기지 최종 판정이 아닙니다 **[공식]**

앱에서 권한을 확인하지 말라는 말이 아닙니다. 버튼을 숨기고, 화면에서 막고, 저장·조회 코드에서 확인하는 것은 사용자 경험을 위해 그대로 합니다. 다만 **판정은 보안 규칙과 서버 함수가 합니다** — 앱 검사가 유일한 문이 되면 앱을 거치지 않는 요청에 통째로 뚫립니다.
