# transfer-ownership — 프로젝트 소유 옮기기

프로젝트가 밖에 만들어 둔 것들 — **저장소·Firebase 프로젝트 둘·구글 플레이 앱·소셜 로그인 앱·AppsFlyer·AI 키** — 을 한 소유에서 다른 소유로 함께 옮긴다. 생애에 한두 번이라 `idea-to-mvp` 본문이 아니라 별도 스킬이다.

**평상시 계정·토큰 관리는 이 스킬이 정하지 않는다.** `docs/account-check.md`(원칙 여섯 + 서비스별 함정)와 `4-0-backend-prep.md`가 정하고, 이 스킬은 그걸 **전제로** 쓴다 — 계정 확인 시점(원칙 ①), 발급 토큰 보관(원칙 ②), 브라우저 작업의 계정 지정(원칙 ④), 한 번만 보이는 값 확보(원칙 ⑤), 카카오 자동화 금지(서비스별 함정). 베껴 적지 않고 가리킨다.

**시작 전 브랜치 확인** — `git branch --show-current`. main이면 `/new-task`로 작업 브랜치를 먼저 연다.

> ⚠ 아래 화면 위치·명령·요금제 조건은 쓴 시점 기준이다. 따라 하기 전에 공식 문서로 확인하고, 다르면 공식 문서를 따르고 이 문서를 고쳐야 한다고 보고한다. 반대로 「계획표 승인 전에는 안 옮긴다」·「검증 전에는 옛 토큰을 안 지운다」 같은 우리 규칙은 그대로 지킨다.

## 1. Aside의 역할 — 넷뿐

나머지 실행·검증은 **CLI와 관리 API**로 한다. 호출은 `aside --account <프로필> "<지시>"`.

| | Aside가 하는 일 |
|---|---|
| ① | 양쪽 프로필에서 각 서비스를 훑어 현재 상태 보고 (읽기 전용) |
| ② | 대시보드 전용 클릭 — 프로젝트 소유자 초대·수락, 플레이 앱 이전 화면 읽기, 서비스 계정 초대, 토큰·키 발급 |
| ③ | 발급된 비밀값을 화면에서 읽어 파일로 저장 |
| ④ | 이메일 인증 코드를 메일함에서 읽어 넣기 |

**비밀값은 대화에 남기지 않는다.** Aside repl에서 세션 폴더에 쓰고(`await fs.writeFile(path.join(pwd, 이름), 값)` — **`/private/tmp`는 거부된다**), 읽어서 제자리에 넣고, 확인하고, 파일을 지운다. 값을 못 읽었으면 살려 두지 않고 바로 폐기 후 재발급(`account-check.md` 원칙 ⑤).

## 2. 0단계 — 입력

- [ ] **프로젝트 `AGENTS.md`의 계정 표는 「옛 상태」로만 읽는다.** 목표를 정하는 근거가 아니다 — 표는 [§7](#7-5단계--마무리)에서 새 소유 기준으로 다시 쓴다.
- [ ] **양쪽 소유의 Aside 프로필을 계정 명부에서 찾고, 없으면 사용자에게 묻고 시작한다.**

`aside account list`로 프로필 목록을 꺼내 **그대로 보여주고 라벨을 받는다** — "u0가 회사, u1이 개인" 식으로.

- **번호로 짐작하지 않는다.** `u0`가 회사라는 규칙은 없다(같은 컴퓨터에서 순서가 뒤바뀐 사례 있음).
- **이메일 도메인으로 단정하지 않는다.** 목록에 보이는 건 Aside 계정 이메일이지 그 프로필 안에 로그인된 저장소·Firebase·플레이 콘솔 계정이 아니다. 판정은 늘 서비스 화면의 계정 표시로 한다(`account-check.md` 원칙 ④).
- **`signed out` 프로필은 못 쓴다.** 사용자가 로그인해야 하고(사람 몫), 그때까지 그 프로필이 맡을 단계는 멈춘다.

**하네스에는 계정 값을 적지 않는다** — `project-init`이 "계정 값은 이 프로젝트 표에만 남는다"고 정해 뒀다. 명부를 새로 만들지 않는다. 사용자가 자기 방식으로 보관하면 그걸 근거로 쓰고, 없으면 물어서 받는다.

## 3. 1단계 — 조사와 이전 계획표

**읽기 전용이다.** 아무것도 만들지 않고 이전·초대 버튼도 누르지 않는다. CLI로 되는 건 CLI로, 대시보드에서만 보이는 건 Aside ①로.

- [ ] 서비스마다 한 줄씩 채운다 — **현재 소유 / 목표 / 방법(이전 vs 재생성) / 도구(CLI vs Aside vs 사람)**. 대상은 저장소 · Firebase 개발용 프로젝트 · Firebase 실서비스 프로젝트 · 구글 플레이 앱 · 플레이 서비스 계정·업로드 키 · 소셜 로그인 앱(제공사별로 한 줄) · AppsFlyer · AI 키.
- [ ] **부작용 셋을 서비스마다 점검한다.** 빈 항목으로 두지 않는다 — "없음"도 확인한 결과여야 한다.
  1. **주소·식별자가 바뀌는가** — 저장소 주소, Firebase 프로젝트 ID(소유자 이전이면 안 바뀐다), 패키지 이름(플레이 이전에서도 안 바뀐다), Hosting 도메인. 바뀌면 코드·설정 파일·콜백이 전부 따라 바뀐다.
  2. **소셜 로그인 앱을 재생성하면 사용자 식별이 갈라지는가** — 제공사 사용자 아이디가 앱 단위면 같은 사람이 새 앱에서 다른 사람으로 보여 기존 계정에 못 들어간다. **이전이 되면 이 문제가 안 생긴다**(id·secret이 따라옴 — [§10](#10-참고--실측-사실)). 제공사마다 **이전 가능 여부부터** 확인하고, 안 되는 곳만 갈라짐을 따진다.
  3. **유료 좌석·결제·등록비가 드는가** — 임시로 넣는 멤버도 자리를 차지할 수 있고, 플레이 개발자 계정이 새로 필요하면 등록비(공식 문서 기준 US$25)와 본인 확인이 든다. 구글 클라우드 청구 계정과 구독·결제 내역이 어디로 가는지도 적는다.

**사용자가 계획표를 승인해야 다음으로 간다.** 되돌리기 비싼 갈림길이다. "이건 나중에"가 나오면 그 줄을 「추후 결정」으로 표시해 [§7](#7-5단계--마무리)에서 남긴다.

## 4. 2단계 — 실행 (순서 고정)

**시작 전에 [§5 정지·금지](#5-3단계--정지금지)를 먼저 읽는다.**

```
저장소 → Firebase 두 프로젝트 → 플레이 앱 이전 → 서비스 계정 다시 초대·업로드 키 → 소셜 로그인 앱 → AppsFlyer → AI 키
```

- **저장소가 맨 앞** — 이전 뒤 CI Secret을 새 값으로 다시 넣는 일이 뒤 단계마다 따라온다. 뒤에 하면 두 번 넣는다.
- **Firebase가 플레이 이전보다 앞** — 플레이 공식 이전 안내가 이전 전에 연동 서비스(구글 클라우드 프로젝트에 새 계정을 소유자로 추가, Firebase 연결 해제 후 다시 연결)를 정리하라고 한다. 소유자가 바뀐 Firebase여야 새 플레이 계정에 다시 연결할 수 있다.
- **서비스 계정은 플레이 이전 뒤** — 앱을 다른 개발자 계정으로 옮기면 서비스 계정의 앱 권한이 따라오지 않는다. 새 개발자 계정의 플레이 콘솔에서 **서비스 계정을 다시 초대**해야 하고, 반영에 **최대 24시간**이 걸린다. 이 시간 동안 `store-release`의 fastlane 올리기는 401·403이 날 수 있다 — 재시도하지 말고 기다린다.
- **소셜 로그인 앱은 Firebase 뒤** — 콜백 주소에 Firebase 프로젝트 도메인이 들어가고, 안드로이드 서명 지문 등록은 플레이 서명이 확정된 뒤에 맞출 수 있다.
- **AI 키가 맨 뒤** — 키를 서버 함수 비밀값(실서비스 Firebase)에 한 번에 갈아 끼운다. 실서비스 비밀값 넣기는 `backend-release`의 절차로, main에서 한다.

- [ ] **단계마다 네 묶음을 거친다** — 전제 확인(명령으로, 말만 믿지 않는다) → 실행 → **API·CLI로 읽어서** 검증(화면의 "됐다"는 검증이 아니다) → 임시 멤버·옛 연결 정리.
- [ ] **저장소는 GitHub의 이전 요청 API(`POST /repos/{owner}/{repo}/transfer`, 실행기로 `.claude/scripts/with-owner.sh gh api …`)로 요청하고, 받는 쪽이 수락해야 끝난다.**
- [ ] **Firebase 프로젝트 둘(`<이름>-dev`·`<이름>-prod`)은 각각 소유자를 옮긴다.** 구글 클라우드 프로젝트는 소유자 권한(Owner)을 가진 새 구글 계정을 IAM에 추가한 뒤 옛 소유자를 빼는 방식이 기본이다(수락은 Aside ④). 새 소유가 구글 클라우드 **조직** 아래에 있어 프로젝트를 조직 사이로 옮겨야 하면, 옮기는 사람에게 프로젝트 이동 권한(`roles/resourcemanager.projectMover` 등)이 필요하고 조직·폴더에서 **상속되던 권한과 조직 정책은 따라오지 않는다**. 이동 전 서비스 계정(함수 실행 계정 포함)이 상속 권한에 기대고 있는지 읽어 두고, 이동 뒤 다시 읽어 같은지 대조한다. 조직 사이 이동의 정확한 절차·청구 계정 처리는 공식 문서(「Migrating projects」)로 확인한다. 새로 만든 조직은 서비스 계정 **키 만들기가 막혀 있을 수 있다**(`4-0-backend-prep.md`) — 막히면 멈추고 사람에게 알린다.
- [ ] **플레이 앱은 개발자 계정 사이 이전이다.** 플레이 콘솔의 앱 이전 요청을 쓰고 받는 쪽 계정 소유자가 승인한다. 공식 안내 기준으로 두 계정이 모두 활성이어야 하고, 받는 계정의 등록 결제 번호가 필요하며, 검토에 보통 영업일 이틀쯤 걸린다. **따라오는 것**: 사용자·통계·평점과 리뷰·스토어 등록정보·제출했던 정책 선언, 플레이 앱 서명 키(그 자리에 그대로 있다). **안 따라오는 것**: 비공개 테스트 등 테스트 그룹(다시 만들고 테스터가 다시 참여해야 한다), 이전 전 주문·정산 보고서, 연동 서비스 권한(서비스 계정·구글 애널리틱스·Firebase 연결). 이전 요청 전에 보고서를 내려받아 둔다. 이전 뒤 업로드 키가 필요하면 새 계정에서 업로드 키 재설정을 요청할 수 있다.
- [ ] **새 소유의 계정 장부를 먼저 준비한다** — 키는 프로젝트가 아니라 이 컴퓨터의 `~/.config/harness/<새 소유>.env`에 둔다(폴더 700·파일 600, 없으면 `project-init` 신규 3단계의 장부 자리 만들기 명령). 이름은 `.claude/scripts/with-owner.sh` 기준이다 — `GH_TOKEN` · `FIREBASE_ACCOUNT`(새 구글 계정 이메일; `firebase login:add`로 이 컴퓨터에 등록) · `FIREBASE_SA_DIR`(개발용 시드 전용 — 개발용 프로젝트의 관리자 키 폴더) · `PLAY_SERVICE_ACCOUNT_FILE`. 업로드 키는 장부에 없다(아래). 같은 소유의 다른 프로젝트가 이미 받아 둔 키가 있으면 다시 발급하지 않고 그대로 쓴다. **`.claude/owner`는 [§7](#7-5단계--마무리)까지 옛 소유 그대로 둔다** — 실행기는 기본으로 옛 소유 장부로 돌아 옛 쪽에서 이전을 실행한다. 새 소유 쪽 키로 한 번 부를 때만 앞에 소유를 적는다: `HARNESS_OWNER=<새 소유> .claude/scripts/with-owner.sh --check`.
- [ ] **새 토큰·키는 발급 즉시 API로 유효성을 확인한 뒤** 새 소유의 계정 장부 · CI Secret · 서버 함수 비밀값(실서비스 Firebase)에 설치한다. 들어가는 자리는 `4-0-backend-prep.md` §4.1 값을 넣는 곳 표가 정본이다 — 한 곳만 바꾸면 나머지가 옛 값으로 남아 특정 기능만 조용히 실패한다.
- [ ] **업로드 키는 소유가 바뀌어도 플레이 앱 서명 키가 그대로 있는 한 계속 쓸 수 있다.** 업로드 키는 장부가 아니라 패키지 이름으로 정한 자리(`~/.config/harness/keys/<패키지 이름>-upload.jks`·`<패키지 이름>-upload.properties`)에 있어, 소유를 바꿔도 옮길 것이 없다. 새 소유가 직접 쥐고 싶으면 업로드 키 재설정을 플레이에 요청한다 — 옛 두 파일은 다른 이름으로 따로 보관해 두고, 새 키 파일과 비밀번호 파일을 같은 자리·같은 이름(파일 600)에 둔다. 키 파일·비밀번호는 대화·커밋에 적지 않는다.
- [ ] **계정 확인은 매 단계 쓰기 작업 직전에 다시 한다**(원칙 ①). CLI는 실행기로 부르고(`.claude/scripts/with-owner.sh gh …`·`… fnm exec --using=.nvmrc -- npx firebase … --project <dev|prod>`), 지금 어느 소유의 장부로 도는지를 `.claude/scripts/with-owner.sh --check`로 먼저 본다 — 실행기를 거치지 않으면 전역 활성 계정이 저절로 바뀌어 있을 수 있다([§10](#10-참고--실측-사실)). 옛 소유 쪽에서 해야 하는 일(이전 요청 등)과 새 소유 쪽에서 해야 하는 일(수락·새 키 확인)을 단계마다 밝힌다.

## 5. 3단계 — 정지·금지

- [ ] **자동화 금지 서비스(카카오)는 사람이 하고 AI는 키 교체만 한다** — 브라우저 에이전트를 붙였다가 계정이 제재된 실사고가 있다(`account-check.md` 서비스별 함정). 조사([§3](#3-1단계--조사와-이전-계획표))에서도 그 화면은 열지 않고 사용자에게 현재 상태를 묻는다.
- [ ] **플레이 콘솔의 앱 이전 요청·승인은 사람이 한다.** 앱의 주인이 바뀌는 일이라 AI는 화면을 읽어 상태만 보고하고, 요청·승인 버튼은 누르지 않는다.
- [ ] **실서비스 데이터를 지우거나 `--project prod`로 배포하지 않는다** — 이전은 소유자만 바꾸는 일이다. 감시 훅도 main이 아니면 막는다.
- [ ] **일회용 코드(OTP)·패스키는 사람 몫이다.** 비밀번호는 Aside 금고가 자동으로 채우고, 에이전트는 비밀번호 값을 직접 다루지 않는다. 이메일 인증 코드만 Aside ④가 읽어 넣는다.
- [ ] **옛 토큰·키·앱은 검증([§6](#6-4단계--검증))이 끝날 때까지 폐기를 보류한다.** 되감기가 가능한 이유가 이 보류다.
- [ ] **폐기 전에 같은 계정의 다른 프로젝트가 쓰는지 확인하고 사용자에게 묻는다** — 발급 토큰은 소유 계정당 하나를 여러 프로젝트가 나눠 쓰는 게 기본이라(원칙 ②), 이 프로젝트만 보고 지우면 남의 프로젝트가 멈춘다.

## 6. 4단계 — 검증

**PR 하나에 셋을 함께 담는다.**

- [ ] **CI가 새 Secret으로 통과하나** — 토큰이 CI Secret에 제대로 들어갔는지 드러난다.
- [ ] **새 소유 계정으로 두 Firebase 프로젝트를 읽을 수 있나** — `.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase projects:list`에 `-dev`·`-prod`가 보이고, 읽기 명령(예: 함수 목록 조회)이 두 프로젝트에서 도는지 본다. 배포는 하지 않는다.
- [ ] **플레이 연결이 사나** — 서비스 계정을 다시 초대했으면 24시간이 지난 뒤 `.claude/scripts/with-owner.sh bundle exec fastlane check_key`가 통과하는지 본다. 401·403이면 재시도하지 말고 초대·API 켜기를 사람에게 확인받는다. 지난 테스트 그룹이 다시 만들어졌는지는 사람이 콘솔에서 본다.

**기기 스모크 검사와 시드 정리는 개발용 데이터가 순수한 상태를 가정한다**([§10](#10-참고--실측-사실)). 리셋할지 스킵할지는 **사람이 정한다.** AI가 임의로 지우지 않는다.

**화면 판정은 사람 몫이다** — 개발용 앱·시험 트랙 앱을 사용자가 직접 열어 로그인·주요 흐름을 확인한다. 확인했다는 말을 들은 뒤에 `/done-task`를 부른다.

## 7. 5단계 — 마무리

- [ ] **소유를 세 곳에서 함께 바꾼다** — 검증([§6](#6-4단계--검증))이 끝난 뒤, 한 커밋에.
  1. `.claude/owner`를 `owner=<새 소유>`로(개인 `personal` · 회사 `company` · 조직 `org-<영문 짧은 이름>`).
  2. `AGENTS.md` 「소유와 계정」 절의 「이 프로젝트의 소유: **…**」 문장을 같은 값으로.
  3. 이 컴퓨터의 새 소유 장부(`~/.config/harness/<새 소유>.env`)에 이 프로젝트가 쓰는 키가 다 있는지 `.claude/scripts/with-owner.sh --check`로 본다(키 이름만 나온다). 옛 소유 장부는 지우지 않는다 — 같은 소유의 다른 프로젝트가 쓴다. 옛 장부의 키를 폐기할지는 맨 끝 질문에서 묻는다.
  4. git 자격 증명 도우미는 그대로 둔다 — 실행기가 `.claude/owner`를 보고 새 장부의 토큰을 건넨다. `git credential fill` 확인(`github-connect` ⑦ 「설정 확인」)만 다시 한다.
  팀원이 있으면 「각자 컴퓨터에서 '깃헙 연결해줘'로 새 소유 장부를 채워 주세요」를 마무리 보고에 남긴다.
- [ ] **계정 표를 새 소유 기준으로 전면 다시 쓴다** — 서비스별 계정·이메일(구글 계정·플레이 개발자 계정 포함), 커밋 작성자(git), 브라우저 작업 프로필까지. **토큰이 들어간 자리·만료일은 표가 아니라 비밀값 장부**(`mvp/backend-build.md`)에 적는다 — 표는 「누구의 계정인가」만 답한다. **「옛 상태는 이랬다」를 남기지 않는다**(산출물은 매 판이 완결, 옛 값은 git 이력에). 로컬 git 작성자 설정도 표와 맞춘다(전역은 안 건드린다).
- [ ] **「추후 결정」 항목을 표에 `추후 결정:`으로 남긴다** — 지우지 않는다.
- [ ] **계정 명부 갱신 문안을 사용자에게 건넨다** — 하네스에 계정을 안 적으므로([§2](#2-0단계--입력)), 사용자가 자기 보관처에 그대로 붙여 넣을 완성된 문단으로. 담을 것: 프로필↔계정 새 대응, 서비스별 계정·이메일, 토큰이 들어간 자리, 재발급 기한. **값 자체(토큰·키 문자열)는 넣지 않는다.**
- [ ] **메모리를 갱신한다** — 이 프로젝트의 소유가 바뀌었다는 사실과 새 프로필 대응.
- [ ] **마지막으로 옛 토큰·키·앱 폐기 여부를 묻는다**([§5](#5-3단계--정지금지)). "지워도 된다"고 답한 것만 지운다.

## 8. 6단계 — 되감기

되감기도 [§4](#4-2단계--실행-순서-고정)의 네 묶음을 그대로 거친다. 되돌리는 중에도 검증을 건너뛰지 않는다.

| 단계 | 되돌리는 법 | 주의 |
|---|---|---|
| 저장소 | 같은 이전 요청 API로 옛 소유에 다시 요청 | 옛 소유 쪽에 같은 이름 저장소가 있으면 실패 — 먼저 확인 |
| Firebase 두 프로젝트 | 옛 소유자를 소유자로 다시 추가하고 새 쪽을 뺀다(조직을 옮겼으면 반대 방향 이동) | 상속 권한·조직 정책은 따라오지 않으니 이동 전후 대조 |
| 플레이 앱 | 반대 방향 앱 이전 요청 | 테스트 그룹·연동 권한이 또 안 따라온다. 사람이 요청·승인한다 |
| 서비스 계정·업로드 키 | 옛 개발자 계정에서 서비스 계정을 다시 초대, 업로드 키를 새로 바꿨으면 따로 보관한 옛 두 파일을 `keys/<패키지 이름>-upload.*` 자리에 되돌린다 | 초대 반영 최대 24시간. 옛 키를 폐기하기 전이어야 한다 |
| 로그인 앱 | 새로 만든 앱이면 옛 앱 값을 값을 넣는 곳 표대로 되돌린다 | **옛 앱을 안 지웠을 때만** — [§5](#5-3단계--정지금지)의 보류가 이걸 위한 것 |
| AppsFlyer | 옛 계정의 앱·키를 다시 연결하고 앱의 키 값을 되돌린다 | 새 쪽에 쌓인 측정 기록은 새 쪽에 남는다 |
| AI 키 | 옛 키를 서버 함수 비밀값에 다시 넣는다(`backend-release`) | 폐기 전이어야 한다 |
| 소유 선언 | `.claude/owner`·`AGENTS.md` 소유 문장을 옛 값으로(파일이라 `/rewind-task`로도 된다) | 옛 소유 장부를 지우지 않았을 때만 바로 돈다 |

**저장소 안 파일**(설정 파일의 키 이름·계정 표·콜백 주소)은 `/rewind-task`로 되감는다 — 이 표는 **밖에 있는 것**을 되돌리는 법이다.

**옮기다 중간에 멈췄으면 되감기보다 마저 끝내는 쪽이 대개 안전하다.** 절반 상태가 가장 잘 깨진다. 되감기는 계획 자체가 틀렸을 때 고르는 길이고, 어느 쪽으로 갈지는 사용자에게 묻는다.

## 9. 안 하는 것 (범위 밖)

- ❌ 계정 만들기 · 플레이 개발자 계정 등록(등록비·본인 확인) · 2단계 인증(2FA) 설정 · 사업자 인증 · 유료 플랜 결제·좌석 구매 — 전부 사람 몫. AI는 필요하다는 사실만 [§3](#3-1단계--조사와-이전-계획표) 부작용에 적어 알린다.
- ❌ 카카오 콘솔 조작 — [§5](#5-3단계--정지금지).
- ❌ 화면을 열어 동작 판정 — 사람이 본다(저장소 검증 규칙).
- ❌ 평상시 계정·토큰 관리 규칙 정하기 — `account-check.md`와 `4-0-backend-prep.md` 몫.
- ❌ 하네스 저장소에 계정 값 적기 — [§2](#2-0단계--입력).

## 10. 참고 — 실측 사실

규칙이 아니라 사실이라 서비스가 바뀌면 낡는다. 어긋나면 공식 문서를 따르고 이 절을 고쳐야 한다고 보고한다.

- **Anthropic API 키는 워크스페이스 범위로 발급해야** 별도 헤더 없이 쓸 수 있다.
- **구글 클라우드 프로젝트의 조직·폴더 사이 이동(`gcloud beta projects move`)은 프로젝트에 직접 붙은 권한만 데려가고, 상속되던 권한·조직 정책은 따라오지 않는다**(공식 문서 기준). 조직 사이 이동은 별도 「Migrating projects」 안내를 따른다.
- **플레이 앱 이전은 사용자·통계·평점·스토어 등록정보·플레이 앱 서명 키를 그대로 옮기고, 테스트 그룹·이전 주문·정산 보고서·연동 서비스 권한은 안 옮긴다**(공식 문서 기준). 검토는 보통 영업일 이틀쯤 걸린다.
- **서비스 계정의 플레이 권한은 이전 뒤 새 개발자 계정에서 다시 초대해야 하고, 반영에 최대 24시간이 걸린다.** 그 사이의 401·403은 코드 문제가 아니다.
- **GitHub 저장소 이전은 `gh api -X POST /repos/{owner}/{repo}/transfer`로 요청하고, 받는 쪽이 이메일 링크로 수락해야 완료된다.** Actions Secrets는 따라온다.
- **GitHub 저장소와 GitHub OAuth 앱은 이전해도 id·secret이 유지된다** — 설정 변경 0건. 그래서 이전되는 앱은 사용자 로그인 식별도 안 갈라진다.
- **구글 로그인 앱의 소유 이전은 아직 실측이 없다** — Firebase 인증의 구글 로그인 설정은 그 프로젝트와 함께 움직이니 프로젝트를 옮기면 따라간다고 보지만, 실제로 옮겨 보면 여기 적는다.
- **gh 토큰 우선순위는 `account-check.md` gh 항목.** 실행기 없이 부를 때 쓰이는 전역 활성 계정은 계정이 둘이면 저절로 바뀌는 일이 있다. git 자격 증명 도우미가 실행기가 아닌 다른 것을 가리키면 `github-connect` ⑦대로 다시 건다(전역 `gh auth setup-git`은 쓰지 않는다).
- **기기 스모크 검사는 개발용 Firebase의 시드 순수 상태를 가정한다** — 개발 중 손으로 넣은 데이터가 남아 있으면 순위·집계가 어긋난다. 개발용 시드 스크립트가 쓰는 관리자 키(`FIREBASE_SA_DIR`)는 개발용 전용이고 실서비스용 키 파일은 만들지 않는다.
