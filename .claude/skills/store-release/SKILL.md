# store-release

**메인이 직접 돌립니다. 서브 에이전트에 맡기지 않습니다.** 결과가 사용자의 폰에 바로 닿는 일이라, 사람이 중간에 낀 채로 한 걸음씩 실행합니다(`AGENTS.md` 「배포는 위임 금지」). **이 맥에서 돌립니다** — 업로드 키와 플레이 서비스 계정 키가 이 컴퓨터를 떠나지 않게 하려는 것입니다. GitHub Actions 같은 바깥 실행 환경에서 올리지 않습니다.

머지(`/done-task`)는 main에 합치는 일일 뿐, 플레이에는 아무것도 나가지 않습니다. 이 스킬이 「main의 이 커밋을 플레이 트랙에 올린다」를 맡습니다. 실서비스 Firebase(규칙·함수·Hosting·Remote Config)는 `backend-release`가 따로 합니다.

> ⚠ 플레이 콘솔의 메뉴 이름·정책(목표 안드로이드 판 하한 등)과 fastlane의 옵션은 바뀝니다. 따라 하기 전에 공식 문서로 지금도 맞는지 확인하고, 달라졌으면 공식 문서를 따르고 이 스킬을 고칠 문안을 사용자에게 줍니다. 판 숫자는 이 문서에 적지 않습니다.

## 1. 언제 부르나

- **3단계 첫 판** — `3-frontend-build.md` §2.6. 「번들만 만들기」 갈래로 번들을 만들고, 사람이 콘솔에서 내부 테스트에 올립니다.
- **3~4단계에 고친 판** — 피드백을 고쳐 합친 뒤. Draft가 풀리기 전이면 「번들만 만들기」.
- **4단계 베타 공유** — `4-3-backend-deploy.md` 「베타 공유」. 차례는 보안 리뷰 → 머지 → `backend-release` → **이 스킬(「번들만 만들기」)** → 사람이 비공개 테스트 트랙에 올림 → 검토 통과. 이 검토를 통과하는 순간 Draft App 제약이 풀립니다.
- **6단계 앞부터** — fastlane을 켠 뒤(§8) 「fastlane으로 올리기」로 올리고, 프로덕션 출시와 단계적 출시를 「출시 관리」로 다룹니다.

사용자가 「올려줘」라고 하지 않았는데 먼저 올리지 않습니다. 이번 변경에 백엔드가 함께 바뀌었으면 `AGENTS.md` 「백엔드와 앱의 배포 순서」를 먼저 봅니다 — **더하는 것은 `backend-release`가 먼저**, 없애는 것은 이 스킬과 §7이 먼저입니다.

## 2. 지키는 것

- **main의 커밋에서만 만듭니다.** 작업 브랜치에서 만든 번들은 「실서비스 = main」을 깹니다. fastlane은 main이 아니면 감시 훅과 Fastfile이 둘 다 막습니다.
- **키를 부르는 명령은 실행기를 앞에 붙입니다** — `.claude/scripts/with-owner.sh …`. 실행기가 계정 장부에서 `PLAY_SERVICE_ACCOUNT_FILE`(플레이 서비스 계정 키 파일 경로)을 넣고, 이 앱의 패키지 이름(`applicationId`)으로 업로드 키 비밀번호 파일 경로 `~/.config/harness/keys/<패키지 이름>-upload.properties`를 찾아 `ANDROID_UPLOAD_KEY_PROPERTIES`로 넣어 줍니다. 업로드 키는 앱마다 따로라 장부에 적지 않습니다. 두 키 파일은 프로젝트 밖 장부 폴더의 `keys/`에 있습니다.
- **키 값을 화면에 내지 않습니다** — 키 파일이나 `key.properties`를 `cat`하지 않고, 비밀번호를 대화·문서·주석·커밋 메시지에 적지 않습니다. 이전 앱에서 확인한 교훈: 워크플로 파일에 비밀번호가 평문으로 남은 사고가 있었습니다. 감시 훅이 커밋 때 `storePassword=` 같은 줄을 막습니다.
- **업로드 키는 빌드하는 동안만 프로젝트에 연결하고 끝나면 지웁니다**(§4.3).
- **개발용(debug) 서명 번들은 올리지 않습니다**(§4.4).
- **같은 빌드 번호는 두 번 못 올립니다** — 한 번 올린 번호로 되돌아가지도 못합니다(§6).
- **바깥으로 나가는 요청은 같은 실패 2회면 멈추고 보고합니다.** 401·403·404는 다시 시도하지 않습니다 — 권한 문제를 되풀이하면 계정 제재로 이어질 수 있습니다(`docs/account-check.md`). 콘솔 로그인은 사람 몫입니다.
- **플레이 콘솔에서 누르는 일은 사람이 합니다** — 첫 업로드·앱 콘텐츠 신고·검토 보내기·약관 동의. AI가 브라우저로 대신 누르지 않습니다.

## 3. 갈래와 트랙 고르기

**갈래** — 앱이 Draft App(한 번도 검토를 통과해 출시된 적 없는 앱)인지가 가릅니다. Draft App에는 명령 도구로 「완료」 상태 릴리스나 스토어 정보를 올릴 수 없습니다(`Only releases with status draft may be created on draft app`). 이전 앱에서 확인한 교훈입니다.

| 갈래 | 언제 | 끝에 하는 일 |
|---|---|---|
| **번들만 만들기** | Draft가 아직 안 풀림(`mvp/backend-build.md`에 「비공개 테스트 트랙: 검토 통과」 줄이 없음), 또는 fastlane을 아직 안 켬 | 번들 경로·버전 이름·변경 내역을 사람에게 건네고, 사람이 콘솔에서 올립니다 |
| **fastlane으로 올리기** | Draft가 풀렸고 fastlane을 켬(§8) | `upload` lane으로 올립니다 |
| **출시 관리** | 이미 올린 판의 비율 바꾸기·멈추기·트랙 옮기기 | §5. 번들을 새로 만들지 않습니다 |

Draft가 풀렸는지 확실하지 않으면 사람에게 묻거나, fastlane 갈래에서 `dry_run:true`(플레이에 검사만 요청)를 먼저 돌려 봅니다 — 위 오류가 나면 「번들만 만들기」로 돌아갑니다.

**트랙** — 사용자에게 어느 트랙인지 확인합니다. fastlane의 트랙 이름은 플레이 API 기준입니다.

| 트랙 | fastlane 이름 | 쓰는 때 | 메모 |
|---|---|---|---|
| 내부 테스트 | `internal` | 3단계, 그 뒤 수시로 | 이메일 목록 최대 100명. 검토 없이 금방 받습니다 |
| 비공개 테스트 | `alpha` | 4단계 베타 공유 | 검토를 거칩니다. 첫 통과가 Draft 해제 지점입니다 |
| 공개 테스트 | `beta` | 기본으로 안 씁니다 | 누구나 참가할 수 있어 측정 기간과 섞입니다 |
| 프로덕션 | `production` | 6단계 정식 출시부터 | 검토를 거칩니다. **처음 내는 프로덕션 출시는 단계적 출시를 쓸 수 없습니다**(공식 도움말) |

## 4. 차례

### 4.1 시작 확인

1. **지금 자리** — `git branch --show-current`가 `main`인지, `git status --porcelain`이 비었는지, `git pull --ff-only`로 원격 main과 같은지 봅니다. 작업 브랜치에 서 있으면 먼저 그 작업을 합칠지 사용자에게 묻습니다 — 합치지 않은 코드는 올리지 않습니다.
2. **계정** — 처음 쓰는 컴퓨터거나 처음 올리는 앱이면 `.claude/scripts/with-owner.sh --check`로 소유와, 「업로드 키」 줄이 「있음」인지(fastlane 갈래면 장부의 키 이름에 `PLAY_SERVICE_ACCOUNT_FILE`도 있는지) 봅니다. 「아직 없음」이면 업로드 키를 아직 만들지 않은 것이고, 장부의 옛 `ANDROID_UPLOAD_KEY_PROPERTIES` 줄을 옮기라는 주의가 나오면 그 안내대로 옮긴 뒤 진행합니다. 콘솔에 로그인한 계정이 `AGENTS.md` 계정 표의 「구글 플레이 콘솔 개발자 계정」과 같은지는 사람이 봅니다.
3. **판 이름과 번호** — `pubspec.yaml`의 `version: x.y.z+N`과 가장 큰 `v*` 태그를 봅니다(`git tag --list 'v*' --sort=-v:refname | head -1`).
4. **사용자에게 한 번에 묻습니다** — 「`<x.y.z>+<N>`(빌드 번호를 올려야 하면 올린 뒤의 번호)으로, `<갈래>`로 `<트랙>`에 내보냅니다. 빌드 번호를 올리는 커밋은 작업 브랜치에서 PR로 합칩니다. 진행할까요?」 이 대답이 빌드 번호 커밋을 합치는 「보내줘」를 겸합니다 — 화면이 바뀌지 않는 한 줄짜리 커밋이라서입니다. 화면 코드가 함께 바뀌어 있으면 겸하지 않고, 평소처럼 화면 확인 뒤 `/done-task`부터 합니다.

### 4.2 빌드 번호 올리기

- **올릴 필요가 없을 때** — `pubspec.yaml`의 N이 가장 큰 태그의 N보다 이미 크면(예: 3단계 첫 판을 작업 브랜치에서 `0.1.0+1`로 적어 합친 경우) 이 절을 건너뜁니다.
- **올릴 때** — `/new-task`로 작업 브랜치(예: `chore/release-0.3.1+13`)를 열고 → `pubspec.yaml`의 `+N`을 가장 큰 태그의 N + 1로, 필요하면 `x.y.z`도 바꾸고 → 그 빌드 번호의 변경 내역 파일을 둡니다(fastlane을 켰으면 `fastlane/metadata/android/ko-KR/changelogs/<N>.txt`, 아니면 사람에게 건넬 문구만) → 커밋 → `/done-task`로 합칩니다 → main으로 돌아와 `git pull --ff-only`.
- 앞 숫자 `x.y.z`는 3단계 `0.x`, 6단계 정식 출시 때 `1.0.0`입니다.
- 빌드 번호는 **올리기 직전에 한 번만** 올립니다. 미리 여러 번 올려 두면 번호가 건너뛰어 어느 판이 어느 커밋인지 헷갈립니다.

### 4.3 앱 번들 만들기

프로젝트 맨 위 폴더에서, main에서 합니다.

1. **업로드 키를 연결합니다** — 서명 설정은 `android/key.properties`가 있으면 업로드 키로, 없으면 debug 키로 서명합니다(서명 틀 `.claude/templates/android-signing/README.md`). 실행기가 넣어 준 이 앱의 비밀번호 파일 경로를 그 자리에 바로가기(심볼릭 링크)로 겁니다. 경로는 실행기 안에서만 펼칩니다.

   ```bash
   .claude/scripts/with-owner.sh bash -c 'test -f "$ANDROID_UPLOAD_KEY_PROPERTIES" && ln -sfn "$ANDROID_UPLOAD_KEY_PROPERTIES" android/key.properties'
   ```

   실패하면 이 앱의 업로드 키 비밀번호 파일(`~/.config/harness/keys/<패키지 이름>-upload.properties`)이 없거나, 실행기가 패키지 이름을 읽지 못한 것입니다 — `.claude/scripts/with-owner.sh --check`의 「업로드 키」 줄을 보고 멈춰 사람에게 알립니다. 업로드 키를 새로 만드는 일은 3단계 문서(§2.6.2 ⑥)와 서명 틀 README 몫입니다.

2. **번들을 만듭니다** — 4단계부터는 실서비스 설정 파일 `env/prod.json`이 있으면 그것을 함께 넘깁니다(`4-3-backend-deploy.md`).

   ```bash
   .claude/scripts/build-lock.sh fvm flutter build appbundle --release --flavor prod -t lib/main_prod.dart
   # env/prod.json이 있으면(4단계부터) 끝에 --dart-define-from-file=env/prod.json
   ```

   다른 빌드(`flutter test`·다른 `flutter build`)와 동시에 돌리지 않습니다 — 같은 빌드 폴더를 씁니다. 앞의 `build-lock.sh`는 다른 프로젝트의 무거운 빌드와도 겹치지 않게 맥 전체에서 한 번에 하나만 돌립니다. 「다른 프로젝트가 빌드 중이라 기다립니다」가 나오면 기다리고, 잠금을 지우지 않습니다. 결과는 `build/app/outputs/bundle/prodRelease/app-prod-release.aab`입니다.

3. **연결을 지웁니다** — 성공했든 실패했든 바로 지웁니다. 바로가기만 지우므로 원본은 그대로입니다.

   ```bash
   rm -f android/key.properties
   ```

### 4.4 서명 확인

```bash
keytool -printcert -jarfile build/app/outputs/bundle/prodRelease/app-prod-release.aab
```

- 서명자 줄에 `CN=Android Debug`가 있으면 **올리지 않습니다** — 업로드 키 연결이 빠진 채 빌드된 것입니다. §4.3부터 다시 합니다.
- SHA-256 지문이 업로드 키 인증서 지문과 같은지 봅니다. 기준 지문은 비밀값 장부(`mvp/backend-build.md`)의 업로드 키 행에, 그 장부가 아직 없으면(4단계 전) 사람이 플레이 콘솔 「앱 무결성」 화면의 「업로드 키 인증서」에서 읽어 줍니다. 처음 올리는 판이면 비교할 기준이 없으니 debug가 아닌 것만 확인합니다. 지문은 비밀값이 아니라 대화에 적어도 됩니다.
- fastlane 갈래는 Fastfile도 올리기 전에 debug 서명을 한 번 더 거릅니다.

### 4.5 올리기

**「번들만 만들기」 갈래** — 사람에게 아래를 건넵니다.

- 파일: `build/app/outputs/bundle/prodRelease/app-prod-release.aab`(필요하면 Finder에서 열어 줍니다)
- 버전: `<x.y.z>+<N>`, 트랙
- 변경 내역: 한국어 몇 줄(플레이 한도 안 — 대략 500자)
- 사람이 할 일: 콘솔 → 그 앱 → 트랙(내부 테스트 / 비공개 테스트) → 「새 버전 만들기」 → 번들 올리기 → 변경 내역 붙여 넣기 → 검토 → 출시(비공개 테스트면 검토로 보내기). 처음이면 플레이 앱 서명을 켭니다.

사람이 「올렸다」고 하면 §4.6으로 갑니다. 콘솔이 낸 경고·오류를 사람이 옮겨 주면 무엇을 고칠지 정리합니다.

**「fastlane으로 올리기」 갈래** — 먼저 검사만, 그다음 실제로 올립니다.

```bash
.claude/scripts/with-owner.sh bundle exec fastlane upload track:internal dry_run:true
.claude/scripts/with-owner.sh bundle exec fastlane upload track:internal
```

- 프로덕션은 `track:production`. 단계적 출시면 `rollout:0.1`처럼 비율을 붙입니다(§5). 처음 내는 프로덕션 출시는 비율 없이 올립니다.
- `upload`는 앱 번들과 그 빌드 번호의 변경 내역만 올립니다. 스토어 정보(글·그림·스크린샷)는 바꾸지 않습니다 — 6단계 측정 기간에 「스토어 등록정보 수정 금지」가 실수로 깨지지 않게 하려는 것입니다. 스토어 정보는 사용자가 따로 「스토어 정보 올려줘」라고 할 때 `listing` lane으로 올립니다(`dry_run:true` 먼저).
- 스토어 정보와 변경 내역은 `fastlane/metadata/android/ko-KR/`의 파일이 정본이고 git으로 관리합니다. 고칠 때는 작업 브랜치 → PR로 고칩니다. `ruby fastlane/check_metadata.rb --version-code <N>`은 어느 브랜치에서나 돌아, PR 전에 글자 수·자리 표시·그림 크기를 걸러 줍니다.

### 4.6 태그 남기기

번들을 만든 main 커밋에 판 태그를 남기고 원격에 올립니다.

```bash
git tag "v<x.y.z>+<N>"
git push origin "v<x.y.z>+<N>"
```

태그는 「이 빌드 번호가 어느 커밋인가」의 유일한 기록입니다. 다음 판의 빌드 번호(§4.2)와 되돌리기(§6)가 이 태그를 봅니다.

## 5. 단계적 출시와 멈추기

단계적 출시(staged rollout)는 새 판을 사용자 일부(예: 10%)에게만 먼저 내보내고, 문제가 없으면 비율을 올리는 방식입니다. 프로덕션에서 씁니다. **처음 내는 프로덕션 출시에는 쓸 수 없고**(공식 도움말: 앱을 처음 낼 때가 아니라 업데이트에만 가능), 그 뒤 업데이트부터 씁니다.

```bash
.claude/scripts/with-owner.sh bundle exec fastlane upload track:production rollout:0.1     # 10%부터
.claude/scripts/with-owner.sh bundle exec fastlane rollout version_code:<N> rollout:0.5    # 50%로
.claude/scripts/with-owner.sh bundle exec fastlane rollout version_code:<N> rollout:1      # 전체로
.claude/scripts/with-owner.sh bundle exec fastlane halt version_code:<N>                   # 멈추기
```

- **비율을 올리기 전에 사람이 지표를 봅니다** — Crashlytics의 비정상 종료, 플레이 콘솔의 「Android vitals」, 리뷰. 몇 % 몇 시간마다 올릴지는 6단계 `launch-plan.md`가 정합니다.
- **멈추면** 그 판을 아직 안 받은 사람에게 더 나가지 않을 뿐, **이미 받은 사람은 그 판에 그대로 남습니다**(공식 도움말). 그래서 멈춤은 피해가 퍼지는 것을 막는 첫 손이지 되돌리기가 아닙니다 — 이어서 §6을 합니다.
- 멈춘 판을 다시 이어 내보내려면 `rollout`으로 비율을 다시 줍니다.
- 이미 다른 트랙에 올린 번들을 그대로 옮길 때는 `promote`를 씁니다 — `promote version_code:<N> from:internal to:production`.
- Draft가 풀리기 전이거나 fastlane을 켜기 전이면 같은 일을 사람이 콘솔 「출시 관리 → 출시 중지·재개」에서 합니다.

## 6. 되돌리기

**플레이는 한 번 올린 빌드 번호로 되돌아갈 수 없습니다.** 옛 판을 다시 올리는 방식은 통하지 않습니다. 차례는 이렇습니다(`docs/git-workflow.md` 「코드 복구와 서비스 복구는 다르다」).

1. **단계적 출시 중이면 멈춥니다**(§5) — 피해가 퍼지는 것부터 막습니다.
2. **고친 커밋, 또는 문제 커밋을 되돌린 커밋을 main에 합칩니다** — 작업 브랜치 → PR. 되돌리기 커밋이라도 사람의 「보내줘」를 받습니다.
3. **더 높은 빌드 번호로 다시 올립니다** — 이 스킬을 처음부터 다시 돕니다(§4.2에서 번호가 올라갑니다).
4. **옛 판이 꼭 막혀야 하는 문제면 §7로 강제 업데이트를 겁니다** — 보안 구멍, 데이터를 망가뜨리는 버그 등.

백엔드가 함께 잘못 나갔으면 `backend-release`의 되돌리기를 먼저 합니다.

## 7. 강제 업데이트와 잇기

옛 판 앱은 사용자 폰에 오래 남습니다. 옛 판을 막아야 할 때는 Remote Config(앱이 켤 때 받아 오는 원격 설정 값)의 `min_version` 키를 올려, 그보다 낮은 판 앱이 「업데이트가 필요합니다」 화면을 띄우게 합니다. 앱 쪽 화면과 키는 4단계에서 넣습니다.

- **순서가 중요합니다** — 새 판이 사용자에게 **다 나간 뒤에**(단계적 출시면 100%가 된 뒤, 스토어에서 받을 수 있게 된 뒤) `min_version`을 올립니다. 먼저 올리면 사용자가 업데이트하려 해도 받을 판이 없어 앱을 못 씁니다.
- **올리는 길** — Remote Config 기본값 파일을 작업 브랜치 → PR로 고친 뒤 `backend-release`로 내보냅니다. 콘솔에서 사람이 바로 바꿀 수도 있는데, 그러면 다음 `backend-release` 전에 저장소 파일도 맞춥니다(그 스킬이 차이를 보여 줍니다).
- **없애는 백엔드 변경**(필드·함수 삭제, 규칙 조이기)은 이 강제 업데이트가 끝났거나, 옛 판 사용자가 충분히 줄었다는 것을 플레이 콘솔에서 확인한 뒤에만 `backend-release`로 합니다(`AGENTS.md` 「백엔드와 앱의 배포 순서」).

## 8. fastlane 처음 켜기 — 6단계 앞

fastlane(스토어 올리기를 명령으로 하는 도구)의 `supply`(플레이용 기능)로 앱 번들과 스토어 정보를 올립니다. Draft가 풀린 뒤(4단계 비공개 테스트 검토 통과)에 켭니다. **권한 반영에 최대 하루가 걸릴 수 있어** 6단계 광고 준비보다 하루 이상 먼저 시작합니다. 이전 앱에서 확인한 교훈입니다.

1. **[사람] 구글 클라우드 쪽** — 플레이 콘솔이 연결된 구글 클라우드 프로젝트에서 「Google Play Android Developer API」를 켜고, 서비스 계정(사람 대신 API를 부르는 계정)을 만들어 JSON 키를 받습니다. 새로 만든 구글 클라우드 조직은 보안 기본값으로 **서비스 계정 키 만들기가 막혀 있을 수 있습니다** — 막히면 멈추고, 조직 관리자가 그 프로젝트에만 예외를 열어야 합니다. 화면 이름은 그때 공식 안내로 확인합니다.
2. **[AI] 키 파일을 장부 폴더로 옮깁니다** — 사람이 받은 파일을 `~/.config/harness/keys/<패키지 이름>-play.json`으로 옮기고 권한을 600으로 바꾼 뒤, 장부에 `PLAY_SERVICE_ACCOUNT_FILE=<그 경로>` 한 줄을 둡니다. 파일 내용은 열어 보지 않습니다. `.claude/scripts/with-owner.sh --check`로 이름이 보이는지 확인합니다.
3. **[사람] 플레이 콘솔 쪽** — 「사용자 및 권한」에서 서비스 계정 이메일을 초대하고, 이 앱에 출시와 스토어 정보를 다룰 권한을 줍니다. 서비스 계정 이메일을 `AGENTS.md` 계정 표의 「플레이 올리기용 서비스 계정」 행에 적습니다. 권한이 퍼지는 데 최대 하루 걸립니다. **앱을 다른 개발자 계정으로 옮기면 이 권한은 따라오지 않습니다** — 옮긴 뒤 다시 초대합니다.
4. **[AI] 작업 브랜치에서 틀을 넣습니다** — `.claude/templates/fastlane/README.md`의 차례대로: `Gemfile`(프로젝트 맨 위)·`fastlane/` 복사, 패키지 이름 바꾸기, `bundle install`로 `Gemfile.lock` 만들기, `mvp/store-listing.md`의 확정 문구를 스토어 정보 파일로 옮기기, 스크린샷 만들기, `ruby fastlane/check_metadata.rb` 통과. 그다음 PR로 합칩니다.
5. **[메인] main에서 키를 확인합니다** — `.claude/scripts/with-owner.sh bundle exec fastlane check_key`. 401·403이면 다시 돌리지 않고 3번 권한과 1번 API 켜기를 사람에게 확인받습니다(하루가 아직 안 지났을 수 있습니다).
6. **[메인] 콘솔의 지금 스토어 정보와 맞대 봅니다** — 콘솔에 사람이 손으로 넣어 둔 정보가 git 파일과 다를 수 있습니다. 임시 폴더로 받아 비교합니다 — 저장소 안에 받으면 git 파일을 덮습니다.

   ```bash
   .claude/scripts/with-owner.sh bundle exec fastlane supply init --metadata_path <스크래치 폴더>/play-now
   diff -r <스크래치 폴더>/play-now fastlane/metadata/android
   ```

   다른 곳은 사용자에게 보여 주고 어느 쪽을 정본으로 할지 묻습니다. 이 명령이 끝에 `undefined method 'name' for nil` 같은 오류를 내도, 받은 파일이 폴더에 다 있으면 받기는 된 것입니다 — 특정 fastlane·Ruby 판 조합의 버그입니다(이전 앱에서 확인한 교훈). 스크린샷·영상은 플레이 API가 내려 주지 않습니다.
7. 그 뒤로는 §4의 「fastlane으로 올리기」 갈래를 씁니다.

## 9. 자주 나는 오류

| 오류·상황 | 뜻 | 할 일 |
|---|---|---|
| `Only releases with status draft may be created on draft app` | 앱이 아직 Draft App | 「번들만 만들기」로 돌아가 사람이 콘솔로 올립니다. 비공개 테스트 검토를 통과하면 풀립니다 |
| 401·403, 「권한이 없습니다」 | 서비스 계정 권한이 아직 안 퍼졌거나, API가 꺼졌거나, 앱에 초대가 안 됨 | 다시 시도하지 않고 §8의 1·3번을 사람에게 확인받습니다. 초대 뒤 하루가 안 지났으면 기다립니다 |
| 「이 버전 코드는 이미 사용되었습니다」 류 | 같은 빌드 번호를 다시 올림 | §4.2로 번호를 올립니다 |
| 「업로드 키가 다릅니다」 류 | 다른 키로 서명됨 | `~/.config/harness/keys/<패키지 이름>-upload.properties`의 `storeFile`이 같은 앱의 `<패키지 이름>-upload.jks`를 가리키는지, 그 키가 이 앱을 처음 올릴 때 쓴 키인지 사람과 확인합니다. 업로드 키를 잃었으면 구글에 재설정을 요청합니다(며칠 걸림) |
| 목표 안드로이드 판이 낮다는 거절 | 그해 플레이 요건보다 `targetSdk`가 낮음 | 공식 요건을 확인하고, Flutter 판 올리기와 함께 작업 브랜치에서 맞춥니다 |
| 스토어 정보 점검 실패 | 글자 수·자리 표시·그림 크기 | `ruby fastlane/check_metadata.rb`가 알려 준 대로 작업 브랜치에서 고칩니다 |
| `ensure_git_branch`·`ensure_git_status_clean` 실패 | main이 아니거나 커밋 안 된 변경이 있음 | §4.1로 돌아갑니다 |

## 10. 끝나고 알리기

사용자에게 짧게 알립니다.

- 무엇을 어디에 올렸나 — 「`<x.y.z>+<N>`을 `<트랙>`에 올렸습니다」(번들만 만들었으면 「번들을 만들었습니다 — 콘솔에서 올려 주세요」와 파일 경로).
- 사람이 할 일 — 참가 링크로 받아 폰에서 확인하기, 프로덕션이면 검토 결과 기다리기, 단계적 출시면 다음 비율을 올릴 시점.
- 남긴 기록 — 태그 이름. 4단계 비공개 테스트 검토를 통과했으면 `mvp/backend-build.md`에 그 날짜를 적는다는 것(`4-3-backend-deploy.md`).
