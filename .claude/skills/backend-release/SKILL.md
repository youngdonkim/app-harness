# backend-release

**메인이 직접 돌립니다. 서브 에이전트에 맡기지 않습니다.** 결과가 실사용자에게 바로 닿는 일이라, 사람이 중간에 낀 채로 한 걸음씩 실행합니다(`AGENTS.md` 「배포는 위임 금지」).

머지(`/done-task`)는 main에 합치는 일일 뿐, 실서비스 Firebase는 그대로입니다. 이 스킬이 「main의 이 커밋을 실서비스에 내보낸다」를 맡습니다. 앱(플레이)을 올리는 일은 `store-release`가 따로 합니다.

## 1. 언제 부르나

- **사용자가 「올려줘」라고 했을 때만** 부릅니다. 머지 뒤에 알아서 부르지 않습니다. 머지가 끝나면 "실서비스 백엔드에도 올릴까요?"라고 묻고 답을 기다립니다.
- 바뀐 것이 앱 코드(`lib/`)뿐이면 이 스킬은 할 일이 없습니다 — `store-release` 몫입니다.
- 4단계 첫 출시(`4-3-backend-deploy.md` §2.4)와, 그 뒤 규칙·색인·서버 함수·Hosting·Remote Config를 바꿀 때마다 부릅니다.
- 3단계에서 개인정보처리방침 페이지만 먼저 띄울 때도 부릅니다 — 그때는 Hosting만 나가고, 설정이 아직 `hosting/` 안에 있어 명령을 그 폴더에서 부릅니다. 개발용 프로젝트가 아직 없으므로 §3의 2번은 「사람이 내 컴퓨터에서 페이지를 열어 확인했다」로, 5·6·8번은 해당 없음으로 봅니다. §6(첫 출시에만 하는 일)은 4단계 첫 출시 때 합니다. 출시 표시 태그(§9)는 이때도 남깁니다. 순서는 `.claude/templates/hosting-site/README.md` §3.

## 2. 지키는 것

- **main에서만 합니다.** 작업 트리가 깨끗하고 원격 main과 같아야 합니다. 감시 훅(`owner-runner-guard.sh`)도 `--project prod`로 실서비스를 바꾸는 명령을 main이 아니면 막습니다.
- **명령 꼴은 하나입니다** — 실행기를 맨 앞에, 별칭 `prod`를 반드시 적습니다.

  ```bash
  .claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase <명령> --project prod
  ```

  실행기가 계정 장부의 Firebase 계정(`--account`)을 붙입니다. 프로젝트 ID를 직접 쓰거나 `firebase use`를 쓰지 않습니다(훅이 막음).
- **실서비스 데이터를 지우지 않습니다** — §7.4. 훅도 막습니다.
- **비밀값을 화면·대화에 내지 않습니다** — `functions:secrets:access`는 훅이 막습니다.
- **같은 실패가 2번 나면 멈추고 보고합니다.** 권한 오류(401·403)는 다시 시도하지 않고 사람에게 넘깁니다. 로그인이 풀렸으면 사람이 `firebase login`을 다시 합니다.
- **한 걸음마다 무엇을 할지 먼저 보여 주고 진행합니다.** 사용자가 「멈춰」라고 하면 그 자리에서 멈춥니다.

## 3. 실서비스 배포 전 확인 — 8항목

맨 앞에서 돌립니다. **하나라도 어긋나면 배포하지 않고 멈춰 무엇이 어긋났는지 보고합니다.** 결과는 항목마다 「통과·어긋남·해당 없음」으로 표로 보여 줍니다.

| # | 확인 | 어떻게 |
|---|---|---|
| 1 | main에 서 있고, 작업 트리가 깨끗하고, 원격 main과 같은가 | `git branch --show-current`가 `main`, `git status --porcelain`이 비어 있음, `git fetch origin main` 뒤 `git rev-parse HEAD` = `git rev-parse origin/main` |
| 2 | 같은 변경이 개발용 프로젝트에 먼저 배포됐고, 사람이 개발용 앱에서 확인했다고 말했는가 | 사용자에게 묻습니다. 「확인했다」는 답이 없으면 멈춥니다. AI가 개발용에 배포했다는 사실만으로는 통과가 아닙니다 |
| 3 | 별칭 `prod`의 프로젝트 ID가 계정 표의 실서비스 프로젝트와 같은가 | `.firebaserc`의 `projects.prod` ↔ `AGENTS.md` 「소유와 계정」 표의 실서비스 프로젝트 행. `.claude/scripts/with-owner.sh --check`의 Firebase 계정도 표와 대조합니다 |
| 4 | 이번에 바뀐 것만 고르는가 | §4로 고른 `--only` 목록을 보여 줍니다. 「전부 배포」(`--only` 없는 `deploy`)는 하지 않습니다 |
| 5 | 보안 규칙 테스트가 통과했는가 | 이 커밋(또는 이 커밋을 만든 PR)의 CI에서 규칙 테스트 단계가 통과. `with-owner.sh gh run list --branch main --limit 5` 등으로 봅니다. 이 맥에서는 에뮬레이터를 띄우지 않습니다 |
| 6 | 보호 필드를 건드렸으면, 규칙·보호 필드 표·규칙 테스트 세 곳이 같은 커밋에서 함께 바뀌었는가 | 이번 범위의 `firestore.rules` 차이에 보호 필드 목록(`protectedFields`·`createsNone`·`changesNone`)이 닿았으면, 같은 범위에 `mvp/backend-build.md` 「보호 필드」 절과 `rules-test/` 차이도 있어야 합니다 |
| 7 | 무언가를 **없애는** 변경이면, 옛 판 앱이 아직 그것을 쓰는지 판단했는가 | 필드·컬렉션·함수 삭제, 규칙 조이기(필수 필드·형식 검사 추가)가 있으면 — 실서비스 Remote Config의 `min_version`(`remoteconfig:get --project prod`로 읽기)과 플레이 콘솔의 판별 사용자 수를 사람에게 보여 「새 앱이 먼저 나갔고 옛 판이 충분히 줄었다」는 답을 받습니다(§5) |
| 8 | 앱 쪽 설정 파일이 실서비스 프로젝트를 가리키는가 | `fvm dart run tool/check_firebase_config.dart` 통과 — 실서비스 설정 파일 세 개의 프로젝트 ID = `.firebaserc`의 `prod`. 이번에 앱을 함께 내지 않아도 돌립니다(Hosting·함수 리전과 앱이 어긋나는 일을 미리 잡음) |

8항목이 모두 통과하면, 나갈 목록(§4)과 순서(§5)를 한 화면에 보여 주고 **「이대로 올릴까요?」 한 번 더 확인받은 뒤** 실행합니다.

## 4. 이번에 나갈 것 고르기

**기준점은 지난 출시입니다.** 출시할 때마다 그 커밋에 태그 `backend-release/<YYYYMMDD>-<짧은 커밋 번호>`를 남기므로(§9), 가장 최근 태그부터 지금 커밋까지의 차이로 고릅니다. 태그가 없으면 이번 커밋의 해당 파일 전부가 나갈 것입니다.

```bash
LAST=$(git tag --list 'backend-release/*' --sort=-creatordate | head -n 1)
git diff --name-only "$LAST"..HEAD -- firestore.rules firestore.indexes.json storage.rules functions/ hosting/ remoteconfig.template.json firebase.json
```

| 바뀐 파일 | `--only`에 넣는 것 |
|---|---|
| `firestore.rules` | `firestore:rules` |
| `firestore.indexes.json` | `firestore:indexes` |
| `storage.rules` | `storage` |
| `functions/src/<기능>/…` | 그 기능 폴더가 내보내는 함수마다 `functions:<함수 이름>` — 이름은 `functions/src/index.ts`에서 그 폴더를 내보내는 줄로 찾습니다 |
| `functions/src/config/`·공용 도우미·`functions/package.json`·잠금 파일 | 그것을 쓰는 함수 전부 — 범위를 사람에게 보여 확인받습니다. 판단이 안 서면 함수 전체(`functions`) |
| `hosting/` | `hosting` |
| `remoteconfig.template.json` | `remoteconfig` |
| `firebase.json` | 바뀐 자리에 해당하는 것 — 차이를 보고 고릅니다 |

- **함수를 고르는 이유** — 함수를 통째로 배포하면 오래 걸리고, 건드리지 않은 함수까지 새로 떠 배포 한도에 걸리기 쉽습니다. 이전 앱에서 확인한 교훈: 영향받는 함수만 골라 배포했습니다.
- **함수를 지운 경우** — `index.ts`에서 빠진 함수는 배포 때 Firebase CLI가 「실서비스에 있는데 코드에 없는 함수를 지울까」를 묻습니다. 이건 「없애는 변경」이라 §3의 7번을 거친 뒤에만, 사람에게 그 함수 이름을 보여 확인받고 진행합니다. 확인 없이 지워지는 옵션(`--force`)은 쓰지 않습니다.
- **Remote Config** — 실서비스 콘솔에서 사람이 바꾼 값이 있을 수 있습니다. 배포 전에 `remoteconfig:get --project prod`로 지금 값을 받아 저장소 파일과 다른 키를 보여 주고, 덮어써도 되는지 확인받습니다.

## 5. 배포 순서

**한 번의 출시 안에서는 이 순서로 나눠 배포합니다** — 앞의 것이 실패하면 뒤로 가지 않습니다.

1. **색인** (`firestore:indexes`) — 새 질의가 색인보다 먼저 나가면 질의가 실패합니다. 색인은 만드는 데 시간이 걸리니, 배포 뒤 실서비스 콘솔에서 「만드는 중」이 끝났는지 보고 다음으로 갑니다. 기다리는 동안 대기 고리를 돌리지 않고, 사람에게 「끝나면 알려 주세요」라고 하거나 다음 확인 때 봅니다.
2. **보안 규칙** (`firestore:rules`, `storage`)
3. **서버 함수** (`functions:<이름>,…`)
4. **Remote Config** (`remoteconfig`)
5. **Hosting** (`hosting`)

**서버 함수가 Hosting보다 먼저인 이유** — Hosting의 재작성 규칙(`/api/deletion-request` → `deletionRequest`)이 서버 함수를 가리키므로, 함수가 아직 없는데 Hosting이 먼저 나가면 폼이 실패합니다. Hosting을 함께 올릴 때는 반드시 함수 배포가 끝난 뒤에 합니다.

```bash
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase deploy --only firestore:indexes --project prod
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase deploy --only firestore:rules,storage --project prod
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase deploy --only functions:<함수1>,functions:<함수2> --project prod
```

**더하는 변경과 없애는 변경의 순서** — 정본은 `AGENTS.md` 「백엔드와 앱의 배포 순서」 표입니다. 이 스킬에서 지키는 꼴은 이렇습니다.

| 변경 | 이 스킬이 하는 일 |
|---|---|
| 더하는 것(새 필드·새 함수·규칙 넓히기) | 앱 출시(`store-release`)보다 **먼저** 이 스킬을 돌립니다. 새 앱이 기대하는 것이 실서비스에 먼저 있어야 합니다 |
| 없애는 것(필드·함수 삭제, 규칙 조이기) | 새 앱이 이미 나갔고, `min_version`을 올렸거나 옛 판 사용자가 충분히 줄었다는 답을 받은 **뒤에만** 합니다(§3의 7번). MVP 기간에는 필드를 지우지 않고 남겨 두는 쪽이 기본입니다 |
| 둘이 함께 바뀌어야 하는 것 | 「더하는 출시」와 「나중의 없애는 출시」 두 번으로 쪼갭니다. 한 번에 하자는 요청이 오면 이 표를 보여 주고 멈춥니다 |

**규칙을 조이는 변경**은 「없애는 것」입니다 — 옛 판 앱의 쓰기가 거부됩니다.

## 6. 첫 출시에만 하는 일

**실서비스에 서버 함수·보안 규칙을 처음 내보낼 때**(보통 4단계 첫 출시 — 3단계에 Hosting만 먼저 올렸어도 마찬가지) 배포 순서(§5)보다 **먼저** 합니다. 이미 했는지는 비밀값 장부(`mvp/backend-build.md`)와 명령으로 확인하고, 된 것은 건너뜁니다.

### 6.1 실서비스 비밀값 넣기

서버 함수의 비밀값은 `defineSecret('이름')`으로 정의되고(`4-1-backend-db.md` §8.3), **프로젝트마다 따로** 넣습니다. 실서비스에는 개발용과 **다른 키**를 넣습니다.

1. 넣어야 할 이름을 코드에서 뽑습니다 — `functions/src/`에서 `defineSecret(` 줄. 비밀값 장부의 「실서비스」 행과 대조해 빠진 이름을 보여 줍니다.
2. 이미 있는지 봅니다 — `functions:secrets:get <이름> --project prod`(값은 안 나오고 판 목록만 나옵니다).
3. **값은 사람이 넣습니다** — 메인이 아래 명령을 보여 주고, 사용자가 자기 터미널에서 쳐 값을 붙여 넣습니다. 값을 대화로 받지 않습니다. 사용자가 원하면 값을 파일로 받아 `--data-file`로 넣고 그 자리에서 파일을 지웁니다(파일 경로는 프로젝트 밖).

   ```bash
   .claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase functions:secrets:set <이름> --project prod
   ```

4. 넣은 뒤에는 **그 비밀값을 쓰는 함수를 다시 배포해야** 새 값이 반영됩니다(공식 동작). 첫 출시에는 §5의 함수 배포가 이것을 겸합니다. 첫 출시 뒤 값만 바꾼 때는 그 함수들만 다시 배포합니다.
5. 비밀값 장부의 「실서비스」 행(저장된 곳·만료일·갱신 시 같이 바꿀 곳)을 채웁니다 — 장부 수정은 작업 브랜치 → PR로 넣습니다.

### 6.2 카카오 로그인 함수의 토큰 서명 권한

카카오 로그인 함수(`4-2-backend-auth.md` §11.2)는 관리자 SDK로 Firebase 커스텀 토큰을 만듭니다. 서버 함수 안에서는 키 파일 없이 함수의 기본 서비스 계정으로 서명하므로, 그 계정에 **토큰 서명 권한**(`iam.serviceAccounts.signBlob` — 보통 「서비스 계정 토큰 생성자」 역할로 줍니다)이 있어야 합니다. 없으면 카카오 로그인만 실패하고, 개발용에서 이미 맞춰 둔 권한은 실서비스에 따라오지 않습니다.

1. **[AI]** 서버 함수가 어느 서비스 계정으로 도는지 공식 문서로 확인해 사람에게 알립니다(함수 세대·설정에 따라 다릅니다).
2. **[사람 또는 Aside]** 구글 클라우드 콘솔에서 **실서비스 프로젝트**를 고른 것을 화면 위 프로젝트 선택기로 확인한 뒤, 「IAM 및 관리자 → IAM」에서 그 서비스 계정에 역할이 있는지 보고, 없으면 줍니다. 역할 이름은 그때 IAM 문서로 확인합니다. 「소유자」·「편집자」 같은 넓은 역할은 주지 않습니다.
3. 첫 출시 뒤 시험 트랙 앱으로 카카오 로그인을 사람이 눌러 확인합니다. 실패하면 함수 로그(`functions:log --project prod`)에서 서명 오류부터 봅니다.

카카오 로그인을 쓰지 않으면 이 절은 건너뜁니다.

### 6.3 예약 백업 걸기

실사용자를 받기 전에 실서비스 Firestore에 정기 백업을 겁니다(`4-1-backend-db.md` §13). Blaze 요금제가 필요합니다(4-0에서 바꿈).

```bash
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase firestore:backups:schedules:list --project prod --database '(default)'
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase firestore:backups:schedules:create --project prod --database '(default)' --recurrence DAILY --retention <보관 기간>
```

- 일정(매일·매주)과 보관 기간은 사용자에게 묻습니다. 데이터베이스마다 매일 일정 하나·매주 일정 하나까지이고, 보관 기간에 상한이 있습니다 — 정확한 한도와 옵션 이름은 그때 Firestore 백업 공식 문서로 확인합니다.
- **시점 복구**(PITR — 지난 며칠 안의 원하는 시각으로 데이터를 되돌리는 기능)는 비용을 공식 문서로 확인해 보여 주고, 켤지 사용자에게 묻습니다.
- **복구는 사람 몫입니다.** 백업 복구는 새 데이터베이스로 되살리는 일이라 앱이 그쪽을 보게 하는 작업까지 붙습니다 — AI가 하지 않습니다.
- 건 일정을 `backend-build.md` 「Firebase 프로젝트」 표 아래에 적습니다(작업 브랜치 → PR).

## 7. 때마다 하는 일

### 7.1 App Check 강제 켜기

App Check는 「이 요청이 진짜 우리 앱에서 왔나」를 확인합니다. 앱 쪽은 처음부터 켜져 토큰을 보내고, 서버 쪽 강제는 **숫자를 본 뒤 단계적으로** 켭니다(`security-baseline.md` 2부). 처음부터 강제하면 옛 판 앱과 설정이 덜 된 기기가 한꺼번에 막힙니다.

1. **[사람 또는 Aside] 숫자를 읽습니다** — 실서비스 프로젝트 콘솔의 「App Check → API」에서 Firestore·Storage·서버 함수마다 **확인된 요청 비율**(확인된 요청 / 전체)과 기간을 읽습니다.
2. **[메인] 숫자를 사용자에게 그대로 보여 주고 확인받습니다** — 「Firestore: 지난 7일 확인된 요청 ○○%, 확인 안 된 요청 ○○건. 강제를 켜면 이 ○○건에 해당하는 요청이 거부됩니다. 켤까요?」 비율이 몇 %면 켤지 하네스가 정하지 않습니다 — 사용자가 숫자를 보고 정합니다. 확인 안 된 요청이 어디서 오는지(옛 판 앱·디버그 앱·웹 페이지) 짐작이 가면 함께 말합니다.
3. **켜는 순서는 Firestore → Storage → 서버 함수입니다.** 한 번에 하나씩 켜고, 다음 것은 하루 이상 뒤 오류·이탈 숫자를 본 뒤에 켭니다.
   - Firestore·Storage — **[사람 또는 Aside]** 콘솔의 강제 버튼. 반영까지 시간이 걸립니다(공식 문서 기준 최대 십여 분).
   - 서버 함수(호출형) — 함수 옵션 `enforceAppCheck: true`를 작업 브랜치에서 넣고 → 머지 → 이 스킬로 그 함수들만 배포합니다.
4. **Hosting의 계정 삭제 요청 폼은 영향이 없습니다.** 폼은 서버 함수(`deletionRequest`)로 받고, 함수가 관리자 권한으로 Firestore에 쓰므로 Firestore 강제를 켜도 막히지 않습니다(`.claude/templates/hosting-site/README.md` 「App Check와 웹 폼」).
5. 켠 날짜와 그때의 비율을 `backend-build.md` 「배포 정보」의 App Check 줄에 적습니다(작업 브랜치 → PR).

문제가 나면 콘솔에서 강제를 끄는 것이 가장 빠른 되돌리기입니다 — 사람에게 그 버튼 위치를 알립니다.

### 7.2 실서비스 데이터 일괄 고치기

옛 문서에 새 필드를 채우는 일처럼 실서비스 데이터를 한꺼번에 고치는 일입니다(`4-1-backend-db.md` §12.1). **지우는 일은 여기 들지 않습니다**(§7.4).

1. **개발용에서 먼저 돌립니다** — 같은 스크립트를 작업 브랜치에서 `--project dev`로 돌려 결과를 사람이 확인합니다.
2. **실서비스 자격 증명은 키 파일로 만들지 않습니다**(4-0 §3.4). 그래서 실서비스 일괄 고치기는 **그 일만 하는 서버 함수**(호출형, 권한 판정 `can('<권한>')`으로 운영자만)로 짜서, 머지 → 이 스킬로 배포 → 운영자 계정으로 부르는 방식으로 합니다. 함수는 일을 마친 뒤 다음 출시에서 지웁니다.
3. **[사람 확인] 부르기 전에 보여 줍니다** — 대상 건수, 바뀔 필드와 값 예시 몇 건, 되돌리는 법. 사용자가 「하세요」라고 해야 부릅니다. 함수에는 「건수만 세고 고치지 않는」 미리보기 모드를 먼저 둡니다.
4. **500건씩 끊어 일괄 쓰기(batch)로** 차례로 고칩니다. 요청 크기 한도에 걸리지 않고, 중간에 실패해도 어디까지 됐는지 압니다. 함수는 처리한 마지막 문서 ID를 돌려줘 이어서 할 수 있게 합니다.
5. 끝나면 건수를 보고하고, 사람이 개발용·실서비스 앱에서 결과를 확인합니다.

### 7.3 역할(클레임) 붙이고 떼기

운영자 같은 특별한 역할은 사용자 정의 클레임(로그인 토큰에 서버가 붙이는 값)의 `roles` 목록에 담습니다(`4-2-backend-auth.md` §12).

- **실서비스에서는 서버 함수를 거칩니다.** 실서비스 관리자 키 파일이 없으므로(4-0 §3.4), 클레임을 쓰는 일은 권한을 가진 호출형 서버 함수(예: `can('roles.manage')`)가 합니다. 그 함수의 배포도 이 스킬로 main에서 합니다.
- **첫 운영자** — 아직 운영자가 아무도 없으면 그 함수를 부를 사람이 없습니다. 첫 한 사람은 **[사람]**이 구글 클라우드 콘솔의 Cloud Shell(구글 클라우드 콘솔 안 터미널 — 소유 계정의 권한으로 돕니다)에서 관리자 SDK 한 줄로 붙입니다. 메인은 그 명령을 대상 `uid`와 함께 보여 주고, 사람이 실행합니다.
- **누구에게 무엇을 붙이고 떼는지** 사람에게 보여 확인받은 뒤 부릅니다.
- 붙인 역할은 그 사용자의 앱이 토큰을 새로 받아야 보이고, 뗀 역할은 옛 토큰이 남은 동안 살아 있습니다(최대 한 시간 — 공식). 급히 거둬야 하면 같은 함수가 갱신 토큰 폐기까지 하게 짭니다(4-2 §12.3 ②).

### 7.4 실서비스 데이터 지우기 — 사람 몫

**AI는 실서비스 데이터를 지우지 않습니다.** `firestore:delete --project prod`, 실서비스를 겨냥한 정리 스크립트, 데이터베이스 지우기는 감시 훅이 언제나 막습니다. 되돌릴 수 없는 일이라서입니다.

정말 지워야 하면(계정 삭제 요청 처리, 시험 요청 문서 정리 등):

1. 메인이 **무엇을, 몇 건, 왜** 지우는지와 지우기 전 백업이 있는지(§6.3)를 정리해 보여 줍니다.
2. **[사람]**이 실서비스 콘솔에서 직접 지우거나, 사람이 자기 터미널에서 명령을 칩니다. 메인은 콘솔의 위치를 안내만 합니다.
3. 계정 삭제 요청이 쌓이는 일이 잦아지면, 앱 안 탈퇴와 같은 서버 함수(`4-2-backend-auth.md` §11.4)로 처리하는 길을 작업 브랜치에서 만듭니다 — 그 함수의 배포는 이 스킬, 부르는 일은 사람의 확인 뒤입니다.

## 8. 되돌리기

**백엔드는 문제가 없던 이전 커밋을 다시 배포해 되돌립니다**(`docs/git-workflow.md` §7). 서비스부터 되돌리고, 코드 정리는 그 뒤입니다.

1. **되돌릴 곳을 고릅니다** — 문제가 생기기 전 출시 태그(`backend-release/…`)가 기본입니다. 그 커밋이 원격 main에 들어 있는지 `git merge-base --is-ancestor <커밋> origin/main`으로 확인합니다. main에 없는 커밋은 실서비스에 내지 않습니다.
2. **나간 것만 되돌립니다** — 이번 출시의 `--only` 목록(태그 사이 차이, §4)만 이전 커밋 것으로 다시 냅니다.
3. **이전 커밋의 파일로 배포합니다** — 지금 폴더는 main 그대로 두고, 이전 커밋을 옆 폴더에 꺼내 그 폴더의 `firebase.json`을 가리켜 배포합니다. 감시 훅은 지금 폴더가 main인 것을 봅니다.

   ```bash
   git worktree add --detach ../<저장소 이름>-rollback <커밋>
   (cd ../<저장소 이름>-rollback/functions && fnm exec --using=../.nvmrc -- npm ci)   # 함수를 되돌릴 때만
   .claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase deploy \
     --config ../<저장소 이름>-rollback/firebase.json --only <되돌릴 목록> --project prod
   git worktree remove ../<저장소 이름>-rollback
   ```

   `--config`가 그 폴더 기준으로 규칙·함수 자리를 읽는지는 그때 Firebase CLI 도움말로 확인합니다. 처음 쓸 때는 개발용(`--project dev`)으로 먼저 한 번 시험합니다. 안 되면 아래 「빠른 길」로 서비스부터 멈추고, 4번의 되돌리는 커밋을 main에 넣은 뒤 그 커밋을 평소대로 출시합니다.
4. **그다음 코드 되돌리기** — `docs/git-workflow.md` §5대로 되돌리는 커밋을 작업 브랜치 → PR → 머지로 넣습니다. 그래야 다음 출시가 문제를 다시 내보내지 않습니다.

**빠른 길(서비스가 급할 때)** — 함수 하나가 문제면 그 함수만 되돌립니다. 보안 규칙은 콘솔의 규칙 기록에서 이전 판을 다시 게시하는 것이 가장 빠르고, Hosting은 콘솔의 출시 기록에서 이전 판으로 되돌릴 수 있습니다 — 둘 다 **[사람 또는 Aside]**가 콘솔에서 합니다. 콘솔에서 되돌린 것은 다음 배포가 저장소 파일로 덮어쓰므로, 4번의 코드 되돌리기를 반드시 뒤따라 합니다.

**데이터는 이 절로 되돌리지 않습니다** — 데이터 복구는 백업에서 사람이 합니다(§6.3).

## 9. 끝나고 알리기

1. **출시 표시 태그를 남깁니다** — `git tag backend-release/<YYYYMMDD>-<짧은 커밋 번호>` → `git push origin backend-release/<…>`. 태그만 올리는 것이라 main에 직접 올리는 일이 아닙니다. 다음 출시의 기준점이 됩니다(§4).
2. **사용자에게 알립니다** — 무엇이 나갔는지(규칙·함수 이름·Hosting), 무엇을 누르면 확인되는지(「시험 트랙 앱에서 ○○ 화면을 열어 ○○을 해 보면 됩니다」 / 「Hosting 주소 ○○을 새로 고침」), 남은 일(App Check 강제·앱 출시 차례 등).
3. **기록할 것이 있으면** `mvp/backend-build.md`(배포 정보·비밀값 장부·App Check 줄·백업 일정)를 고칩니다. main에서 직접 고치지 않습니다 — `/new-task`로 브랜치를 열어 넣습니다.
4. 함수 로그를 한 번 봅니다 — `functions:log --project prod`에 배포 직후 오류가 쏟아지면 바로 사용자에게 알리고 §8을 제안합니다.
