# ship-task

메인 세션의 `done-task` 스킬이 부르는 내부 스킬이다 — 사람이 직접 칠 일은 없다. 현재 브랜치의 WIP 커밋들을 PR 흐름으로 main에 ship한다. **(코드 변경 시 코드 정리 관문) → (조건부 origin/main 합치기) → (백엔드 파일이 바뀌었을 때만 순서 안내) → (`integration_test/` 있을 때만 기기 스모크 관문) → push → PR 생성 → (머지 권한 있을 때만) CI 대기 → squash merge → remote 브랜치 삭제** 한 흐름.

머지 권한은 사람마다 다르다 — 오너는 squash merge까지, 팀원은 PR 생성까지 (§2.5).

이 스킬은 `context: fork`로 git-flow 서브에이전트(sonnet)에서 격리 실행된다 — 메인 세션 토큰 절약 목적. 실행 중 사용자 질문이 불가능하므로 결정 지점은 [결정 필요] 반환 → 결정을 args에 담아 재호출하는 프로토콜을 쓴다.

**이 스킬이 돌 때는 사용자의 ship 신호(승인)가 이미 끝난 상태다 — 이후 [결정 필요]는 호출자(done-task)가 판단해 재호출한다.**

## 호출 인자

이번 호출의 인자: **$ARGUMENTS**

위가 비어 있으면 인자 없이 호출된 것. 인자에는 작업 의도와 [결정 필요]에 대한 결정 지시가 자연어로 담긴다 — 해석은 §호출 패턴. (fork 실행 시 호출 인자는 위 자리표시자를 치환해 전달된다 — 이 섹션이 이 스킬의 인자 수신 지점이므로 삭제 금지.)

**사용자의 ship 신호 = 승인, 호출은 done-task가 대행**: 이 스킬이 도는 시점엔 사용자가 이미 ship(푸시·PR 생성·(머지 권한 있으면) 머지까지)을 승인한 상태다 — PR 제목·body는 AI 초안 그대로 사용, 별도 확인 없음 (사용자가 정한 규칙). 머지 권한이 없으면 애초에 승인해도 머지가 안 되니, 이 경우 승인의 범위는 자연히 PR 생성까지로 줄어든다 (§2.5).

### 왜 GitHub squash인가 (local squash 아님)

- main은 squash 1개, wip은 PR 페이지 Commits 탭에 보존.
- 근거는 `docs/git-workflow.md` §2.

## 진입 전 가정

- 프로젝트 루트가 git repo
- 현재 브랜치는 feature 브랜치 (main 아님)
- 의미 있는 작업이 wip 커밋으로 누적된 상태
- 내 브랜치를 push할 권한은 있음 (PR로 올리니 main 직접 push 권한은 불필요)
- main으로 **머지**할 권한은 사람마다 다를 수 있음 (§2.5). 이 스킬은 강제하지 않고 GitHub 저장소 설정을 그대로 따른다 — 브랜치 보호 규칙을 걸 수 있는지는 `## 안 하는 것` 참조.

## 실행 흐름

### 1. 안전 검사 (실패 시 사용자 안내 후 중단)

**1-0. 계정 확인** (프로젝트 `AGENTS.md`에 「소유와 계정」 표가 있을 때만 — 없으면 건너뛴다) — 절차·서비스별 함정은 `docs/account-check.md`를 읽는다. 원격 저장소를 처음 만드는 일은 이 스킬이 아니라 `github-connect` 몫이다(아래 하드 ②).

**먼저 gh가 어느 계정으로 도는지 정한다.** gh 인증은 이 프로젝트 소유의 계정 장부(`~/.config/harness/<소유>.env` — 소유는 `.claude/owner`)에 든 `GH_TOKEN`으로 한다. **이 스킬의 모든 `gh` 명령은 실행기를 앞에 붙여 부른다** — 실행기가 장부를 읽어 같은 호출 안에서 환경변수로 넣고 진짜 `gh` 프로그램을 띄운다(셸 함수를 거치지 않는다).

```bash
.claude/scripts/with-owner.sh --check          # 소유·장부·있는 키 이름·gh 계정 (키 값은 안 나옴)
.claude/scripts/with-owner.sh gh api user --jq .login
```

- **장부에서 `GH_TOKEN`을 읽었으면** 위 명령이 답하는 계정이 곧 gh가 쓸 계정이다. 이 값을 표와 대조한다. **전역 활성 계정은 보지 않고 `gh auth switch`도 쓰지 않는다** — 환경변수 토큰이 저장된 자격 증명보다 우선해서 전환이 아무 효과가 없다.
- **실행기가 옛 `.env.cli`를 읽었다고 알리면 (옛 프로젝트 호환)** 그대로 진행하되 §4 완료 보고에 이 한 줄을 남긴다: "○ 이 프로젝트는 아직 옛 `.env.cli`를 씁니다 — '하네스 동기화해줘'라고 말씀하시면 계정 장부로 옮깁니다."
- **장부도 `.env.cli`도 없어 실행기가 멈추면** — 이 스킬은 토큰을 받지 않는다. 중단하고 "GitHub 키가 없습니다 — '깃헙 연결해줘'라고 말씀하시면 `github-connect`가 받아 둡니다"로 안내한다.
- **`git push`도 같은 토큰으로 인증한다** — 기본 방식은 HTTPS + 토큰이다(`github-connect` ⑦: 이 저장소의 로컬 git 설정에 걸린 자격 증명 도우미가 실행기 `--git-credential`로 장부의 `GH_TOKEN`을 git에게만 건넨다). 그래서 **git 명령(push·fetch·pull·ls-remote)에는 실행기를 앞에 붙이지 않고 맨 형태로 부른다** — 훅이 첫 낱말 `git`으로 명령을 본다.
- **원격 주소가 ssh 형식(`git@github.com:`·`ssh://`)인 옛 프로젝트만** push가 SSH로 인증해서 이 토큰과 무관하다 — 그때는 아래 하드 ①(원격 주소의 SSH 호스트 별칭)이 그 방식을 맡고, 두 방식이 다 표의 소유와 맞아야 한다.

검사가 두 축이다.

- **하드 (다르면 멈춤)**: ① 원격 주소(SSH 호스트 별칭 포함)가 표 소유자의 저장소를 가리키는가. ② 원격이 아직 없으면(`git remote get-url origin` 실패) **만들지 않고 멈춘다** — "먼저 `github-connect`로 GitHub 저장소를 이어야 합니다 ('깃헙 연결해줘'라고 말씀하시면 됩니다)"로 안내한다. 원격 생성은 저장소가 계정에 묶이는 순간이라, 표 대조 뒤에 만드는 `github-connect` ⑥·⑧ 몫이다. (토큰을 안 걸면 CLI 활성 계정은 전역이라, 다른 소유의 프로젝트를 오가면 바뀌어 있다 — 그 계정이 조용히 저장소의 주인이 된다.)
- **소프트 (원격이 이미 있을 때)**: **위에서 정한 gh 계정**이 표와 다를 때 — **토큰 자체가 다른 계정 것이다.** 계정 전환으로는 못 고치니(토큰이 우선한다) 막지 말고 §4 완료 보고에 한 줄 남긴다 — "⚠ 계정 장부의 `GH_TOKEN`이 표와 다른 계정(<계정>) 것입니다. 표의 계정 토큰으로 바꿔 주세요('깃헙 연결해줘')." 팀원이 자기 계정으로 일하는 정상 경우이거나 이 저장소의 커밋 작성자가 표와 다르면, 막지 않고 진행하되 §4 완료 보고에 한 줄 남긴다 — "⚠ 표의 소유자와 다른 계정(<계정>)으로 작업 중입니다. 팀원이면 정상이고, 소유자 본인이면 계정을 확인해 주세요." 하드로 막으면 팀원의 모든 ship이 오탐으로 멈추고, 잘못된 계정의 push는 어차피 GitHub이 권한 오류로 거부한다 (§3-a가 처리).

```bash
# 1-a. 현재 브랜치 확인
git rev-parse --abbrev-ref HEAD
```

- **main 브랜치** → 중단. "지금 main 브랜치 위에 있습니다. 이 스킬은 feature 브랜치를 main으로 ship하는 도구라서, 먼저 작업한 feature 브랜치로 이동해야 합니다."
- **브랜치에 안 묶인 상태 (detached HEAD)** → 중단. "지금 어느 브랜치에도 위치하지 않고 과거 커밋한 파일들을 보고 있습니다. 이 스킬은 feature 브랜치를 main으로 ship하는 도구라서, 어느 feature 브랜치를 ship할지 알려 주세요."

```bash
# 1-b. origin/main 최신화 후, 그 대비 새 commit 있는가
# (로컬 main이 아니라 origin/main 기준 — 팀 작업이라 로컬 main은 금방 뒤처짐.
#  여기서 최신화해두면 §1.6 동기화 판단·§2 PR 정보 수집도 같은 fetch 결과를 그대로 씀)
git fetch origin main
git log origin/main..HEAD --oneline | head -1
```

- 비어 있으면 → 중단. "지금 브랜치에 main 대비 새 변경이 없습니다. 이 스킬은 새 변경을 main으로 ship하는 도구라서, 작업이 끝난 것이 맞는지 확인이 필요합니다."

```bash
# 1-c. working tree 깨끗한가
git status --porcelain
```

- 비어 있지 않으면 args에 결정 지시(예: "변경은 커밋하고 진행")가 있으면 그대로 적용하고 계속. 없으면 **[결정 필요] 반환**:
  ```
  [결정 필요] 커밋되지 않은 변경(수정·추가·삭제된 파일)이 남아 있습니다.
  이 스킬은 *커밋된 wip*만 ship하는 도구라서, 변경을 먼저 정리해야 합니다.

  선택지:
  (a) 지금 변경을 커밋하고 진행 (메시지 필요)
  (b) 임시 보관소에 넣어두고 진행 (`git stash` — 나중에 다시 꺼낼 수 있습니다)
  (c) 중단 — 직접 정리하겠습니다

  재호출 예시: `ship-task 변경은 커밋하고 진행` / `ship-task stash하고 진행`
  ```

### 1.5 코드 정리 관문 (코드 변경이 있을 때만)

ship 전에 코드 정리(`code-cleanup` 스킬 — 지난 정리 뒤 바뀐 파일만 재사용·단순화·효율·깊이로 검토해 화면 동작을 안 바꾸는 것만 반영)를 거쳤는지 확인하는 관문.
**정상 흐름에선 여기 안 걸린다** — 메인의 done-task가 위임 전에 정리 판단을 끝낸다. 이 관문은 그 판단이 빠졌을 때의 안전망이다.

```bash
# 코드 파일 변경 여부 (lib/·functions/src/ 기준 — 문서·설정만이면 관문 skip)
# origin/main 기준 (§1-b에서 이미 fetch해뒀음)
git diff origin/main...HEAD --name-only | grep -E '^(lib/|functions/src/)' | head -1

# 마지막 정리 표시 커밋 — code-cleanup이 반영을 커밋할 때만 붙이는 제목이다.
# 훅이 만드는 `wip: …` 커밋은 제목에 무엇이 들어 있어도 표시가 아니다.
# --format='%H %s' 출력이라 줄 앞에 해시가 붙는다 — 앵커를 거기에 맞춘다.
marker=$(git log origin/main..HEAD --no-merges --format='%H %s' | grep -E '^[0-9a-f]+ chore: 코드 정리 반영( |$)' | head -1 | cut -d' ' -f1)

# 표시 뒤에 이 브랜치가 lib·functions/src를 또 고쳤는지 (합치기 커밋으로 들어온 남의 변경은 뺀다)
[ -n "$marker" ] && git log --no-merges --format= --name-only "$marker"..HEAD -- lib functions/src | sort -u | head -1
```

- **코드 변경 없음** (docs·.claude·설정만) → 관문 skip, §2로.
- **표시가 있고, 그 뒤 고친 `lib/`·`functions/src/` 파일이 없음** → 정리를 마친 코드 그대로다. skip, §2로.
- **args에 "스킵" 류 지시 있음** → 관문 skip, §2로.
- **표시가 없거나, 표시 뒤에 `lib/`·`functions/src/`가 또 바뀜** → **[결정 필요] 반환** (fork 안에서 정리를 직접 하지 않는다 — 에이전트를 띄우는 건 메인 세션 몫).
  ```
  [결정 필요] 아직 정리하지 않은 Dart·TypeScript 코드 변경이 있습니다 (<표시 없음 / 표시 뒤에 바뀐 파일 N개>).

  선택지:
  ① 메인 세션(done-task)이 code-cleanup을 돌려 반영 커밋(`chore: 코드 정리 반영 — …`)을 남긴 뒤 ship-task 재호출.
     표시 뒤 바뀐 파일만 다시 보므로 두 번째 정리는 작다.
  ② 스킵하고 바로 ship

  재호출 예시: `ship-task 스킵`
  ```

> 근거: 유저가 브라우저로 검증한 코드와 main에 들어가는 코드가 달라지면 안 됨 — 화면 검증은
> 사람 몫이고 Claude가 스스로 결과를 승인하지 않는다는 원칙. 그래서 정리는 화면 동작을 바꾸지 않는 것만 반영한다.

> **왜 표시 뒤의 변경을 다시 보나**: 표시는 반영을 커밋하는 그 커밋에 붙어서, 정리 자신이 고친 코드는 늘 표시 **앞**에 있다 — 정리 결과를 또 정리하라고 요구하는 일은 생기지 않는다. 표시 **뒤**의 `lib/`·`functions/src/` 변경은 정리 뒤에 새로 한 작업이라, 그것만 한 번 더 본다.

### 1.6 조건부 동기화 — origin/main 합치기(merge)

팀 작업이라 내가 작업하는 동안 다른 사람 PR이 먼저 main에 들어갈 수 있다. origin/main이 내 브랜치보다 앞서 있으면, 안전할 때만 합치기(merge)로 맞추고, 위험하면 아예 시작하지 않는다.

**왜 리베이스가 아니라 합치기인가:** 예행 검사(`git merge-tree`)와 실제 동작이 같은 종류라 어긋남이 없고, 어차피 squash라 리베이스의 선형 기록 이점이 없고, 합치기는 커밋을 새로 쓰지 않아 강제 push가 필요 없다 — 그래서 push 여부로 갈래를 나눌 필요가 없다. 자세한 근거는 `docs/git-workflow.md` §8.3.

```
origin/main이 내 브랜치보다 앞서 있나? (git rev-list --count HEAD..origin/main)
  아니오 (0) → 맞출 게 없음, 그대로 §2로
  예 (0보다 큼) ↓
    충돌 예행 검사 (git merge-tree --write-tree origin/main HEAD — 작업 트리는 안 건드리는 모의 병합)
      충돌 없음 → git merge --no-edit origin/main 실행 후 §2로   (push 여부와 무관)
      충돌 있음 → [결정 필요]로 멈춤. 합치기를 시작하지 않는다
```

**핵심 규칙:**

1. **자동 경로에서는 리베이스를 아예 쓰지 않는다.** 리베이스는 커밋을 전부 새로 써서(모든 sha가 바뀜) push된 브랜치에선 강제 push(force push)가 필요해지는데, **force push는 금지다.** 합치기는 기존 커밋을 그대로 두고 병합 커밋 하나만 얹으니 이미 push한 브랜치에서도 평범한 push로 올라간다. 리베이스가 필요하면 그건 사용자가 직접 판단해서 할 일이다(아래 [결정 필요] ③).
2. **충돌이 있으면 합치기도 시작하지 않는다.** 이 스킬은 fork로 격리 실행돼 중간에 사용자에게 물어볼 수 없다. 충돌 난 상태로 merge를 시작하면 저장소가 "병합 진행 중"인 어중간한 상태로 반환돼버린다. 그래서 손대기 전에 예행 검사로 먼저 걸러내고, 이 경우 [결정 필요]로 멈춘다.
3. **이미 push한 브랜치라도 충돌이 있으면 멈춘다.** 합치기는 push된 브랜치에서도 되니 사용자가 실제로 고를 수 있는 행동이 있다. 그래도 그냥 올리고 싶으면 `동기화 없이 진행` 지시로 통과할 수 있다.

```bash
# origin/main이 앞서 있는지 (0보다 크면 앞섬 — 뒤 명령들 모두 origin/main이 앞서 있을 때만 실행)
# 이 개수는 §4 완료 보고에 그대로 쓰이니 값을 기억해둔다
git rev-list --count HEAD..origin/main

# 충돌 예행 검사 — exit 0 = 충돌 없음(병합 결과 tree sha만 출력), exit 1 = 충돌
# (충돌 시 tree sha 뒤에 stage 1/2/3 항목과 "충돌 (내용): ..." 메시지가 같이 출력됨.
#  충돌 파일 목록만 뽑으려면: 위 출력을 `awk -F'\t' 'NF>1 {print $2}' | sort -u`)
git merge-tree --write-tree origin/main HEAD

# 충돌 없을 때만 실행. --no-edit = 병합 커밋 메시지 기본값 그대로 (편집기가 열려서 멈추면 안 되니까)
git merge --no-edit origin/main
```

args에 "동기화 없이 진행"(옛 표현 "리베이스 없이 진행") 류 지시가 있으면 이 절 전체를 건너뛰고 §2로 간다 — 이미 판단이 끝난 재호출이다. 그 경우 §4 보고 문구는 §4의 경고 줄을 쓴다.

- **origin/main이 안 앞서 있음 (0)** → 맞출 게 없다. 그대로 §2로.
- **앞서 있음 + 충돌 없음** → `git merge --no-edit origin/main` 실행. 성공하면 §2로. push 여부는 보지 않는다.
- **앞서 있음 + 충돌 있음** → **[결정 필요] 반환**:
  ```
  [결정 필요] origin/main이 내 브랜치보다 앞서 있고, 합치면 충돌이 납니다.
  이 스킬은 충돌 상태로 합치기를 시작하지 않습니다 (중간에 멈추면 저장소가 어중간해지기 때문입니다).

  충돌 파일: <merge-tree로 뽑은 파일 목록>

  선택지:
  ① (권장) 로컬에서 합치기(merge)로 충돌 풀고 재호출 —
     `git merge origin/main` → 충돌난 파일 고치기 → `git add <파일>` → `git commit` → 다시 ship-task 호출
     (합치기를 권하는 이유: 이 저장소는 매 턴 wip 커밋이 쌓여서 브랜치 하나에 커밋이 많습니다 —
     합치기는 두 갈래를 한 번에 붙여서 충돌을 딱 한 번만 풀면 됩니다. 마지막엔 어차피 squash로
     다 뭉치기 때문에 병합 커밋 하나 끼는 것은 main 기록에 남지 않습니다. 합친 뒤 재호출하면 내 브랜치가
     origin/main을 전부 품게 돼서, §1.6 판정에서 "앞서 있나?" 검사가 0이 되어 이 단계는
     자연히 건너뜁니다. 이미 push한 브랜치여도 강제 push 없이 그대로 올라갑니다.)
  ② 그냥 PR 올리고 GitHub에서 충돌 해결 (머지 시점에 GitHub이 충돌을 알려줌)
  ③ (최후 수단) 굳이 한 줄로 깔끔한 기록(선형 기록)을 원하면 로컬에서 직접 리베이스 —
     `git rebase origin/main` → 충돌난 파일 고치기 → `git add <파일>` → `git rebase --continue` → 다시 ship-task 호출
     ⚠️ 커밋이 많으면 충돌 난 파일을 건드린 커밋마다 멈춰서 같은 충돌을 여러 번 풀어야 합니다.
        게다가 이미 push한 브랜치면 강제 push가 필요해져서 이 워크플로 규칙을 어기게 됩니다.
        squash로 어차피 뭉쳐지니 선형 기록을 위해 이것을 감수할 이유는 거의 없습니다.

  재호출 예시: `ship-task 머지로 진행` (① 선택 시) / `ship-task 동기화 없이 진행` (② 선택 시)
  ```

### 1.7 백엔드 변경 순서 안내 (백엔드 파일이 바뀌었을 때만)

**머지는 출시가 아니다** — main에 합쳐도 실서비스 Firebase에도, 사용자 폰의 앱에도 아무것도 안 나간다. 실서비스에 나가는 건 사람이 「올려줘」라고 한 뒤 메인이 부르는 `backend-release`(규칙·색인·서버 함수·Hosting)와 `store-release`(앱 번들)뿐이다. 그래서 머지 전에 멈추지 않는다 — **막는 게 아니라, 이 브랜치에 백엔드 변경이 있다는 것과 출시 순서를 완료 보고에 남기는 관문**이다.

```bash
# 이 브랜치가 origin/main 대비 바꾼 백엔드 파일
git diff --name-only origin/main...HEAD -- firestore.rules firestore.indexes.json storage.rules firebase.json functions
```

- **출력이 비어 있으면 아무 말 없이 §2로 간다.** 백엔드를 안 건드린 브랜치가 대부분이다.
- **파일이 있으면** 멈추지 않고 §2로 가되, §4 완료 보고 끝에 아래 안내를 붙일 것을 기억해 둔다. 옛 판 앱이 사용자 폰에 오래 남는다는 점이 순서의 이유다.
  - **더하는 것**(새 필드·새 함수·규칙 넓히기) → `backend-release` 먼저, 그다음 `store-release`. 새 앱이 기대하는 것이 먼저 있어야 한다.
  - **없애는 것**(필드·함수 삭제, 규칙 조이기) → 새 앱을 먼저 내보내고, Remote Config `min_version`으로 옛 판을 막거나 옛 판 사용자가 충분히 줄어든 것을 확인한 뒤 백엔드에서 없앤다.
  - 둘이 함께 바뀌어야 하면 「더하는 것」과 「나중에 없애는 것」 두 번으로 쪼갠다.

> 근거: 앱은 머지와 출시가 갈라져 있어, 백엔드와 앱의 출시 순서를 정하는 자리가 `backend-release`·`store-release`에 있다. 여기서는 그 순서를 잊지 않게 알리기만 한다.

### 1.8 기기 스모크 관문 (`integration_test/`가 있을 때만)

ship 전에 핵심 흐름이 살아 있는지 스모크 테스트(smoke test)로 확인하는 관문. §1.6 합치기 **뒤**에 두는 이유 — origin/main을 합친 최종 코드로 돌아야, main에 실릴 코드 그대로를 검사한다.

4-3의 스모크 셋은 셋이다. 이 관문이 맡는 건 **③ 기기 통합 테스트 하나**뿐이다.

| # | 무엇 | 어디서 돌아가나 | 이 관문의 몫 |
|---|---|---|---|
| ① | 보안 규칙 테스트 | CI에서만(§3-c에서 기다림) | 없음 |
| ② | 서버 함수 린트·빌드·단위 테스트 | CI | 없음 |
| ③ | 기기 통합 테스트(`integration_test/`, 개발용 flavor) | 이 맥 — 사람이 기기(시뮬레이터나 USB 폰)를 연결해 둔 때 | 여기서 실행 |

코드 정리 관문(§1.5)과 달리 **fork 안에서 직접 실행한다** — 정리가 [결정 필요]로 미루는 건 에이전트를 띄우는 일이 메인 세션 몫이라서고, 통합 테스트는 단일 명령이라 fork가 스스로 판정까지 할 수 있다.

```
integration_test/ 폴더가 있나? (Glob으로 확인)
  없음 (4단계 이전) → 관문 skip, 아무 말 없이 §2로
  있음 ↓
    코드 변경이 없나 (lib/·functions/src/·integration_test/ 모두 그대로)? → skip, §2로
    args에 "스모크 스킵" 류 지시 있음 → 관문 통과, §2로
    fvm flutter devices 로 연결된 기기 확인
      기기 없음 → [결정 필요]로 멈춤 (기기 연결 또는 스킵 선택)
      기기 있음 ↓
        fvm flutter test integration_test --flavor dev -d <기기 ID> \
          --dart-define-from-file=env/dev.json --dart-define-from-file=build/seed_login.json
          성공 → §2로. §4 완료 보고에 "기기 스모크 N건 통과 (<기기 이름>)" 한 줄
          실패 → [결정 필요]로 멈춤
```

- **`integration_test/` 없음** → 관문 skip. 스모크가 없는 프로젝트(4단계 이전)가 대부분이라 여기서 멈추면 안 된다. 아무 말 없이 §2로 간다.
- **args에 "스모크 스킵" 류 지시 있음** → 관문 통과, §2로 (해석은 §호출 패턴).
- **통과** → §2로. 출력에서 통과 건수를 읽어 §4 완료 보고에 한 줄을 남긴다. **통과의 뜻을 과장하지 않는다** — 개발용 Firebase에서 이 흐름이 돈다는 데까지다.
- **기기가 없음** → **[결정 필요] 반환**:
  ```
  [결정 필요] 기기 스모크 테스트를 돌릴 기기가 연결돼 있지 않습니다. 이 테스트는 CI에서 못 돌고 이 맥에서만 돕니다.

  선택지:
  ① (권장) 시뮬레이터를 켜거나 USB로 폰을 연결한 뒤 재호출
  ② 스킵하고 그대로 ship — 이번 변경이 핵심 흐름과 상관없다고 확인했을 때만

  재호출 예시: `ship-task 스모크 스킵` (② 선택 시)
  ```
- **실패** → **[결정 필요] 반환**:
  ```
  [결정 필요] 기기 스모크 테스트가 실패했습니다. 이대로 ship하면 깨진 상태가 main에 실립니다.

  실패 출력 요약:
  <실패한 검사 이름·오류 메시지 요약>

  선택지:
  ① (권장) 실패 원인 고치고 재호출 — 다시 ship-task를 부르면 스모크가 또 돕니다
  ② 스킵하고 그대로 ship — 실패가 코드 문제가 아니라 스모크 쪽 문제(환경·테스트 자체 결함)라고 확인했을 때만

  재호출 예시: `ship-task 스모크 스킵` (② 선택 시)
  ```

> 근거: 4-3-backend-deploy §2.2가 스모크 테스트 셋을 만들게 하지만 ship 전 실행을 강제하는 장치가 없어, 깨진 계약이 그대로 main에 실린 사고가 있었다. ①②는 CI가 머지 전에 잡고(§3-c), 기기가 필요한 ③은 이 관문이 push 전에 잡는다.

### 2. PR 정보 수집

#### 2-a. 자동 추출 (AI 단독)

```bash
# diff 요약 (origin/main 기준 — §1-b에서 이미 최신화했고, §1.6에서 합쳤다면 그 결과 위에서 계산됨)
git diff origin/main...HEAD --stat
git log origin/main..HEAD --oneline
git log origin/main..HEAD --pretty=format:'%s' | head -30
```

- 브랜치명 → type·topic 분리 (예: `feat/dark-mode-toggle` → type=`feat`, topic=`dark-mode-toggle`)
- 변경 파일 list + 추가/삭제 라인
- wip 커밋 메시지 list (사용자 의도 fragment 추출)

#### 2-b. PR title·body 초안 (AI 단독)

자동 추출 데이터로 초안 작성:

- **title**: 70자 이하. 주요 변경을 자연어로 압축. type prefix는 _PR title에는 안 붙임_ (브랜치명에 있고 squash 후 main commit 메시지에 `(#N)`으로 묶임)
  - 예: `다크모드 토글 추가 + 색 토큰 정리`
- **body 템플릿**:

```markdown
## Summary

- [bullet 1: 가장 큰 변경 + 왜]
- [bullet 2]
- [bullet 3]

## Test plan

- [ ] [수동 검증 항목 1]
- [ ] [수동 검증 항목 2]

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- Summary는 _결정·이유_ 위주. 파일 list 나열 X.
- Test plan은 _사용자가 브라우저로 직접 확인할 항목_ — Claude는 브라우저 검증 안 함 (화면 검증은 사람 몫이라는 원칙).
- 카피 룰: AGENTS.md `## 응답·문서 작성`·`ux-writing-reviewer` 에이전트 (있으면) 따름.

초안이 곧 확정본이다 (§호출 인자 아래 승인 규칙) — 바로 §2.5로.

### 2.5 역할 판별 — 머지까지 할지, PR까지만 할지

이 저장소는 팀원들이 협업자(collaborator)로 직접 브랜치를 올리는 구조라, 사람마다 main 머지 권한이 다르다. 설정 파일 없이 GitHub 권한 조회로 판별한다.

```bash
# 저장소 경로는 하드코딩하지 말고 매번 조회
# gh 호출은 §1-0대로 실행기를 앞에 붙인다: .claude/scripts/with-owner.sh gh …
REPO=$(.claude/scripts/with-owner.sh gh repo view --json nameWithOwner --jq .nameWithOwner)
.claude/scripts/with-owner.sh gh api repos/$REPO --jq '.permissions'
```

- **`admin` 또는 `maintain`이 `true`** → 오너/메인테이너 경로. §3을 지금까지처럼 끝까지(머지 포함) 실행.
- **`admin`·`maintain`은 `false`고 `push`만 `true`** → 팀원 경로. §3에서 PR 생성까지만 하고 멈춘다(머지 안 함).
  - 이 경우 오너를 리뷰어로 지정한다. 오너는 `.claude/scripts/with-owner.sh gh repo view --json owner --jq .owner.login`으로 구한다.
- **조회 자체가 실패함** (네트워크 오류 등) → **안전한 쪽 = 팀원 경로**로 판정하고, 조회가 실패해서 보수적으로 처리했다는 사실을 완료 보고에 남긴다. 머지는 되돌리기 번거로운 작업이라, 권한이 확인 안 되면 안 하는 쪽을 택한다.
- **args에 "머지까지" 류 지시** → 위 판정과 상관없이 오너/메인테이너 경로로 진행 (주로 권한 조회가 실패했지만 실제로는 머지 권한이 있는 걸 아는 경우에 씀).
- **args에 "머지하지 마" / "PR까지만" 류 지시** → 위 판정과 상관없이 팀원 경로로 진행 (오너라도 이번엔 리뷰를 먼저 받고 싶을 때 씀).
- args 지시가 실제 권한과 안 맞으면(예: 팀원인데 "머지까지" 지시) §3-d의 `gh pr merge`가 권한 오류로 실패할 뿐이니 위험하지 않다 — 그 경우는 §3-d의 실패 처리를 그대로 따른다.


- 생성 성공 시 PR 번호·URL 보고.
- 실패 시 (이미 PR 존재 등) → `.claude/scripts/with-owner.sh gh pr view --json number,url` 로 기존 PR 가져와서 사용. 새로 안 만듦.
- **팀원 경로일 때만** (§2.5) — PR 생성 뒤에 오너를 리뷰어로 지정한다:
  ```bash
  .claude/scripts/with-owner.sh gh pr edit <N> --add-reviewer <OWNER>
  ```
  이건 best-effort다 — 권한·설정 문제로 실패해도 PR 생성 자체는 그대로 유지하고, 리뷰어 지정만 실패했다는 사실을 완료 보고에 남긴다. 여기서 중단하지 않는다.

#### 3-c. CI 대기 — **오너/메인테이너 경로만** (§2.5)

팀원 경로면 이 단계도 건너뛰고 바로 §4 팀원용 완료 보고로 간다 (팀원은 애초에 머지를 안 하니 CI를 기다릴 필요가 없음).

머지 전에 CI가 끝날 때까지 기다린다.

```bash
# gh 호출은 §1-0대로 실행기를 앞에 붙인다: .claude/scripts/with-owner.sh gh …
.claude/scripts/with-owner.sh gh pr checks <N> --watch --interval 10
```

- **통과 (exit 0)** → 3-d로 진행해서 머지.
- **실패** → 머지하지 않고 중단. 실패한 검사 이름과 PR URL을 사용자에게 보고하고, "고쳐서 push하면 CI가 다시 돕니다. 그 뒤 `/done-task`를 다시 불러 주세요"라고 안내한다. PR은 지우지 않고 그대로 둔다.
- **검사가 하나도 없음** (gh가 "no checks reported" 류 메시지로 종료) → push·PR 생성 직후엔 GitHub이 검사(check run)를 등록하는 데 몇 초 걸릴 수 있어서, 곧 CI가 붙을 PR인데 등록이 늦어 이렇게 나온 것일 수도 있다. 바로 검사 없음으로 단정하지 말고 **20초 기다렸다가 `gh pr checks <N> --watch --interval 10`을 한 번 더 실행**한다.
  - 재시도에서 검사가 잡히면 위 통과/실패 분기를 그대로 따른다.
  - 재시도에서도 "no checks reported"면 그때 비로소 이 PR엔 CI가 안 붙어 있거나(워크플로 적용 전 브랜치 등) 적용이 안 된 상황으로 확정하고, 기다리지 않고 3-d로 진행해서 머지한다. 대신 완료 보고(§4)에 "이 PR엔 CI 검사가 안 붙어 있었습니다" 한 줄을 남긴다.

#### 3-d. squash merge + remote 브랜치 삭제 — **오너/메인테이너 경로만** (§2.5)

팀원 경로면 이 단계를 건너뛰고 바로 §4 팀원용 완료 보고로 간다.

```bash
# --subject 로 §2-b 확정 PR 제목을 명시 → 커밋이 1개뿐이어도 main에 wip 메시지 대신 PR 제목이 들어감
# (미지정 시 gh는 단일 커밋 PR에서 그 커밋 메시지를 squash 제목으로 써버려 main이 지저분해짐)
# --delete-branch 는 머지 뒤 원격 브랜치를 지우고, 로컬도 main으로 옮겨 앉은 뒤 그 브랜치를 치운다
# gh 호출은 §1-0대로 실행기를 앞에 붙인다: .claude/scripts/with-owner.sh gh …
.claude/scripts/with-owner.sh gh pr merge <N> --squash --delete-branch --subject "<PR title> (#<N>)"
```

**머지 여부는 종료코드가 아니라 PR 상태로 판정한다.** 명령이 0이 아닌 코드로 끝나도 서버 쪽 머지는 성공했을 수 있어서다 — 머지는 GitHub에서 이미 끝났는데 그 뒤 로컬 정리에서 걸려 넘어지면, 종료코드만 보고 "머지 실패"로 잘못 읽게 된다:

```bash
.claude/scripts/with-owner.sh gh pr view <N> --json state,mergedAt --jq '.state'
```

- `MERGED` → **성공이다.** 명령이 실패했더라도 그대로 다음 단계로 간다. 명령 쪽 오류 메시지는 §4 보고에 참고로만 한 줄 남긴다.
- `OPEN`·`CLOSED` → 진짜 실패다. 중단하고 사용자에게 stdout + PR URL 보고: "GitHub에서 직접 해결한 다음 다시 호출해 주세요." (conflict·branch protection·CI 미통과·**권한 부족** 등. 권한 부족으로 실패한 거면 애초에 팀원 경로였어야 하는 상황이니, PR은 그대로 두고 팀원용 보고에 준해 안내)

머지가 확인되면 **원격 브랜치와 로컬 브랜치가 치워졌는지 확인하고, `--delete-branch`가 못 치운 건 여기서 직접 마무리한다.** `--delete-branch`가 대개 여기까지 이미 해놨다 — 아래 확인 명령들의 출력이 비어 있으면 그냥 넘어간다 (없는 걸 지우려 하면 오류가 난다):

```bash
git ls-remote --heads origin <branch>        # 출력이 있으면 원격에 아직 살아있다
git push origin --delete <branch>            # 살아있을 때만

git rev-parse --abbrev-ref HEAD              # main이 아니면 아래를 실행
git switch main
git pull origin main --ff-only               # squash 커밋을 로컬 main에도 반영
git branch --list <branch>                   # 출력이 있으면 로컬 브랜치가 아직 남아있다
git branch -D <branch>                       # 남아있을 때만 (squash merge라 -D 필요)

git fetch --prune origin                     # 원격에서 사라진 브랜치의 로컬 캐시 참조 정리
git rev-parse main origin/main               # 두 값이 같아야 로컬 main이 원격과 일치
```

- **`git pull origin main --ff-only`를 하는 이유**: 머지는 GitHub 쪽에서 일어나서 squash 커밋이 로컬 main엔 아직 없다. 이걸 안 하면 방금 합친 작업이 로컬 main에 없는 상태로 남아 혼란스럽다. `--ff-only`라 로컬 main에 딴 게 섞여 있으면 조용히 합치지 않고 실패한다 — 그러면 억지로 진행하지 않고 실패 사유를 §4 보고에 남긴다.
- **`git branch -D`를 쓰는 이유**: squash merge는 원래 커밋들을 그대로 옮기지 않아서 git이 이 브랜치를 "머지 안 됨"으로 본다. 그래서 안전한 `-d`로는 안 지워지고 `-D`가 필요하다.
- **`git fetch --prune origin`을 하는 이유**: `gh pr merge --delete-branch`는 원격 브랜치와 로컬 브랜치는 지우지만, **로컬에 캐시된 원격 추적 참조(`origin/<branch>`)는 안 지운다.** 바로 위의 `git pull origin main`도 main 하나만 가져올 뿐 그 참조를 정리하지 않는다. 그대로 두면 로컬이 "원격에 없는 브랜치가 아직 있다"고 믿는 상태로 남아서, `git branch -a`나 자동완성에 유령 브랜치가 계속 뜬다.
- **`git rev-parse main origin/main`을 하는 이유**: 출력된 두 sha가 같으면 로컬 main이 원격과 정확히 일치한다는 뜻이다. 다르면 앞의 `--ff-only` pull이 조용히 실패한 것이니 §4 보고에 남긴다.
- **`new-task`의 `git remote prune origin`과 역할이 겹치지 않는다**: **ship-task는 자기가 방금 만든 잔재를 치우고, new-task는 그 외 전부를 훑는다.** 팀원 경로에선 자기가 머지하지 않아 ship-task가 여기까지 오지 않고, 다른 사람이 지운 브랜치의 잔재도 여기선 안 걷힌다 — 그건 new-task가 시작할 때 훑어서 정리한다. 그래서 `new-task` 쪽은 그대로 둔다.
- **어느 단계가 실패해도 머지 자체는 이미 끝난 것**이라 여기서 중단하지 않는다. 실패한 단계만 사유와 함께 §4 보고에 남기고 마무리한다.

## 사용자 응대 톤

톤은 `AGENTS.md 응답·문서 작성`을 따름. 이 스킬 고유: 결정이 필요하면 진행을 멈추고 [결정 필요] 보고로 반환한다 (fork 실행이라 실행 중 질문 불가). 안전 검사 결과는 반환 보고에 모아서.

## 엣지 케이스

| 상황                                                    | 처리                                                                     |
| ------------------------------------------------------- | ------------------------------------------------------------------------ |
| 원격(origin)이 없음                                     | 멈추고 `github-connect`부터 안내 — 이 스킬은 저장소를 만들지 않는다 (§1-0 하드 ②) |
| `gh pr merge`가 0이 아닌 코드로 끝남                    | 종료코드로 판정하지 않는다. `gh pr view --json state`가 `MERGED`면 성공으로 보고 그대로 진행 (§3-d) |
| 머지는 됐는데 원격·로컬 브랜치가 안 지워짐              | §3-d에서 직접 확인 후 원격 삭제 → main 이동 → 로컬 삭제까지 마무리. 그래도 실패하면 사유를 §4 보고에 남김 |
| 로컬 main이 origin/main과 갈라져 `--ff-only` pull 실패  | 억지로 진행하지 않고 실패 사유를 §4 보고에 남긴다 (§3-d)                  |
| `git branch -D` 실패                                    | §4 보고에 실패 사유를 남긴다 (§3-d)                                      |
| 이미 그 브랜치에 PR이 있음                              | 새로 안 만들고 기존 PR 사용. 새 commit 있으면 push만 추가 후 (오너 경로면) merge |
| push 후 PR 생성 실패                                    | push는 유지. GitHub UI에서 직접 만들라고 안내                            |
| squash merge 시 conflict                                | GitHub UI에서 conflict 해결 후 머지하라고 안내                           |
| branch protection 룰 (CI 통과 필요 등)                  | 정상 동작 — merge 실패 시 사유 그대로 보고 (규칙을 걸 수 있는지는 `## 안 하는 것` 참조) |
| CI 실패 (§3-c, 오너/메인테이너 경로)                    | 머지하지 않고 중단, PR은 그대로 둔다 (§3-c)                              |
| CI 검사가 하나도 없음 (§3-c)                            | 20초 기다렸다 재확인 → 그래도 없으면 머지 진행 + 완료 보고에 한 줄 (§3-c) |
| 사용자 working tree 변경이 _이번 작업 일부_             | (a) 옵션으로 추가 commit하고 진행 권장 ([결정 필요] 반환에 명시)         |
| 사용자 working tree 변경이 _별개_                       | (b) stash 권장 ([결정 필요] 반환에 명시)                                 |
| 정리 표시 뒤 이 브랜치가 고친 `lib/`·`functions/src/` 없음                | 관문 skip (§1.5)                                                       |
| 정리 표시 뒤에 `lib/`·`functions/src/`가 또 바뀜                 | [결정 필요] — 표시 뒤 바뀐 파일만 다시 정리 (§1.5)                       |
| 정리했는데 고칠 게 없었음                                | code-cleanup이 검토를 마친 뒤 `chore: 코드 정리 반영 — 고칠 것 없음` 빈 커밋을 남김 → 표시로 인정 (§1.5) |
| `wip: …` 커밋 제목에 정리·simplify 같은 말이 섞임         | 표시 아님 — 표시는 `chore: 코드 정리 반영`으로 시작하는 제목뿐 (§1.5)    |
| 계정 장부도 옛 `.env.cli`도 없어 실행기가 멈춤           | 중단, `github-connect` 안내 (§1-0)                                      |
| 백엔드 파일(`firestore.rules`·`functions/` 등) 변경 없음 (대부분의 브랜치) | 아무 말 없이 통과 (§1.7)                                               |
| 백엔드 파일 변경 있음                                   | 멈추지 않고 진행, 완료 보고 끝에 출시 순서 안내 (§1.7, §4)               |
| `integration_test/` 없음                                | 관문 skip (§1.8)                                                       |
| 연결된 기기 없음                                        | [결정 필요]로 멈춤 (§1.8)                                                |
| 기기 스모크 실패                                        | [결정 필요]로 멈춤 (§1.8)                                                |
| 스모크를 "스모크 스킵" 지시로 통과                      | 그대로 ship, 완료 보고에 ⚠️ (§1.8, §4)                                   |
| 권한 조회(`gh api repos/.../permissions`) 실패          | 팀원 경로, 완료 보고에 남김 (§2.5)                                       |
| 팀원 계정 (`push`만 `true`)                             | PR 생성까지, 오너를 리뷰어로, 머지 안 함 (§2.5)                          |
| 리뷰어 자동 지정 실패 (팀원 경로)                       | PR 유지, 완료 보고에 남김 (§3-b)                                         |
| origin/main이 안 앞서 있음 (0)                          | 그대로 진행 (§1.6, §4)                                                   |
| origin/main이 앞서 있음 + 충돌 없음                     | `git merge --no-edit origin/main` 후 진행 (§1.6, §4)                     |
| origin/main이 앞서 있음 + 충돌 있음                     | [결정 필요]로 멈춤, 합치기 시작 안 함 (§1.6)                             |
| 이미 push한 브랜치                                      | 특별 취급 없음 (§1.6)                                                    |
| `git fetch --prune origin` 실패 (§3-d)                  | 중단 않고 §4 보고에 남김 (§3-d)                                          |
| `git rev-parse main origin/main`의 두 sha가 다름 (§3-d) | §4 보고에 남김 (§3-d)                                                    |

## 호출 패턴

아래 인자는 메인의 done-task가 사용자 의도와 [결정 필요] 결정을 담아 넘긴다.

- `ship-task` — args 없음. PR title·body는 자동 추출(branch명·diff·wip 메시지)만으로 초안 짜서 바로 ship.
- `ship-task <자연어 의도>` — 자연어를 *사용자의 핵심 강조 hint*로 받음. Claude가 자동 추출 + hint 종합해 초안 짬. hint가 _title 그 자체가 되는 건 아님_ — 다른 변경도 함께 묶어서 종합 title 만듦. 예: `ship-task 다크모드 토글 추가` → "다크모드 토글 + 색 토큰 정리" 식으로 종합.
- `ship-task 스킵` — §1.5 코드 정리 관문 [결정 필요]에 대한 결정. 정리하지 않은 코드 변경이 있어도 바로 ship.
- `ship-task 변경은 커밋하고 진행` — §1-c working tree [결정 필요]에 대한 결정을 담아 재호출.
- `ship-task 머지로 진행` — §1.6 충돌 [결정 필요]에 대한 결정(선택지 ①). 사용자가 로컬에서 `git merge origin/main`으로 충돌을 이미 풀었을 때 씀. 이 경우 내 브랜치가 origin/main을 이미 품고 있어서 §1.6 판정이 "앞서 있지 않음"으로 나와 자연히 통과한다.
- `ship-task 동기화 없이 진행` — §1.6 충돌 [결정 필요]에 대한 결정(선택지 ②). origin/main과 맞추지 않고 그냥 PR만 올림. **옛 표현 `리베이스 없이 진행`도 같은 뜻으로 받는다** (판정이 리베이스에서 합치기로 바뀌기 전 이름).
- `ship-task 스모크 스킵` — §1.8 기기 스모크 관문 [결정 필요]에 대한 결정. 스모크가 실패해도(또는 기기가 없어 못 돌려도) 그대로 ship한다. 이 경우 §4 완료 보고에 스킵 사실을 ⚠️로 남긴다.
- `ship-task 머지까지` — §2.5 권한 판정과 상관없이 오너/메인테이너 경로로 진행 (권한 조회가 실패했지만 실제로 머지 권한이 있는 걸 알 때 씀).
- `ship-task 머지하지 마` / `ship-task PR까지만` — §2.5 권한 판정과 상관없이 팀원 경로로 진행 (오너라도 이번엔 리뷰부터 받고 싶을 때 씀).

## 안 하는 것 (의도적)

- ❌ 다른(옛) 브랜치 정리·새 브랜치 생성 — 그건 `new-task` 스킬 몫. 이번에 머지한 브랜치의 뒷정리(원격·로컬 삭제 + main 최신화)는 §3-d에서 직접 끝낸다
- ❌ done-task를 거치지 않은 호출 — 이 스킬은 사용자 ship 신호를 받은 메인의 done-task만 부른다. 처음 방아쇠는 사람 몫이다. 머지는 main에 합치는 일이지 실서비스 출시가 아니다(출시는 `backend-release`·`store-release`). 그래도 "사람이 화면을 봤다"는 증거가 사용자의 그 한마디뿐이라 사람이 먼저 방아쇠를 당긴다
- ❌ stage·commit 자동화 — *현재 commit된 wip*만 ship. 추가 변경은 사용자가 commit 또는 §1-c (a) 옵션 선택.
- ❌ 코드 정리 직접 실행 — fork 안에서는 Skill 도구·에이전트를 쓰지 않는다. §1.5에서 [결정 필요] 반환만 하고, 실제 정리와 표시 커밋은 메인 세션(done-task → code-cleanup) 몫이다
- ❌ PR title·body 별도 확인 — §호출 인자 아래 승인 규칙
- ❌ 실서비스에 직접 내보내기 — `firebase deploy`·`fastlane`은 이 스킬이 실행하지 않는다 (권한 밖이고, 출시는 사람이 「올려줘」라고 한 뒤 메인이 `backend-release`·`store-release`로 한다). §1.7은 순서를 알리기만 한다
- ❌ 스모크 없는 프로젝트에서 스모크 만들라고 요구 — `integration_test/`가 없으면(4단계 이전 프로젝트) 아무 말 없이 통과한다. 스모크 셋을 만드는 건 4-3-backend-deploy 단계 몫 (§1.8)
- ❌ 스모크 실패를 조용히 넘기기 — 기기 스모크가 실패하면 반드시 [결정 필요]로 멈추고, 스킵은 명시 지시(`스모크 스킵`)로만 통과한다 (§1.8)
- ❌ 다른 base 브랜치 — main 전제
- ❌ merge commit·rebase merge — PR을 main에 넣는 방식은 **squash 전용** (wip archaeology 보존 + main 깨끗을 위해). §1.6에서 origin/main을 합칠 때 생기는 병합 커밋은 별개다 — 그건 내 브랜치 안에만 있고 squash될 때 다 뭉쳐져서 main엔 안 남는다
- ❌ local squash (`git reset --soft` 후 1 commit) — wip archaeology 손실. _GitHub squash가 best of both worlds_
- ❌ force push — 안전한 push만
- ❌ 자동 경로에서 리베이스 — 합치기로만 한다 (§1.6)
- ❌ 충돌 있는 상태로 합치기 시작 — `git merge-tree`로 먼저 예행 검사하고, 충돌 있으면 [결정 필요]로 멈춤 (§1.6)
- ❌ 머지 권한 없는데 머지 강행 — `push`만 있고 `admin`·`maintain`이 없으면 PR 생성까지만 (§2.5)
- ❌ 브랜치 보호 규칙으로 강제 — 저장소가 비공개+무료 플랜이면 GitHub 브랜치 보호 규칙 자체를 걸 수 없음(API 403). "머지는 오너만"은 이 스킬이 지키는 관례일 뿐, GitHub이 막아주는 강제 규칙이 아니다
