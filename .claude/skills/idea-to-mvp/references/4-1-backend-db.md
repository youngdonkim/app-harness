3단계가 만든 앱은 화면도 돌고 버튼도 눌리지만, 데이터가 **기기 안 작은 저장소(shared_preferences — 앱이 폰 안에 값을 적어 두는 공간)**에만 쌓입니다. 다른 폰에서 열면 아무것도 없고, 여러 사람이 같은 데이터를 나눠 쓸 수도 없습니다. 4단계는 그 앱에 **진짜 백엔드(Firebase — 구글이 운영하는, 로그인·DB·파일 저장·서버 함수를 한데 묶은 서비스)를 붙여 실서비스로 완성**하고, 퍼널 계측을 심어 내보내는 자리입니다. 산출물은 실서비스가 된 앱 코드 + `backend-build.md` 하나입니다.

이 문서는 4단계에서 **실제 코드 작업이 시작되는 첫 하위 단계**입니다. 계정·외부 서비스 준비(4-0)가 끝난 뒤, 단계 전체의 목표와 범위를 먼저 잡고, 기기 안 저장소를 걷어낼 자리를 채울 **Firestore(Firebase의 DB — 문서와 컬렉션으로 데이터를 담음)의 데이터 모양과 보안 규칙**을 만듭니다. 이걸 정하지 않고 콘솔(Firebase 웹 관리 화면)에서 손으로 컬렉션부터 만들거나 규칙을 고치면, 무엇이 왜 열려 있는지 아무도 모르는 상태가 됩니다.

> ⚠ **여기 적힌 Firebase의 명령·옵션·콘솔 위치·한도는 이 글을 쓴 시점 기준입니다.** 그대로 따라 하기 전에 공식 문서로 지금도 맞는지 확인합니다. 달라졌으면 공식 문서를 따르고, 이 문서를 고쳐야 한다고 사용자에게 보고합니다. 반대로 **우리가 정한 규칙**(기본 전부 거부, 보호 필드 한 묶음 갱신, 실서비스 데이터는 사람만 지움 등)과 **이전 앱에서 확인한 교훈**은 우리 몫이라 공식 문서에 없습니다 — 그건 그대로 지킵니다.

## 1. 단계 목표

- **실서비스로 나간 앱** — 3단계 앱(기기 안 저장소로 도는 Flutter 앱)에서 기기 안 저장소를 걷어내고 Firebase(Firestore·Storage·로그인·서버 함수)를 붙여, 실데이터가 흐르는 서비스로 완성해 플레이 시험 트랙으로 내보냅니다.
- **(선택) 베타 공유** — 3단계에서 앱을 같이 본 지인·팀 동료가 있으면 실데이터가 붙은 시험 트랙 링크를 보내 크게 깨지는 데가 없는지 확인합니다(판정이 아니라 확인). **마땅한 사람이 없으면 건너뜁니다.**
- **퍼널 계측 심기** — 유입·가입·핵심 행동·재방문·결제 이벤트가 실제로 찍힙니다. 6단계(MvpLaunch) 판정의 데이터 원천입니다.
- **(지불이 이 서비스의 핵심 교환이면) 실결제** — 판단 기준은 코드입니다. **3단계 화면에 결제 흐름이 있으면** 실제로 돈이 오가게 붙입니다. 화면에 없으면 만들지 않습니다.
- **`backend-build.md`** — 스택 추가분·보호 필드 표(§7.1)·베타 공유 관찰(해당 시)·배포 정보·추후 결정·빌드 중 발견 기록. **코드를 서술하는 내용은 적지 않습니다.**
- **실서비스 개통은 이 4단계에서 끝납니다** — 실 DB·개인정보 수집·결제·실서비스 배포가 전부 여기 안에 들어갑니다. 6단계는 광고를 돌려 숫자로 판정하고 회고하는 단계지, 인프라를 새로 세우는 단계가 아닙니다.

**정본(SoT — 가장 믿을 기준) 책임** (SKILL.md §2.1): **이 단계의 스펙은 3단계 앱 코드 하나입니다.** 화면에 구현된 것을 백엔드로 실물화하고, 화면에 없는 건 만들지 않습니다. 데이터 모양의 정본은 앱의 데이터 클래스·보안 규칙·규칙 테스트(§5.3), 계측 이벤트의 정본은 `lib/core/analytics/events.dart`입니다.

**그래서 `backend-build.md`에는 코드에 실을 수 없는 것만 남깁니다.** 컬렉션 구조 설명, 계측 이벤트 정의, 「어느 파일에 뭐가 있다」 식의 안내는 **어떤 형태로도 적지 않습니다.** 낡은 문서가 코드와 충돌해 그걸 읽은 다음 작업이 엉뚱한 결과를 내기 때문입니다. 예외는 하나, **보호 필드 표**입니다(§7.1) — 「누가 이 필드를 써도 되나」라는 결정이라 코드만 봐서는 의도를 알 수 없고, 규칙과 규칙 테스트를 맞춰 보는 기준이 됩니다. 스택 조합(Flutter·Firebase와 판)은 2단계 개발환경 준비에서 정해졌으니 여기선 참조만 합니다.

**여기서 안 하는 것 (의도적)**:

- ❌ 스택 선택·개발환경 구성·화면 신규 구현 — 2단계 개발환경 준비(`2-0-dev-setup.md`)와 2·3단계(`2-1-mockup.md`·`3-frontend-build.md`) 몫입니다. 여기선 **이미 있는 코드에 백엔드를 얹습니다**.
- ❌ 화면 구조 갈아엎기 — 코드를 고치는 건 정상이지만, 화면이 늘거나 빠지는 구조 변경은 3단계로 돌아가 고친 뒤 다시 오는 일입니다(§2.3).
- ❌ PRD·설계·**DB 설계** 문서 작성 — 앱 코드와 보안 규칙이 스펙입니다(§5.3).
- ❌ 명세 밖 기능·화면 추가 — `추후 결정:` 표시만 합니다.
- ❌ 다크 모드·다국어 문구 추가·태블릿 화면·성능 튜닝·부하 대비 — production 영역입니다. 단, 광고로 들어오는 사람이 처음 지나는 경로(스토어 → 설치 → 첫 실행 → 가입 → 핵심 행동)는 실제 폰에서 끝까지 도는지 사람이 확인해야 합니다. 이 경로가 깨져 있으면 6단계 숫자가 제품 반응이 아니라 깨진 화면을 재게 됩니다.
- ❌ CI·테스트 정교화 — 보안 규칙 테스트와 서버 함수 단위 테스트(§10)만 갖추고, 그 밖의 테스트 인프라는 production에서 합니다.
- ❌ 광고·채널 준비 — 6단계 영역입니다(단 결제 심사처럼 오래 걸리는 것만 함께 시작해도 됩니다).

## 2. 단계 시작

### 2.1 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내합니다

이 단계에 들어오면 가장 먼저 사용자와 「지금까지 어디까지 왔고, 이제 무엇을 할지」를 맞춥니다.

1. **이전 단계까지 정리된 내용을 먼저 보여줍니다.** 입력은 **저장소의 앱 코드**(3단계 산출물)입니다. 지금 데이터가 기기 안 저장소의 어느 키에 어떤 모양으로 쌓이는지, 저장·조회 코드(repository — 화면 대신 데이터를 읽고 쓰는 코드)에 각 데이터의 **소유자 주석**(`2-1-mockup.md`의 저장·조회 코드 규칙)이 뭐라고 적혀 있는지부터 읽고, 짧게 요약해 보여줍니다.
2. **그 내용을 바탕으로 이번 단계가 무엇을 하는지 설명합니다.** 지금 앱은 데이터가 폰 안에만 쌓여서 다른 폰으로 열면 비어 있다고 짚고 — 이제 기기 안 저장소를 걷어내고 Firestore·로그인을 붙여서 → 실데이터가 도는 상태로 베타 공유해 치명 결함 확인 → 퍼널 계측을 심고 → 실서비스로 내보내는 단계라고 안내합니다.
3. **이미 `backend-build.md`가 있으면**(스킬 중간 재실행 등) 4단계 재진입입니다. 앱 코드는 2단계부터 있으니 이 단계를 했다는 표시가 못 됩니다 — 4단계 진행 여부는 `backend-build.md`로 판단합니다. 어디서부터 이어갈지는 SKILL.md §1.3이 안내합니다.

**진입 조건**: 저장소에 2·3단계가 만든 앱 코드(`pubspec.yaml`·`lib/`)가 있고, **사용자가 3단계를 완료로 선언했고**, 4-0(백엔드 준비)의 계정 답을 받고 그 완료 기준을 사용자와 확인한 뒤여야 합니다 — 어느 계정에 묶일지 정해지기 전에 클라우드 리소스를 만들면 전부 다시 만들게 됩니다. 아직 화면을 고치는 중이면 강행하지 말고 3단계에서 마무리하자고 안내합니다.

### 2.2 4단계 전체가 도는 순서

이 단계의 작업은 SKILL.md §1.5 **초안 모드**입니다 — AI가 끝까지 완주한 뒤 완성본으로 리뷰받습니다. 중간에 컬렉션 하나하나 승인받지 않습니다.

**Firebase 두 프로젝트는 4-0에서 만들어진 상태입니다** — 프로젝트 생성·리전·요금제·앱 등록·설정 파일·backend 틀 넣기(`apply.sh backend`)까지 4-0에서 끝나 있고, **컬렉션·규칙·서버 함수는 여기서 처음 채웁니다.**

전체가 도는 순서는 이렇습니다. **1~4번이 이 문서의 몫**이고, 5번부터는 다음 하위 단계 문서가 이어받습니다.

1. **지금 저장 모양 파악** — 앱 코드가 기기 안 저장소에 무엇을 어떤 모양으로 저장하는지 읽습니다. 여기가 데이터 모양의 실측 근거입니다.
2. **데이터 모양 정하기** — 1에서 읽은 저장 모양을 컬렉션·문서로 옮깁니다. 2·3단계가 화면을 만들며 저장 구조를 데이터 모델 그대로 만들어 뒀기 때문에 **코드가 곧 데이터 모델입니다** — 다른 문서를 뒤지지 않습니다(§5).
   - **규칙·코드를 쓰기 전에, 어떤 컬렉션을 만들고 각 문서의 소유자를 무엇으로 잡을지, 어느 필드를 보호 필드로 둘지 대화로 요약해 보여주고 승인받습니다.** 되돌리기 비싼 갈림길이라 초안 모드의 예외입니다(SKILL.md §1.5 에스컬레이션 (c)). 이 요약은 파일로 남기지 않습니다 — 승인 뒤 바로 규칙과 데이터 클래스를 쓰고, 보호 필드만 표로 남깁니다(§7.1).
3. **보안 규칙·보호 필드·규칙 테스트** — 셋을 한 묶음으로 씁니다(§6·§7·§10.1).
4. **서버 함수·색인·개발용 시드** — 비밀값이 필요한 일과 보호 필드 쓰기를 서버 함수로 옮기고(§8), 색인을 파일로 남기고(§9), 개발용 프로젝트에 견본 데이터를 넣습니다(§11).
5. **로그인 붙이기** — Firebase Authentication으로 가입·로그인. 기기 안 저장소 시절엔 「사용자」가 없었으니, 소유자 기준을 이때 실제 사용자 ID와 잇습니다. **다음 하위 단계(4-2)에서 합니다.**
6. **읽기·쓰기 경로 교체** — 저장·조회 코드의 기기 안 저장소 호출을 Firestore·Storage·서버 함수 호출로 바꿉니다. **마지막 하위 단계(4-3)에서 합니다.**
7. **기기 안 저장소 코드 제거** — 남겨두고 대체 경로로 쓰지 않습니다. 이것도 4-3 몫입니다(화면 설정처럼 원래 기기에 둘 값은 예외).

그 뒤로 스모크 테스트·베타 공유·퍼널 계측·실서비스 배포가 이어지고, 4단계 완료 체크리스트도 4-3에 있습니다.

### 2.3 범위 가드 (강제)

- 3단계 앱 코드에 없는 화면·기능을 추가하지 않습니다. 이 단계에서 새로 생기는 화면은 **동의 온보딩**과, 앱이 원래 갖춰야 하는 시스템 화면(강제 업데이트 등 — 2단계 화면 목록의 「시스템」 갈래에 이미 있음)뿐입니다. 「이것도 있으면 좋겠는데」는 `추후 결정:`으로 `backend-build.md`에 표시만 합니다.
- 3단계에서 화면만 있고 동작은 비워둔 영역이 있다면 — 이번에 *실제로 작동*시켜야 하는지는 **핵심 흐름(첫 실행 → 가입 → 핵심 행동)이 돌아가는 데 필요한가**로 판단합니다. 그 흐름에 안 걸리면 그대로 둡니다.

**이 단계에서 새로 더하는 스택만 ADR(결정 기록)로 남깁니다** (`mvp/adr.md` — SKILL.md §3.1 「스택 주요 컴포넌트 추가·제거」 계기). 대상은 플레이 결제·외부 AI 제공사처럼 이 단계에 와서 붙이는 것들입니다. 결제는 심사에 시간이 걸려 백엔드 연동과 함께 시작합니다.

**에스컬레이션**: 명세와 모순 발견·데이터 모양이 크게 갈리는 선택·외부 서비스 추가가 필요하면 멈추고 배치 질문(한 번에 묶어 묻기)을 합니다. 그 외 애매함은 합리적 가정 + `추후 결정:` 표시 후 계속합니다.

### 2.4 프로젝트는 둘입니다 — 개발용과 실서비스용

손대기 전에 이것부터 머리에 둡니다. **Firebase 에뮬레이터(내 컴퓨터에서 Firebase를 흉내 내는 도구)는 개발에 쓰지 않습니다.** 개발 기기(iOS 시뮬레이터·USB로 연결한 안드로이드폰)의 개발용 앱은 클라우드의 **개발용 프로젝트**에 붙고, 플레이에서 받은 앱은 **실서비스 프로젝트**에 붙습니다. 이름과 별칭은 `.firebaserc`에 있습니다(예: `example-dev` = `dev`, `example-prod` = `prod`).

| | 개발용(`dev`) | 실서비스용(`prod`) |
|---|---|---|
| 누가 붙나 | 개발 기기의 개발용 앱, 기기 통합 테스트 | 플레이에서 받은 앱, Hosting 웹 페이지 |
| 데이터 | 시드·테스트 계정 — 언제든 지움 | 실사용자 — AI는 지우지 않음 |
| 규칙·색인·서버 함수 배포 | 작업 브랜치에서 AI가 자유롭게 | main에서, `backend-release` 절차로 메인이 직접 |
| 리전 | 두 프로젝트가 같음 — Firestore 위치는 한 번 정하면 못 바꿉니다 | 같음 |

**프로젝트가 하나뿐이면 어떻게 될까요?** 개발하며 넣은 연습 데이터·테스트 계정이 실사용자 데이터와 분석 숫자에 섞이고, 규칙을 시험 삼아 바꾸는 순간 실사용자에게 바로 적용됩니다. 이전 앱에서 확인한 교훈이 바로 이것입니다. 그래서 둘로 나눴고, 이 문서의 모든 작업은 **개발용에서 먼저** 합니다.

**개발용도 인터넷에 열려 있습니다.** 개발용 앱 파일과 설정값도 밖으로 나갈 수 있어서, 개발용 규칙을 느슨하게 두면 그대로 뚫립니다. 개발용과 실서비스용은 **같은 규칙 파일**을 씁니다 — 개발용에서만 규칙을 열어 두는 일은 하지 않습니다.

## 3. 도구 확인

2단계와 4-0에서 깔고 인증까지 끝난 상태입니다. 여기서는 확인만 합니다. 명령은 모두 저장소 최상위 폴더에서 부릅니다.

### 3.1 Firebase CLI와 실행기

- **확인** — Firebase CLI는 4-0에서 저장소 최상위 `package.json`의 개발 의존성으로 깔렸습니다. 전역에 깔지 않고 `npx firebase`로 부릅니다.
- **부르는 꼴은 하나입니다** — 실행기(`.claude/scripts/with-owner.sh` — 이 컴퓨터의 계정 장부에서 이 프로젝트 소유의 계정을 골라 붙여 주는 스크립트)를 맨 앞에, 프로젝트 별칭을 맨 뒤에 적습니다.

  ```bash
  .claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase <명령> --project dev
  ```

  감시 훅이 이 꼴이 아닌 명령을 막습니다. `--project`가 없거나 별칭 대신 프로젝트 ID를 직접 쓰거나, `firebase use`(기본 프로젝트 지정)를 쓰면 막힙니다. `--project prod`로 무언가를 바꾸는 명령은 main에서만 통과하고, 실서비스 데이터를 지우는 명령(`firestore:delete` 등)은 언제나 막힙니다(§12).
- **계정 확인** — `.claude/scripts/with-owner.sh --check`가 계정 표의 Firebase 계정을 답하는지 봅니다. 다르면 만들지 않고 멈춰 보고합니다(`AGENTS.md` 「소유와 계정」).

### 3.2 gh CLI

PR을 만들고 머지하는 데 씁니다. 인증은 계정 장부의 `GH_TOKEN`이고, `.claude/scripts/with-owner.sh gh api user --jq .login`이 표의 계정을 답하면 준비된 것입니다. 없으면 `done-task`가 위임하는 ship-task가 아예 돌지 않습니다.

### 3.3 에뮬레이터는 이 컴퓨터에서 띄우지 않습니다

예외는 하나, **보안 규칙 테스트**입니다. Firebase 공식 규칙 테스트 도구(`@firebase/rules-unit-testing`)는 에뮬레이터 위에서만 돌기 때문에, GitHub Actions(CI — 올릴 때마다 자동으로 도는 검사) 안에서만 에뮬레이터를 잠깐 띄웁니다. 프로젝트 ID는 `demo-`로 시작하는 가짜라 실제 Firebase에 닿지 않습니다. 이 컴퓨터에서 `emulators:*` 명령을 부르면 감시 훅이 막습니다. 그래서 규칙 테스트 결과는 PR에서 확인합니다(§10.1).

## 4. 손대기 전에 정본부터 받아옵니다

**규칙과 서버 함수를 기억으로 짜지 않습니다.** 공식 예제를 받아 읽지 않고 처음부터 우리 식으로 짜면, 공식 권고와 어긋나도 「어긋난 줄도 모르는」 상태가 됩니다. 그리고 「최신인지 확인해라」라는 지시는 통하지 않습니다 — AI는 확인하지 않고 기억으로 짭니다. 그래서 지시가 아니라 **절차**로 적습니다. 아래를 실제로 실행합니다. **[공식 + 우리 결정]**

**① 공식 문서와 예제를 받아 읽습니다**

| 무엇을 쓰기 전에 | 받아 읽을 것 |
|---|---|
| Firestore 보안 규칙 | Firebase 문서의 Firestore 보안 규칙 시작하기·조건 쓰기·질의와 규칙(「규칙은 거름망이 아니다」) 페이지 |
| Storage 규칙 | Firebase 문서의 Storage 보안 규칙 페이지 |
| 규칙 테스트 | Firebase 문서의 보안 규칙 단위 테스트 페이지와 `firebase/quickstart-testing` 저장소의 규칙 테스트 예제 |
| 서버 함수 | Firebase 문서의 Cloud Functions(2세대) 페이지와 `firebase/functions-samples` 저장소의 Node 2세대 예제 중 쓰려는 것과 같은 종류(호출형·Firestore 트리거·예약 실행) |
| 앱 쪽 Firestore 코드 | FlutterFire 문서의 Cloud Firestore 사용법과 `cloud_firestore` 패키지 예제 |

**② 우리 틀과 맞춰 봅니다** — 4-0이 넣은 틀(`firestore.rules`·`storage.rules`·`functions/`·`rules-test/`)은 이 하네스가 이미 맞춰 둔 것입니다. 공식 예제와 틀이 다른 자리가 보이면 어느 쪽이 맞는지 공식 문서로 판정하고, 틀이 낡았으면 사용자에게 고칠 문안을 줍니다(`AGENTS.md` 「하네스 수정」).

**③ 어긋나는 자리에만 주석을 남깁니다** — 우리 사정 때문에 공식과 다르게 간 줄에만 이 모양으로 적습니다.

```
// 공식은 X, 우린 Y, 이유는 Z
```

기준선 설명 문서는 만들지 않습니다 — **코드가 정본**입니다.

> 저장소 이름·페이지 이름은 바뀔 수 있습니다. 없으면 공식 문서에서 지금 자리를 찾고, 이 문서를 고쳐야 한다고 보고합니다. 이 절의 핵심은 경로가 아니라 「기억으로 짜지 말고 실제로 받아 읽는다」는 절차 자체입니다.

## 5. 데이터 모양 만들기

### 5.1 기기 안 저장소의 구조를 읽고 컬렉션으로 옮깁니다

출발점은 3단계 코드입니다. 저장·조회 코드가 기기 안 저장소에 담던 목록 하나가 대개 컬렉션 하나가 되고, 목록의 항목 하나가 문서 하나가 됩니다.

1. **키마다 무엇이 담기는지 적어 봅니다** — 저장·조회 코드의 데이터 클래스와 소유자 주석(`// 소유자: 이 항목을 만든 사용자`·`// 소유자: 없음(모두가 읽는 공용 목록)`)을 함께 읽습니다.
2. **문서마다 소유자를 정합니다** — 소유자 주석이 그대로 규칙의 기준이 됩니다. 「만든 사용자」면 문서에 소유자 필드(예: `ownerId`)를 두거나 경로를 `users/{uid}/…` 아래로 둡니다. 「없음(공용)」이면 누가 쓰는지(관리자·서버 함수)를 정합니다.
3. **사용자가 바꾸면 안 되는 필드를 고릅니다** — 결제·구독 상태·포인트·카운터 같은 것입니다. 이것이 보호 필드입니다(§7).
4. **위 셋을 대화로 요약해 승인받습니다**(§2.2의 2번).

### 5.2 모양을 정하는 규칙

- **문서 ID** — 사용자 문서는 로그인 ID(`uid`)를 문서 ID로 씁니다. 그 밖에는 Firestore가 만들어 주는 ID를 씁니다. 사람이 읽는 값(이메일·닉네임)을 문서 ID로 쓰지 않습니다 — 바뀌면 문서를 옮겨야 합니다.
- **화면 하나가 읽는 것을 문서 하나에 모읍니다** — Firestore는 표를 이어 붙이는 조회(join)가 없습니다. 목록 화면이 항목마다 다른 문서를 또 읽으면(N+1 — 목록 1번 + 항목 N번 읽기) 읽기 비용과 시간이 항목 수만큼 늘어납니다. 목록에 보일 값(작성자 이름·썸네일 주소 등)은 항목 문서에 복사해 둡니다. 복사본이 바뀔 때 함께 고치는 일은 서버 함수가 합니다.
- **문서 크기에는 상한이 있습니다** — 한없이 자라는 목록(댓글·메시지·기록)은 배열 필드가 아니라 하위 컬렉션으로 둡니다. 정확한 한도는 Firebase 문서의 「사용량 및 한도」 페이지로 확인합니다.
- **시간은 서버 시간으로** — 만든 시각·고친 시각은 `FieldValue.serverTimestamp()`로 넣습니다. 기기 시계는 사용자가 바꿀 수 있습니다.
- **질의를 먼저 떠올립니다** — 화면마다 「무엇을, 어떤 순서로, 몇 개」 읽는지 적어 보고, 그 질의가 규칙(§6.2)과 색인(§9)으로 가능한지 같이 봅니다.
- **필드를 지우지 않고 더해 갑니다** — 옛 판 앱이 사용자 폰에 오래 남기 때문에, 이미 쓰는 필드의 이름이나 뜻을 바꾸지 않습니다(§12.1).

### 5.3 데이터 모양의 정본은 코드입니다

Firestore에는 표 정의(스키마) 파일이 없습니다. 그래서 「데이터 모양을 문서로 정리해 두고 싶다」는 유혹이 큽니다. 하지만 `docs/db-design.md` 같은 문서는 **실행할 수 없어 검증되지 않고**, 코드와 늘 같이 고쳐야 하는 두 번째 정본이 됩니다. 자리를 이렇게 나눕니다.

- **어떤 모양인가 → 코드.** 앱의 데이터 클래스(문서를 읽고 쓰는 `fromDoc`·`toMap`)가 필드를 정하고, 보안 규칙이 허용하는 필드·값을 정하고, 규칙 테스트가 그것을 고정합니다.
- **누가 써도 되나(보호 필드) → `backend-build.md`의 보호 필드 표**(§7.1).
- **왜 그렇게 정했나 → `mvp/adr.md`.** 예: 목록에 작성자 이름을 복사해 둔 이유, 사진 주소를 전체 주소로 담을지 Storage 경로만 담을지.

**보안 baseline**: 보안 규칙·서버 함수·`lib/core/firebase/`·기능 폴더의 데이터 코드를 만지면 `.claude/rules/security-baseline.md`가 자동으로 읽힙니다(정확한 목록은 그 파일의 `paths`). 광고로 모르는 사람이 실제로 들어오는 코드라 전부 지킵니다.

## 6. 보안 규칙

**앱은 서버를 거치지 않고 기기에서 Firestore·Storage에 바로 붙습니다.** 앱 파일은 누구나 내려받아 뜯어볼 수 있으니, 「앱이 이런 요청은 안 보낸다」는 막는 수단이 못 됩니다. 그래서 **보안 규칙(Security Rules — 요청마다 허락·거부를 판정하는 Firebase의 규칙 파일)이 사실상 유일한 벽**입니다.

### 6.1 기본은 전부 거부, 컬렉션마다 엽니다

4-0이 넣은 `firestore.rules`는 맨 끝에 「위에 없는 경로는 전부 거부」를 두고 시작합니다. 새 컬렉션은 `match`를 하나 열어 **필요한 동작만** 허락합니다. **[우리 결정]**

이유는 **실수의 방향**입니다.

- 기본 거부 → 실수하면 **「안 보인다」** → 바로 티가 납니다.
- 기본 허용 → 실수하면 **「다 보인다」** → 아무도 모릅니다.

규칙을 쓸 때 지키는 모양은 `security-baseline.md` 2부에 있습니다. 요점만 적으면 이렇습니다.

1. `allow write` 한 줄로 묶지 않고 `create`·`update`·`delete`를 나눠 씁니다.
2. `create`는 소유자 필드가 로그인한 사람과 같은지, 들어오는 필드가 정해진 것뿐인지(`keys().hasOnly([...])`), 값의 형식·길이가 맞는지 봅니다.
3. `update`는 소유자 필드를 바꾸지 못하게 하고, 보호 필드를 건드리지 않는지 봅니다(§7).
4. 규칙 안의 작은 함수(`isOwner` 등)는 틀에 있는 것을 씁니다.

### 6.2 규칙은 거름망이 아닙니다 — 질의가 규칙과 맞아야 합니다

공식 문서가 분명히 적어 둔 동작입니다. **[공식]** 질의 결과 중 읽을 권한이 없는 문서가 **하나라도 나올 수 있으면, 질의 전체가 거부됩니다.** 규칙이 읽을 수 있는 문서만 골라 주지 않습니다.

그래서 「내 글 목록」은 `where('ownerId', isEqualTo: uid)`처럼 **규칙과 같은 조건을 질의에 직접 적어야** 합니다. 조건 없이 컬렉션 전체를 읽고 앱에서 거르는 코드는 권한 오류로 실패합니다 — 그리고 그 방식은 어차피 비용 규칙(§8.4)에도 어긋납니다.

### 6.3 Storage 규칙

사진 같은 파일은 `storage.rules`가 따로 지킵니다. 틀의 예(사용자 사진 — 본인 폴더에만 올리고, 이미지 형식·크기를 제한)에서 시작합니다.

- **경로에 소유자를 넣습니다** — `users/{uid}/…`처럼 경로로 주인을 가르면 규칙이 짧고 분명해집니다.
- **형식과 크기를 규칙에서 막습니다** — 앱이 검사해도, 앱을 거치지 않는 요청은 규칙만 막을 수 있습니다.
- **누가 읽을 수 있나를 따로 정합니다** — 「로그인한 누구나」와 「본인만」을 파일 종류마다 정합니다. 프로필 사진처럼 남에게 보여야 하는 것과 신분증 사진처럼 본인만 볼 것은 경로를 나눕니다.

### 6.4 규칙은 파일로만 고칩니다

**콘솔의 규칙 편집기에서 고치지 않습니다.** CLI로 규칙을 배포하면 저장소의 파일이 콘솔의 규칙을 **덮어씁니다**(공식 문서에 적힌 동작입니다). 콘솔에서 고친 것은 다음 배포에서 말없이 사라지고, git에는 그런 변경이 있었다는 흔적도 남지 않습니다. **[공식 + 우리 결정]** 콘솔의 규칙 놀이터(Rules Playground)는 「이 요청이 통과하나」를 눈으로 볼 때만 씁니다.

같은 이유로 **git에서 규칙 파일을 되돌려도 이미 배포된 규칙은 그대로**입니다. 되돌린 파일을 다시 배포해야 반영됩니다.

## 7. 보호 필드

**보호 필드는 사용자가 직접 바꾸면 안 되는 필드입니다** — 결제·구독 상태·포인트·카운터(좋아요 수 등)·역할. 이전 앱에서 확인한 교훈을 그대로 규칙으로 둡니다. **[이전 앱에서 확인한 교훈]**

1. **보안 규칙으로 앱의 쓰기를 막고, 서버 함수만 씁니다.** 서버 함수는 관리자 권한(Admin SDK)으로 돌아 규칙을 거치지 않습니다. 틀의 `createsNone`·`changesNone` 함수가 「만들 때 보호 필드를 담지 않는다」「고칠 때 보호 필드를 바꾸지 않는다」를 봅니다.
2. **규칙·보호 필드 표·규칙 테스트를 한 커밋에서 함께 고칩니다.** 셋 중 하나만 바뀌면 실서비스 배포 전 확인(`backend-release`)에서 멈춥니다.
3. **보호 필드마다 「앱이 이 필드를 바꾸려 하면 거부된다」 규칙 테스트를 둡니다.** 4-0이 넣은 규칙 테스트 틀은 보호 필드 규칙을 빼면 테스트가 실패하는 것까지 확인해 둔 것입니다. 새 보호 필드도 같은 꼴로 더합니다.

### 7.1 보호 필드 표

`backend-build.md`의 「보호 필드」 절에 둡니다. 코드를 서술하지 않는다는 원칙(§1)의 유일한 예외입니다 — 「누가 써도 되나」라는 결정이라 코드만 봐서는 의도를 알 수 없고, 규칙과 규칙 테스트가 이 표와 맞는지 대조하는 기준이 되기 때문입니다.

| 컬렉션 | 필드 | 누가 쓰나 | 어느 서버 함수가 쓰나 | 규칙 테스트 |
|---|---|---|---|---|
| `users` | `plan` | 서버 함수만 | `verifyPurchase` | 「보호 필드는 앱이 못 쓴다」 |
| `posts` | `likeCount` | 서버 함수만 | `onLikeWrite` | 같음 |

(표의 값은 예시입니다. 컬렉션·필드·함수 이름은 그 프로젝트의 것으로 채웁니다.)

### 7.2 카운터는 서버 한 곳에서만

**카운터(좋아요 수·참여자 수 등)는 서버 함수 한 곳에서만 올리고 내립니다.** 앱과 서버가 둘 다 올리면 숫자가 두 번 셉니다. **[이전 앱에서 확인한 교훈]**

그 한 곳을 Firestore 트리거(문서가 바뀔 때 자동으로 도는 서버 함수)로 짤 때는 공식 문서의 두 가지를 지킵니다. **[공식]**

- **같은 일이 두 번 올 수 있습니다** — 트리거는 「적어도 한 번」 전달되어 한 번의 변경에 함수가 여러 번 돌 수 있습니다. 그래서 함수가 두 번 돌아도 결과가 같게(멱등 — 여러 번 해도 한 번 한 것과 같은 성질) 짭니다. 예: 이벤트 ID를 기록해 두고 이미 처리한 ID면 건너뛰기, 또는 개수를 더하는 대신 실제 개수를 다시 세어 덮어쓰기.
- **순서가 보장되지 않습니다** — 빠르게 이어진 변경이 뒤바뀐 순서로 올 수 있습니다. 앞 이벤트를 전제로 하는 계산을 하지 않습니다.

### 7.3 웹 폼 컬렉션은 서버 함수만 쓴다

Hosting 웹 페이지의 폼(계정 삭제 요청 등)은 Firestore에 바로 쓰지 않습니다. 계정 삭제 요청 폼은 HTTP 서버 함수(`deletionRequest`)로 받고, 그 함수가 관리자 권한으로 컬렉션에 씁니다. 그래서 컬렉션은 **클라이언트(앱·웹)의 읽기·쓰기를 전면 차단**합니다. 함수 안에서 이메일 형식·글자 길이·봇 빈칸을 검사합니다. 처리는 사람이 콘솔에서 하거나 서버 함수가 합니다. **[이전 앱에서 확인한 교훈]** 틀의 `deletionRequests`가 이 꼴입니다(`.claude/templates/hosting-site/README.md`).

## 8. 서버 함수

### 8.1 무엇을 서버 함수로 옮기나

앱에서 하면 안 되는 일만 옮깁니다. 나머지는 앱이 규칙 아래에서 직접 읽고 씁니다.

| 서버 함수로 하는 일 | 왜 |
|---|---|
| 비밀값이 필요한 일(AI 제공사 호출·결제 검증·카카오 토큰 확인) | 앱에 넣은 비밀값은 뜯어 볼 수 있습니다 |
| 보호 필드 쓰기·카운터 | §7 |
| 여러 사람의 문서를 함께 고치는 일(복사본 맞추기 등) | 규칙으로 「남의 문서 고치기」를 열지 않으려고 |
| 알림 보내기 | 받는 사람의 기기 토큰은 남이 읽으면 안 됩니다 |

**앱이 부르는 함수는 호출형(callable — 앱 SDK가 로그인 정보를 함께 실어 보내는 함수)으로 씁니다.** 함수 안에서는 앱이 보낸 사용자 ID를 믿지 않고, 함수가 받은 로그인 정보(`request.auth`)로 누구인지 판단합니다. 주소만 알면 누구나 부를 수 있는 HTTP 함수(`onRequest`)는 결제사 웹훅처럼 밖에서 오는 요청에만 쓰고, 보내는 쪽 서명을 확인합니다 — 예외는 Hosting 웹 페이지의 폼 받기(계정 삭제 요청 등) 하나로, 서명 대신 함수 안에서 입력 검증과 반복 요청 제한을 합니다(앱 뼈대 틀 `functions/src/deletion/`).

### 8.2 폴더와 리전

- **기능별 폴더** — `functions/src/<기능>/`에 함수와 그 단위 테스트를 둡니다. 판단 로직은 Firebase 없이 도는 순수 함수로 떼어 내고(틀의 `example/greeting.ts`가 본보기), 함수 본체는 그 순수 함수를 부르는 얇은 껍데기로 둡니다. 그래야 §10.2의 단위 테스트가 Firebase 없이 돕니다.
- **진입점 하나** — `functions/src/index.ts`가 기능 폴더의 함수를 내보냅니다.
- **리전 상수 하나** — 리전은 `functions/src/config/region.ts`의 `REGION` 하나로 모든 함수에 한 번에 적용합니다. 함수마다 리전을 따로 적지 않습니다. 앱의 `lib/core/firebase/firebase_providers.dart`의 `functionsRegion`과 같은 값이어야 합니다 — 다르면 앱이 함수를 찾지 못합니다. Firestore 위치와도 같은 리전에 둡니다(거리가 멀면 느려집니다).

### 8.3 비밀값

- **함수마다 묶어서 씁니다** — 비밀값은 `defineSecret('이름')`으로 정의하고, 그 값을 쓰는 함수의 옵션 `secrets: [...]`에 묶습니다. 묶은 함수만 값을 읽을 수 있습니다. 예전 방식인 `functions.config()`는 공식적으로 폐기 예정이라 쓰지 않습니다. **[공식]**
- **값은 프로젝트마다 따로 넣습니다** — 개발용과 실서비스용은 다른 키를 씁니다. 개발용은 작업 브랜치에서 AI가 넣을 수 있고, 실서비스용은 main에서 `backend-release` 절차로 넣습니다.

  ```bash
  .claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase functions:secrets:set AI_API_KEY --project dev
  ```

  값을 넣은 뒤에는 그 비밀값을 쓰는 함수를 **다시 배포해야** 새 값이 반영됩니다. **[공식]**
- **값을 화면에 내지 않습니다** — 비밀값을 출력하는 `functions:secrets:access`는 감시 훅이 막습니다. 값을 확인해야 하면 사람이 콘솔에서 봅니다.
- **지우기 전에 쓰는 함수가 없는지 봅니다** — 지워진 비밀값을 쓰는 함수는 오류 없이 조용히 실패합니다. **[공식]**
- **어떤 비밀값이 어느 프로젝트에 있고 언제 만료되는지**는 비밀값 장부(`backend-build.md` — 서식은 4-0)에 적습니다. 값은 적지 않습니다.

### 8.4 읽기·쓰기 비용을 처음부터 지킵니다

Firestore는 읽은 문서 수만큼 돈이 나갑니다. 사용자가 적을 때는 티가 안 나다가 광고로 사람이 몰리는 6단계에 한꺼번에 터집니다. **[이전 앱에서 확인한 교훈]**

- **컬렉션 전체 `.get()` 금지** — 앱이든 서버 함수든 범위 조건과 개수 제한(`limit`) 없이 컬렉션을 통째로 읽지 않습니다. 목록은 페이지 단위로 읽습니다.
- **N+1 금지** — 목록 항목마다 문서를 또 읽지 않습니다(§5.2).
- **서버에서 여러 문서를 고칠 때는 500건씩 끊어 일괄 쓰기(batch)로** — 한 번에 수천 건을 한 요청에 담지 않고, 500건 단위로 나눠 차례로 씁니다. 요청 크기 한도에 걸리지 않고, 중간에 실패해도 어디까지 됐는지 알 수 있습니다.
- **실시간 구독은 화면이 사라질 때 끊습니다** — 구독을 열어 둔 채 화면을 떠나면 보지도 않는 변경마다 읽기가 쌓입니다.

## 9. 색인

여러 필드로 거르거나 정렬하는 질의는 **복합 색인**(여러 필드를 묶은 찾아보기 표)이 있어야 돕니다. 색인이 없으면 질의가 오류를 내고, 그 오류 메시지에 색인을 만드는 콘솔 링크가 들어 있습니다. **[공식]**

**색인의 정본은 `firestore.indexes.json`입니다.** 흐름은 이렇습니다.

1. 개발용 앱에서 질의가 「색인 없음」 오류를 냅니다.
2. 오류의 링크로 **개발용 프로젝트** 콘솔에서 색인을 만듭니다.
3. 개발용 프로젝트의 색인 목록을 파일로 받아 `firestore.indexes.json`에 반영합니다.

   ```bash
   .claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase firestore:indexes --project dev
   ```

4. 파일을 커밋합니다. 실서비스에는 이 파일이 `backend-release`로 나갑니다 — 실서비스 콘솔에서 손으로 만들지 않습니다.

**에뮬레이터는 복합 색인을 강제하지 않습니다** — 색인이 없어도 질의를 그냥 실행합니다(공식 문서에 적힌 동작). 그래서 CI의 규칙 테스트가 통과해도 「색인이 다 있다」는 뜻이 아닙니다. 이 하네스는 개발 중에 클라우드의 개발용 프로젝트에 붙기 때문에, 빠진 색인은 개발용 앱을 써 보는 순간 드러납니다. **[공식 + 이전 앱에서 확인한 교훈]**

## 10. 검증

| 무엇을 | 어떻게 | 언제 |
|---|---|---|
| 남의 데이터는 못 읽고 못 쓴다, 보호 필드는 앱이 못 쓴다, 웹 폼 컬렉션은 클라이언트가 읽기·쓰기 모두 못 함, Storage 본인 폴더·형식·크기 | 보안 규칙 테스트(§10.1) | 규칙을 바꿀 때마다, PR의 CI에서 |
| 서버 함수의 판단 로직 | `functions/`의 단위 테스트(§10.2) | 함수를 바꿀 때마다 |
| 실제로 앱에서 읽고 써진다, 색인이 다 있다 | 개발용 프로젝트에 배포하고 개발용 앱으로 써 봄(§10.3) | 규칙·함수·색인을 바꾼 뒤 |

### 10.1 보안 규칙 테스트

- **자리** — `rules-test/`. 공식 도구 `@firebase/rules-unit-testing`과 Node 기본 테스트 실행기를 씁니다. 틀의 테스트가 본보기입니다.
- **규칙을 바꾸면 테스트도 같은 커밋에서 바꿉니다** — 새 컬렉션을 열면 최소한 「본인은 된다」「남은 안 된다」「로그인 안 하면 안 된다」「정해진 필드 밖은 못 넣는다」를 둡니다. 보호 필드는 §7의 3번.
- **허락만 시험하지 않습니다** — 규칙 사고는 대개 「막아야 할 것이 열려 있는」 쪽입니다. 거부되어야 하는 경우(`assertFails`)를 허락되는 경우(`assertSucceeds`)보다 많이 둡니다.
- **새 테스트가 정말 무언가를 잡는지 한 번 확인합니다** — 그 테스트가 지키는 규칙 줄을 잠깐 빼면 테스트가 실패해야 합니다. 실패하지 않으면 그 테스트는 아무것도 지키지 않는 것입니다. 이 확인은 PR에 올려 CI 결과로 봅니다(이 컴퓨터에서는 에뮬레이터를 띄우지 않으므로 — §3.3). 확인한 뒤 규칙 줄을 되돌립니다.
- **통과의 뜻을 과장하지 않습니다** — 규칙 테스트가 통과했다는 것은 「규칙이 이 경우들을 이렇게 판정한다」까지입니다. 색인이 있다는 뜻도(§9), 앱이 맞는 질의를 보낸다는 뜻도 아닙니다(§10.3).

### 10.2 서버 함수 단위 테스트

`functions/`에서 린트·빌드·단위 테스트를 돌립니다. CI에서도 돕니다.

```bash
cd functions && fnm exec --using=../.nvmrc -- npm run lint && fnm exec --using=../.nvmrc -- npm run build && fnm exec --using=../.nvmrc -- npm test; cd ..
```

단위 테스트는 §8.2에서 떼어 낸 순수 함수만 다룹니다. Firebase에 붙어야 하는 부분은 개발용 프로젝트에서 기기로 확인합니다(§10.3).

### 10.3 개발용 프로젝트에 배포해 기기로 확인합니다

작업 브랜치에서 개발용 프로젝트에 배포하는 것은 자유입니다 — 개발용은 연습장입니다. **바꾼 것만 골라서** 배포합니다.

```bash
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase deploy --only firestore:rules,firestore:indexes,storage,functions:<함수1>,functions:<함수2> --project dev
```

- 함수를 고르는 이유 — 함수를 통째로 배포하면 오래 걸리고, 건드리지 않은 함수까지 새로 뜨며 배포 한도에 걸리기 쉽습니다. 이전 앱에서도 영향받는 함수만 골라 배포했습니다. 바뀐 함수 목록은 `functions/src/<기능>/` 폴더의 git 차이로 뽑습니다.
- 배포한 뒤 사람에게 알릴 때는 「앱은 그대로 두고, 개발용 앱에서 ○○ 화면을 열어 ○○을 해 보면 됩니다」처럼 무엇을 누르면 보이는지 말합니다(`AGENTS.md`의 변경 종류별 반영 표).
- 화면을 보고 판정하는 일은 사람 몫입니다. AI는 배포와 화면 밖 검사까지입니다.

## 11. 개발용 데이터 넣기와 지우기

`AGENTS.md` 「개발용 데이터 넣기와 지우기」가 정본입니다. 여기서는 만드는 방법을 적습니다.

**시드 스크립트**(`functions/scripts/seed.ts` — 관리자 권한으로 Firestore·Storage에 견본 데이터를 넣는 스크립트)

- **개발용 프로젝트만 대상으로 합니다.** 대상은 `--project dev` 별칭으로 받고, `.firebaserc`에서 프로젝트 ID를 찾습니다. 별칭이 `prod`이거나 찾은 ID가 `.firebaserc`의 실서비스 ID와 같으면 **아무것도 하지 않고 멈춥니다.** 관리자 자격 증명이 가리키는 프로젝트가 개발용 ID와 다를 때도 멈춥니다.
- **문서 ID를 고정값으로 씁니다** — 여러 번 돌려도 같은 문서를 덮어써서 데이터가 불어나지 않습니다.
- **모든 시드 문서에 「시드」 표시 필드를 붙입니다** — 정리 스크립트가 이 표시로만 지웁니다.
- **테스트 계정도 고정 ID로 만듭니다** — 로그인 ID 앞에 정해 둔 머리말(예: `seed-`)을 붙여, 정리 스크립트가 머리말로 찾습니다.
- **Storage 파일(이미지)도 함께 올립니다** — 파일은 DB 문서를 따라오지 않습니다. 문서만 넣고 파일을 안 올리면 화면에서 사진이 통째로 안 보이는데, 오류도 나지 않아 한참 뒤에 사람이 눈으로 발견합니다.
- **예시 데이터는 진짜처럼** — 3단계 저장·조회 코드에 있던 견본 데이터를 옮겨 씁니다(`테스트1` 같은 값은 봐도 판단이 서지 않습니다).

**정리 스크립트**(`functions/scripts/cleanup.ts`)

- **「시드」 표시가 붙은 문서와 머리말이 붙은 테스트 계정만 지웁니다.** 컬렉션 통째 지우기는 쓰지 않습니다.
- **하위 컬렉션까지 지웁니다** — 문서를 지워도 그 아래 하위 컬렉션은 남습니다(공식 문서에 적힌 동작). 시드 문서는 하위 컬렉션까지 함께 지우는 관리자 SDK의 재귀 삭제로 지웁니다.
- 시드 스크립트와 같은 프로젝트 확인을 맨 앞에서 합니다. 이름에 `cleanup`이 들어 있어, 실서비스 표시와 함께 부르면 감시 훅도 막습니다.

**부르는 꼴** — 두 스크립트는 `functions/package.json`의 `seed`·`seed:cleanup`으로 묶고, 대상 별칭을 인자로 넘깁니다.

```bash
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npm --prefix functions run seed -- --project dev
```

관리자 자격 증명은 실행기가 넘깁니다 — 명령에 `--project dev`가 있을 때만, 장부 폴더의 **개발용 관리자 키 파일**(`<FIREBASE_SA_DIR>/<개발용 프로젝트 ID>.json`)을 `GOOGLE_APPLICATION_CREDENTIALS`로 넣습니다. 스크립트 안에서 키 파일 경로를 읽거나 적지 않습니다. 키 파일을 만드는 절차는 4-0 §3.4입니다. **실서비스용 키 파일은 만들지 않습니다** — 실서비스 자격 증명이 이 스크립트에 닿을 길 자체가 없습니다.

**실서비스에 견본 데이터가 꼭 필요하면**(예: 처음 보여 줄 공지) 시드 스크립트를 쓰지 않습니다. 넣을 것을 사람에게 보여 확인받은 뒤, 메인이 main에서 그 일만 하는 별도 스크립트로 넣습니다. **실서비스 데이터를 지우는 일은 AI가 하지 않습니다** — 사람 몫이고, 감시 훅도 막습니다.

## 12. 실서비스에 반영하기 — 머지와 따로입니다

**머지해도 실서비스 Firebase는 그대로입니다.** 규칙·색인·서버 함수를 실서비스에 내보내는 것은 사용자가 「올려줘」라고 할 때 메인이 main에서 `backend-release`로 직접 합니다. 맨 앞에서 「실서비스 배포 전 확인」(같은 변경이 개발용에 먼저 나갔고 사람이 확인했는지, 바뀐 것만 고르는지, 규칙 테스트가 통과했는지, 보호 필드 세 곳이 함께 바뀌었는지 등)을 돌립니다.

**백엔드와 앱은 서로를 기다리지 않습니다.** 그래서 순서가 정해져 있습니다 — `AGENTS.md` 「백엔드와 앱의 배포 순서」 표가 정본입니다. 원리는 하나입니다 — **사용자 폰에 떠 있는 앱이 없는 것을 찾지 않게 합니다.** 더하는 것은 백엔드가 먼저, 없애는 것은 새 앱이 먼저 나가고 옛 판 사용자가 충분히 줄어든 뒤입니다.

### 12.1 이미 쌓인 데이터에 걸리는 변경

Firestore는 표 정의가 없어서 필드를 더하는 데 실패가 없습니다. 대신 **옛 문서에는 새 필드가 없습니다.** 개발용의 새 시드 데이터로는 잘 돌다가, 실서비스의 옛 문서를 읽는 순간 깨지는 일이 여기서 생깁니다.

| 이런 변경 | 실서비스에서만 생기는 일 | 대응 |
|---|---|---|
| 필드 더하기 | 옛 문서에는 그 필드가 없음 | 앱의 데이터 클래스가 빈 값을 기본값으로 받게 짭니다 |
| 필드 이름·뜻 바꾸기 | 옛 판 앱은 옛 이름을 읽고 씀 | 바꾸지 않고, 새 필드를 더한 뒤 옛 필드는 남겨 둡니다(MVP 기본) |
| 규칙 조이기(필수 필드·형식 검사 추가) | 옛 판 앱의 쓰기가 거부됨 | 「없애는 것」 순서로 — 새 앱을 먼저 내고 옛 판이 줄어든 뒤 |
| 옛 문서 일괄 고치기(새 필드 채우기) | 실데이터의 모양을 잘못 가정하면 엉뚱하게 바뀜 | 개발용에서 먼저 돌리고, 실서비스는 사람에게 대상 건수와 바뀔 내용을 보여 확인받은 뒤 메인이 main에서 500건씩 끊어 돌립니다(§8.4) |

## 13. 실사용자를 받기 전에 백업을 켭니다

**실서비스 프로젝트에 정기 백업이 잡혀 있는지**, 그리고 **시점 복구(PITR — 지난 며칠 안의 원하는 시각으로 데이터를 되돌리는 기능)를 켤지**를 확인합니다. 둘 다 없으면 잘못 지운 데이터를 되돌릴 수단이 아예 없습니다.

- **정기 백업** — Firestore의 예약 백업은 Blaze 요금제가 필요하고(4-0에서 이미 바꿈), 매일·매주 일정을 걸 수 있습니다. 콘솔이나 Firebase CLI(`firestore:backups:schedules:create`)로 겁니다. 실서비스 설정을 바꾸는 명령이라 main에서 메인이 하거나 사람이 콘솔에서 합니다. 보관 기간·일정 한도는 공식 문서로 확인합니다.
- **시점 복구** — 켜는 방법과 비용을 공식 문서로 확인하고, 켤지 사용자에게 묻습니다.
- **복구는 사람 몫입니다** — 백업에서 되돌리는 일은 실서비스 데이터를 덮어쓰는 일이라 AI가 하지 않습니다.

**왜 6단계가 아니라 4단계에서 하나요?** 이 단계가 끝나는 시점엔 이미 개인정보 동의를 받은 실사용자 데이터가 쌓입니다. 광고를 돌리는 6단계까지 기다릴 일이 아닙니다.

## 14. 이 하위 단계의 완료 기준

4단계 전체의 완료 체크리스트는 4-3에 있습니다. 이 문서의 몫은 아래가 다 되면 끝납니다.

- [ ] 컬렉션·소유자·보호 필드를 사용자에게 요약해 승인받았습니다(§2.2).
- [ ] 쓸 Firebase 기능의 공식 문서·예제를 받아 읽었고, 공식과 다르게 간 줄에는 이유 주석이 있습니다(§4).
- [ ] `firestore.rules`·`storage.rules`가 기본 전부 거부에서 필요한 컬렉션·경로만 엽니다(§6).
- [ ] 보호 필드 표가 `backend-build.md`에 있고, 규칙과 규칙 테스트가 표와 맞습니다(§7).
- [ ] 비밀값이 필요한 일·보호 필드 쓰기·카운터가 서버 함수에 있고, 비밀값은 개발용 프로젝트에 들어갔습니다(§8).
- [ ] 쓰는 질의의 색인이 `firestore.indexes.json`에 있습니다(§9).
- [ ] 규칙 테스트가 PR의 CI에서 통과했고, 서버 함수 린트·빌드·단위 테스트가 통과했습니다(§10).
- [ ] 개발용 프로젝트에 규칙·색인·함수를 배포했고, 시드로 견본 데이터가 들어갔습니다(§10.3·§11).
- [ ] 실서비스 백업 일정을 언제 걸지 정했습니다 — 실사용자를 받기 전입니다(§13).
