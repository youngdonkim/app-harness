# 웹 페이지 틀 (Firebase Hosting)

앱만 있어도 구글 플레이는 웹 주소 둘을 요구합니다 — ① **개인정보처리방침 웹 주소**, ② 계정을 만드는 앱이면 **앱 밖에서 계정 삭제를 요청할 수 있는 웹 주소**. 이 틀은 그 두 페이지와 이용약관, 간단한 랜딩을 실서비스 Firebase 프로젝트의 Hosting(Firebase의 웹 페이지 호스팅)에 올리는 묶음입니다. 이전 앱에서 확인한 방식을 틀로 옮겼습니다.

주소는 기본 주소(`https://<실서비스 프로젝트 ID>.web.app`)로 시작하고, 자기 도메인은 6단계 전에 검토합니다.

## 1. 파일

프로젝트에는 `hosting/public/` 아래로 들어갑니다.

| 틀 파일 | 넣는 자리 | 하는 일 |
|---|---|---|
| `public/index.html`·`landing.js` | `hosting/public/` | 랜딩 — 출시 단계에 맞는 블록 하나만 보여 줍니다(§5) |
| `public/privacy.html` | 〃 | 개인정보처리방침 — 처리 항목·위탁·국외 이전·광고 ID·보유 기간. **초안 표시가 붙어 있습니다** |
| `public/terms.html` | 〃 | 이용약관 — 초안 표시 |
| `public/delete-account.html`·`delete-account.js` | 〃 | 계정 삭제 요청 — 앱 안 삭제 방법, 웹 요청 폼(또는 메일 안내), 지워지는 데이터와 남는 데이터. 폼은 같은 사이트의 `/api/deletion-request`(서버 함수)로 보냅니다(§6) |
| `public/site-config.js` | 〃 | **이 파일 하나로** 출시 단계·연락처·스토어 링크·폼 켜기를 바꿉니다 |
| `public/styles.css`·`404.html` | 〃 | 겉모습·없는 주소 페이지 |
| `public/.well-known/assetlinks.json.template` | 〃(`.template` 붙은 채) | 안드로이드 앱 링크 확인 파일 틀(§8). 배포에서 빠집니다 |
| `stage3/firebase.json`·`.firebaserc`·`package.json` | `hosting/` | 3단계에서 Hosting만 먼저 올릴 때의 설정(§3). 4-0 뒤의 `hosting` 설정은 이 폴더가 아니라 앱 뼈대 틀의 최상위 `firebase.json`(`../firebase/backend/firebase.json.template`)에 처음부터 들어 있습니다(§4) |
| `apply.sh` | — | 복사하면서 `<앱 이름>` 같은 자리를 값으로 바꿉니다 |

`apply.sh`가 받는 값

| 이름 | 뜻 | 예 |
|---|---|---|
| `앱 이름` | 플레이 스토어에 보이는 앱 이름 그대로 | `예시앱` |
| `개발자 이름` | 플레이 스토어에 보이는 개발자 이름 그대로 | (플레이 콘솔의 개발자 계정 이름) |
| `문의 메일` | 사람이 실제로 읽는 메일함 | |
| `패키지 이름` | 실서비스 앱 패키지 이름 | `app.example` |
| `실서비스 프로젝트 ID` | Firebase 실서비스 프로젝트 ID(3단계 설정 파일에 들어감) | `example-prod` |
| `저장소 이름` | 3단계 `package.json` 이름 앞부분 | `example` |

`<앱 한 줄 소개>`·`<예: …>`·`<처리 기간 — …>`처럼 프로젝트마다 다른 내용은 `apply.sh`가 남은 자리로 알려 줍니다. AI가 그 프로젝트의 실제 수집 항목·화면 경로로 채우고, 사람이 읽고 확정합니다. 화면에 뜨는 문구는 합쇼체가 기본이고, 프로젝트 `mvp/design-brief.md`의 보이스 앤 톤이 확정돼 있으면 그것을 따릅니다.

## 2. 플레이 요건과 이 틀

플레이 콘솔 도움말이 정한 「계정 삭제 웹 주소」 요건과, 이 틀이 그것을 맞추는 자리입니다. 요건 문구는 바뀔 수 있으니 콘솔에 주소를 넣기 전에 도움말을 다시 확인합니다.

| 요건 | 이 틀에서 |
|---|---|
| 링크가 오류 없이 열린다 | Hosting의 정적 페이지 |
| 삭제 요청 방법이 눈에 잘 띈다 | 페이지 맨 위 제목이 「계정 삭제 요청」, 바로 아래에 방법 |
| 스토어에 보이는 **앱 이름이나 개발자 이름**이 페이지에 있다 | 제목과 첫 문단에 `<앱 이름>`·`<개발자 이름>` |
| 앱으로 되돌려 보내거나 다시 설치하게 하지 않는다 | 웹 폼(또는 메일)로 요청이 끝납니다. 폼은 앱 없이 웹 페이지 → 서버 함수로 받습니다. 앱 안 방법은 함께 적을 뿐 필수가 아닙니다 |
| 먼저 해야 할 일(구독 해지 등)이 있으면 분명히 적는다 | 유료 구독이 있으면 「남는 데이터」 위에 해지 방법을 더합니다 |
| 남겨 두는 데이터가 있으면 분명히 알린다 | 「지워지는 데이터」·「남는 데이터와 기간」 두 절 |

폼은 플레이 도움말이 허락하는 방법 중 하나입니다(폼·삭제를 시작하는 링크·고객 지원 메일). 폼을 아직 켜지 않은 3단계에는 메일 안내로 같은 요건을 맞춥니다.

## 3. 3단계에서 먼저 띄우기

**왜 3단계에서?** 3단계에서 첫 앱을 내부 테스트에 올리려면 플레이 「앱 콘텐츠」 신고에 개인정보처리방침 웹 주소가 필요할 수 있습니다. 그런데 Firebase는 4단계에 붙습니다. 그래서 `4-0-backend-prep.md` §3.2(Firebase 프로젝트 만들기)를 앞당겨, **실서비스 프로젝트와 Hosting만** 먼저 만듭니다. 앱은 아직 Firebase에 붙이지 않습니다.

순서는 이렇습니다.

1. **[사람] 계정부터 대조합니다** — 4-0 §2와 §3.2 ①. Firebase 콘솔 오른쪽 위 이메일이 `AGENTS.md` 「소유와 계정」 표의 소유 계정인지 봅니다.
2. **[사람] 실서비스 프로젝트만 만듭니다** — 4-0 §3.2 ②의 실서비스 행. 개발용 프로젝트는 4-0에서 만듭니다. Google Analytics 연결은 켭니다. 만든 뒤 실제 프로젝트 ID를 계정 표에 적습니다. **Firestore는 아직 만들지 않습니다** — 위치(리전)는 한 번 정하면 못 바꾸니 4-0 §3.2 ③에서 두 프로젝트를 함께 정합니다. Hosting만이면 요금제를 바꾸지 않아도 되는지는 그때 공식 요금 안내로 확인합니다.
3. **[사람] Firebase CLI 로그인** — 4-0 §3.4 앞부분(`firebase login`은 사람이 자기 터미널에서). **[AI]**는 계정 장부에 `FIREBASE_ACCOUNT=<그 이메일>`을 두고 `.claude/scripts/with-owner.sh --check`로 확인합니다.
4. **[AI] 틀을 넣습니다** — 작업 브랜치에서, 저장소 최상위 폴더에서.

   ```bash
   bash .claude/templates/hosting-site/apply.sh --stage3 '앱 이름=예시앱' '개발자 이름=<…>' '문의 메일=<…>' \
     '패키지 이름=app.example' '실서비스 프로젝트 ID=example-prod' '저장소 이름=example'
   cd hosting && fnm exec --using=../.nvmrc -- npm install --save-dev --save-exact firebase-tools && cd ..
   ```

   Firebase CLI를 `hosting/`에 따로 까는 이유 — 최상위 `package.json`·`firebase.json`·`.firebaserc`는 4-0에서 앱 뼈대 틀(backend 묶음)이 넣는데, 그 스크립트는 이미 있는 파일을 덮어쓰지 않고 멈춥니다. 3단계 것을 `hosting/` 안에 가둬 두면 4-0에서 부딪히지 않습니다. `hosting/node_modules` 안의 Dart 견본 파일은 `flutter analyze`가 읽어 오류를 냅니다(앱 뼈대 틀 README 「실측 메모」). 2-0에서 앱 뼈대 틀의 분석 제외 조각(`snippets/analysis_options-exclude.yaml`)을 넣었다면 `- hosting/**`가 이미 있습니다. 없으면 `analysis_options.yaml`의 `analyzer: exclude:`에 그 한 줄을 더합니다(웹 페이지 폴더는 Dart가 아닙니다).
5. **[AI] 내용을 채웁니다** — `site-config.js`는 `releasePhase: 'pre-register'`, `deletionForm: false`. 개인정보처리방침은 **지금 앱이 실제로 하는 것**만 적습니다 — 3단계 앱은 데이터를 폰 안에만 저장하고 서버로 보내지 않으므로, 위탁·국외 이전·광고 ID 줄은 지금 해당이 없으면 지우고 4단계에서 다시 넣습니다(`4-2-backend-auth.md` §9).
6. **[사람] 내 컴퓨터에서 열어 봅니다** — `python3 -m http.server --directory hosting/public 8080`을 AI가 띄우고, 사람이 `http://localhost:8080/privacy.html` 등을 엽니다. 주소에서 `.html`을 빼는 것(`/privacy`)은 Hosting에서만 됩니다. 다 보면 AI가 띄운 그 서버만 끕니다.
7. **머지** — 3단계 브랜치를 합칠 때 함께 들어갑니다(`/done-task`).
8. **[메인] main에서 Hosting만 올립니다** — `backend-release` 스킬로. 3단계에는 개발용 프로젝트가 없으므로 그 스킬의 「실서비스 배포 전 확인」 중 2번은 「사람이 6번에서 페이지를 확인했다」로, 5·6·8번은 해당 없음으로 봅니다. 명령은 `hosting/` 안에서 부릅니다.

   ```bash
   cd hosting && ../.claude/scripts/with-owner.sh fnm exec --using=../.nvmrc -- npx firebase deploy --only hosting --project prod
   ```

9. **[사람] 플레이 콘솔에 주소를 넣습니다** — 「앱 콘텐츠 → 개인정보처리방침」에 `https://<실서비스 프로젝트 ID>.web.app/privacy`.

## 4. 4-0에서 합치기

4-0에서 앱 뼈대 틀(backend 묶음)이 최상위에 넣는 `firebase.json`에는 `hosting` 설정이 처음부터 들어 있습니다 — `public`이 `hosting/public`이고, 계정 삭제 요청 폼의 주소(`/api/deletion-request`)를 서버 함수로 넘기는 재작성 규칙과 머리글이 함께 있습니다. 그래서 손으로 합칠 설정은 없고, 3단계 설정을 지우기만 합니다.

1. **[AI]** `hosting/firebase.json`·`hosting/.firebaserc`·`hosting/package.json`·`hosting/package-lock.json`·`hosting/node_modules/`를 지웁니다. 별칭과 Firebase CLI는 이제 최상위 것 하나만 씁니다 — 두 벌이 있으면 언젠가 프로젝트 ID가 어긋납니다. 3단계 설정의 머리글을 손으로 바꿨다면 지우기 전에 최상위 `firebase.json`의 `hosting`에 옮깁니다.
2. 3단계를 건너뛰고 4-0에서 처음 넣는 경우는 `--stage3` 없이 `apply.sh`를 돌립니다. 합칠 것은 없습니다.
3. **Hosting용 웹 앱 등록은 하지 않습니다.** 폼은 Firestore SDK나 REST API를 쓰지 않고 같은 사이트의 서버 함수 주소로만 보냅니다. 그래서 웹 API 키도, 콘솔 「프로젝트 설정 → 내 앱」의 웹 앱도 필요 없습니다. 이 사이트에 Firebase 웹 SDK(로그인·분석 등)를 들이게 되면 그때 등록합니다.
4. **삭제 요청 폼은 서버 함수 `deletionRequest`와 그 재작성 규칙이 실서비스에 나간 뒤에 켭니다** — `site-config.js`의 `deletionForm: true`로 바꿔 작업 브랜치 → 머지 → `backend-release`. 같은 출시에 함께 나간다면 순서는 보안 규칙 → 서버 함수 → Hosting입니다. 함수가 없는데 폼부터 켜면 요청이 전부 실패합니다.
5. **개인정보처리방침을 4단계에서 실제로 붙은 것에 맞게 고칩니다** — Firebase(인증·DB·분석·오류 수집), AppsFlyer, 국외 이전, 광고 ID(`4-2-backend-auth.md` §9). 플레이 콘솔 「앱 콘텐츠 → 데이터 보안」의 「데이터 삭제」 질문에 `https://<실서비스 프로젝트 ID>.web.app/delete-account`를 넣습니다.

## 5. 출시 단계 바꾸기 — RELEASE_PHASE

`hosting/public/site-config.js`의 `releasePhase` 한 줄로 랜딩을 바꿉니다.

| 값 | 언제 | 랜딩에 보이는 것 |
|---|---|---|
| `pre-register` | 3단계~4단계 초 — 아직 아무나 받을 수 없음 | 「곧 나옵니다」, `playStoreUrl`이 있으면 사전 등록 버튼 |
| `beta` | 4단계 비공개 테스트 트랙 | 「지금은 시험 중입니다」, `betaJoinUrl`이 있으면 참가 버튼 |
| `production` | 6단계 정식 출시 | 플레이 스토어 버튼 |

바꾸면 작업 브랜치 → 머지 → `backend-release`(Hosting만). 6단계 측정 기간에는 랜딩 문구도 「스토어 등록정보 수정 금지」와 같은 이유로 고치지 않습니다. 지금 단계를 `mvp/backend-build.md` 「배포 정보」에 적습니다.

## 6. 계정 삭제 요청 처리

폼은 같은 사이트의 `/api/deletion-request`로 보내고, Hosting이 그 요청을 서버 함수 `deletionRequest`(앱 뼈대 틀 `functions/src/deletion/`)로 넘깁니다. 함수가 받는 순서는 이렇습니다.

1. POST만 받고, 이메일 형식·길이(320자)와 이유 길이(500자)를 다시 검사합니다. 페이지의 검사는 사람이 바로 고칠 수 있게 하려는 것이고, 막는 일은 함수가 합니다.
2. 봇이 채우는 빈칸(사람에게 안 보이는 칸)이 채워졌으면 받은 척만 하고 쓰지 않습니다.
3. 같은 이메일의 요청이 24시간 안에 이미 있으면 새로 쓰지 않습니다. 어느 경우든 답은 같습니다 — 어떤 이메일이 요청했는지 바깥에서 알아낼 수 없게 하려는 것입니다.
4. 실서비스 Firestore의 `deletionRequests` 컬렉션에 `email`(소문자로 맞춤)·`reason`·`createdAt`(서버 시간) 셋을 관리자 권한으로 씁니다.

보안 규칙은 이 컬렉션의 앱·웹 읽기·쓰기를 전부 막습니다(앱 뼈대 틀 `firestore.rules`). 함수만 씁니다.

**처리는 사람이 합니다.** 실서비스 데이터를 지우는 일이라 AI가 하지 않습니다(감시 훅도 막음).

1. **[사람]** 실서비스 콘솔에서 새 요청을 봅니다. 알림이 필요하면 새 문서가 생길 때 운영자에게 메일을 보내는 서버 함수를 따로 만듭니다(작업 브랜치 → `backend-release`).
2. **[사람] 본인 확인** — 폼은 누구나 남의 이메일을 적을 수 있습니다. 그 이메일로 확인 메일을 보내 답을 받은 뒤에만 지웁니다. 확인 없이 지우면 남이 남의 계정을 지우게 됩니다.
3. **[사람] 지우기** — 앱 안 탈퇴와 같은 범위(`4-2-backend-auth.md` §11.4 — 사용자 문서·올린 파일·Firebase 계정·카카오 연결 끊기)로 지웁니다. 같은 일을 하는 서버 함수가 있으면 그것을 부르는 것이 빠뜨림이 없습니다.
4. **[사람] 처리 결과를 메일로 알리고**, 요청 문서는 개인정보처리방침에 적은 기간이 지나면 지웁니다.

**스팸에 대한 메모** — 함수에는 봇 빈칸, 길이 제한, 같은 이메일 24시간 제한, 인스턴스 2개 상한만 있습니다. 이메일을 바꿔 가며 보내는 요청은 막지 못합니다. 쌓이는 양이 문제가 되면 함수에 보낸 곳(IP) 기준 요청 수 제한을 더합니다.

## 7. App Check와 웹 폼

App Check는 「우리 앱에서 온 요청인지」를 확인하는 장치입니다. 웹 페이지는 앱이 아니라서 App Check 토큰이 없습니다. 그래서 폼이 Firestore에 바로 쓰면, Firestore의 App Check 강제를 켜는 순간(`backend-release` §7.1) 폼이 막힙니다.

이 틀은 그래서 폼을 **서버 함수로 받습니다** — 폼 → 같은 사이트 주소 → Hosting 재작성 규칙 → `deletionRequest` 함수 → 관리자 권한으로 Firestore. 관리자 권한 쓰기는 App Check 강제와 보안 규칙을 거치지 않으므로, Firestore 강제를 켜도 폼은 그대로 동작합니다.

- 이 함수에는 App Check를 요구하지 않습니다. 웹 페이지가 토큰을 낼 수 없기 때문입니다. 대신 함수 안의 검사(§6)가 막는 일을 합니다.
- 웹 페이지를 App Check에 등록하는 길(웹용 공급자 + 폼에 토큰)은 쓰지 않습니다. 웹용 Firebase SDK와 웹 앱 등록이 필요해 이 작은 사이트에 비해 무겁습니다.

## 8. 앱 링크 확인 파일

안드로이드 앱 링크(웹 주소를 누르면 브라우저 대신 우리 앱이 열리는 링크)를 쓸 때만 필요합니다 — 이메일 링크 로그인 등.

1. `hosting/public/.well-known/assetlinks.json.template`을 `assetlinks.json`으로 복사합니다(`.template` 파일은 배포에서 빠집니다).
2. 지문 자리에 **플레이 앱 서명 키**와 **업로드 키**의 SHA-256 지문을 넣습니다(플레이 콘솔 「앱 무결성」 화면). SHA-1이 아니라 SHA-256입니다.
3. Hosting 설정(4-0 뒤에는 최상위 `firebase.json`의 `hosting`, 3단계에는 `hosting/firebase.json`)이 이 파일에 `Content-Type: application/json` 머리글을 붙이고, 기본 무시 목록의 「점으로 시작하는 파일」을 빼 두었습니다 — 그래서 `.well-known/`이 배포됩니다.
4. 올린 뒤 구글의 확인 도구(Digital Asset Links)로 확인합니다.

## 9. 확인한 것

이 틀을 만들며 임시 폴더에서 확인한 것입니다(실제 Firebase에는 올리지 않았습니다).

- 페이지 다섯 개가 내 컴퓨터의 정적 서버로 열리고, 서로의 링크가 맞습니다.
- `landing.js`·`delete-account.js` 문법 검사(`node --check`) 통과.
- `stage3/*.json` JSON 형식 통과.
- `demo-` 가짜 프로젝트로 Hosting·서버 함수·Firestore 에뮬레이터를 함께 띄워, 앱 뼈대 틀의 `firebase.json`대로 `/api/deletion-request`가 서울 리전 함수로 넘어가고 문서가 서버 시간과 함께 쓰이는 것을 확인했습니다. 같은 이메일 두 번째 요청과 봇 빈칸은 쓰이지 않고, 잘못된 이메일은 400, GET은 405입니다.
- `apply.sh`가 자리를 바꾸고, 채우지 않은 `<…>` 자리를 알립니다.

실제 Hosting 배포와 실제 서버 함수로의 재작성은 처음 올릴 때 개발용 프로젝트에서 먼저 확인합니다 — 개발용 프로젝트에 서버 함수와 Hosting을 `--project dev`로 올려 폼을 한 번 보내 보고, 개발용 콘솔에 문서가 생기는지 봅니다.

## 10. 지켜야 할 것

- **실서비스 Hosting은 main에서 `backend-release`로만 올립니다.** 작업 브랜치에서는 `--project dev`로 확인합니다.
- **개인정보처리방침·이용약관은 AI 초안입니다.** 초안 표시를 지우는 것은 사람이 법률 검토를 받은 뒤입니다(`4-2-backend-auth.md` §9).
- **사실만 적습니다** — 안 받는 정보를 적지 않고, 받는 정보는 빠뜨리지 않습니다. 앱에 수집이 더해지면(계측·MMP·결제) 같은 작업에서 이 페이지도 고칩니다.
- **폼에 프로젝트 값을 적지 않습니다** — 같은 사이트 주소(`/api/deletion-request`)로만 보냅니다. 필드나 길이를 바꾸려면 서버 함수의 검사·그 단위 테스트·이 폼을 한 커밋에서 함께 고칩니다.
- **폼이 Firestore에 직접 쓰게 되돌리지 않습니다** — App Check 강제를 켜면 막히고, 보안 규칙도 이 컬렉션의 직접 쓰기를 막습니다.
- **페이지에 바깥 스크립트를 들이지 않습니다** — 머리글의 보안 정책(Content-Security-Policy)이 이 사이트 주소만 허락합니다. 바깥 스크립트(분석 도구 등)를 들이려면 이 정책과 개인정보처리방침을 함께 고칩니다.
