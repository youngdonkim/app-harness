# 계정 확인 — 절차와 서비스별 함정

**언제 읽나**: 첫 push(원격 저장소 생성)·플레이 콘솔에 앱을 처음 만들기 직전(3단계 배포 전)·Firebase 프로젝트를 처음 만들기 직전(4-0, 또는 3단계에서 개인정보처리방침 페이지를 먼저 띄울 때)·광고 계정과 설치 출처 측정 서비스(MMP)를 처음 연결하기 직전(6단계 앞). 메인이 읽고, 그 작업에 닿는 제약만 지시서에 몇 줄로 넘긴다 (`AGENTS.md` 위임 원칙과 같은 방식 — 에이전트에게 이 문서를 통째로 읽히지 않는다). 계정 이름·이메일의 정본은 프로젝트 `AGENTS.md` 「소유와 계정」 표이고, CLI 키 값은 이 컴퓨터의 **계정 장부**(`~/.config/harness/<소유>.env`)에 있다 — 이 문서는 절차와 함정만 담는다.

## 원칙 여섯

**① 확인은 외부 리소스가 처음 생기는 순간마다 한다** — 첫 push(원격 저장소)·플레이 콘솔 앱 만들기·Firebase 프로젝트 만들기·OAuth 앱·광고 계정 연결 직전에 인증된 계정을 표와 대조하고, **다르면 만들지 않고 멈춰 보고한다.** 한 번 맞춘 계정을 여러 걸음 뒤에 믿지 않는다 — 계정에 묶이는 쓰기(리소스 생성·환경변수 설정·PR 생성·머지·브라우저 콘솔 작업) 직전에, 같은 걸음에서 다시 확인한다. 리소스가 엉뚱한 계정에 이미 생겼으면 다시 만들지 말고 「이전(Transfer)」부터 찾는다 — 주소·키가 그대로면 코드·배포를 안 건드린다. 끝나면 옛 계정 토큰이 있던 자리를 전부 교체한다.

**② CLI 인증은 두 종류다 — 로그인 세션과 발급 토큰(키 파일 포함).** 로그인 세션은 `login` 류 명령이 만드는 것으로 컴퓨터에 남고 영구가 아니다(기간 만료·장기 미사용 회수). 발급 토큰·키 파일은 계정 화면에서 손으로 만드는 접근 토큰이나 서비스 계정 키 파일로 여러 개가 공존한다 — 무기한이어도 장기간 안 쓰면 회수하는 서비스가 있으니, 안 되면 재발급이 정답이다. 만료가 있으면 **비밀값 장부**(`mvp/backend-build.md` — 서식은 `4-0-backend-prep.md` §4)에 만료일과 토큰이 들어간 자리(계정 장부·CI 시크릿)를 같이 적는다. 계정 표에는 「누구의 계정인가」만 적는다. **소유가 다른 프로젝트가 한 컴퓨터에 있으면 전역 로그인 전환으로 갈아타지 않는다** — 로그인 전환은 전역이라 다른 프로젝트를 조용히 망가뜨린다. gh는 소유마다 발급 토큰을 장부에 두고 CLI가 그걸 읽게 한다. **Firebase CLI는 예외로 로그인 세션을 쓴다** — 여러 구글 계정을 `firebase login`으로 등록해 두고 명령마다 `--account <이메일>`로 고르는 방식이라 전역 전환이 없다(실행기가 장부의 `FIREBASE_ACCOUNT`로 이 옵션을 자동으로 붙인다). 서비스 계정 키 파일(장부의 `FIREBASE_SA_DIR` 아래)은 개발용 시드·정리 스크립트에만 쓰고, 실서비스용 키 파일은 만들지 않는다. **발급 토큰은 소유 계정당 하나가 기본이고, 그 소유의 프로젝트들이 장부 파일 하나를 나눠 쓴다.** 더 좁혀야 하면 서비스가 지원하는 프로젝트 스코프 토큰을 따로 만든다. **손으로 넣은 로컬 값은 도구가 덮어쓰거나 앱이 읽는 파일에 두지 않는다** — 설정 내려받기 류 명령은 기본 대상 파일을 통째로 다시 쓰는 일이 있으니, 손으로 넣은 값(`env/*.json` 등)은 내려받기 전에 따로 보관돼 있는지 확인한다. **gh처럼 계정 전환이 되는 CLI도 전환하지 않고 장부의 발급 토큰으로 부른다** — 아래 「계정 장부와 실행기」. 인공지능 제공사 키는 로그인이 아니라 API 키라 여기 해당 없다.

**③ 프로젝트는 별칭으로만 고르고, 실서비스는 main에서만 건드린다** — Firebase 프로젝트가 개발용·실서비스용 둘이라, 어느 쪽을 건드리는지가 곧 사고의 크기다. 모든 `firebase` 명령은 `--project dev` 또는 `--project prod`를 직접 적고, 「기본 프로젝트」(`firebase use`)는 쓰지 않는다. `.firebaserc`의 별칭이 가리키는 프로젝트 ID가 `AGENTS.md` 계정 표의 개발용·실서비스용 ID와 같은지 실서비스 배포 전에 대조한다. 실서비스를 바꾸는 명령은 현재 브랜치가 main일 때만, 실서비스 데이터를 지우는 명령은 AI가 하지 않는다(사람 몫). 감시 훅이 이 조건들을 기계적으로 막는다.

**④ 브라우저 작업(브라우저 에이전트 포함)은 소유별 프로필에서 하고, 표의 계정으로 대조한다** — 프로필 원칙은 `AGENTS.md` 「소유와 계정」 그대로다. **프로필을 골랐다고 계정이 맞는 건 아니다 — 작업 시작 전에 화면의 로그인 계정 이메일을 표와 대조한다.** 여러 계정을 지원하는 서비스(구글·GitHub)는 계정을 지정해 열고, 한 번에 하나만 되는 서비스(카카오 developers·광고 계정·MMP 콘솔 등)는 로그인된 계정을 표와 대조해 다르면 전환한 뒤 진행한다. 전환할 때는 로그아웃이 실제로 됐는지(로그인 폼이 뜨는지) 확인한 뒤 로그인한다 — 세션이 살아 있으면 로그인이 "현재 계정에 연결"로 처리돼 계정이 섞인다. **서비스 간 연결(연동 로그인·앱 설치·저장소 연결)은 양쪽을 대조한다** — 연결에 붙는 건 상대 서비스(로그인·권한을 빌려주는 쪽)의 지금 세션이라, 내가 서 있는 서비스만 보면 상대 쪽의 다른 계정이 조용히 붙는다. 시작 전에 상대 서비스의 로그인 계정도 표와 대조해 다르면 거기서 먼저 전환하고(계정 선택창이 뜨면 표의 계정을 고른다), 끝나면 화면에 표시된 연결 계정을 표와 다시 대조한다. **로그인·재로그인 자체는 에이전트가 한다 — 사람은 일회용 코드(OTP)·패스키 입력만 맡는다.** 이메일로 오는 인증 코드는 에이전트가 메일함에서 읽어 넣는다. 다만 **브라우저 세션은 영구가 아니고, 2FA(2단계 인증)가 켜진 계정은 에이전트가 혼자 전환하지 못한다** — 로그인 화면에서 멈춰 사람에게 코드·패스키를 부탁한다. 복구 코드는 쓸 때마다 사라지는 소모품이라 상시 수단이 아니다. 프로필을 소유별로 나눠도 오래 안 쓴 프로필은 재로그인이 필요할 수 있다 — 프로필 분리는 재로그인 확률을 낮추는 수단이지 보장이 아니다. 손 갈 일을 줄이는 순서: CLI는 발급 토큰으로 로그인 자체를 없애고, 남는 브라우저 작업은 에이전트가 쓰는 컴퓨터에 패스키를 등록해 한 번의 승인으로 줄인다.

**⑤ 한 번만 보여주는 값은 보이는 그 순간 확보하고, 못 했으면 그 자리에서 폐기한다** — 에이전트가 토큰·키를 만들 땐 값을 그 자리에서 확보하고, 값 모르는 살아 있는 토큰을 남기지 않는다. 다단계 선택(스코프 → 프로젝트 등)은 마지막 단계 값이 화면에 표시된 것을 확인한 뒤에 만든다. 사용자가 넣은 값과 브라우저 에이전트의 "했다"는 쓰기 전에 실제 호출로 확인한다 — 값이 맞는지는 그 자격 증명으로 제공사 API를 한 번 호출하면 즉석에서 확인된다.

**⑥ 막히면 다시 하지 말고 멈춘다 — 반복된 실패는 계정을 잃는 길이다.** 계정이 제재되는 건 요청이 많아서가 아니라 **실패한 인증·가입 시도가 되풀이될 때**다(실사고: 카카오 새 계정이 「비정상적인 가입 시도」로 제재). 그래서 속도를 늦추는 게 아니라 **위험한 자리에서 횟수를 끊는다.**

| 등급 | 무엇이 | 한도 |
|---|---|---|
| 높음 — 계정이 걸린다 | 로그인·가입·2FA·비밀번호·인증 코드 | **1회 실패하면 즉시 사람에게. 재시도 금지** |
| 중간 | 토큰·키 발급, 앱 설정 변경, 서비스 간 연결 | 2회 |
| 낮음 | 페이지·목록 읽기 | 서로 다른 시도를 합쳐 3회까지, 같은 응답이 2회면 거기서 멈춘다. 실패하면 「확인 못 함」으로 적고 넘어간다 |

- **재시도할 실패인지 먼저 가린다.** 타임아웃·5xx·요청 한도·「일시적」 문구만 다시 해볼 값어치가 있다. **401·403·404·「권한 없음」·「찾을 수 없음」은 방법이 틀린 것이라 몇 번을 해도 같다** — 명령을 다시 치지 말고 원인을 바꾼다(실측: 다른 소유 계정 토큰으로 조회해 404 / 외부 서비스의 앱 접근 목록에 저장소가 빠져 연동 실패 — 둘 다 재시도로는 안 풀렸다).
- **같은 실패만 센다.** 오류 내용이 달라졌으면 뭔가 알아낸 것이라 새 시도다. **똑같은 응답이 두 번이면 거기서 멈춘다.**
- **시간 간격이 아니라 횟수를 센다** — 「몇 초 기다려라」는 지켰는지 확인할 수 없다. 멈출 때는 **무엇을 몇 번 시도했고 무엇이 돌아왔는지**를 보고에 남겨 사람이 이어받게 한다.
- 자동화를 붙이면 계정이 제재되는 서비스는 아래 「서비스별 함정」에 적는다 — **실제로 덴 것만** 올린다.

## 서비스별 확인·전환·함정

- **계정 장부와 실행기** — CLI 키와 키 파일 경로(gh·Firebase·플레이 서비스 계정)는 프로젝트가 아니라 이 컴퓨터의 `~/.config/harness/<소유>.env`에 둔다. 소유마다 파일 하나(`personal.env` 개인 · `company.env` 회사 · `org-<영문 짧은 이름>.env` 조직), 폴더 권한 700·파일 600, git 저장소 밖이라 커밋되지 않는다. 한 줄에 `이름=값` 하나 — `GH_LOGIN`·`GH_TOKEN`·`GIT_USER_NAME`·`GIT_USER_EMAIL`(GitHub), `FIREBASE_ACCOUNT`(Firebase CLI가 쓸 구글 계정 이메일 — 값이 아니라 이름표), `FIREBASE_SA_DIR`(개발용 시드·정리 스크립트 전용 관리자 키 폴더 경로 — 실행기가 개발용 대상(`--project dev`)인 Node 스크립트일 때만 `GOOGLE_APPLICATION_CREDENTIALS`로 넘긴다. 실서비스용 키 파일은 만들지 않는다), `PLAY_SERVICE_ACCOUNT_FILE`(플레이 올리기용 서비스 계정 키 파일 경로, fastlane이 읽는다)(없는 항목은 줄을 두지 않는다). 키 파일(서비스 계정 JSON)은 장부 폴더 안 `keys/`(파일 권한 600)에 두고 장부에는 경로만 적는다. 어느 장부를 쓸지는 프로젝트의 `.claude/owner`(커밋되는 한 줄 `owner=…`)가 정하고, `AGENTS.md`의 소유 문장과 같은 값이다.
  - **업로드 키는 장부에 적지 않는다 — 앱마다 따로다** — 소유마다 한 줄인 장부에 적으면 같은 소유로 두 번째 앱을 만들 때 덮이기 때문이다. 업로드 키 파일은 `~/.config/harness/keys/<패키지 이름>-upload.jks`, 비밀번호 파일은 같은 폴더의 `<패키지 이름>-upload.properties`(둘 다 파일 권한 600)이고, 패키지 이름은 접미사 없는 실서비스 `applicationId`다. 실행기가 `android/app/build.gradle.kts`(없으면 `build.gradle`)에서 그 이름을 읽어 비밀번호 파일 경로를 `ANDROID_UPLOAD_KEY_PROPERTIES` 환경변수로 넣고, `store-release`가 빌드 때만 프로젝트로 연결한다. 장부에 옛 `ANDROID_UPLOAD_KEY_PROPERTIES` 줄이 있으면 실행기는 읽지 않고 `--check`가 옮기라고 알린다.
  - **CLI는 실행기를 앞에 붙여 부른다** — `.claude/scripts/with-owner.sh gh …` · `… fnm exec --using=.nvmrc -- npx firebase … --project dev|prod` · `… flutterfire …` · `… bundle exec fastlane …`(프로젝트 최상위 폴더에서). 실행기가 `firebase`·`flutterfire` 명령에 장부의 계정(`--account`)을 붙여 준다. `npx`·`fnm exec`·`fvm`·`bundle exec` 건너뛰기는 감시 훅이 알아서 처리한다. 실행기가 장부를 한 줄씩 읽어(셸 코드로 실행하지 않는다) 같은 호출 안에서 환경변수로 넣고 명령을 바로 띄운다 — 셸 함수를 거치지 않으니, 셸에 `gh` 같은 이름의 편의 함수가 있어도 토큰이 바뀌지 않는다. 부모 셸에 남은 같은 이름의 키는 먼저 지운다.
  - **지금 상태는 `.claude/scripts/with-owner.sh --check`로 본다** — 소유·장부 자리·있는 키 이름·업로드 키 자리(있음·아직 없음·패키지 이름을 못 읽음)·(GH_TOKEN이 있으면) gh가 답하는 계정만 나오고 키 값은 나오지 않는다. 어떤 경우에도 실행기는 키 값을 화면에 내지 않는다.
  - **소유 이전 중 한 번만 다른 소유로** — `HARNESS_OWNER=<소유> .claude/scripts/with-owner.sh …`(`transfer-ownership`).
  - **프로젝트마다 다른 키는 프로젝트의 `.env.cli`에** — 소유가 아니라 프로젝트에 딸린 값은 프로젝트 최상위의 `.env.cli`(git 미추적)에 둔다. 실행기는 장부를 읽은 뒤 이 파일에서 **장부가 다루지 않는 이름만** 더 읽는다. 장부가 다루는 이름(위에 든 이름)이 여기 있으면 읽지 않고 「옮기세요」라고 알린다. 앱에 들어가는 공개 설정(MMP 앱 키·카카오 앱 키 등)은 여기가 아니라 `env/dev.json`·`env/prod.json`이다.
  - **옛 프로젝트 호환** — 장부가 없고 프로젝트에 옛 `.env.cli`가 있으면 실행기가 그것을 읽고 「장부로 옮기세요」 한 줄을 남긴다. 해당되면 사람이 장부로 옮긴다.
- **gh** — 다른 CLI와 같은 **발급 토큰 방식**으로 쓴다(원칙 ②). 장부의 `GH_TOKEN`을 실행기가 넘긴다.
  - **토큰이 걸리면 활성 계정 전환은 의미가 없다.** 환경변수 토큰이 저장된 자격 증명보다 우선한다(실측: `gh help environment`의 "takes precedence over previously stored credentials"). 프로젝트를 옮길 때마다 계정을 전환하던 습관은 버린다.
  - 지금 누구로 도는지는 `.claude/scripts/with-owner.sh gh api user --jq .login`으로 확인한다 — 실제로 API를 부르는 값이라 가장 분명하다. `gh auth status`도 환경변수 토큰을 「Active account: true」로 비추고 저장된 계정들은 `false`로 내린다(실측 gh 2.97).
  - **설치 확인은 `command gh --version`으로** — 셸 함수가 있으면 `which gh`·`command -v gh`가 실행 파일이 없어도 「있음」처럼 보인다.
  - **토큰 권한(스코프 — 토큰이 할 수 있는 일의 범위)은 `repo`·`workflow`·`read:org`다.** 하네스가 gh로 하는 일은 PR 생성·머지·저장소 조회·Actions Secret 설정·저장소 이전·저장소 생성이다. 실측(2026-09-29, gh 2.97 도움말·소스와 GitHub 공식 문서): gh 로그인의 기본 스코프는 `repo`·`read:org`·`gist`다. `repo`가 저장소 조회·생성(비공개 포함)·PR·Secret 설정을 덮는다. **`.github/workflows/` 파일을 push하려면 `workflow`가 따로 있어야 한다** — 하네스가 `ci.yml`을 넣으니 필수다. 대화형 로그인에서 「Git 자격 증명 설정」에 동의하면 gh가 `workflow`를 알아서 붙이지만, 클로드 코드의 셸은 대화형이 아니라 그 질문을 건너뛰고 안 붙인다 — 그래서 `gh auth login`에 `--scopes workflow`를 명시한다(같은 이유로 전역 git 설정도 안 건드린다). 저장소 이전에 필요한 스코프는 공식 문서에 적혀 있지 않았다(확인 못 함 — 이전할 때 확인). 스코프 이름은 제공사가 바꿀 수 있으니 발급할 때 최신 확인.
  - **토큰을 얻는 1순위 길은 `gh auth login`이다 — 원칙 ②(로그인 세션은 쓰지 않고 발급 토큰을 쓴다)와 부딪히지 않는다.** 로그인은 토큰을 꺼내는 수단일 뿐이고(`gh auth token --user <계정>`으로 꺼내 장부에), 그 뒤 모든 호출은 환경변수 토큰이 우선한다. 꺼낸 뒤에는 **로그인 세션을 지운다**(`gh auth logout --hostname github.com --user <계정>`) — 로그아웃은 이 컴퓨터의 저장본만 지우고 토큰을 폐기하지 않는다(실측 2026-09-29 `gh auth logout --help`: "The authentication configuration is only removed locally. This command does not revoke authentication tokens."). 그래서 장부의 사본은 살아 있고, 전역 활성 계정은 로그인 전 상태로 돌아간다. 단 로그인 전부터 저장돼 있던 계정이면 사용자가 쓰던 세션이라 지우지 않는다. 절차는 `github-connect` ⑤. gh 로그인으로 받은 토큰을 폐기하려면 GitHub 설정 → Applications → Authorized OAuth Apps의 「GitHub CLI」에서 접근을 끊는다 — 이 컴퓨터만이 아니라 **모든 기기의 gh 토큰이 함께 폐기된다**(같은 도움말).
  - **`git push`도 이 토큰으로 인증한다 — 기본은 HTTPS + 토큰이다.** 프로젝트 **로컬** git 설정에 실행기를 부르는 자격 증명 도우미를 건다: 물려받은 도우미 목록을 빈 값으로 비운 뒤(`git config --local credential.helper ''`) 도우미 함수를 등록한다(`git config --local --add credential.helper '!f() { "$(git rev-parse --show-toplevel)/.claude/scripts/with-owner.sh" --git-credential; }; f'`, `github-connect` ⑦). git이 비밀번호를 물을 때마다 실행기가 장부의 `GH_TOKEN`을 사용자명 `x-access-token`과 함께 git에게만 건넨다(출력이 터미널이면 거절한다). 그래서 **git 명령에는 실행기를 붙이지 않는다** — 사람이 자기 터미널에서 `git push`를 쳐도 되고, `no-main-push` 훅도 첫 낱말이 `git`인 그대로 검사한다. 확인은 `git credential fill`에 `username=x-access-token`이 나오는지로 한다(비밀번호 줄은 가려서 본다). 도우미를 걸기 전에 push하면 전역 도우미(다른 계정)로 인증해 비공개 저장소가 「없음」으로 보인다 — 그래서 ⑦을 저장소 만들기·push와 한 호출에 묶지 않는다.
- **GitHub SSH 키** — **원격 주소가 ssh 형식(`git@github.com:`·`ssh://`)인 옛 프로젝트에만 해당한다.** 새 프로젝트는 HTTPS + 토큰(위 gh 항목)이라 SSH 키가 필요 없다. 옛 프로젝트에서는 push는 SSH로, gh API는 토큰으로 인증하니, **두 방식이 다 표의 소유와 맞아야 한다.** 키 하나는 한 계정에만 등록된다. 소유가 다른 저장소가 한 컴퓨터에 있으면 계정별 키를 따로 두고, ssh 설정의 호스트 별칭으로 저장소 원격 주소에 어느 키를 쓸지 적어 둔다 — 별칭 규약: `github.com-<소유자 태그>`. 설정 방법은 그때 공식 문서로. (실사고: 개인 키로 회사 저장소 push 거부 — 키를 옮기면 반대쪽이 막힌다.)
- **Firebase CLI·FlutterFire CLI** — 인증은 `firebase login`으로 컴퓨터에 등록해 둔 구글 계정 중 장부의 `FIREBASE_ACCOUNT`로 고른다(원칙 ②). 지금 어느 계정이 등록돼 있는지는 `… npx firebase login:list`로 본다. 프로젝트 별칭 규칙은 원칙 ③. 실측으로 확인된 함정은 아직 없다 — 덴 것만 여기 올린다.
  - **서비스 계정 키 만들기가 막힐 수 있다.** 새로 만든 구글 클라우드 조직은 보안 기본값으로 서비스 계정 키 만들기를 막아 두는 일이 있다. 막히면 우회하지 말고 멈춰 사람에게 알린다 — 조직 관리자가 해당 프로젝트에만 예외를 열어야 한다(4-0과 6단계 앞 준비에서 만난다).
  - **리전은 처음에 정하면 못 바꾼다.** Firestore 위치는 한 번 정하면 바꿀 수 없어, 두 프로젝트를 같은 리전(`asia-northeast3`)으로 처음부터 만든다. 만들기 전에 화면의 로그인 이메일을 표와 대조한다(원칙 ①·④).
  - **두 프로젝트는 같은 구글 클라우드 조직 아래에 둔다.** 소유 이전이나 요금 정리를 할 때 한 곳에서 보이게 하려는 것이다.
- **구글 클라우드 콘솔·Firebase 콘솔·구글 플레이 콘솔** — 아이디가 아니라 **오른쪽 위 프로필의 이메일**로 판단한다. 여러 구글 계정이 동시에 로그인돼 있으면 마지막에 쓴 계정이 기본으로 열린다 — 주소의 `authuser=` 값이나 프로필 전환으로 바꾼다. 플레이 콘솔은 같은 구글 계정이어도 개발자 계정(조직)이 여러 개일 수 있으니 왼쪽 위에 표시된 개발자 계정 이름도 표와 대조한다. 플레이 콘솔의 앱 만들기·첫 앱 번들 올리기·신고 답안 제출은 사람이 직접 한다(AI는 초안과 번들까지).
  - **플레이 서비스 계정 권한은 반영에 최대 24시간 걸린다.** fastlane 자동화를 켜기 하루 전에 구글 클라우드에서 서비스 계정을 만들고, 플레이 콘솔 「사용자 및 권한」에서 그 이메일을 앱에 초대해 둔다.
  - **업로드 키를 잃으면** 구글에 업로드 키 재설정을 요청해야 하고 며칠 걸린다. 키 파일과 비밀번호는 만드는 그 순간 사용자의 비밀번호 관리자로 옮기게 한다(원칙 ⑤).
- **광고 계정(구글 광고·메타·X)·MMP(AppsFlyer)** — 계정 확인과 앱 연결은 브라우저 콘솔 작업이라 원칙 ④(소유별 프로필·화면의 이메일 대조)를 그대로 따른다. 광고 매체 로그인은 2FA가 켜진 경우가 많으니 코드 입력 화면에서 멈춰 사람에게 부탁한다. 로그인·가입 실패는 1회에 멈춘다(원칙 ⑥). 결제 수단 입력과 광고비 집행은 사람이 한다.
- **맥 키체인** — 키체인에서 CLI 토큰을 꺼내는 조회 명령은 허용 창이 떠서 무한 대기한다(실측 여러 번). 계정 확인은 그 CLI 자체의 계정·조직 조회 명령으로 하고, 무한 대기 가능성이 있는 명령은 시간 상한을 걸어 부른다.
- **카카오 — 브라우저 에이전트를 붙이지 않는다.** 카카오 계정·카카오 디벨로퍼스 콘솔은 사람이 직접 연다. 에이전트로 접근했다가 새 계정이 「비정상적인 가입 시도」로 제재된 실사고가 있다. AI는 사용자가 건네준 키를 설정에 넣는 CLI 작업만 맡고, 조사 단계에서도 카카오 화면은 열지 않고 현재 상태를 사용자에게 묻는다.
- **Aside(브라우저 에이전트)** — **프로필은 소유별로 가른다**(원칙 ④). 어느 프로필을 쓸지는 프로젝트 표가 정하고, 열고 나서는 **화면의 계정을 표와 대조한다**. 비밀번호는 Aside의 암호화 금고가 저장·자동 채움하니 표에는 계정 ID·이메일만 둔다. 실측한 함정:
  - `aside account list`의 프로필(u0·u1…)은 **Aside에 로그인한 구글 계정 단위**다. 서비스(광고 계정·MMP 등) 로그인은 프로필과 별개라, 프로필이 개인 구글이어도 그 안의 서비스 계정은 다른 소유일 수 있다 — 판정은 늘 서비스 화면의 계정 표시로 한다.
  - u번호(u0·u1)와 UI 프로필 이름의 대응은 CLI로 안 나온다 — 프로젝트 표에 "u1 「이름」"처럼 둘 다 적는다. u0에 로그인된 구글 계정이 그 프로필의 소유를 뜻하지 않는다(실측: 직장 프로필 u0에 개인 gmail이 로그인돼 있었다).
  - **프로필마다 비밀번호 금고와 Aside 로그인을 그 소유에 맞게 갈라 두는 것은 사용자 몫이다.** AI는 이걸 대신 맞추지 않는다 — 대조하다 어긋난 것을 발견하면 **멈추고 사용자에게 고쳐 달라고 한다.** 사람이 손으로 맞추는 일이라 시간이 지나면 어긋나 있을 수 있다.
  - **비밀번호 금고는 프로필이 아니라 Aside 계정(구글 로그인) 단위다.** 프로필마다 Aside 로그인을 따로 할 수 있고, 저장한 사이트 비번은 그 프로필에 로그인된 Aside 계정의 클라우드 금고로 올라간다.
  - Aside에 로그인하지 않은 프로필("Local Account, signed out")의 금고는 이 기기에만 남는다. 사이트 로그인·비번 저장은 그래도 정상 동작한다 — 브라우저 자체 로그인과 사이트 로그인은 별개다.
  - **이미 비번이 든 프로필의 Aside 계정을 바꾸지 않는다** — "This device holds another account's vault … items saved only on this device will be permanently deleted" 경고가 뜨면 중단한다. 기기 전용 항목이 삭제된다.
  - `aside repl`에서 파일 쓰기(`fs`)는 세션 폴더에만 된다(`/private/tmp`는 거부). `getByPlaceholder` 같은 이름 로케이터는 없다 — CSS 로케이터(`page.locator('input[placeholder="…"]')`)와 `console.log` 출력만 쓴다(최신 확인 — 쓴 시점 기준). `openTab`으로 연 탭은 호출이 끝나면 닫혀서 다음 호출에서 다시 못 읽는다.
  - 한 번만 보여주는 값(발급 토큰 등)은 접근성 트리 스냅샷에 안 잡힌다 — 생성 직후 `page.evaluate(() => document.body.innerText)`에서 정규식으로 읽어 같은 호출 안에서 출력한다. 스코프처럼 다단계로 고르는 선택 UI는 마지막 단계까지 고른 값이 입력란에 표시된 것을 스냅샷으로 확인한 뒤 만든다.
  - 로그아웃 확인은 로그인 폼이 스냅샷에 보이는 것으로 한다. 구글 로그인을 누르면 프로필에 든 구글 계정 전부가 선택 화면에 나오므로 이메일로 고른다.
  - 2FA 화면이 뜨면 거기서 멈춘다. 패스키 버튼은 사람이 컴퓨터 앞에 없거나 이 브라우저에 패스키가 없으면 아무 반응이 없다. 로그인 폼에 뜨는 Aside의 「Save credential」 창은 금고 저장 제안이라 무시해도 된다.
  - Aside는 사용자가 실제로 쓰는 브라우저다. 열려 있는 다른 탭을 닫거나 건드리지 않는다.
  - Aside에 일을 통째로 맡기는 방식(`aside exec`)은 Aside 쪽 AI 모델의 사용량 한도에 걸리면 바로 실패한다(실측 2026-10-17: 기본 모델 429, 다른 모델은 「이 계정에서 쓸 수 없음」). 그때는 같은 실패를 되풀이하지 말고 직접 조작하는 방식(`aside repl`)으로 바꾼다 — 쓴 시점 기준.
  - `aside repl`에서 `openTab`으로 연 탭은 그 호출이 끝나면 닫힌다(쓴 시점 기준). 그래서 GitHub 본인 확인(sudo)처럼 「버튼 → 메일에서 코드 읽기 → 코드 입력」이 이어지는 일은 **한 번의 호출 안에서** 끝낸다. 메일 코드는 Aside의 `google-gmail` 기능(`gmail.search`)으로 같은 호출 안에서 읽는다. 한 번 본인 확인을 통과하면 몇 시간은 다시 묻지 않으니, 그다음 설정 변경은 새 호출로 해도 된다.
