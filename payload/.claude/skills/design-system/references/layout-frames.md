## 1. 핵심 개념 — frame · region · content

**이 문서의 용어** (레이아웃·조립 계층). 대부분 은유·관행어라 원어 감각과 다를 수 있어 여기서 정한다:

| 용어 | 뜻 | 비고 |
|---|---|---|
| frame(프레임) | 셸 + 영역 분할 + 크기 예산 — 콘텐츠와 무관한 뼈대 | 여러 화면이 공유하는 재사용 단위 |
| shell(셸) | 프레임을 코드로 만든 위젯 — `lib/app/shell.dart` | 대개 `Scaffold`(Material의 화면 뼈대 위젯 — 상단 바·본문·하단 자리를 가진다)를 감싼다 |
| region(영역) | 프레임 안의 이름 붙은 구역 (위치·크기 예산으로 정의, 콘텐츠 무관) | **개념(자리)이지 특정 위젯이 아님** — `Scaffold`의 `appBar`·`body`·`bottomNavigationBar` 자리로 구현되는 일이 많다 |
| content(콘텐츠) | 영역을 채우는 실제 요소 (목록·카드·입력 묶음…) | |
| section | 콘텐츠 쪽의 의미 묶음 부품 | region과 층위 다름 — 아래 `region ≠ section` 참조 |
| 크기 예산(size budget) | 영역마다 미리 배정해 둔 크기 한도 | 최소 높이(하단 버튼 막대 = 누르는 영역 48 + 여백)든 좌우 여백이든 |
| gutter(화면 좌우 여백) | 화면 가장자리와 콘텐츠 사이의 좌우 여백 (`context.layout.screenX`) | |
| 크롬(chrome) | 콘텐츠를 둘러싸고 탐색·조작을 돕는 **틀 UI** (상단 바·하단 탭·단계 표시·닫기 버튼) | 브라우저 이름 아님 |
| pattern | 프레임+부품을 화면 유형별로 묶은 검증된 틀 | 한 프레임 위에 여러 개 가능 |

**레이아웃 ≠ 화면 디자인.** 레이아웃은 여러 화면이 공유하는 재사용 뼈대이고, 화면은 그 뼈대에 콘텐츠를 채운 인스턴스다. (예: 가입 단계 10개 = 화면 10개, 레이아웃 1개)

region ≠ section: 층위가 다르다 — 위계는 frame → region → content(section → 카드/행 → 부품). section은 region 안에서 콘텐츠를 주제별로 묶으며, 컨테이너 정책(§3)의 적용 대상이다.

## 2. frame-first 절차 — 콘텐츠부터 쓰지 말 것

1. **프레임 선택**: 프로젝트의 셸 중 하나를 고른다 (프레임 목록 위치는 §6)
2. **영역 예산 확인**: 각 영역의 크기는 2층 `AppLayout`에 정의돼 있다 (`screenX`·`touchMin`·`listRowMin`·`bottomBarGap` 류). 새 영역이 필요하면 토큰부터 추가
3. **컨테이너 정책 결정**: 영역마다 두 가지를 정한다 (§3)
   - 행(row)이냐 카드(card)냐
   - 여백 담당자는 화면(gutter)이냐 카드(바깥 여백)냐
4. **그다음에** 콘텐츠(부품·토큰 선택)로 내려간다

### 2.1 셸 선택 규칙 — 공통 · 변형 · 독립

셸은 세 가지로 관리한다:

| 분류 | 정의 | 구현 |
|---|---|---|
| 공통 셸(base) | 여러 화면 성격이 공유하는 뼈대 | 셸 위젯 (예: `AppShell`) |
| 변형 셸(variant) | 뼈대(영역 구성·크기 예산)는 공통 셸과 같고 **표현**(바탕·글자 단계·여백 톤)만 다름 | 셸 위젯의 `variant` 열거형 (예: `AppShell(variant: AppShellVariant.wizard, …)`) |
| 독립 셸(standalone) | **영역 구성 자체가 다름** — 상단 바 유무·하단 탭 유무·스크롤 모델·사진이 화면 끝까지 차는 형 등 | 별도 셸 위젯 신설 |

판정 기준은 하나: **영역(region) 구성과 크기 예산이 같은가?** 같으면 변형, 다르면 독립.

철칙:
- **공유 셸의 기본 규칙은 공유 자산** — 직접 수정은 그 셸을 쓰는 화면 전부를 동시에 바꾸겠다는 의도일 때만. 한 성격만 바꿀 땐 반드시 변형(`variant`)으로. 수정 전에 그 셸의 사용처를 검색으로 확인한다.
- 변형 셸이 뼈대까지 갈라지기 시작하면(영역 추가·삭제) **독립 셸로 승격**한다 — variant에 영역 구조 변경을 계속 쌓으면 base가 사실상 두 개가 된다.
- 셸 3종 모두 프레임 인벤토리(§6)에 등록 — 새 화면은 인벤토리 검색부터.
- 변형 셸에서 화면 전체의 토큰을 비례 조정할 땐 1층 원본 기준으로 바꾼 토큰 한 벌을 `Theme`으로 씌운다 (문법과 예시는 [naming-taxonomy.md](naming-taxonomy.md) §2).
- **하단 탭이 있는 셸은 go_router 셸 경로가 감싼다** — 탭마다 화면 쌓임(뒤로 가기 이력)을 따로 지키는 `StatefulShellRoute` 안에 셸을 둔다. 탭 사이를 오가도 각 탭의 스크롤 위치와 쌓인 화면이 남는다.

### 2.2 하단 고정 요소 — 셸 설계 시점에 자리를 정한다

화면 아래에 늘 보여야 하는 것(주 행동 버튼 막대·대화 입력창·하단 탭)은 **셸을 설계하는 시점에 자리를 정한다. 나중에 얹지 않는다.**

- **셸은 상단 / 본문 / 하단 세 영역이고, 스크롤은 본문 영역만 한다.** 하단 요소는 `Stack`+`Positioned(bottom: …)`으로 화면에 띄우지 않고 셸의 하단 자리(`Scaffold.bottomNavigationBar` 또는 본문 `Column`의 마지막 자리)에 흐름대로 앉힌다. 그래야 막대 높이가 얼마든 본문이 가려지지 않고, 본문 끝을 "막대 높이만큼" 어림잡아 비우는 일이 사라진다 — 막대 높이는 안내 문구·안전 영역·글자 배율·기기마다 달라 어림값은 늘 어긋난다.
- **안전 영역은 하단 요소가 스스로 처리한다** — 하단 막대를 `SafeArea(top: false, …)`로 감싸거나 셸이 `MediaQuery.paddingOf(context).bottom`을 더한다. 본문은 그 값을 몰라도 된다. Material 하단 탭(`NavigationBar`)은 아래 안전 영역을 스스로 비운다(도입 때 시뮬레이터·폰으로 확인) — 우리가 만든 막대만 직접 처리한다.
- **화면 전체를 덮는 것(아래서 올라오는 판·알림 띠·대화상자)만 화면 위에 띄운다** — `showModalBottomSheet`·`ScaffoldMessenger`·`showDialog`가 그 자리다.
- **새 프로젝트의 공통 셸은 하단 고정 요소가 아직 없어도 세 영역으로 시작한다.** 나중에 막대를 띄워 얹고 본문 끝을 어림 여백으로 비우면, 어떤 화면은 가려지고 어떤 화면은 너무 비어 결국 셸을 다시 짜게 된다.
- **`Scaffold`는 화면마다 하나, 누가 둘지 셸 설계 때 정한다** — 셸이 `Scaffold`를 두고 화면은 본문만 주거나, 셸은 두지 않고 화면마다 두거나 둘 중 하나다. 둘 다 두면 `Scaffold`가 겹쳐 키보드 비키기·알림 띠 자리·안전 영역이 두 번 계산된다. 정한 쪽을 프레임 인벤토리(§6)에 적고, 개발용 화면(목업 캔버스·디자인 시스템 페이지)도 같은 쪽을 따른다.

## 3. 컨테이너 정책 — 카드 vs 행, 여백 한 겹 원칙

### 3.1 카드 vs 행

**카드는 위젯 컨테이너지, 목록 항목 감싸개가 아니다.**

| 데이터 성격 | 컨테이너 |
|---|---|
| 밀집 데이터·훑는 목록 | **행(row)** — `ListTile` 계열 목록 |
| 자기완결 위젯 (숫자 요약 부품, 차트, 사진 묶음 항목) | **카드** |

금지: 모든 항목을 카드로 감싸기 · 카드를 화면 구조 대신 사용 · 카드 중첩.

### 3.2 여백 한 겹 원칙

프레임 안에 카드가 있으면 여백이 **이중으로 쌓인다**:

```
✗ 겹침: 화면 좌우 여백(20) + 카드 안쪽 여백(20) = 콘텐츠가 좌우 40씩 손해
│여백│ ┌카드──────────┐ │여백│
│    │ │pad 콘텐츠 pad│ │    │   ← 폰 폭에서 치명적
```

규칙: **화면 가장자리와 콘텐츠 사이 여백은 한 겹만.** 영역별로 담당자를 정한다:

- **방식 A — 화면이 여백 담당** (기본값): 카드·행은 좌우 바깥 여백 없이 화면 좌우 여백(`context.layout.screenX`)에 맞춰 가득. 행 목록·글 콘텐츠에 적합.
- **방식 B — 카드 바깥 여백이 화면 여백 역할**: 영역에 좌우 여백을 주지 않고, 카드 자신의 바깥 여백이 가장자리 여백을 만든다. 지도·사진·가로로 밀어 보는 목록처럼 **화면 끝까지 차는 콘텐츠와 카드가 섞이는 영역**에서 가로폭을 최대로 확보.

**화면 끝까지 닿는 면(브랜드 색 띠 등)은 영역의 좌우 여백 밖에 둔다.** 방식 A 영역 안에서도 이 면만은 화면 좌우 여백(`screenX`)을 받지 않고 화면 폭 전체를 채우게 짠다(방식 B와 같은 생각). 대신 면 안의 글·버튼에는 다시 `context.layout.screenX`를 준다 — 면 안 내용이 가장자리에 붙으면 안 된다. 면을 상태 표시줄 뒤까지 칠할지는 셸의 안전 영역(`SafeArea`) 처리를 따른다 (§4.3).

## 4. 기기 차이 — 작은 폰·큰 폰과 안전 영역

지원 기기는 폰뿐이다. 태블릿·컴퓨터 화면은 다루지 않는다. 대신 폰끼리의 차이 — 폭, 화면 위아래의 가려지는 곳, 키보드, 글자 배율 — 가 레이아웃을 흔든다.

### 4.1 폭 예산 — 작은 폰을 기준으로

- **기준 폭은 둘이다** — 작은 폰(폭 360dp 안팎)과 보통 폰(390~412dp 안팎). 목업 캔버스가 이 한 쌍을 나란히 띄운다. 큰 폰(430dp 안팎)은 보통 폰과 배치가 같고 여백만 남는다.
- **넘침은 작은 폰 + 큰 글자 배율에서 먼저 난다** — 글자 배율 검사 도우미가 작은 폰 폭으로 그리는 이유다([bootstrap-project.md](bootstrap-project.md) §1.7).
- **가로 화면을 허용할지는 앱 뼈대가 정한다** — 허용한다면 본문 최대 폭(`context.layout.contentMaxWidth`)을 셸이 걸어, 가로로 눕혀도 글 한 줄이 끝없이 늘어나지 않게 한다.

### 4.2 화면 좌우 여백

폰 폭에서는 좌우 여백이 콘텐츠 가로폭을 직접 깎아 먹는다. 좌우 여백을 2층 토큰(`AppLayout.screenX`)으로 뽑아 둔 이유가 이것 — 값 하나로 앱 전체를 맞춘다. 보통 16~20 사이에서 고른다. 카드가 있는 영역이라면 §3.2 한 겹 원칙(방식 B)과 조합해 폭 손실을 줄인다.

### 4.3 안전 영역과 키보드

폰 화면은 위아래가 가려진다 — 위는 상태 표시줄·카메라 구멍, 아래는 홈 막대·제스처 영역. 이 가려지는 폭이 안전 영역(safe area)이다. 값은 기기마다 다르니 숫자로 적지 않고 늘 읽는다.

- **셸이 맡는다** — 위쪽은 `AppBar`가 상태 표시줄 아래로 스스로 내려온다. 상단 바가 없는 독립 셸(사진이 위까지 차는 화면 등)은 셸이 `SafeArea(bottom: false, …)`나 `MediaQuery.paddingOf(context).top`으로 비운다. 아래쪽은 §2.2의 하단 요소가 맡는다.
- **안전 영역을 숫자로 비우지 않는다** — `SizedBox(height: 34)`처럼 홈 막대 높이를 어림해 넣으면 기기마다 어긋난다(디자인 규칙 검사 1번에도 걸린다).
- **키보드가 올라오면** — `Scaffold`가 본문을 키보드 위로 줄인다(`resizeToAvoidBottomInset` 기본값). 그래서 입력창·보내기 버튼을 하단 자리에 흐름대로 두면 키보드 바로 위에 붙는다. `Stack`으로 띄운 입력창은 키보드 뒤로 숨는다. 키보드 높이가 따로 필요하면 `MediaQuery.viewInsetsOf(context).bottom`을 읽는다 — 셸이나 입력 막대 부품 안에서만.
- **두 플랫폼** — 안드로이드와 iOS의 안전 영역·뒤로 가기(안드로이드는 시스템 뒤로 가기, iOS는 화면 왼쪽 끝에서 밀기)가 다르다. 겉모양 차이는 Material 테마로 거의 없애고, 이 둘은 셸이 플랫폼 기본 동작을 막지 않는 것으로 맞춘다.

## 5. 반응형 계약

지원 기기가 폰뿐이라 **화면 전체 폭으로 메뉴 구조를 바꾸는 갈래(넓으면 옆 메뉴, 좁으면 하단 탭 같은 것)는 없다.** 남는 것은 부품 단위의 대응이다.

- **기준은 화면 폭이 아니라 부품이 받은 자리**다 — 기본 수단은 `LayoutBuilder`(부품이 받은 자리의 폭 `constraints.maxWidth`를 읽는 위젯)다. (예: "가로 카드는 자기 폭이 좁아지면 사진을 위로 올린다.")
- **같은 부품이 폭이 다른 자리 여러 곳에 놓인다** — 화면 가득, 두 열 격자의 한 자리, 가로로 밀어 보는 목록의 한 장. 화면 폭으로 갈래를 걸면 한 자리에 맞춘 값이 다른 자리에서는 어긋난다. `LayoutBuilder`는 부품이 놓인 자리를 스스로 보고 맞추니, 어디에 넣어도 조합이 깨지지 않는다.
- **화면 전체 폭(`MediaQuery.sizeOf`)은 셸만 읽는다** — 가로 화면의 본문 최대 폭처럼 화면 전체의 일만 셸이 맡는다. 화면·부품이 `MediaQuery.sizeOf`·`MediaQuery.of(context).size`를 부르면 디자인 규칙 검사 3번이 찍는다.
- **갈래를 거는 폭 값도 토큰이다** — `LayoutBuilder` 안의 「이 폭보다 좁으면」 기준값은 `context.layout`의 이름(`compactBreak` 등)으로 쓰고 숫자로 적지 않는다.
- **글자 배율도 폭처럼 다룬다** — 글자가 커지면 같은 폭에 들어가는 글자 수가 줄어 사실상 폭이 좁아진 것과 같다. 그래서 「좁은 자리」 갈래는 글자 배율 2.0에서도 확인한다(SKILL.md 「글자 배율 규칙」).

## 6. 프로젝트별 프레임·패턴 기록

프레임 인벤토리(셸 종류·영역·예산·`Scaffold`를 누가 두나)와 화면 패턴 목록은 **각 프로젝트 문서**에 기록한다 (위치는 프로젝트 AGENTS.md 참조). 이 파일은 방법론만 담는다.
