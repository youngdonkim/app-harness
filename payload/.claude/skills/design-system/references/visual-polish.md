# 화면 생김새 개선 점검 항목

화면을 전문가가 만든 수준으로 다듬을 때 보는 점검 항목의 정본입니다. 항목마다 **무엇을 보나 · 예 · 지시 문장 예**를 적었습니다. 지시 문장은 화면을 만드는 에이전트에게 그대로 줄 수 있는 모양입니다.

항목은 화면을 처음 보는 사람이 「무엇을 먼저 보고, 무엇을 누르면 되는지」를 바로 알게 하는 쪽으로 골랐습니다. 항목 코드(A1·B2 같은 것)는 지시서와 완료 보고에서 그대로 씁니다.

**모든 항목은 기본값입니다 — 사용자 결정이 이깁니다.** 프로젝트가 이미 다르게 정해 기록해 둔 결정(idea-to-mvp는 `mvp/design-brief.md`에 `사용자 확정`으로 적힌 것)과 부딪히면 그 결정을 따르고, 지시서에는 그 항목을 결정에 맞춰 고쳐 넣습니다. 예는 항목의 뜻을 보이려는 것이지 정답 화면이 아닙니다 — 예와 같은 모양으로 만들라고 지시하지 않습니다.

## 1. 언제 쓰나

- 목업의 화면이 「동작은 하지만 평범해 보일 때」 — 위계가 없고, 간격이 들쭉날쭉하고, 글자 크기가 제각각일 때
- 화면을 개선하라는 지시서를 쓸 때 — 아래 항목 코드 중 고칠 것을 골라 지시서에 적습니다
- 개선이 끝난 화면을 점검할 때 — 항목 코드별로 지켜졌는지 봅니다

**지시서를 쓰는 메인이 이 문서를 읽고, 그 화면에 닿는 항목만 걸러서 지시서에 넣습니다.** 화면을 만드는 에이전트에게 이 문서를 통째로 읽히지 않습니다.

## 2. 작업 순서와 확인 폭

1. **글자·간격·색 규칙을 디자인 시스템 페이지에 먼저 올립니다** — 「[서비스 이름] 디자인 시스템」 페이지에 지금 값과 나란히 비교안 값으로 둡니다 ([bootstrap-project.md](bootstrap-project.md) §6.3).
2. **그 규칙으로 핵심 화면 하나의 비교안(A판·B판)을 만듭니다** — 본 화면과 본 토큰은 그대로 두고, 따로 떼어 둔 비교안 자리에서만 만듭니다.
3. **비교안을 보통 폰과 작은 폰에서 함께 봅니다** — 작은 폰 배치 규칙(아래 R)은 처음부터 `LayoutBuilder`로 비교안 안에 만듭니다. 작은 폰 판을 따로 만들지 않습니다.
4. **사람이 판을 고르면 토큰·부품으로 나머지 화면 전체에 적용합니다** — 고른 값을 1·2층 토큰과 공통 부품에 넣고, 화면은 다시 만들지 않습니다.

**규칙을 먼저 올리게 하고, 그다음 비교안을 만들게 합니다.** 화면을 만든 뒤에 규칙을 뽑으면 이미 어긋난 값을 규칙으로 굳히게 됩니다.

확인 크기는 셋입니다 — 보통 폰(폭 390~412dp 안팎), 작은 폰(폭 360dp 안팎), 그리고 작은 폰 + 글자 배율 2.0. **보통 폰과 작은 폰은 목업 캔버스(만든 화면을 폰 틀에 담아 흐름 순서로 나란히 펼쳐 보는 개발용 앱)에서 늘 함께 보고**, 큰 글자 모습은 디자인 시스템 페이지의 글자 배율 견본과 폰 설정으로 봅니다. 「작은 폰에서 무엇이 줄어드는지」는 메모로 디자인 시스템 페이지에 남깁니다.

## 3. A 시선과 위계

**A1 화면마다 주인공 하나**
- 무엇을 보나 — 화면을 3초 봤을 때 먼저 눈에 들어오는 것이 그 화면의 목적과 같은가
- 예 — 목록 화면인데 제목 배너가 가장 커서 목록이 묻힘
- 지시 — 「1순위 ○○, 2순위 ○○, 3순위 ○○. 1순위만 가장 크고 진하게, 나머지는 크기·굵기·명도로 한 단계씩 낮춰라」

**A2 주 버튼은 화면당 하나**
- 무엇을 보나 — 강조색으로 꽉 찬 버튼이 둘 이상 있는가, 또는 주 행동이 있는데 강조색 주 버튼이 하나도 없는가
- 예 — 「저장」과 「공유」가 둘 다 꽉 찬 강조색 / 입력 화면인데 「저장」이 회색 테두리 버튼이라 어디서 끝내는지 안 보임
- 지시 — 「강조색 꽉 찬 버튼은 이 화면의 주 행동 「○○」 하나, 나머지는 테두리 버튼이나 글자 버튼으로. 이 화면만의 주 행동이 없으면 상단 바의 대표 행동이 주 버튼이다」 — 원칙과 이유는 design-system `SKILL.md` 「강조색은 어디에 쓰나」

**A3 덜어내기**
- 무엇을 보나 — 같은 정보가 두 번 나오는가, 지금 판단에 필요 없는 정보가 있는가
- 예 — 목록 한 줄에 정보 덩어리가 일곱 개
- 지시 — 「목록 한 줄 정보는 최대 ○개, 뺀 것은 상세 화면으로」

## 4. B 글자

**B1 크기 단계 제한**
- 무엇을 보나 — 쓰는 글자 크기가 다섯 안팎으로 정해져 있는가
- 예 — 13·15·17·19 같은 어중간한 크기가 섞임
- 지시 — 「글자 크기는 다섯 단계 안팎만 쓴다(예: 30·22·18·16·14). 고정 글자 이름 중에서 고르고, 단계마다 쓰는 자리를 표로 먼저 만든다」

**B2 줄 간격과 자간**
- 무엇을 보나 — 줄 간격이 글 종류에 맞는가
- 예 — 제목 1.3, 본문 1.6, 24 이상 제목은 자간을 글자 크기의 -2%
- 지시 — 「제목 줄 높이(`height`) 1.3, 본문 1.6, 24 이상 제목 자간(`letterSpacing`)은 글자 크기의 -2%. 값은 1층 글자 원본에 두고 2층 글자 단계가 읽는다」

**B3 한글 줄바꿈**
- 무엇을 보나 — 낱말 중간에서 줄이 끊기는가, 두 줄 제목의 길이가 크게 다른가
- 예 — 「추천 여행 코-스」처럼 낱말 가운데서 끊김. Flutter는 한글을 글자 단위로 줄바꿈하고, 웹의 `keep-all` 같은 설정이 없습니다
- 지시 — 「짧은 글자(제목·버튼·탭 이름)만 낱말 단위로 끊기게 한다. 방법은 제목 글자 부품 한 곳에서 처리하고(예: 한 낱말 안 글자 사이에 줄바꿈을 막는 보이지 않는 문자를 넣는 도우미), 본문·사용자가 쓴 글에는 쓰지 않는다 — 복사·검색에 보이지 않는 문자가 섞인다. 두 줄 제목은 두 줄 길이가 비슷하게」
- 방법 — 낱말 안 글자 사이에 보이지 않는 문자 U+2060(WORD JOINER — 그 자리에서 줄을 바꾸지 말라는 표시)을 넣어, 띄어쓰기 자리에서만 줄이 바뀌게 하는 도우미를 공통 부품 자리(`lib/shared/components/common/`)에 한 곳 둔다. 제목·버튼·탭 이름 같은 짧은 표시 글에만 쓰고, 본문·사용자가 쓴 글에는 쓰지 않는다.

  ```dart
  /// 낱말 안 글자 사이에 U+2060을 넣어 띄어쓰기 자리에서만 줄이 바뀌게 한다 (짧은 표시 글 전용).
  String keepWords(String text) => text
      .split(' ')
      .map((word) => word.runes.map(String.fromCharCode).join('\u2060'))
      .join(' ');

  // 쓰는 자리 — 화면 읽기 프로그램에는 원래 글자를 읽히려고 semanticsLabel을 함께 준다
  Text(keepWords(title), semanticsLabel: title)
  ```
- 주의 — 화면에 그려지는 글자에 보이지 않는 문자가 섞이니, 글자로 찾는 위젯 테스트(`find.text`)는 같은 도우미를 거친 글자로 찾거나 `find.bySemanticsLabel`로 원래 글자를 찾는다. 화면 읽기 프로그램(TalkBack·VoiceOver)이 이 문자를 끊어 읽지 않는지 폰에서 한 번 켜서 확인한다

## 5. C 간격과 정렬

**C1 간격 단위**
- 무엇을 보나 — 간격이 4의 배수인가
- 예 — `s1`·`s2`·`s3`·`s4`·`s6`·`s8`·`s12`·`s16`(4·8·12·16·24·32·48·64)만 쓰기로 했는데 숫자 13, 18이 끼어 있음
- 지시 — 「간격은 `context.space`의 `s1`·`s2`·`s3`·`s4`·`s6`·`s8`·`s12`·`s16`만 쓴다」

**C2 근접성(가까운 것끼리 한 묶음으로 보이는 현상)**
- 무엇을 보나 — 같은 묶음 안의 간격이 묶음 사이 간격보다 충분히 작은가
- 예 — 제목과 설명 사이가 카드와 카드 사이만큼 벌어져 한 묶음으로 안 보임
- 지시 — 「묶음 안 간격은 묶음 사이 간격의 절반 이하로」

**C3 정렬 기준선**
- 무엇을 보나 — 모든 요소의 왼쪽 끝이 같은 선에 맞는가
- 예 — 묶음마다 왼쪽 시작 위치가 조금씩 다름 (어떤 묶음은 화면 여백에, 어떤 묶음은 카드 안쪽 여백에 맞춤)
- 지시 — 「모든 요소의 왼쪽 끝을 화면 좌우 여백(`context.layout.screenX`) 선 하나에 맞춘다. 카드 안 글자도 이 선에서 카드 안쪽 여백만큼 들어간 선 하나로」

**C4 읽는 폭**
- 무엇을 보나 — 긴 글 한 줄이 너무 길지 않은가. 세로 폰에서는 거의 문제가 안 되고, 가로 화면을 허용한 앱에서 생깁니다
- 예 — 폰을 눕히니 한 줄이 80자를 넘어 눈이 줄을 놓침
- 지시 — 「가로 화면을 허용하면 셸이 본문 최대 폭(`context.layout.contentMaxWidth`)을 걸어 긴 글 한 줄을 40~45자 안팎으로」

## 6. D 색

**D1 강조색 쓰는 자리**
- 무엇을 보나 — 강조색이 세 자리(화면의 주 버튼 하나 · 지금 선택된 것 · 키보드 포커스 표시)에만 쓰이는가. 원칙과 이유의 정본은 design-system `SKILL.md` 「강조색은 어디에 쓰나」입니다
- 예 — 장식 선과 제목 글자, 로고에도 강조색을 칠해서 어디를 눌러야 하는지 흐려짐
- 지시 — 「강조색은 주 버튼 하나·선택된 것·포커스 표시에만 쓰고, 장식·제목·로고·아이콘에는 쓰지 않는다」
- 서비스를 알리는 브랜드 색은 다른 규칙입니다 — design-system `SKILL.md` 「브랜드 색은 어디에 쓰나」와 아래 I2

**D2 회색 단계**
- 무엇을 보나 — 회색이 몇 단계로 정해져 있는가
- 예 — 글자 회색이 여섯 가지
- 지시 — 「글자 회색 3단계, 선 회색 2단계만」

**D3 상태 색 의미 고정**
- 무엇을 보나 — 강조색과 성공 색이 비슷해 헷갈리지 않는가
- 예 — 초록 계열 강조색 옆에 초록 성공 표시가 붙어, 「저장됨」이 눌러야 할 버튼처럼 보임. 사람이 색만으로 뜻을 가르지 못하면 강조색이 주는 「여기를 누르세요」 신호와 성공 신호가 섞입니다
- 지시 — 「강조색과 성공 색이 비슷하면 색이나 아이콘으로 가른다」

**D4 흰 바탕과 대비가 모자란 강조색은 쓰는 자리를 나눠 색을 정한다**
- 무엇을 보나 — 강조색이 흰 바탕과 대비 4.5:1 미만(노랑·민트·하늘색처럼 밝은 색)인데(색이 밝은지와 상관없이 대비 계산 도우미 `contrastRatio`로 잰다 — [bootstrap-project.md](bootstrap-project.md) §1.5), 흰 바탕 위 글자·밑줄·테두리에 그대로 쓰고 있는가
- 예 — 밝은 노랑 강조색으로 흰 바탕 위 선택된 탭 글자를 썼더니 읽히지 않음
- 지시 — 「강조색이 흰 바탕과 대비 4.5:1 미만이면 네 값으로 나눠 쓴다. ① 원래 색: 주 버튼·선택된 칩의 바탕(그 위 글자는 진한 색). 어두운 바탕을 쓰지 않는 서비스라 이 색을 쓸 자리가 없으면 비워 둔다 ② 진하게 한 색: 흰 바탕 위 선택 밑줄·테두리·포커스(3:1 이상) ③ 더 진한 색: 흰 바탕 위에서 선택된 것을 글자로 보여야 할 때(4.5:1 이상) ④ 아주 옅은 색: 선택된 항목의 바탕. 네 값과 각 대비를 브리프 「4」 「색 — 강조」 행에 적는다」
- 네 값은 2층 색 이름 넷이 된다 — ① `primary` ② `primaryStrong` ③ `onPrimaryContainer` ④ `primaryContainer`. ②처럼 Material에 없는 이름은 [naming-taxonomy.md](naming-taxonomy.md) §5로 더하고, 짝마다 `contrastPairs`에 한 줄씩 넣어 대비 테스트가 거르게 한다
- 네 값으로 나눠도 쓰는 자리는 「강조색은 어디에 쓰나」의 세 자리 그대로입니다 — 값이 늘었다고 장식에 쓸 자리가 생기지 않습니다

## 7. E 부품

**E1 버튼 세 종류**
- 무엇을 보나 — 버튼이 주·보조·글자 세 종류이고 높이가 하나인가
- 예 — 화면마다 버튼 높이가 다름
- 지시 — 「버튼은 주·보조·글자 세 종류, 높이 하나」

**E2 상태까지 그리기**
- 무엇을 보나 — 부품의 상태가 다 있는가
- 예 — 평소 모양만 있고 비활성·포커스가 없음
- 지시 — 「평소·누름·비활성·포커스(입력칸) 상태와, 해당되면 선택됨·불러오는 중 상태를 모두 만들고 디자인 시스템 페이지에서 보이게 한다」

**E3 누르는 것과 보여 주기만 하는 것을 다르게 (필수)**
- 무엇을 보나 — 눌러지는 것과 정보만 보여 주는 것이 같은 모양인가. 사람은 테두리·바탕이 있는 상자를 「눌러지는 것」으로 읽습니다
- 예 — 조회수를 담은 상자와 「저장」 버튼이 같은 테두리·같은 크기라, 사람이 조회수를 눌러 봄
- 지시 — 「누르는 것과 보여 주기만 하는 것의 모양을 가른다 — 보여 주기만 하는 정보는 기본으로 버튼처럼 생긴 상자를 쓰지 않고, 상자로 두기로 했다면 누르는 것과 바탕·테두리를 다르게 한다」
- 프로젝트가 다르게 정했으면 그 결정이 이깁니다(이 문서 머리의 「모든 항목은 기본값입니다」). 정한 것은 브리프 「12. 화면 규칙」에 적습니다

**E4 아이콘 크기·선 굵기 통일**
- 무엇을 보나 — 아이콘 크기와 선 굵기가 같은가, 뜻이 애매한 아이콘에 글자가 붙어 있는가
- 예 — 아이콘 크기 하나(Material 기본 24)·한 아이콘 묶음으로 통일
- 지시 — 「아이콘은 한 묶음(Material 아이콘 등)·한 크기로. 크기는 테마의 아이콘 크기(`iconTheme`)가 정하고 화면에서 `size:` 숫자를 주지 않는다. 뜻이 애매하면 글자를 붙인다」

## 8. F 이미지 · G 상태 화면 · H 문구 · I 개성

**F1 이미지 비율 두 가지**
- 무엇을 보나 — 목록 이미지와 큰 이미지의 비율이 정해져 있는가
- 예 — 목록 1:1, 크게 16:9
- 지시 — 「이미지 비율은 목록 1:1, 크게 16:9 두 가지만」

**F3 작은 그림 위 표시는 작게, 모서리에**
- 무엇을 보나 — 작은 썸네일 위의 재생 표시·배지가 그림 안 글자를 가리는가
- 예 — 작은 썸네일 한가운데 큰 재생 표시가 올라가 썸네일 안 글자가 안 보임
- 지시 — 「작은 썸네일 위 재생 표시·배지는 20 안팎으로 작게 모서리에 두고, 썸네일 안 글자를 가리지 않는다. 큰 그림에서는 키워도 된다」

**F2 자리 표시 모양 통일**
- 무엇을 보나 — 실제 사진이 없는 자리가 한 가지 모양인가, 사진을 지어내지 않았는가
- 예 — 옅은 단색 바탕 + 작은 아이콘 + 한 줄 설명
- 지시 — 「사진 자리는 옅은 단색 바탕, 작은 아이콘, 한 줄 설명으로 통일. 사진을 지어내지 않는다」

**G 상태 화면**
- 무엇을 보나 — 목록이 있는 화면마다 빈 상태와 로딩 화면이 있는가
- 예 — 데이터가 없을 때 빈 화면만 남음
- 지시 — 「목록이 있는 화면마다 빈 상태(다음 행동 버튼 하나)와 로딩(목록 모양 뼈대)과 오류(다시 시도 버튼)를 만든다」

**H 문구**
- 무엇을 보나 — 버튼 글자가 무엇이 일어나는지 말하는가, 고정 문구가 글자 그대로인가
- 예 — 「확인」 대신 「일정 저장」
- 지시 — 「버튼은 무엇이 일어나는지 동사로 6자 안팎. 문구는 `.arb` 문구 파일에 두고 화면에 직접 쓰지 않는다. 브리프 「문자 그대로」 표의 문구는 글자 그대로. 끝나면 화면 문구 검토 에이전트(ux-writing-reviewer)로 한 번 점검한다」

**I 개성** — 이 묶음은 idea-to-mvp 2-3 개성 입히기(`2-3-personality.md`)에서 씁니다. 판(대담판·혁신판·파격판)마다 쓰는 항목은 이 묶음 끝의 표를 봅니다. 화면의 바닥 규칙(위 A~H)을 다듬는 2-2 비교안에는 넣지 않습니다 — 개성까지 섞이면 바닥 규칙만 비교하기 어렵습니다. 공통 원칙은 **한 곳에 힘을 모은다**입니다. 모든 곳을 조금씩 꾸미면 어디도 기억에 남지 않습니다.

**I1 그림 소재 하나**
- 무엇을 보나 — 서비스를 떠올리게 하는 모양(그림 소재)이 주 소재 하나(+ 보조 하나까지)로 정해져 여러 자리에서 되풀이되는가. 소재가 여럿이면 화면이 「조금씩 다 꾸민」 상태가 됩니다. 대표 장면 밖에서도 소재의 모양은 되풀이할 수 있지만(크기·자리·개수 규칙 안에서) 큰 그림·면·움직임은 대표 장면에만 둡니다
- 예 — 반려동물 건강 기록 서비스의 「체중 눈금 선」이 로고·소개 화면 띠 아래 끝선·빈 상태 그림에 같이 쓰임. 모양을 보이는 예라 후보로 그대로 쓰지 않습니다 — 같은 소재가 떠오르면 그 서비스의 브랜드 인상에서 다시 짓습니다(예의 서비스 유형이 시험 서비스와 같으면 그 소재가 그대로 그려진 실사고가 있다)
- 지시 — 「브랜드 인상 한 줄에서 나온 주 소재 「○○」 하나와 보조 소재 하나까지만 쓴다. 쓰는 자리는 로고·브랜드 색 면의 무늬나 모서리·빈 상태 그림·대표 움직임의 모양뿐이고, 대표 장면 밖에서는 모양만 되풀이한다. 소재는 SVG로 직접 그린다 — 외부 이미지 생성 도구를 부르지 않는다」

**I2 브랜드 색 면 자리**
- 무엇을 보나 — 브랜드 색이 정해진 넓은 면 자리에만 쓰였는가(대표 장면은 여러 겹 면 가능, 그 밖 화면은 화면당 하나, 화면 폭 전체 띠는 소개 화면만). 질감·그라데이션 면이면 대비를 가장 나쁜 자리로 쟀는가. 버튼·칩·태그·아이콘·제목 글자에 번지지 않았는가. 원칙의 정본은 design-system `SKILL.md` 「브랜드 색은 어디에 쓰나」입니다
- 예 — 소개 화면 맨 위 띠 하나만 브랜드 색이고, 띠 위 주 버튼은 면과 대비 3:1 이상이라 버튼으로 읽힘
- 지시 — 「브랜드 색(`context.brand.surface`)은 ○○ 자리의 넓은 면에만(대표 장면 ○○는 여러 겹, 그 밖 화면은 하나), 전용 부품 안에서만 쓴다. 질감·그라데이션(예: 옅은 모눈, 부드러운 빛 번짐, 종이 결)은 허용하되 「피할 것」은 그대로 지키고, 대비는 가장 나쁜 자리로 잰다. 진한 면이면 주 버튼은 면 밖이 기본이고 면 위에는 테두리 버튼만 둔다. 띠는 화면 좌우 여백 밖까지 닿게 하고, 띠 안의 글·버튼에는 다시 `context.layout.screenX`를 준다. 버튼·칩·태그·아이콘·제목 글자에는 쓰지 않는다. 면 위 글자 4.5:1, 면 위 회색 글자(`context.brand.onSurfaceMuted`) 4.5:1, 면 위 주 버튼과 면 3:1 이상 — 못 맞추면 버튼을 면 밖으로 내리거나 면을 옅게 한다. 면과 바탕(`context.colors.surface`)은 1.2:1 이상 — 바탕이 옅은 색이면 옅은 끝 단계를 피한다. 2층에 이미 이어진 단계(`primaryContainer`·`secondaryContainer`·`surfaceContainer*`)는 쓰지 않는다」

**I3 제목 서체 하나**
- 무엇을 보나 — 큰 제목에만 쓰는 서체가 하나 있고, 본문·버튼·입력칸 서체는 그대로인가. 한글 11,172자가 다 있는 무료 서체인가
- 예 — `t1`·`t2`·`h1`에만 제목 서체, 굵기 하나만 받음
- 지시 — 「제목 서체는 한글이 다 있는 무료 서체 하나, 굵기 하나만 받는다. 1층 `FoundationType.titleFamily` → 2층 `AppTextStyles`의 ○○ 글자 이름에만 `fontFamily`를 준다. 비교안은 판 토큰 파일의 `text:`에서 그 이름들의 `fontFamily`만 바꾼다. `theme.dart`의 `TextTheme` 연결로 번지는 Material 부품(상단 바·대화상자 제목)도 함께 적고 의도한 것인지 확인한다. 글자 크기 단계는 바꾸지 않는다 — 서체 파일 넣기는 [font-loading.md](font-loading.md)」
- 대표 장면 한 곳에는 「전시용 제목」(`AppTextStyles.display`) 한 단계를 더할 수 있습니다 — 다른 글자 단계는 바꾸지 않습니다. `display`는 본 값 「없음」(`t1`과 같게)으로 본 파일에 먼저 만들어 두고, 판 토큰 파일의 `text:`에서 `display`에 진짜 값을 얹습니다

**I4 로고**
- 무엇을 보나 — 로고가 한 가지 색으로도 성립하고, 상단 바 크기·앱 아이콘 크기·큰 크기에서 모두 알아볼 수 있는가
- 예 — 소재 A형 · 소재 B형 · 서비스 이름 글자 로고 세 안을 디자인 시스템 페이지 「브랜드」 영역에 세 크기로 나란히 둠. 아이콘 크기에서 뭉개지는 안은 아이콘용 단순판을 따로 둠
- 지시 — 「로고는 SVG 파일로 직접 그린다(`assets/brand/`). 화면 안 로고는 `flutter_svg`로 띄우는 공통 부품 하나로, 색은 한 가지로 입힌다. 글자 로고의 글자는 제목 서체로 쓰고 모양(패스)으로 바꿔 둔다. 남의 로고와 닮게 그리지 않는다. 고른 로고로 폰 앱 아이콘(안드로이드 적응형 아이콘 = 앞 그림 + 배경, 안드로이드 13 단색 테마 아이콘)도 만든다」

**I5 사진 톤 맞추기**
- 무엇을 보나 — 견본 사진끼리 밝기·채도·따뜻함이 맞는가. 상품·공간·결과 사진의 색이 실제와 달라 보이지 않는가
- 예 — 사진 톤 공통 부품 하나로 모든 견본 사진에 같은 보정을 씌움. 디자인 시스템 페이지에 같은 사진의 원본 · 보정판을 나란히 둠
- 지시 — 「사진 파일을 고치지 않는다 — 공통 부품 하나(`ColorFiltered`와 `ColorFilter.matrix`)를 견본 사진 자리에 씌운다. 보정 값은 `context.brand.photoTone`(1층 값을 가리키는 2층 묶음)에 둔다. 밝기·채도·따뜻함만 조금 바꾸고 색상(hue)을 돌리지 않는다」

**I6 대표 장면**
- 무엇을 보나 — 로고 없이 봐도 그 서비스인 줄 아는 장면이 1~2곳 있고, 큰 그림·브랜드 색 면·대표 움직임이 그곳에 몰려 있는가. 나머지 화면은 규칙대로 조용한가
- 예 — 팀 일정 공유 서비스의 소개 화면 맨 위에 브랜드 색 띠 + 큰 소재 그림 + 들어올 때 소재 모양이 띠를 따라 그려지는 움직임
- 지시 — 「대표 장면 ○○에만 큰 그림·브랜드 색 면·움직임을 모은다. 나머지 화면은 규칙대로 둔다. 움직임은 장면마다 2~3개, 탄성 곡선(`context.motion.emphasis`)으로, 그중 핵심 행동에 붙는 감탄 포인트(예: 물 마시기 기록에서 하루 목표를 채우면 컵의 물이 한 번 출렁이며 가득 참, 팀 일정 공유에서 모두 가능한 시간을 고르면 겹친 칸이 한 줄로 합쳐짐) 하나를 둔다. 움직임은 추가 패키지 없이 Flutter 기본 애니메이션(암묵 애니메이션 위젯·`AnimationController`)만, 길이·곡선은 `context.motion` 이름으로 만든다. 동작 줄이기 설정이면 `context.motion`이 길이를 0으로 돌려줘 꺼지고, 끝없이 도는 반복 움직임(`AnimationController.repeat`)은 동작 줄이기에서 시작하지 않는다」
- 전시용 제목(`AppTextStyles.display`)은 I3 끝 줄 참조 — 본 파일에 「없음」 값으로 먼저 두고, 판 토큰 `text:`의 `display`에 값을 줍니다

**I7 조작 방식 (혁신판부터)**
- 무엇을 보나 — 핵심 행동을 하는 방법이 서비스 맥락(브리프 「6. 주 사용 맥락 한 줄」)에 맞게 바뀌었는가. 같은 기능이 빠지지 않았는가, 주 행동을 맡은 조작 대상이 강조색 자리인가
- 손맛 — 조작이 얕게 끝나지 않았는가: 누를 때의 저항(차오름·눌림), 놓았을 때 되돌아옴·튕김, 진동은 손맛 순간에 `HapticFeedback` 짧게 한 번(기본 켜짐 — 같은 손동작 중 되풀이 금지), 소리는 기본 꺼짐(사람이 켜면 코드로 만든 짧은 효과음), 끝났을 때의 보상 연출, 실패·중간에 놓으면 다시 하기, 동작 줄이기·대체 경로 그대로. 자기 점검은 누르는 중·끄는 중을 손을 떼기 전에 찍고 진동 호출 수를 센다(`2-3-personality.md` §1.1 「혁신판의 손맛 기준」)
- 예 — 갈래는 손동작(길게 누르기·끌어 놓기·밀기·꼬집기), 말로 입력, 카메라로 찍기, 한 번에 여럿 고르기, 기울이기·흔들기(센서), 진동 반응. 갈래는 서비스 유형이 아니라 브리프 「6. 주 사용 맥락 한 줄」(어떤 상황에서·어떻게 조작하나)과 `intent.md` 「3. 원하는 것」에서 고르고, 맥락에 맞는 둘 + 맥락 밖 하나를 후보로 둡니다. 발상은 다른 분야(게임·실물 물건·놀이·다른 장르의 앱)에서 가져옵니다. 「이 유형이면 이 조작」 식의 짝은 정답지처럼 쓰여 첫 후보가 그 짝으로 굳습니다
- 지시 — 「핵심 행동 「○○」을 「△△」 방식으로 바꾼다. 조작 대상은 판 폴더 안 전용 부품으로 만들고 주 행동을 맡으면 그 부품이 강조색 자리다. 같은 기능을 다른 방식으로 하는 것은 되지만 기능이 빠지면 안 되고, 새 기능은 후보로 보고만 한다. 저장하는 때는 바꾸지 않는다. 손동작은 패키지 없이 Flutter 기본 제스처 위젯(`GestureDetector`·`Draggable`/`DragTarget`·`LongPressDraggable`·`Dismissible`·`ReorderableListView`·`InteractiveViewer`)으로 만든다. 가로 손동작은 `onHorizontalDrag…`로 받고 `onPan…`은 쓰지 않는다 — 세로 스크롤이 살아 있게 하려는 것이다. 세로 스크롤까지 막는 영역은 폰 화면 높이의 절반 이하. 움직임 길이·곡선은 `context.motion` 이름으로만, 숫자는 판 값 파일에 모은다」

**I8 은유 (파격판만)**
- 무엇을 보나 — 화면이 무엇을 닮았는지가 하나로 정해져 있고, 그 수단의 숫자·색이 정해진 자리에 모여 있으며, 무거운 패키지가 정해진 부품 안에서만 불리는가
- 예 — 수단은 입체 장면, 지도 위에 펼치기, 대화로 주고받기, 카드 더미 넘기기, 게임판, 카메라로 비추기 중 하나. 은유는 서비스 유형에서 고르지 않고 다른 분야의 물건·놀이에서 가져옵니다(예: 별자리판, 세탁소 옷걸이 레일, 도서관 서가 — 어느 서비스 유형과도 묶지 않은 예). 「이 유형이면 이 은유」 식의 짝은 정답지처럼 쓰여 첫 후보가 그 짝으로 굳습니다. 이 예들도 후보로 그대로 쓰지 않습니다 — 예와 같은 물건이 떠오르면 버리고 다시 짓습니다(예가 그대로 첫 후보로 떠오른 실사고가 있다)
- 지시 — 「첫 화면을 「○○」 은유로 바꾼다(수단: △△). 수단의 숫자 값(원근 값·처음 각도·회전 범위·확대 범위·면 좌표·물건 자리 등)은 판 값 파일 한 곳에 모은다 — 길이·곡선은 여기 두지 않고 `context.motion`으로만. 수단 안의 색은 판 접두 확장의 2층 이름으로만 두고 1층 램프(`Palette.*`)를 바로 읽지 않는다. 입체는 3D 패키지 없이 원근 `Transform`(원근 행렬)과 `CustomPainter`로 그려 끌어서 돌리기·두 손가락 확대(`InteractiveViewer`)·물건 누르기를 만든다. 3D 패키지(예: `flutter_scene`)는 사람이 컨셉 고르기에서 골랐을 때만, 메인이 깐다 — 위젯 테스트에서 그리기에 실패하므로 장면 앞의 안내 글·버튼·상태만 테스트하고 3D 부분은 가짜 위젯으로 바꿔 끼우는 구조로 짓는다. 무거운 패키지(3D·지도)는 이 화면의 전용 부품 안에서만 부르고(디자인 규칙 검사 18번), 엔진이 뜨는 동안(지도 스타일 받기 등) 로딩 뼈대를 보인다. 은유 안의 「지금 선택된 것·오늘」에는 강조색을 쓸 수 있고 장식에는 쓰지 않는다. 대비는 가장 나쁜 자리로 잰다. 외부 3D 모델·외부 이미지 생성 도구는 부르지 않는다」

**I9 대체 경로 (혁신판부터)**
- 무엇을 보나 — 바뀐 조작과 은유마다 같은 일을 하는 평범한 길(버튼·목록)이 같은 화면에 있고, 누르는 영역이 48dp 이상이며 화면 읽기 이름(`Semantics` 라벨·`tooltip`)이 있는가. 동작 줄이기에서 정지 화면으로 되는가. 고른 수단이 안 되는 상황의 대체 화면이 있는가
- 예 — 끌어 놓기 ↔ 옮길 곳을 고르는 버튼, 명령창 ↔ 메뉴, 말로 입력 ↔ 글 입력란(마이크 권한 거부·인식 실패 때), 지도 못 불러옴·오프라인 ↔ 목록, 카메라 권한 거부 ↔ 직접 입력
- 지시 — 「바뀐 조작과 은유마다 같은 일을 하는 버튼·목록 경로를 같은 화면에 테두리 버튼으로 둔다. 누르는 영역은 `context.layout.touchMin` 이상, 아이콘만 있는 버튼에는 이름을 단다. 동작 줄이기면 움직임을 끄고 정지 화면 + 대체 경로로 보인다. 고른 수단이 안 되는 상황(권한 거부·인식 실패·못 불러옴·오프라인)에서는 대체 화면을 보이고, 엔진을 받는 동안은 로딩 뼈대를 보인다」

**판마다 쓰는 항목**

| 판 | 쓰는 항목 |
|---|---|
| 대담판 | I1~I6 |
| 혁신판 | I1~I6(대담판 것을 이어받음) + I7 + I9 |
| 파격판 | I1~I6(대담판 것을 이어받음) + I7(핵심 행동 흐름까지 이어질 때) + I8 + I9 |

## 9. J 머무는 공간

이 묶음은 idea-to-mvp 2-4 머무는 공간(`2-4-stay-space.md`)에서 씁니다. 머무는 공간은 **사용자가 들어가 어디를 볼지 스스로 고르며 둘러보는 장소**입니다. 정해진 핵심 행동 한 번을 손으로 하는 방법(손맛)은 I7이 맡습니다 — 가르는 질문은 「사용자가 어디를 볼지 고르나, 정해진 한 가지를 손으로 하나?」입니다. 공통 원칙은 **멀리서 본 그림보다 가까이 다가간 모습**입니다. 사람은 물건을 골라 다가간 뒤에 머뭅니다. 예는 뜻을 보이려는 것이지 후보가 아닙니다.

**J1 세계**
- 무엇을 보나 — 빛(시간대·방향·그림자)·재질(표면 3~5가지)·모서리·늘 도는 작은 움직임 3~5가 공간 지시서의 참고 분위기 하나에 맞춰 정해졌는가. 기본 도형만 놓인 채 끝나지 않았는가
- 지시 — 「참고 분위기 「○○」를 먼저 정하고 빛·재질·모서리·작은 움직임을 모두 거기에 맞춘다. 늘 도는 움직임은 3~5개, 길이·곡선은 `context.motion` 이름으로만, 동작 줄이기면 모두 멈춘다」

**J2 채움**
- 무엇을 보나 — 데이터를 맡은 물건이 데이터 필드마다 있고 상태(진행 중·끝남·없음)에 따라 모습이 다른가. 이야기 소품 8~15개가 저마다 이 서비스·이 사용자와 이어진 이야기 한 줄을 갖는가. 숨은 재미가 2~3개 있는가
- 지시 — 「데이터 필드마다 물건 하나, 상태마다 다른 모습. 소품마다 지시서의 이야기 한 줄이 보이게. 숨은 재미 2~3개 — 저장이 새로 필요하면 저장하지 말고 새 기능 후보로 보고한다」

**J3 캐릭터**
- 무엇을 보나 — 캐릭터가 있으면 정체(사용자 자신·분신·안내하는 존재)가 근거와 함께 정해졌고, 평소 하는 일과 물건을 고를 때의 반응이 있는가. 없으면 없는 이유가 있는가. 코드로 그렸는가
- 지시 — 「캐릭터는 도형 조합·픽셀·선 그림으로 코드(`CustomPainter`·`Path`)에서 그린다. 바깥 이미지 생성 도구·바깥 3D 모델·내려받은 그림은 쓰지 않는다. 동작 줄이기면 걷기·몸짓을 멈춘다」

**J4 누른 뒤**
- 무엇을 보나 — 물건마다 ① 반응(진동 한 번 포함) ② 다가가기 ③ 가까이 세부 2~3가지 ④ 내용 열림(어느 데이터·어느 주 행동) ⑤ 돌아오기가 있는가. 누르면 이름표만 뜨고 끝나지 않는가. 가까이 본 모습이 `devFocusProvider` 값으로 처음부터 그려지는가(목업 캔버스 「가까이」 창)
- 지시 — 「물건을 고르면 `HapticFeedback.selectionClick()` 한 번, 다가가고, 가까이에서 세부 2~3가지가 보이고, 아래에서 올라오는 판(`showModalBottomSheet`)이 열린다. 판을 내리거나 바깥을 누르면 돌아온다. 동작 줄이기면 다가가기 없이 바로 가까이 모습이나 내용으로」

**J5 늘리기**
- 무엇을 보나 — 데이터가 0개·1개·10개·100개일 때의 모습과 넘칠 때 묶는 법이 있는가. 빈 공간이 첫 행동을 이끄는가. 물건 수 상한과 저가폰 성능 바닥(그림 층 `RepaintBoundary`, 움직이는 부분만 다시 그림, 가려지면 `TickerMode`로 멈춤)이 있는가
- 지시 — 「`DevState.empty`는 첫 행동 안내가 되는 빈 공간, `devManyProvider`가 참이면 묶인 모습. 물건 수 상한을 두고 넘치면 묶거나 「더 보기」 목록으로. 움직이지 않는 배경은 한 번 그려 남겨 쓴다」

**J6 공간 안 색**
- 무엇을 보나 — 물건은 제 색(나무는 나무색)이고 그 색이 공간 팔레트 한 곳에만 있는가(16개 안팎까지). 신호 자리(지금 고른 물건·오늘·주 행동)는 2층 이름(`context.colors.primary` 등)인가. 팔레트에 강조색과 헷갈리는 색이 없는가. 데이터 글자는 그림 층 위 글 층(`Text` 위젯)에 있는가. 원칙의 정본은 design-system `SKILL.md` 「브랜드 색은 어디에 쓰나」 끝의 「머무는 공간 안 색」입니다
- 지시 — 「물건 색은 판 토큰 파일 `stay.dart` 안 `Stay{수단}Palette` 한 곳에서만 이름으로 불러 쓴다. 지금 고른 물건·주 행동은 2층 이름. 팔레트에 강조색과 헷갈리는 색을 두지 않는다 — 디자인 시스템 페이지 「머무는 공간」 영역에 팔레트와 강조색을 나란히 보인다. 데이터 글자는 그림 층에 그리지 않고 그 위 글 층에」

## 10. R 작은 폰과 큰 글자로 옮기기

보통 폰에서 다듬은 화면을 작은 폰(폭 360dp 안팎)과 큰 글자 배율로 옮길 때 보는 항목입니다. 폰만 지원하므로 격자 열 수가 크게 바뀌는 일은 드물고, 대부분 「덜어내기」와 「넘치지 않기」입니다.

**R1 작은 폰에서 줄어드는 순서**
- 예 — 목록 한 줄의 보조 정보 → 가로 줄의 아이콘 글자 → 격자 열 수 차례로 줄임
- 지시 — 「작은 폰에서 무엇부터 덜어내는지 순서를 디자인 시스템 페이지의 작은 폰 메모에 적는다. 갈래는 부품 안 `LayoutBuilder`로, 기준 폭은 `context.layout`의 이름으로」

**R2 상단 바 행동 개수**
- 무엇을 보나 — 상단 바 오른쪽 아이콘 버튼이 몇 개인가, 작은 폰에서 제목이 잘리는가
- 지시 — 「상단 바 오른쪽 행동은 둘까지, 나머지는 더보기 메뉴로. 끝까지 밖에 남길 행동 하나를 정한다」

**R3 목록 한 줄 덜어내기**
- 예 — 회색 정보 셋 → 둘, 태그 둘 → 하나
- 지시 — 「작은 폰에서는 목록 한 줄의 정보를 하나씩 덜어낸다」

**R4 주 버튼은 화면 아래 고정 줄**
- 무엇을 보나 — 긴 화면의 주 버튼이 스크롤 끝에 묻혀 있지 않은가
- 지시 — 「입력·확인 화면의 주 버튼은 셸 하단 자리의 고정 줄에 둔다(layout-frames.md §2.2). 본문 끝에 두지 않는다」

**R5 가로로 긴 표 → 한 줄씩 카드나 행**
- 지시 — 「가로로 긴 표는 한 행을 카드 하나나 두 줄짜리 목록 행으로 바꾼다」

**R6 격자 열 수**
- 예 — 2 → 1 (작은 폰이나 큰 글자에서)
- 지시 — 「격자 열 수는 부품이 받은 폭과 글자 배율을 보고 줄인다. 열 비율을 숫자로 묶지 않는다(SKILL.md 「글자 배율 규칙」 3)」

**R7 큰 제목만 한 단계 줄이기**
- 지시 — 「작은 폰에서 큰 제목(`t1`·`t2`)만 한 단계 줄이고 본문은 그대로 둔다. 화면에서 크기를 바꾸지 않고 `LayoutBuilder` 갈래에서 다른 글자 단계 이름을 고른다」

**R8 엄지 자리**
- 무엇을 보나 — 자주 누르는 버튼이 화면 아래쪽에 있고, 누르는 영역이 48dp 이상인가
- 지시 — 「자주 누르는 버튼은 아래쪽에, 누르는 영역은 48dp(`context.layout.touchMin`) 이상으로」

**R9 가로로 밀리는 곳은 하나만**
- 예 — 거르기 칩 줄
- 지시 — 「가로로 밀어서 보는 곳은 화면당 하나만」

**R10 큰 글자에서 넘치지 않기**
- 무엇을 보나 — 글자 배율 2.0에서 글자가 잘리거나 겹치거나, 버튼 글자가 버튼 밖으로 나가는가
- 지시 — 「SKILL.md 「글자 배율 규칙」의 세 자리를 고치고, 화면마다 글자 배율 2.0 위젯 테스트를 통과시킨다. 보기 좋은지는 사람이 본다」

**R 규칙은 화면 전체 폭이 아니라 `LayoutBuilder`로 구현한다 — 화면 전체 폭(`MediaQuery.sizeOf`)은 셸만 읽는다.**

## 11. 지시서 한 장의 모양

개선을 맡기는 지시서는 아래 여섯 항목으로 씁니다. 핵심은 **규칙을 디자인 시스템 페이지에 먼저 올리게 하고, 그다음 비교안을 만들게 하는 것**입니다.

| 항목 | 내용 |
|---|---|
| 화면 | 어느 화면을 고치나 |
| 1·2·3순위 | 이 화면에서 눈에 띄어야 할 순서 |
| 고칠 항목 코드 | 위 목록에서 고른 코드 (예: A1·A2·B1·C1·E3) |
| 바꾸지 말 것 | 기능 자리, 브리프 「문자 그대로」 고정 문구, 피할 것 |
| 비교안 개수 | A 지금 구조 다듬기, B 밀도를 낮춘 판 |
| 완료 보고 | 정한 규칙, 그리고 항목 코드별로 무엇을 왜 바꿨는지 |

예: 「화면: 글 목록 / 1순위 글 줄, 2순위 거르기 칩, 3순위 상단 바 / 고칠 항목: A1·A2·A3·B1·C1·E3 / 바꾸지 말 것: 줄마다 있는 저장 버튼 자리, 고정 문구 / 비교안: 비교안 자리에 A, B 두 벌로 / 완료 보고: 정한 규칙 + 코드별 변경 이유」

## 12. 정한 규칙은 어디로 가나

규칙을 디자인 시스템 페이지에 비교안 값으로 먼저 올리고 비교안을 만들게 한 뒤, 사용자가 고른 판의 값은 다음 자리로 갑니다.

- **브리프 「12. 화면 규칙」** — 고른 판의 비교안 값이 여기로 갑니다. 사용자가 고른 판의 값만 적습니다.
- **1·2층 토큰과 공통 부품** — 고른 판의 바뀐 값은 판 토큰 파일(`lib/core/design/drafts/{판}.dart`)에서 2층(필요하면 1층)으로, 판 접두 이름은 접두를 떼고, 비교안 전용 부품의 모양은 본 부품(감싸개)으로 갑니다. 디자인 시스템 페이지는 「지금 값」 하나로 돌아갑니다 ([bootstrap-project.md](bootstrap-project.md) §6.3).
- **코드에서** —
  - 글자 단계는 고정 글자 이름(`t1`·`t2`·`h1`·`h2`·`h3`·`b1`·`b2`·`label`·`caption` — [naming-taxonomy.md](naming-taxonomy.md) §2)의 크기 값으로 갑니다. 이름은 바꾸지 않습니다.
  - 간격 허용 단계 · 화면 좌우 여백 · 긴 글 폭은 프로젝트 `AGENTS.md` 「디자인 시스템 연결 정보」의 **적용 규칙 요약**으로 갑니다.
  - **새 토큰 층을 만들지 않습니다.** 간격은 2층 간격 단계(`s1`~`s16`) 그대로 씁니다.
