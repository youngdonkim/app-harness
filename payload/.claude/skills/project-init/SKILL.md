# project-init — 프로젝트에 하네스 적용·동기화

하네스는 **파일 복사로 배포**한다. app-harness 저장소가 원본이고, 그 저장소의 `payload/`가 **프로젝트 루트의 미러**다. 적용은 이 미러를 프로젝트 루트에 그대로 복사하는 일이다. 복사된 파일은 프로젝트 저장소에 커밋되므로, 팀원은 프로젝트를 clone만 하면 하네스가 이미 들어 있다 — 하네스 저장소를 따로 받을 필요가 없다.

이미 하네스가 적용된 프로젝트에서 재실행하면, 신규 복사 대신 원본과 비교해 갱신하는 동기화 모드로 동작한다.

신규 적용 길은 둘이다. **기본은 옆 폴더 경로** — 하네스 저장소 폴더에서 연 세션이 그 옆에 새 프로젝트 폴더를 만들고 하네스 복사·첫 커밋·GitHub 연결·첫 push까지 끝낸다. 사용자는 끝난 폴더에서 새 세션을 열기만 하면 되고, 새 세션은 열 때부터 `.claude/`가 있어 스킬·에이전트·훅이 다 잡힌다. **예외 경로**는 하네스를 한 번도 안 깐 폴더(빈 폴더나 기존 코드가 있는 폴더)에서 직접 세션을 연 경우다 — 그 폴더에 적용하고, 끝에 앱을 한 번 껐다 켜게 한다.

## 전제 확인

1. **어느 길인가 — 아래 순서로 판별하고 「대상 폴더」(하네스를 깔 폴더, 절대 경로)를 정한다.** 이 문서의 「프로젝트 루트」·「프로젝트」는 전부 대상 폴더를 뜻한다.
   1. **세션 폴더가 하네스 원본 저장소 자신인가** — 세션 폴더의 최상위(`git rev-parse --show-toplevel`)에 `README.md`와 `payload/.claude/skills/project-init/SKILL.md`가 있으면 그렇다 → **옆 폴더 경로(신규 적용)**. 이 하네스(Flutter판)인지는 [원본 검증](#원본-검증-필수--건너뛰지-않는다) 0번이 가린다. 대상 폴더는 [대상 폴더 정하기](#대상-폴더-정하기--옆-폴더-경로)대로 `<하네스 저장소의 부모 폴더>/<이름>`이다. 하네스 저장소에도 `.claude/harness-version`이 있으니 **이 판별이 2번보다 먼저다** — 순서를 바꾸면 하네스 저장소를 자기 자신과 동기화하려 든다. 하네스 저장소 자신에는 적용도 동기화도 하지 않는다 — 이 세션에서 "하네스 동기화해줘"가 오면 "동기화는 그 프로젝트 폴더에서 연 세션에서 합니다"라고 안내한다.
   2. **현재 폴더 최상위에 `.claude/harness-version`이 있나** → **동기화 모드**. 대상 폴더 = 현재 폴더 최상위.
   3. **그 밖** → **예외 경로(신규 적용)**. 대상 폴더 = 현재 폴더(git 저장소면 그 최상위).
2. **git이 있고 대상 폴더가 git 저장소인가** — git이 없으면 `github-connect` ①을 먼저 돌려 설치한다 (예외 경로에서는 스킬이 아직 프로젝트에 없으니 3번에서 찾을 원본의 `payload/.claude/skills/github-connect/SKILL.md`를 읽고 그 단계만 따른다). 저장소가 아니면 project-init이 대상 폴더에서 직접 `git init -b main`을 한다 (done-task·new-task·훅 모두 git 전제). 윈도우: 훅·명령은 Git Bash에서 돌 것으로 보이지만 실측이 없다 — 막히면 멈추고 보고한다. 훅이 쓰는 `jq`가 없으면(윈도우 Git Bash에는 기본으로 없다) `github-connect` ③을 같은 방식으로 먼저 돌려 묻지 않고 깐다.
3. **하네스 원본 저장소가 어디 있나** — 아래 [하네스 원본 찾기](#하네스-원본-찾기).
4. **새로 깐 스킬·에이전트가 언제 잡히나** — 길마다 다르다.
   - **옆 폴더 경로** — 이 세션은 하네스 저장소의 스킬·훅으로 돌고, 새 폴더의 것은 사용자가 그 폴더에서 새 세션을 열 때 처음부터 잡힌다. 재시작 안내는 하지 않는다.
   - **예외 경로** — `.claude/` 폴더 없이 연 세션이라 새로 깐 스킬·에이전트가 이 세션에서는 잡히지 않는다. 그래도 신규 적용은 이 세션에서 끝까지(로컬 단계 + `github-connect`) 하고 — `github-connect`는 원본의 SKILL.md를 읽어 돈다(9단계) — **모두 끝난 뒤 한 번만** 앱을 껐다 켜 달라고 한다(10번 마무리 안내).
   - **동기화 모드** — 이미 `.claude/` 폴더가 있으니 스킬은 몇 초 뒤, 에이전트는 응답을 한 번 끝낸 다음 턴부터 잡힌다.

## 대상 폴더 정하기 — 옆 폴더 경로

옆 폴더 경로에서만 쓴다. 예외 경로·동기화 모드는 대상 폴더가 현재 폴더라 이 절을 건너뛴다.

1. **이름 뽑기** — 스킬 인자가 있으면 그 첫 낱말(`/project-init cafe-booking`). 없으면 사용자 말의 「옆에 `X` 폴더」·「`X`라는 새 프로젝트」·「`X` 만들고 하네스 적용」에서 `X`. 못 뽑았거나 둘 이상이면 묻는다 — "새 프로젝트 폴더 이름을 무엇으로 할까요? (예시 답: 「cafe-booking」)". 경로(`/`가 든 값)를 받으면 이름만 다시 묻는다.
2. **이름 규칙 — 영문 소문자·숫자·하이픈만**, 첫 글자는 소문자나 숫자, 100자 이하(`^[a-z0-9][a-z0-9-]{0,99}$`). 이 이름이 그대로 GitHub 저장소 이름이 된다(`github-connect` ⑧). 다른 글자(대문자·한글·공백 등)가 섞이면 바꾼 이름 하나를 제안하고 확인받는다 — "「카페 예약」은 `cafe-booking`으로 만들까요?"
3. **자리** — 대상 폴더 = `<하네스 저장소 최상위의 부모 폴더>/<이름>`(하네스가 `/Users/me/dev/app-harness`면 `/Users/me/dev/<이름>`). 부모 폴더 경로에 공백이 있으면 멈추고 보고한다 — 훅이 명령을 공백으로 잘라 읽어 경로를 못 읽는다.
4. **이미 있는 폴더**
   - 없거나 비어 있으면(`.DS_Store`만 있어도 빈 것으로 본다) 그대로 진행한다.
   - 비어 있지 않으면 멈추고 묻는다 — "이 폴더에 이미 파일이 있습니다. 다른 이름으로 할까요?" 안에 `mvp/`(1단계 산출물)만 있으면 「그대로 적용」도 함께 고를 수 있게 한다 — 그러면 1번 인터뷰의 `intent.md` 갈래가 돈다. `.claude/harness-version`이 있으면 이미 적용된 프로젝트라 "그 폴더에서 세션을 열고 '하네스 동기화해줘'라고 하세요"로 안내한다. 기존 코드가 있는 폴더에 얹으려면 예외 경로(그 폴더에서 세션을 열고 "하네스 적용해줘")로 안내한다.
5. **시작 알림** — 만들 절대 경로를 한 줄로 보여 주고, 허용 창 안내를 붙인다: "`<절대 경로>`에 만들겠습니다. 이 폴더는 지금 세션 폴더 밖이라 클로드 코드가 명령마다 허용을 물을 수 있습니다 — 뜨면 「허용」을 눌러 주세요."

**옆 폴더 경로의 명령 형태** — 클로드 코드는 세션 폴더 밖으로 `cd`한 셸을 다음 호출 전에 세션 폴더로 되돌린다(실측 2026-10-20). 그래서 대상 폴더를 향한 명령은 **매 호출마다 `cd <대상 절대 경로> && <명령>` 한 줄**로 부른다. 경로는 따옴표·`~`·변수 없이 절대 경로 그대로 쓴다 — 훅(`no-main-push`·`owner-runner-guard`)이 `cd` 조각을 글자 그대로 읽어 그 폴더 기준으로 검사한다. 파일 도구(Write·Edit)에는 대상 폴더 안의 절대 경로를 준다. 이 절차의 상대 경로 명령(`git …`·`.claude/…`)은 전부 이 형태로 부른다. 원본 쪽 명령(`git -C <원본경로> …`)은 그대로다.

## 하네스 원본 찾기

복사해 올 원본은 **로컬에 clone된 app-harness 저장소**다. 순서대로 찾는다.

0. **옆 폴더 경로면 세션 폴더(하네스 저장소)가 곧 원본이다** — 아래 1~3을 건너뛰고 원본 검증으로 간다. 검증의 pull로 원본의 HEAD가 바뀌었으면(pull 전후 sha가 다르면) 지금 읽은 이 스킬이 옛 판일 수 있으니, 원본의 `payload/.claude/skills/project-init/SKILL.md`를 다시 읽고 이어 간다.
1. **기본 위치 `~/dev/app-harness`** 를 먼저 본다. `payload/`가 있으면 그게 원본이다.
2. 없으면 사용자에게 경로를 묻는다 — "하네스 저장소를 어디에 받아 두셨습니까?"
3. 아직 안 받았다면 clone을 제안한다:

   ```bash
   git clone https://github.com/youngdonkim/app-harness.git ~/dev/app-harness
   ```

   이 저장소는 공개라 https 주소면 로그인 없이 받는다. SSH 키를 등록해 둔 사람은 `git@github.com:youngdonkim/app-harness.git`로 받아도 된다.

   **clone 주소는 프로젝트에 버전 기록 파일(`.claude/harness-version`)이 있으면 거기 적힌 `repo=` 값이 먼저다** — fork로 쓰는 사용자면 그게 자기 fork 주소라서다. 버전 기록 파일이 없거나, 그 파일에 `origin=self` 줄이 있으면(그 프로젝트가 하네스 원본을 겸하던 시절의 기록이라 `repo=`가 프로젝트 자기 주소다) 위 기본 주소를 쓴다.

### 원본 검증 (필수 — 건너뛰지 않는다)

원본을 찾았으면 복사하기 전에 **반드시** 아래 순서를 전부 실행해 검증한다. 제안이 아니라 실행이다.

```bash
test -f <원본경로>/payload/.claude/skills/store-release/SKILL.md   # 0. 있어야 Flutter판 하네스다
git -C <원본경로> rev-parse --abbrev-ref HEAD    # main이어야 한다
git -C <원본경로> status --porcelain             # 출력이 비어 있어야 한다
git -C <원본경로> pull --ff-only origin main     # 반드시 실행
git -C <원본경로> rev-parse HEAD origin/main     # 두 sha가 같아야 한다
```

**어느 하나라도 어긋나면 중단**한다. 무엇이 문제고 사용자가 뭘 하면 되는지 안내한다:

- **`store-release` 스킬이 없음** → 찾은 저장소는 이 하네스가 아니다(웹 하네스처럼 `payload/` 구조가 같은 다른 하네스일 수 있다). 그대로 복사하면 프로젝트의 Flutter 하네스 파일이 전부 다른 하네스 것으로 덮인다. 찾은 경로를 알리고 app-harness를 받아 둔 경로를 다시 묻는다.
- **main이 아님** → 원본이 지금 어느 브랜치에 있는지 알려준다. 작업 중인 브랜치 내용이 프로젝트로 새어 나가면 안 되니, 원본에서 main으로 옮긴 뒤 다시 불러달라고 안내한다.
- **커밋 안 된 변경이 있음** → 그대로 복사하면 버전 기록 파일이 가리키는 커밋과 실제 복사되는 내용이 어긋난다고 짚고, 원본을 정리한(커밋하거나 되돌린) 뒤 다시 불러달라고 안내한다.
- **pull 실패** (네트워크 오류·충돌 등) → 중단한다. 낡은 원본을 복사하면 적용하자마자 뒤처진 상태가 되므로 그냥 진행하지 않는다.
- **HEAD와 origin/main이 다름** → 로컬 원본이 원격과 어긋난 상태라고 알리고 중단한다.

*왜 중단하나*: 검증을 건너뛰고 잘못된 원본을 복사하면 (가) 프로젝트가 조용히 미확정 내용이나 낡은 하네스, 엉뚱한 하네스를 갖게 되고, (나) 버전 기록 파일(`.claude/harness-version`의 `commit=`)이 "이 커밋 기준으로 맞췄다"는 거짓 값을 갖게 된다. 버전 기록 파일은 다음 동기화에서 프로젝트 파일이 그냥 뒤처진 것인지 프로젝트가 손댄 것인지 가르는 유일한 근거([로컬 수정 흔적 판별](#3-로컬-수정-흔적-판별))라, 한번 거짓이 되면 나중에서야 드러나고 되짚기도 어려운 사고로 이어진다.

검증을 통과했으면 **적용할 커밋을 기록해둔다**. 버전 기록 파일에 쓸 값이다:

```bash
git -C <원본경로> rev-parse --short=12 HEAD
```

### 동기화 모드만 — 프로젝트가 이 원본에서 받은 것인지 대조

동기화 모드에서는 검증에 이어 프로젝트의 `.claude/harness-version`을 원본과 대조한다. 원본 자리(`~/dev/app-harness`)에 fork나 다른 사본이 놓여 있으면, 다른 원본으로 프로젝트를 덮게 되기 때문이다.

```bash
git -C <원본경로> remote get-url origin   # 주소에서 「소유자/저장소」만 뽑는다(https://github.com/·git@github.com:·끝의 .git을 뗀다)
sed -n 's/^repo=//p;s/^commit=//p;/^origin=self/p' .claude/harness-version
git -C <원본경로> merge-base --is-ancestor <commit= 값> HEAD   # 성공해야 원본 이력에 있는 커밋이다
```

- **`repo=`가 원본 주소의 「소유자/저장소」와 같고 `commit=`이 원본 이력에 있다** → 보통 동기화다. 그대로 [동기화 모드 절차](#동기화-모드-절차)로 간다.
- **아래 셋 중 하나** → **옛 원본에서 넘어오는 첫 동기화**다. [동기화 모드 절차](#동기화-모드-절차)를 하되, 다른 파일 처리는 [옛 원본에서 넘어오는 첫 동기화](#옛-원본에서-넘어오는-첫-동기화)를 따른다. 시작할 때 「이 프로젝트의 버전 기록은 `<repo= 값>`(옛 원본)을 가리킵니다. 이번 동기화로 `<원본 주소>`를 기준으로 옮겨 맞춥니다」 한 줄을 알린다.
  - 버전 기록 파일에 `origin=self` 줄이 있다(프로젝트가 하네스 원본을 겸하던 시절의 기록)
  - `commit=`이 없거나 비어 있다
  - `commit=` 값이 원본 이력에 없다(`merge-base --is-ancestor`가 실패)
- **`commit=`은 원본 이력에 있는데 `repo=`만 다르다** → fork에서 원본으로(또는 그 반대로) 옮기는 경우일 수 있다. 덮어쓰기 전에 멈추고 묻는다 — 「이 프로젝트는 `<repo= 값>`에서 받은 하네스인데, 찾은 원본은 `<원본 주소>`입니다. 이 원본으로 맞출까요?」(예시 답: 「응, 이걸로 맞춰」, 「아니, fork 경로는 ~/dev/my-harness야」). 맞추기로 하면 보통 동기화로 하고, [버전 기록 파일 갱신](#6-버전-기록-파일-갱신)에서 `repo=`를 새 주소로 바꾼다. 사람이 바로 대답할 수 없는 동기화([동기화 모드 절차](#동기화-모드-절차) 맨 앞)면 새 파일 복사도 하지 않고 여기서 멈춰 이 질문을 보고한다 — 다른 원본의 파일은 하나도 안전하지 않다.

## 모드 판별

[전제 확인 1번](#전제-확인)의 판별 그대로다 — 옆 폴더 경로·예외 경로는 **신규 적용 모드**(아래 [진행 순서](#진행-순서-신규-적용-모드)), 현재 폴더에 `.claude/harness-version`이 있으면 **동기화 모드**(아래 [동기화 모드 절차](#동기화-모드-절차)). 판별은 늘 대상 폴더 기준이고, 하네스 원본 저장소 자신은 동기화 대상이 아니다. `CLAUDE.md`는 하네스와 상관없이 프로젝트가 스스로 갖고 있을 수 있어 판별에 쓰지 않는다.

## 진행 순서 (신규 적용 모드)

신규 적용은 **로컬 단계**(1~8단계: 인터뷰·파일 복사·훅 등록·버전 기록 파일·첫 커밋 — 이 컴퓨터 안에서 끝나는 일)와 **원격 단계**(9단계: `github-connect` — GitHub 저장소 생성·첫 push). 그다음 10단계 마무리 안내 한 번. 사용자에게 브랜치·커밋·PR을 손으로 하라고 넘기지 않는다.

두 길의 절차는 같다. 다른 점은 둘뿐이다 — ① 모든 일이 대상 폴더에서 일어난다(옆 폴더 경로면 [명령 형태](#대상-폴더-정하기--옆-폴더-경로)대로 `cd <대상 절대 경로> && …`), ② 10단계 마무리 안내가 길마다 다르다. 옆 폴더 경로는 허용 창을 줄이려고 로컬 단계의 파일 만들기(폴더·`git init -b main`·payload 복사·`chmod`·`mvp/`, 그다음 만들 파일 쓰기)를 몇 번의 Bash 호출로 묶어도 된다 — 로컬 단계에는 훅이 막는 명령이 없다. 원격 단계는 `github-connect`의 「한 번에 한 단계씩」을 따른다.

### 1. 시작 인터뷰 (소유 1질문)

사용자에게 하나만 묻는다 — 이미 대화에서 나왔으면 생략:

- **이 프로젝트의 소유 — 개인입니까, 회사입니까, 아니면 다른 조직입니까?** (예시 답: 「회사」, 「개인」, 「동아리 — 영문 짧은 이름은 club」) — 외부 서비스(GitHub·Firebase·구글 플레이 콘솔·OAuth·광고·AI 키)를 어느 계정으로 만들지가 이 답으로 갈린다. 아이디어가 아니라 관리 질문이지만, 계정이 잘못 묶이면 나중에 리소스를 전부 다시 만들게 되어(idea-to-mvp `4-0-backend-prep.md`) 처음에 받는다. **개인/회사를 구분할 필요가 없는 사용자면**(모든 프로젝트를 같은 계정으로 만들면) **「개인」이다**. 회사·개인이 아닌 조직이면 장부 파일 이름에 쓸 영문 짧은 이름(소문자·숫자·하이픈)을 함께 받는다.

**서비스 이름·한 줄 정의·타겟은 여기서 묻지 않는다** — idea-to-mvp 1단계 인터뷰의 질문 1·2라, 1단계가 코칭 규칙(되묻기·고쳐 써서 확인받기·한 항목당 최대 2번)대로 받아 확정하고 `AGENTS.md`에 써넣는다. *왜*: 여기서 코칭 없이 차갑게 받으면 설치 때 대충 한 답이 `AGENTS.md`에 적히고, 1단계가 그걸 확인만 하고 넘어가 그 첫 답에 묶인 채 확정된다. 설치 단계엔 이름·타겟이 꼭 필요한 곳도 없다 — `AGENTS.md` 제목과 저장소 이름은 폴더 이름으로 충분하다.

- 사용자가 대화에서 서비스 이름·정의·타겟을 **이미 말했으면** 묻지 않고 그 말을 초안으로 받아 적는다 — 프로젝트 정의 줄의 해당 자리에 그 말을 쓰고 바로 뒤에 `(초안 — 1단계에서 확정)`를 붙인다. 1단계가 이 표시를 보고 초안으로 다듬는다.
- **안 했으면** 빈 자리 표시 `(1단계 인터뷰에서 채움)`를 그대로 둔다. 1단계가 이 표시를 보고 새로 묻는다.

소유 답은 [3단계](#3-agentsmd-생성)에서 `AGENTS.md`의 「소유와 계정」 표·소유 문장과 `.claude/owner`를 함께 쓰는 데 쓴다. 값은 셋 중 하나다 — 개인 `personal`, 회사 `company`, 조직 `org-<영문 짧은 이름>`.

**`mvp/intent.md`가 이미 있으면**(1단계를 다른 곳에서 끝내고 산출물을 들고 온 프로젝트) 그 「1. 서비스」에서 서비스 이름·한 줄 정의·타겟을 읽어 아래 「이미 말했으면」과 같은 초안으로 쓴다 — 빈 자리 표시로 두면 1단계가 이미 끝난 질문을 다시 묻는다.

### 2. CLAUDE.md 생성

프로젝트 루트에 `CLAUDE.md`를 만들고 **내용을 정확히 `@AGENTS.md` 한 줄로** 쓴다. 템플릿은 없다 — 이 파일은 규칙을 담지 않고, 클로드 코드가 규칙 정본인 `AGENTS.md`를 읽게 하는 포인터일 뿐이다. 이미 있고 내용이 그 한 줄이면 그대로 둔다. 다른 내용이 들어 있으면 지우거나 덮어쓰지 않는다 — 3단계에서 `AGENTS.md`를 만든 뒤 [CLAUDE.md 이행 절차](#claudemd--한-줄로-줄이되-옛-내용은-확인받고-옮긴다)대로 확인받고 옮긴다.

*왜 한 줄만 두나*: 클로드 코드는 버전·실행 환경에 따라 `AGENTS.md`를 혼자 읽지 못한다. 그래서 어디서 열어도 규칙이 읽히도록 이 포인터를 남기되, 규칙 자체는 한 파일에만 둔다.

### 3. AGENTS.md 생성

`AGENTS.md`는 이 프로젝트의 **규칙 정본**이다. 클로드뿐 아니라 Codex 같은 다른 AI 도구도 이 파일을 읽는다.

- 프로젝트 루트에 `AGENTS.md`가 **없으면** 원본의 `payload/AGENTS.md.template`을 프로젝트 루트에 `AGENTS.md`로 복사하고 자리 표시를 아래 표대로 처리한다. 템플릿 구조는 **수정하지 않고 그대로** — 하네스 표준이다.

  | 템플릿의 자리 표시 | 있는 곳 | 이 단계에서 |
  |---|---|---|
  | `{{폴더 이름}}` | 제목 `# {{폴더 이름}}`, 계정 표의 Firebase 두 행(`{{폴더 이름}}-dev`·`{{폴더 이름}}-prod`), 「이 프로젝트가 쓰는 도구」의 「환경은 2단이다」 줄 | 전부 프로젝트 폴더 이름으로 바꾼다. Firebase 프로젝트 ID는 예정값이다 — 이미 쓰인 ID면 4-0에서 실제 ID로 고친다 |
  | `{{개인 \| 회사 \| 조직 이름}}` | 「소유와 계정」 절의 「이 프로젝트의 소유」 문장 | [1번](#1-시작-인터뷰-소유-1질문)의 소유 답(개인·회사·조직 이름) |
  | 그 밖의 `{{…}}`(`{{계정 (이메일)}}`·`{{이메일}}` 등) | 「소유와 계정」 표의 값 | 아래 「소유와 계정」 항목대로 받은 값. 모르는 항목은 `(확인 필요)` |
  | `(1단계 인터뷰에서 채움)` | 프로젝트 정의 줄(서비스 이름·한 줄 정의·타겟) | 그대로 둔다. 1번에서 받아 둔 초안이 있으면 그 자리에 초안과 `(초안 — 1단계에서 확정)`를 적는다 |
  | `(2-0 개발환경 준비에서 채움)` | 「이 프로젝트가 쓰는 도구」 첫 줄의 앱 패키지 이름 | 그대로 둔다. 2-0이 패키지 이름을 확정하며 채운다 |

  자리 표시 없이 값이 적힌 행(플레이 업로드 키 보관 위치, 애플 개발자 계정 `해당 없음 (iOS 출시 때 정한다)`)은 그대로 둔다. 다 쓴 뒤 `grep -n '{{' AGENTS.md`의 출력이 비어 있어야 한다 — 남은 `{{…}}`가 있으면 위 표에서 빠뜨린 자리다.
- **idea-to-mvp 방법론 설명은 `AGENTS.md`에 넣지 않는다** — 방법론은 스킬 발동 중에만 필요하고 스킬이 전부 관리한다. `AGENTS.md`는 만드는 제품(앱)과 사용자 취향의 자리다.
- **「소유와 계정」 표는 1번의 소유 답과 함께 사용자에게 물어 채운다** — 서비스별 계정·이메일을 아는 만큼만 받고, 모르는 항목은 `(확인 필요)`로 둔다 — 그 서비스가 처음 필요해지는 때(플레이 콘솔은 3단계 배포 전, Firebase는 4-0, 광고·MMP는 6단계 앞) 확정되면 채운다. 계정 값은 이 프로젝트 표에만 남는다 (하네스에는 계정을 적지 않는다).
- **소유 선언 `.claude/owner`를 쓴다** — 한 줄 `owner=<1번의 값>`. 커밋되는 파일이라 팀원도 같은 소유로 돈다. `AGENTS.md` 「소유와 계정」 절의 「이 프로젝트의 소유: **개인/회사/<조직 이름>**」 문장과 **같은 값**이어야 한다 — 둘을 이 자리에서 함께 쓴다. 하네스 소유물이 아니라 프로젝트 파일이라 동기화가 지우거나 덮어쓰지 않는다.
- **이 컴퓨터의 계정 장부 자리를 만든다** — 키는 프로젝트가 아니라 `~/.config/harness/<소유>.env`(폴더 700, 파일 600, git 저장소 밖)에 둔다. 같은 소유의 프로젝트끼리 한 파일을 나눠 쓴다. 파일이 이미 있으면 그대로 쓴다(다른 프로젝트가 받아 둔 키가 들어 있다).
  ```bash
  o=$(sed -n 's/^owner=//p' .claude/owner); mkdir -p "$HOME/.config/harness" && chmod 700 "$HOME/.config/harness" && touch "$HOME/.config/harness/$o.env" && chmod 600 "$HOME/.config/harness/$o.env"
  ```
  키 값(GitHub 토큰 등)은 여기서 넣지 않는다 — 원격 단계의 `github-connect` ⑤가 채운다(토큰 받는 길 셋). 키를 부르는 법(실행기 `.claude/scripts/with-owner.sh`)과 이유는 `payload/docs/account-check.md`(프로젝트에 복사되면 `docs/account-check.md`) gh 항목에 있다.
- **「커밋 작성자」 행은 표만 채우지 않고 이 저장소의 로컬 git 설정(작성자 이름·이메일)도 같이 맞춘다** — 장부에 `GIT_USER_NAME`·`GIT_USER_EMAIL`이 있으면 그 값을 쓰고(같은 소유의 다른 프로젝트가 넣어 둔 것), 없으면 사용자에게 받아 로컬 git 설정과 장부 두 곳에 쓴다(장부 쓰기는 `github-connect` 「장부에 키 한 줄 쓰기」 모양). 전역 설정은 건드리지 않는다(같은 컴퓨터에 다른 소유의 프로젝트가 있다). GitHub은 커밋을 작성자 이메일로 계정에 묶어서, 표와 다르면 이 프로젝트의 커밋이 다른 소유의 계정 기록으로 쌓인다.
- **이미 있으면** 파일을 지우거나 덮어쓰지 않는다. `<!-- BEGIN:project-rules -->` 마커 구역이 없을 때만, 템플릿의 마커 구역(placeholder를 채운 상태)을 파일 맨 끝에 덧붙인다.
- **다른 도구가 자동으로 만든 구역은 절대 건드리지 않고 그대로 둔다** — `<!-- BEGIN:project-rules -->` 말고 다른 이름의 `<!-- BEGIN:… -->` 마커 구역이 그렇다. 우리 마커 구역만 우리가 관리하고 나머지는 그 도구 몫이다.
- 2단계에서 만든 `CLAUDE.md`의 내용이 정확히 `@AGENTS.md`인지 확인한다.

### 4. payload 미러 복사

원본의 `payload/` 아래 파일을 프로젝트 루트에 **같은 경로로 통째로 복사**한다 (폴더 없으면 생성). 원본의 구조가 곧 프로젝트에 놓일 모양이라, 무엇을 어디로 옮길지 따로 셀 필요가 없다.

```
<원본>/payload/.claude/  →  <프로젝트>/.claude/   (skills·agents·hooks·scripts·rules·templates — settings-hooks.json 빼고)
<원본>/payload/docs/     →  <프로젝트>/docs/      (git-workflow.md·account-check.md)
<원본>/payload/.github/  →  <프로젝트>/.github/   (workflows/ci.yml)
```

**복사에서 빼는 파일 셋** — 미러 규칙의 예외는 이 셋뿐이다. 그대로 놓이는 파일이 아니라서 빠진다.

- `payload/AGENTS.md.template` — 복사 대상이 아니라 가공 대상. [3단계](#3-agentsmd-생성)에서 이미 썼다.
- `payload/.claude/settings-hooks.json` — 복사 대상이 아니라 병합 원본. 다음 단계에서 내용만 합친다.
- `payload/gitignore.template` — 복사 대상이 아니라 프로젝트 `.gitignore`의 원본. [8단계](#8-로컬-단계-마무리--비밀-파일-검사와-첫-커밋)에서 줄 단위로 넣는다.

훅 스크립트와 실행기에 실행 권한을 준다: `chmod +x <프로젝트>/.claude/hooks/*.sh <프로젝트>/.claude/scripts/*.sh`

이번에 들어오는 것 중 설명이 필요한 둘 — `docs/git-workflow.md`는 `no-main-push`·`auto-wip-commit` 훅과 `new-task`·`done-task`·`rewind-task` 스킬이 따르는 워크플로를 사람이 읽게 정리해둔 문서고, `.github/workflows/ci.yml`은 `done-task`가 머지 전에 통과를 기다리는 CI다 — `pubspec.yaml`이 없으면(앱 코드가 아직 없으면) 통과 처리되고, 생기면 형식·정적 분석·테스트·개발용 빌드를 돈다(서버 함수 `functions/`와 보안 규칙도 생기면 같은 식으로 검사가 붙는다).

### 5. 훅 등록 — settings.json 병합

원본의 `payload/.claude/settings-hooks.json`은 **훅 등록 원본**이다. 이 파일의 `hooks` 블록을 프로젝트의 `.claude/settings.json`에 병합한다.

- 프로젝트에 `settings.json`이 없으면 그 내용 그대로 새로 만든다.
- 있으면 **기존 키를 전부 보존한 채** `hooks` 블록만 넣는다. 프로젝트가 이미 자기 훅을 등록해뒀다면 지우지 말고, 같은 이벤트 안에 하네스 훅을 덧붙인다 — 겹치는 하네스 훅(같은 스크립트 경로)은 하나만 남긴다.

경로는 `"$CLAUDE_PROJECT_DIR"/.claude/hooks/<이름>.sh` 형태라 프로젝트를 어디에 두든 그대로 작동한다.

`.claude/settings.json`은 저장소에 커밋되는 파일이라, 이 상태로 main에 합쳐두면 팀원 전원에게 똑같이 적용된다.

### 6. 폴더 정리

```
mvp/                   # 단계 산출물 (market-research.md 등이 단계 진행하며 생김)
docs/                  # 사람이 읽는 문서 (Claude 자동 로드 X)
```

### 7. 버전 기록 파일 쓰기

프로젝트에 `.claude/harness-version` 파일을 만든다. 다음 동기화 때 이 값을 기준으로 프로젝트 쪽 하네스 파일이 그냥 낡은 것인지 로컬에서 손본 것인지 가른다([로컬 수정 흔적 판별](#3-로컬-수정-흔적-판별)).

```
repo=youngdonkim/app-harness
commit=<하네스 원본 찾기에서 구한 12자리 이상 커밋 sha>
date=<오늘 날짜 YYYY-MM-DD>
```

`repo=`는 원본 저장소 주소다. 포크해서 쓴다면 그 주소로 적는다 — 나중에 이 프로젝트의 하네스가 어디서 왔는지 알아보는 값이다.

### 8. 로컬 단계 마무리 — 비밀 파일 검사와 첫 커밋

1. **`.gitignore` 넣기** — 원본의 `payload/gitignore.template`이 원본이다. 프로젝트에 `.gitignore`가 **없으면** 그 내용을 그대로 `.gitignore`로 쓴다. **있으면** 지우거나 덮어쓰지 않고, 템플릿 줄 가운데 프로젝트 파일에 없는 줄만 파일 끝에 덧붙인다 — 빈 줄과 `#` 주석 줄은 대조하지 않고, 덧붙일 줄이 있으면 그 앞에 `# --- app-harness gitignore.template에서 더한 줄 ---` 한 줄을 둔다(이 머리줄이 이미 있으면 다시 넣지 않는다). 키는 프로젝트 밖 장부에 두지만, 업로드 키·서비스 계정 키 같은 키 파일이 실수로 프로젝트 안에 생겨도 올라가지 않게 템플릿이 막아 둔다.
   ```bash
   t=<원본경로>/payload/gitignore.template
   if [ ! -f .gitignore ]; then cp "$t" .gitignore
   else
     add=$(grep -vE '^[[:space:]]*(#|$)' "$t" | while IFS= read -r l; do grep -qxF -- "$l" .gitignore || printf '%s\n' "$l"; done)
     if [ -n "$add" ]; then
       h='# --- app-harness gitignore.template에서 더한 줄 ---'
       grep -qxF -- "$h" .gitignore || printf '\n%s\n' "$h" >> .gitignore
       printf '%s\n' "$add" >> .gitignore
     fi
   fi
   ```
2. **비밀 파일 검사** — 이미 추적 중이거나 커밋 대상이 될 파일 가운데 비밀 파일이 보이면 **멈추고 보고한다.** 기준은 `auto-wip-commit` 훅의 시크릿 패턴과 같다(`.env`·`.env.*`·`*.key`·`*.pem`·`secret`·`credentials.json`·`id_rsa`·`id_ed25519`·`*.jks`·`*.keystore`·`key.properties`·`*service-account*.json`(`serviceAccount`도) — 끝이 `.example`·`.sample`·`.template`인 예시 파일은 뺀다). 두 패턴은 늘 같이 고친다.
   ```bash
   { git ls-files; git status --porcelain --untracked-files=all | sed -E 's/^...//'; } \
     | grep -iE '(^\.env$|/\.env$|^\.env\.|/\.env\.|\.key$|\.pem$|secret|credentials\.json$|id_rsa|id_ed25519|\.jks$|\.keystore$|(^|/)key\.properties$|service-?account[^/]*\.json$)' \
     | grep -ivE '\.(example|sample|template)$'
   ```
   출력이 있으면 그 파일을 `.gitignore`에 넣을지(이미 추적 중이면 추적에서 뺄지) 사용자에게 묻고, 정리된 뒤에 커밋한다.
3. **첫 커밋** — 하네스가 넣은 파일과, 이미 있던 1단계 산출물(`mvp/` 안 파일 — 들고 온 `intent.md`·`design-brief.md` 등)을 담는다. `mvp/`를 빼면 main에 미추적으로 남아 첫 `/new-task`가 따로 처리해야 한다. 그 밖에 원래 있던 미커밋 파일은 건드리지 않고 마무리 안내에 적는다.
   ```bash
   git add -- CLAUDE.md AGENTS.md .gitignore .claude docs/git-workflow.md docs/account-check.md .github/workflows/ci.yml
   [ -d mvp ] && git add -- mvp
   git commit -m "chore: app-harness 하네스 적용 (<적용한 하네스 커밋>)"
   ```
   **main에 바로 커밋한다 — 부트스트랩 예외다.** 프로젝트 `AGENTS.md` 브랜치 절에 적힌 "main에서 직접 작업하지 않는다"의 유일한 예외(하네스 첫 적용 커밋과 그 첫 push)다. 빈 저장소라 리뷰할 화면도 배포도 없다. (옆 폴더 경로에서는 하네스 저장소의 같은 훅이 돈다 — `auto-wip-commit`은 세션 폴더인 하네스 저장소를 보고, 하네스 저장소는 main이라 건너뛴다. 예외 경로에서는 훅이 벌써 잡혀 있을 수도 있다 — main에서 쉬니 이 커밋과 부딪히지 않는다.)

   **예외에 안 드는 경우** — 원격 main에 이미 작업 이력이 있는 저장소(원래 쓰던 저장소에 하네스를 처음 얹는 경우)는 main이 곧 실서비스라 예외가 아니다. 원격이 있으면(`git remote get-url origin` 성공) 로컬의 `origin/main`을 본다 — `git rev-list --count origin/main`이 1이고 `git ls-tree --name-only origin/main`이 `README.md`·`.gitignore`·`LICENSE` 안에 드는 경우(GitHub에서 저장소를 만들 때 생긴 첫 커밋뿐)만 예외에 든다. 그 밖이면 `git switch -c chore/harness-apply`로 작업 브랜치를 열어 거기에 같은 커밋을 하고, 마무리 안내(앱 재시작 안내 바로 뒤)에서 "다시 열린 세션에서 화면을 확인하시고 '보내줘'라고 말씀하시면 `/done-task`로 합치겠습니다"라고 알린다. (원래 쓰던 저장소는 예외 경로로만 들어온다 — 옆 폴더 경로는 비어 있는 새 폴더만 받는다.)

### 9. 원격 단계 — `github-connect` 호출

`github-connect`를 Skill 도구로 호출하고, **대상 폴더의 절대 경로를 넘긴다**(인자 `<대상 절대 경로>`). github-connect는 그 폴더를 기준으로 모든 명령을 돈다 — 넘기지 않으면 세션 폴더를 대상으로 삼아, 옆 폴더 경로에서는 하네스 저장소를 보고 "이미 연결됨"으로 거짓 성공을 낼 수 있다. 옆 폴더 경로에서는 하네스 저장소 세션에 이미 잡혀 있는 `github-connect`를 쓴다. 예외 경로에서 스킬이 안 잡혀 있으면(방금 복사한 `.claude/`라 목록에 없다) 원본의 `payload/.claude/skills/github-connect/SKILL.md`를 읽고 그대로 실행한다. git·gh 설치, GitHub 계정·토큰(계정 장부), 계정 확인, HTTPS push 인증 방식, 저장소 생성, 첫 push까지 거기서 끝난다. 사람 몫(가입·로그인·권한 창)이 나오면 `github-connect`가 한 단계씩 안내하고 멈췄다가 이어간다.

사용자가 GitHub 연결을 지금은 미루자고 하면 억지로 하지 않는다 — 마무리 안내에 "나중에 '깃헙 연결해줘'라고 말씀하시면 이어서 진행합니다. 그 전에는 `/new-task`·`/done-task`가 동작하지 않습니다"라고 남긴다.

### 10. 마무리 안내

보고·안내는 ~입니다 체로 쓴다.

`github-connect`의 마무리 보고와 합쳐 **한 번에** 알린다. 두 길에 공통으로 알리는 것:

- 방금 대상 폴더(옆 폴더 경로면 그 절대 경로를 적는다)에 들어온 것: `CLAUDE.md`, `AGENTS.md`, `.gitignore`, `.claude/`(skills·agents·hooks·scripts·rules·templates·settings.json·harness-version·owner), `docs/git-workflow.md`, `docs/account-check.md`, `.github/workflows/ci.yml`. **8단계에서 첫 커밋으로 main에 들어갔고, 9단계에서 GitHub에 올라갔다** — 팀원은 프로젝트를 clone하는 것만으로 하네스를 그대로 받는다. 팀원이 하네스 저장소를 따로 받을 필요는 없다. 8단계에서 건드리지 않은 원래 파일(미커밋)이 있었으면 그 목록도 알린다.
- 키 자리: 이 컴퓨터의 `~/.config/harness/<소유>.env` — 프로젝트 밖이라 커밋되지 않고, 같은 소유의 다른 프로젝트와 나눠 쓴다. 팀원은 clone한 뒤 자기 컴퓨터에서 「깃헙 연결해줘」로 자기 장부를 채운다.
- 훅 3개가 자동 작동: `no-main-push`(main 직접 push 차단), `owner-runner-guard`(gh·Firebase CLI·FlutterFire CLI·fastlane 명령을 실행기 없이 부르면 차단 — 컴퓨터에 남은 다른 계정 로그인으로 도는 것을 막음. `--project dev`·`--project prod` 없는 firebase 명령, 실서비스 데이터 지우기, 평문 비밀번호·개인 키가 든 커밋도 막는다), `auto-wip-commit`(응답 끝날 때마다 feature 브랜치에 wip 커밋 — main에서는 자동으로 건너뛴다). 뭔가 잘못돼서 되돌리고 싶으면 `/rewind-task` 스킬을 쓴다.
- 그다음부터 파일을 바꾸는 작업은 `/new-task`로 브랜치를 열고 `/done-task`로 합친다 — 클로드가 알아서 부른다. (idea-to-mvp가 `mvp/` 산출물을 보고 현재 단계를 스스로 판별하니, 이미 진행한 프로젝트면 알아서 이어서 시작한다.)

**옆 폴더 경로 — 마지막 말.** 재시작 안내는 하지 않는다(새 세션이 열 때부터 다 잡는다). 이렇게 끝낸다:

> 이제 `<대상 절대 경로>`에서 새 세션을 여세요. 터미널이면 `cd <대상 절대 경로>` 뒤 `claude`를 실행하고, 데스크톱 앱이면 새 대화를 열고 그 폴더를 고르시면 됩니다. 열고 `/idea-to-mvp`를 치거나 '인터뷰 시작하자'라고 하면 1단계가 시작됩니다. 지금 이 세션(하네스 저장소)에서는 1단계를 시작하지 마세요 — 산출물이 하네스 저장소에 쌓입니다.

**예외 경로 — 마지막 말.** 앱 재시작 안내는 **여기서 한 번만** 한다. 이 세션은 `.claude/` 폴더 없이 열려 새로 깐 스킬·에이전트를 끝까지 못 잡기 때문이다. 이렇게 끝낸다:

> 하네스 적용과 GitHub 연결이 다 끝났습니다. 새로 넣은 스킬·에이전트가 잡히도록 앱을 한 번 껐다 켜 주세요(대화는 안 날아갑니다 — 대화를 버리는 `/clear`와는 다릅니다). 다시 열리면 `/idea-to-mvp`를 치거나 '인터뷰 시작하자'라고 하면 1단계가 시작됩니다.

예외 경로에서 재시작 전에 알아 둘 것(AI용):

- 재시작 전에 스킬을 써야 하면 `.claude/skills/<이름>/SKILL.md`를 읽어 같은 절차를 따르되 임시다. `/reload-skills`로 스킬만 먼저 잡을 수도 있다.
- 에이전트는 재시작 전까지 안 잡힌다. **정의된 에이전트를 못 찾으면 오류 없이 일반 에이전트(메인 모델)로 조용히 떨어진다** — 정해 둔 모델·도구 제한이 빠지니, 에이전트를 쓰는 스킬(`new-task`·`ship-task` 등)은 재시작 뒤에 부른다.
- 훅과 `.claude/rules/`는 복사 즉시 이 세션에 잡힌다(실측 2026-10-19) — 그래서 첫 push에서 `no-main-push` 훅이 먼저 돈다(`github-connect` ⑦을 혼자 먼저 실행하라는 이유). `AGENTS.md`는 컴팩션이나 `/clear`부터.

## 동기화 모드 절차

이미 하네스가 적용된 프로젝트에서는 신규 복사 대신, 프로젝트에 있는 파일을 원본과 비교해 갱신한다. 먼저 [하네스 원본 찾기](#하네스-원본-찾기)로 원본 위치를 확인하고 원본 검증을 마친다.

**사람이 바로 대답할 수 없는 동기화** — 다른 세션이나 다른 에이전트가 시킨 동기화(예: 하네스 저장소 세션이 옆 프로젝트를 맞추라고 시킴)는 그 자리에 대답할 사람이 없다. 이 절차의 「확인받고 쓴다」·「사용자에게 묻는다」 자리를 만나면 멈추지도, 혼자 정하지도 않는다. 그 항목은 쓰지 않고 남겨 두고, 확인 없이 해도 되는 것(동일 파일 넘기기, 새 파일 복사, 옛 버전과 같아 뒤처진 것만 확인된 파일 교체, `.gitignore`에 빠진 줄 덧붙이기)만 하고 끝까지 간다. 남겨 둔 항목 — 지울 파일 목록, 충돌 파일과 다른 곳(옛 원본에서 넘어오는 첫 동기화면 「전부 원본으로 / 하나씩」 질문), `AGENTS.md` 병합안 요지, `CLAUDE.md` 옮길 안 — 을 [7. 마무리 보고](#7-마무리-보고)에 「확인이 필요한 것」 한 묶음으로 모아 시킨 쪽에 돌려준다. 시킨 쪽이 사람에게 한 번에 물어 답을 받은 뒤 다시 부르면 그 항목만 반영한다. 1번 미커밋 검사에 걸리거나 [원본 대조](#동기화-모드만--프로젝트가-이-원본에서-받은-것인지-대조)에서 `repo=`만 다른 원본이 나오면, 덮어쓰기 전에 거기서 멈추고 걸린 것을 보고한다(덮어쓰면 되돌릴 수 없다).

**payload 미러로 온 파일은 전부 하네스 소유물**이고, **`AGENTS.md` 하나만 예외**다. `.claude/owner`·`.claude/harness-version`·`.claude/settings.json`(hooks 블록 밖)·`.claude/settings.local.json`은 payload에 없는 프로젝트 파일이라 「원본에서 사라짐」으로 지우지 않는다. `.gitignore`도 프로젝트 파일이다 — 원본 `payload/gitignore.template`에 새로 생긴 줄만 덧붙이고 덮어쓰지 않는다([5번](#5-폴더와-gitignore-보정)). `CLAUDE.md`는 `@AGENTS.md` 한 줄짜리 포인터라 하네스 소유물로 다룬다 — 다만 옛 구조로 만든 프로젝트는 여기에 규칙이 들어 있을 수 있어, 확인 없이 줄이지 않는다([4. AGENTS.md — 예외 하나, 병합이 기본](#4-agentsmd--예외-하나-병합이-기본)).

### 1. 프로젝트 쪽 미커밋 검사

**먼저 지금 프로젝트가 main 브랜치에 있는지 본다.**

```bash
git branch --show-current
```

- **main이면 `/new-task`를 직접 호출해 작업 브랜치를 연 뒤 동기화를 이어간다.** 사용자에게 되묻지 말고 클로드가 연다. 이유는 짧게 짚어준다 — `auto-wip-commit`(턴이 끝날 때마다 바뀐 파일을 알아서 커밋해두는 훅)은 작업 브랜치에서만 돈다. main에서 그대로 동기화하면 바뀐 파일이 커밋 안 된 채 쌓여 되돌릴 지점이 안 남고, 나중에 `no-main-push` 훅에 막혀 올리지도 못한다.
- **main이 아니면** — 그대로 다음으로 넘어간다.

동기화는 하네스 소유 파일을 **원본 내용으로 덮어쓴다.** 그 전에 프로젝트 쪽에 커밋 안 된 변경이 있는지도 먼저 본다 — 있는 채로 진행하면 되돌릴 수 없이 사라진다.

```bash
git status --porcelain -- .claude docs/git-workflow.md docs/account-check.md .github/workflows/ci.yml
```

- **출력이 있으면** 멈추고 사용자에게 묻는다. 이 파일들을 곧 덮어쓸 참이라 커밋하거나 되돌린 뒤 다시 진행해야 한다고 짚고, 걸린 파일 목록을 보여준다.
- **하네스 소유 경로 밖의 미커밋 변경은 상관없다** — 동기화가 안 건드리는 파일이라 그대로 두고 진행한다.

### 2. 하네스 소유물 — 교체가 기본

프로젝트에서 고치지 않는 전제의 파일들이다. 하네스가 관리하니 **원본 내용으로 교체**하는 게 기본이다.

- `payload/.claude/*` ↔ `.claude/*` (skills·agents·hooks·scripts·rules·templates — `settings-hooks.json`은 아래 hooks 블록으로 따로)
- `payload/docs/*` ↔ `docs/git-workflow.md`·`docs/account-check.md`
- `payload/.github/workflows/ci.yml` ↔ `.github/workflows/ci.yml`
- `payload/.claude/settings-hooks.json`의 hooks 블록 ↔ `.claude/settings.json`의 hooks 블록

처리 갈래:

- **동일** → 넘어간다.
- **프로젝트에 없음** (원본에 새로 생긴 파일) → 복사한다.
- **원본에서 사라짐** (이름이 바뀌었거나 폐기된 파일) → 프로젝트에서도 지운다. 지우기 전에 목록으로 보여주고 확인받는다.
- **다름** → 아래 [로컬 수정 흔적 판별](#3-로컬-수정-흔적-판별)로 갈라진다.

`settings.json`은 파일 전체가 아니라 **hooks 블록만** 하네스 소유물이다. 나머지 키(`permissions`·`env` 등 프로젝트가 넣은 것)는 손대지 않는다.

교체한 훅 스크립트와 실행기에는 실행 권한을 다시 준다: `chmod +x .claude/hooks/*.sh .claude/scripts/*.sh`

**파일을 교체한 뒤 이 스킬을 새 판으로 다시 읽는다** — 지금 따르는 본문은 동기화 전 프로젝트에 있던 옛 판일 수 있다(스킬을 부른 순간 들어온 본문이다). 이 절에서 `.claude/skills/project-init/SKILL.md`가 교체됐으면 그 파일을 디스크에서 다시 읽고, 3번 이후(로컬 수정 흔적 판별·AGENTS.md 병합·마무리 보고)는 새 판대로 한다. (웹 하네스 실사고 2026-10-22 시험: 옛 본문에는 「사람이 바로 대답할 수 없는 동기화」가 없어, 디스크의 새 판을 읽고서야 그 절차를 알았다.)

### 3. 로컬 수정 흔적 판별

하네스 소유물인데 프로젝트 쪽이 원본과 다를 때, 그냥 뒤처진 것인지 프로젝트가 손댄 것인지 가른다.

- **원본의 옛 버전과 같다** → 그냥 뒤처진 것이다. 조용히 교체한다.
  - 옛 버전은 버전 기록 파일의 `commit=` 값으로 꺼낸다: `git -C <원본경로> show <버전기록커밋>:payload/<프로젝트에서의 경로>`
- **원본의 옛 버전과도 다르다** → 프로젝트가 로컬에서 고친 흔적이다. **충돌로 보고 사용자에게 묻는다** — 어디가 어떻게 다른지 짚어주고 (a) 원본으로 교체 (b) 로컬 수정 유지 중 고르게 한다. 임의로 정하지 않는다.
- 버전 기록 파일이 없거나 그 커밋에서 파일을 못 찾으면(그때는 payload 안 경로가 달랐으면) 판별할 수 없다 → 안전하게 **충돌로 보고 물어본다**.
- 버전 기록 파일의 커밋이 원본 이력에 아예 없으면(옛 원본에서 넘어오는 첫 동기화) 모든 「다름」이 판별 불가다 → 아래 [옛 원본에서 넘어오는 첫 동기화](#옛-원본에서-넘어오는-첫-동기화)대로 한 번에 묻는다.

#### 옛 원본에서 넘어오는 첫 동기화

[원본 대조](#동기화-모드만--프로젝트가-이-원본에서-받은-것인지-대조)에서 「옛 원본에서 넘어오는 첫 동기화」로 갈렸으면, 버전 기록 파일로 옛 버전을 꺼낼 수 없어 「다름」인 파일이 하나도 빠짐없이 판별 불가가 된다. 파일이 수십 개라 하나씩만 물으면 사람이 같은 답을 수십 번 해야 하니, 이렇게 묻는다.

1. **다른 파일을 한 목록으로 먼저 보여 준다** — 파일마다 경로와 다른 곳의 요지 한 줄(`diff --stat` 줄 수와, 눈에 띄는 차이 한 가지).
2. **한 번에 고를 길을 먼저 묻는다** — 「원본과 다른 하네스 파일이 N개입니다. 어떻게 할까요? (가) 전부 원본으로 교체 (나) 하나씩 고르기」(예시 답: 「전부 원본으로」, 「하나씩 볼게」). (나)면 파일마다 (a) 원본으로 교체 (b) 프로젝트 것 유지를 묻고, 도중에 「남은 것 전부 원본으로」도 고를 수 있게 한다.
3. **「원본에 없는 파일」은 따로 묻는다** — 프로젝트 `.claude/`에 있는데 원본 `payload/.claude/`에 없는 파일은, 원본에서 사라진 것인지 프로젝트가 스스로 더한 것인지 가릴 수 없다. 지우는 쪽을 기본으로 두지 않는다 — 목록을 보여 주고 「전부 남김 / 전부 지움 / 하나씩」 가운데 고르게 한다.
4. **프로젝트 고유 파일은 이 갈래에서도 건드리지 않는다** — `mvp/`, `lib/`(앱 코드 전체), `docs/` 안의 하네스 문서 둘(`git-workflow.md`·`account-check.md`) 말고 다른 문서, `.claude/owner`, `.claude/settings.json`의 hooks 밖 키. `AGENTS.md`는 [4번](#4-agentsmd--예외-하나-병합이-기본) 병합으로만 바꾸고, 계정 표·서비스 정의·패키지 이름 같은 프로젝트 값은 그대로 남긴다. `.gitignore`는 [5번](#5-폴더와-gitignore-보정)대로 빠진 줄만 덧붙인다.
5. **버전 기록 파일은 새 모양으로 다시 쓴다** — [6번](#6-버전-기록-파일-갱신)에서 `origin=self`·`forked-from=` 같은 옛 줄을 지우고 `repo=`·`commit=`·`date=` 세 줄로 쓴다. `repo=`는 이번 원본 주소다.

사람이 바로 대답할 수 없는 동기화면 1번 목록과 2번 질문을 「확인이 필요한 것」 한 항목으로 남긴다(고를 길: 「전부 원본으로 / 하나씩」). 3번도 같다. 이때 하는 일은 동일 파일 넘기기와 새 파일 복사뿐이다 — 옛 버전과 대조할 수 없으니 「뒤처진 것만 확인된 파일 교체」에 드는 파일이 없다.

### 4. AGENTS.md — 예외 하나, 병합이 기본

`AGENTS.md`는 프로젝트가 자기 사정에 맞게 채우고 덧붙이는 규칙 정본이라 덮어쓰지 않는다. 비교도 파일 전체가 아니라 **템플릿(`payload/AGENTS.md.template`)에서 온 부분만** 한다.

- **보존 대상 (대조 안 함)** — placeholder가 채워진 프로젝트 고유 내용(서비스 이름·한 줄 정의·타겟, 「소유와 계정」 표에 채워진 값)과 프로젝트가 스스로 추가한 문장·섹션(디자인 시스템 adapter에 채워진 경로, 앱 개발 컨벤션에 쌓인 규칙 등). 템플릿과 다른 게 정상이고, 병합해도 그대로 남는다.
- **대조 대상** — 템플릿에서 그대로 오는 공용 문구와 구조. 작업 원칙 섹션, 진행 방식·기획 문서 위치 안내문, 섹션 골격과 제목, 그 안에 들어 있는 단계 번호 같은 것. 신규 적용 모드에서 "수정하지 않고 그대로" 복사하는 부분([3. AGENTS.md 생성](#3-agentsmd-생성))이 곧 이 범위다.
- **대조·병합 범위는 `<!-- BEGIN:project-rules -->` 구역 안으로만 한정한다.** 마커 밖과 다른 이름의 `<!-- BEGIN:… -->` 구역(다른 도구가 만든 구역)은 절대 건드리지 않는다.

**자리 표시가 있는 줄은 대조하지 않는다** — [3. AGENTS.md 생성](#3-agentsmd-생성) 표의 다섯 가지(`{{폴더 이름}}`·`{{개인 | 회사 | 조직 이름}}`·계정 표의 `{{…}}`·`(1단계 인터뷰에서 채움)`·`(2-0 개발환경 준비에서 채움)`)가 든 줄 — 제목, 프로젝트 정의 줄, 소유 문장, 계정 표 값, Firebase 프로젝트 ID가 든 줄, 앱 패키지 이름 줄 — 은 낡은 공용 문구가 아니라 자리 표시다. 프로젝트 쪽 값(확정 문구든 초안 표시든 빈 자리 표시든)을 그대로 둔다 — 템플릿의 빈 자리 표시로 되돌리면 1단계에서 확정한 정의, 2-0에서 정한 패키지 이름, 4-0에서 고친 Firebase 프로젝트 ID가 사라진다. 같은 줄의 자리 표시 밖 문구가 바뀌었으면 그 부분만 병합안에 넣는다.

*왜 대조하나*: 공용 문구는 하네스가 바뀌면 같이 낡는다. 예를 들어 하네스가 단계 수를 바꿔 `/idea-to-mvp`가 7단계가 되면 프로젝트 AGENTS.md에 남은 "6단계로 검증·개발한다"가 틀린 안내가 되는데, 파일 전체를 비교에서 빼두면 아무도 못 잡는다.

다르면 **병합이 기본 동작이다.** AI가 곧장 병합안을 만든다 — 프로젝트 고유 내용은 그대로 두고 공용 문구만 최신으로 맞춘다. 무엇이 어떻게 합쳐지는지 요지를 한 줄씩 모아 보여주고, 사용자가 확인하면 반영한다.

병합에는 안전 규칙 둘이 있다:

- **진짜 충돌은 AI가 임의로 정하지 않는다** — 같은 대목을 템플릿과 프로젝트가 서로 다르게 고쳤으면, 그 대목만 양쪽 내용을 나란히 짚어 어느 쪽으로 갈지 사용자에게 물어본다. 안 겹치는 나머지는 그대로 합친다.
- **확인 없이 파일에 쓰지 않는다** — 병합도 예외가 아니다. 병합안을 보여주고 사용자 확인을 받은 뒤에만 파일을 고친다.

병합안을 본 사용자가 다른 걸 원하면 (a) 템플릿 공용 문구로 교체 (b) 지금 내용 그대로 유지 중에 고를 수 있다 (기본이 아닌 예외 경로다).

나머지 갈래:

- 마커 구역이 아예 없으면 템플릿의 마커 구역을 파일 맨 끝에 덧붙인다. 파일 자체가 없으면 [3. AGENTS.md 생성](#3-agentsmd-생성)대로 템플릿에서 새로 만든다.
- 병합으로 「소유와 계정」 표가 **처음 들어오는** 옛 프로젝트면, 소유(개인/회사)와 서비스별 계정을 사용자에게 물어 채운다 ([3. AGENTS.md 생성](#3-agentsmd-생성)과 같은 방식).
- 「소유와 계정」 절처럼 **템플릿의 규칙 문단이 크게 줄어든 경우** — 규칙 문단은 템플릿대로 줄이고, 표의 행과 채워진 값은 그대로 둔다.
- **프로젝트가 하네스 원본을 겸하던 때의 문단** — 옛 원본에서 넘어오는 첫 동기화면, 프로젝트 `AGENTS.md`에 「이 저장소가 하네스의 원본이다」를 전제한 문장(하네스 파일을 이 저장소에서 바로 고친다, 다른 하네스의 개선을 손으로 옮긴다, `origin=self` 같은 것)이 남아 있을 수 있다. 템플릿의 같은 절 문단(프로젝트 안의 하네스 사본은 고치지 않고 고칠 내용을 문안으로 넘긴다)으로 바꾸는 안을 병합안에 넣는다.
- **템플릿에서 표의 행이 빠진 경우** — 프로젝트 표에 그 행의 값이 채워져 있으면 지우지 않고 그대로 둔다. 채운 값은 프로젝트 소유물이고, 그 행을 쓰는 절차가 그 프로젝트에 아직 남아 있을 수 있다. 값 없이 `{{…}}` 자리 표시만 남은 행은 템플릿대로 빼는 쪽으로 병합안에 넣는다.

#### CLAUDE.md — 한 줄로 줄이되, 옛 내용은 확인받고 옮긴다

`CLAUDE.md`는 규칙을 담지 않는 포인터라 **내용이 정확히 `@AGENTS.md` 한 줄인지만 확인한다.** 그 한 줄이면 손대지 않고 넘어간다.

**그 밖의 내용이 들어 있으면 옛 구조로 만든 프로젝트다** — 예전에는 위임 원칙 같은 규칙이 이 파일에 있었다. 그 내용은 규칙이지 찌꺼기가 아니므로 **지우지 않는다.** 이행 절차는 이렇다:

1. `@AGENTS.md` 줄 말고 남아 있는 내용을 전부 뽑아, 무엇이 들어 있는지 사용자에게 **그대로 보여준다.**
2. 각 대목을 `AGENTS.md`의 어느 절로 옮길지 안(案)을 함께 보여준다. 이미 `AGENTS.md`에 같은 규칙이 있으면 "옮길 필요 없음(중복)"으로 표시하고, 없으면 옮길 자리를 짚는다.
3. **사용자 확인을 받은 뒤에** 그 내용을 `AGENTS.md`로 옮긴다 (위 병합 안전 규칙 둘이 그대로 적용된다).
4. 옮기기가 끝난 다음에야 `CLAUDE.md`를 `@AGENTS.md` 한 줄로 줄인다.

**확인 없이 지우거나 줄이지 않는다.** 사용자가 옮기지 말라고 하면 `CLAUDE.md`를 그대로 두고, 그 사실을 마무리 보고에 적는다.

### 5. 폴더와 .gitignore 보정

`mvp/`·`docs/` 폴더는 신규 모드와 동일하게, 없으면 채운다.

`.gitignore`는 [신규 8단계 1번](#8-로컬-단계-마무리--비밀-파일-검사와-첫-커밋)의 명령을 그대로 돌린다 — 없으면 템플릿으로 만들고, 있으면 템플릿에 새로 생긴 줄만 끝에 덧붙인다. 프로젝트가 넣은 줄은 지우지 않는다. 덧붙인 줄이 있으면 마무리 보고에 그 줄들을 적는다.

### 6. 버전 기록 파일 갱신

반영이 끝나면 `.claude/harness-version`의 `commit=`을 이번에 적용한 원본 커밋으로, `date=`를 오늘 날짜로 갱신한다. 파일이 없으면 [7. 버전 기록 파일 쓰기](#7-버전-기록-파일-쓰기) 형식으로 새로 만든다. 옛 원본에서 넘어오는 첫 동기화면 `repo=`도 이번 원본 주소로 바꾸고, 그 세 줄 말고 남은 옛 줄(`origin=self`·`forked-from=` 등)은 지운다.

**사용자가 로컬 수정을 유지하기로 골라서 원본과 다른 파일이 남았어도 버전 기록 파일은 갱신한다** — 버전 기록 파일은 "언제 기준 원본과 맞춰봤나"를 가리키는 값이지 "모든 파일이 원본과 똑같다"는 보증이 아니다. 다만 남은 차이는 마무리 보고에 반드시 적는다.

### 7. 마무리 보고

보고·안내는 ~입니다 체로 쓴다.

**두 갈래가 드러나게** 나눠 보고한다.

- **하네스 소유물** (스킬·에이전트·훅·실행기·rules·templates·git-workflow.md·account-check.md·ci.yml·훅 등록) — 교체됨 / 새로 복사됨 / 삭제됨 / 로컬 수정 유지됨(사용자가 고름) / 전부 최신. 옛 원본에서 넘어오는 첫 동기화면 그 사실과 「전부 원본으로 / 하나씩」 가운데 무엇을 골랐는지, 프로젝트 것을 유지한 파일 목록을 함께 적는다
- **.gitignore** — 그대로 / 템플릿에서 덧붙인 줄(그 줄 목록) / 새로 만듦
- **AGENTS.md** — 병합됨 / 템플릿으로 교체됨(사용자가 고름) / 그대로 유지됨(사용자가 고름) / 최신 / 새로 만듦
- **CLAUDE.md** — `@AGENTS.md` 한 줄 그대로 / 옛 내용을 AGENTS.md로 옮기고 한 줄로 줄임 / 옛 내용을 그대로 둠(사용자가 고름)

- **확인이 필요한 것** — 사람이 바로 대답할 수 없는 동기화([동기화 모드 절차](#동기화-모드-절차) 맨 앞)에서 남겨 둔 항목 전부를 한 묶음으로. 항목마다 무엇을 어떻게 바꿀 안인지와 고를 수 있는 길을 한 줄씩 적는다. 없으면 이 줄은 뺀다.

끝에 버전 기록 파일을 어느 커밋으로 갱신했는지 적는다. 확인이 필요한 것이 남았으면 버전 기록 파일은 갱신하되, 남은 것이 있다는 것을 같은 자리에 적는다. 그다음 커밋 안내는 지금 어느 브랜치에 있었는지에 따라 다르게 준다:

- **작업 브랜치에서 진행했으면** — `auto-wip-commit` 훅이 턴마다 알아서 커밋해뒀을 테니, `/clear` 뒤 `/done-task`로 PR을 만들어 main에 합치면 된다고 안내한다.
- **main에 서 있으면** — 동기화 모드는 1단계에서 작업 브랜치를 먼저 여니 정상 흐름에선 이 갈래가 안 나온다. 신규 적용 직후라면 첫 커밋·첫 push가 이미 끝나 있어([8](#8-로컬-단계-마무리--비밀-파일-검사와-첫-커밋)·[9](#9-원격-단계--github-connect-호출)단계) 따로 할 일이 없다. 그런데도 main에 미커밋 변경이 남아 있으면 클로드가 `git switch -c <작업 브랜치>`로 변경을 들고 옮긴 뒤 `/done-task`로 합친다 — 사용자에게 손으로 하라고 넘기지 않는다.

**반영 시점도 함께 알린다** — 스킬·에이전트·훅은 `.claude/` 폴더가 이미 있던 세션이라 지금 세션에 잡힌다(새로 들어온 스킬은 몇 초 뒤, 에이전트는 응답을 한 번 끝낸 다음 턴부터다 — 같은 턴에서 바로 부르면 「없음」이 나거나 일반 에이전트로 떨어진다. 훅은 바뀐 다음 명령부터 돈다). 그래도 안 잡히면 앱을 껐다 켠다 — 대화는 안 날아간다. `AGENTS.md`는 컴팩션이나 `/clear`부터. **바뀐 스킬은 같은 세션에서 다시 불러도 옛 본문이 들어올 수 있다** — 동기화 직후 그 스킬을 이어 쓰면 `.claude/skills/<이름>/SKILL.md`를 직접 읽어 따르라고(또는 `/reload-skills`) 함께 알린다.

## 안 하는 것 (의도적)

- ❌ 앱 스캐폴딩(`pubspec.yaml`·`lib/`) 생성 — 그건 idea-to-mvp 2단계 개발환경 준비(`2-0-dev-setup.md`) 영역. 목업 캔버스 틀(`.claude/templates/mockup-canvas/`)도 복사만 하고 `lib/`에 펼치지 않는다
- ❌ GitHub 저장소 생성·push를 이 스킬 본문에서 직접 하기 — 원격 쪽은 `github-connect`가 한다 (신규 적용 [9단계](#9-원격-단계--github-connect-호출)에서 호출)
- ❌ 기존 AGENTS.md 무단 덮어쓰기 — 동기화 모드에서도 프로젝트 고유 내용은 병합으로 보존하고, 반영은 사용자 확인 뒤에만. AGENTS.md 안에서 다른 도구가 만든 구역도 손대지 않는다
- ❌ 옛 프로젝트의 CLAUDE.md 내용 무단 삭제 — `@AGENTS.md` 말고 다른 내용이 있으면 AGENTS.md로 옮길 안을 보여주고 확인받은 뒤에만 줄인다
- ❌ 하네스 원본 저장소를 프로젝트에서 고치기 — 하네스 개선은 app-harness 저장소에서 PR로. 프로젝트 `.claude/` 안의 복사본을 고쳐봐야 다음 동기화에서 충돌로 잡힌다
- ❌ 프로젝트 `.claude/settings.json`의 hooks 이외 키 건드리기
- ❌ 프로젝트 `.gitignore`의 줄 지우기·덮어쓰기 — 템플릿에 새로 생긴 줄만 덧붙인다
- ❌ 동기화(옛 원본에서 넘어오는 첫 동기화 포함)에서 `mvp/`·`lib/`·`.claude/owner`·`AGENTS.md`의 프로젝트 값 건드리기
- ❌ 하네스 원본 저장소 자신에 적용·동기화하기 — 하네스 저장소 세션은 옆 폴더를 만들 때만 쓴다
- ❌ 하네스 저장소 안에 새 프로젝트 폴더 만들기 — 대상은 늘 하네스 저장소의 부모 폴더 아래다
- ❌ 옆 폴더 경로에서 하네스 저장소에 브랜치 열기(`/new-task`) — 원본 검증이 「원본은 main」을 요구한다
