이 문서는 3단계 배포 전 검사 ②(`3-frontend-build.md` §2.5.3)에서 쓰는 **코드 품질 점검표**입니다. 점검표에 든 것은 화면을 눌러 봐서는 안 보이지만, 실제 앱에서 멈춤·느려짐·데이터 꼬임·비용으로 터지는 것들입니다. 이전 앱에서 확인한 교훈과 Flutter 공식 문서가 권하는 것을 함께 담았습니다.

**쓰는 법** — 메인이 이 문서를 읽고, 아래 「점검표」 절을 sonnet 에이전트 하나의 지시서 `<data>`에 그대로 붙입니다. 에이전트는 항목마다 `lib/`(생성 파일 `*.g.dart`·`*.freezed.dart` 제외)를 보고 위반을 고칩니다. 「패키지」 항목은 웹을 조회해야 해서 메인이 직접 합니다. 화면 겉모습·문구·디자인 값은 바꾸지 않습니다 — 그것은 검사 ①·③과 사람의 눈이 맡습니다.

**언제 다시 돌리나** — 3단계 배포 전에 한 번, 그 뒤로는 화면이나 저장·조회 코드를 크게 고친 라운드마다 돌립니다. 4단계 이후에는 「4단계부터」 표시가 붙은 항목도 봅니다.

## 1. 점검표

항목마다 「무엇을 · 왜 · 찾는 법 · 고치는 법」입니다. 찾는 법의 grep은 실마리일 뿐이라, 걸린 줄은 열어 보고 판단합니다.

### 1.1 화면과 수명

**Q1. 기다린 뒤에 화면 정보(`BuildContext`)를 쓰기 전에 화면이 아직 살아 있는지 확인한다**

- 왜: `await` 뒤에 그 화면이 이미 닫혔으면, 그 화면의 정보로 화면 이동·알림 띠·대화상자를 띄우는 순간 오류가 나거나 엉뚱한 화면에 뜹니다. 저장 버튼을 누르고 바로 뒤로 가는 사람이 흔합니다.
- 찾는 법: `await` 다음 줄들에서 `context.`·`Navigator`·`ScaffoldMessenger`·`showDialog`·`context.go`/`push`를 쓰는 곳. `flutter analyze`의 `use_build_context_synchronously` 경고도 봅니다.
- 고치는 법: 위젯 안이면 `if (!context.mounted) return;`(상태 클래스 안이면 `if (!mounted) return;`)을 `await` 바로 뒤에 둡니다.

**Q2. 만든 것은 닫을 때 정리한다**

- 왜: `TextEditingController`·`AnimationController`·`ScrollController`·`FocusNode`·`StreamSubscription`·`Timer`를 정리하지 않으면 화면을 오갈 때마다 메모리가 새고, 닫힌 화면이 계속 일을 합니다.
- 찾는 법: 위 이름을 만드는 상태 클래스마다 `dispose()`에서 같은 것을 정리하는지. 구독(`.listen(`)·`Timer(`가 있는 파일.
- 고치는 법: `dispose()`에서 `.dispose()`·`.cancel()`을 부릅니다. Riverpod provider 안이면 `ref.onDispose`로 정리합니다.

**Q3. `build` 안에서 무거운 일을 하지 않는다**

- 왜: `build`는 화면이 다시 그려질 때마다(글자 하나 칠 때도) 다시 돕니다. 그 안에서 정렬·JSON 해석·저장소 읽기·provider 만들기를 하면 화면이 버벅이고, 저장소를 매번 부릅니다.
- 찾는 법: `build(` 안의 `.sort(`·`jsonDecode`·`SharedPreferences`·저장·조회 함수 호출·`Future`를 만드는 줄.
- 고치는 법: 계산은 provider(필요하면 파생 provider)로 옮겨 결과만 읽고, 불러오기는 provider가 한 번 합니다. `FutureBuilder`에 `build` 안에서 새로 만든 `Future`를 넘기지 않습니다.

**Q4. 바뀌지 않는 위젯은 `const`로 만든다**

- 왜: `const`인 위젯은 다시 그릴 때 건너뛰어 화면이 가벼워집니다.
- 찾는 법: `flutter analyze`의 `prefer_const_constructors` 계열 안내.
- 고치는 법: 안내대로 `const`를 붙입니다. 이것 때문에 구조를 바꾸지는 않습니다.

### 1.2 목록과 이미지

**Q5. 순서가 바뀌거나 항목이 빠지는 목록에는 key를 준다**

- 왜: key가 없으면 Flutter가 항목을 자리 순서로만 짝지어, 하나를 지우면 옆 항목의 입력값·펼침 상태·움직임이 엉뚱한 항목에 붙습니다.
- 찾는 법: `ListView.builder`·`AnimatedList`·`Column(children: [...map(...)])`으로 그리는 항목 중 상태가 있거나(입력칸·체크·펼침) 지우기·순서 바꾸기가 되는 것.
- 고치는 법: 항목 위젯에 `key: ValueKey(item.id)`를 줍니다. 자리 번호(`index`)를 key로 쓰지 않습니다.

**Q6. 긴 목록은 보이는 만큼만 그린다**

- 왜: `Column`이나 `ListView(children: [...])`에 수백 개를 한꺼번에 넣으면 화면을 열 때 전부 그려 느려집니다.
- 찾는 법: 데이터 개수만큼 늘어나는 목록을 `ListView(children:`·`Column`·`SingleChildScrollView` + `Column`으로 그리는 곳.
- 고치는 법: `ListView.builder`·`SliverList`로 바꿉니다.

**Q7. 큰 그림을 원본 크기로 풀지 않는다**

- 왜: 폰 사진(수천 화소)을 작은 썸네일 자리에 그대로 풀면 그림 하나에 수십 MB 메모리를 씁니다. 목록에 여러 장이면 오래된 폰에서 앱이 꺼집니다.
- 찾는 법: `Image.file`·`Image.network`·`Image.memory`·`Image.asset`·`DecorationImage` 중 크기가 작은 자리에 쓰인 것.
- 고치는 법: `cacheWidth`(또는 `ResizeImage`)로 그 자리에 필요한 크기만큼만 풀게 합니다. 자리 폭은 `LayoutBuilder`로 받은 폭 × 기기 화소 배율입니다.

### 1.3 데이터와 오류

**Q8. 저장·조회는 `Result`로 돌려주고, 예외를 화면까지 던지지 않는다**

- 왜: 예외가 화면까지 올라오면 화면마다 따로 잡거나, 잡지 못해 빨간 오류 화면이 뜹니다. `Result`(「성공 또는 실패」)와 `AppError`의 네 갈래(네트워크·권한 없음·찾을 수 없음·알 수 없음)로 돌려주면 화면이 갈래마다 상태 표의 오류 화면을 고릅니다.
- 찾는 법: 각 흐름 `data/`의 공개 함수 중 돌려주는 꼴이 `Future<Result<…>>`가 아닌 것, `throw`가 있는 것. 화면의 `try {`.
- 고치는 법: `Result.guard`로 감싸고, 아는 예외는 알맞은 갈래로 바꿉니다. 화면은 `Result`의 갈래로 그립니다.

**Q9. 기기 안 저장소 읽기 실패를 처리한다**

- 왜: 저장된 JSON이 깨졌거나(앱을 올리며 데이터 모양이 바뀜) 읽기가 실패하면, 처리하지 않은 앱은 켤 때마다 멈춥니다. 지우고 다시 까는 것 말고는 사용자가 빠져나갈 길이 없습니다.
- 찾는 법: `jsonDecode`·`fromJson`·`SharedPreferences`를 쓰는 `data/` 코드 중 실패를 `Result`로 감싸지 않은 곳.
- 고치는 법: 읽기·해석을 `Result.guard`로 감싸, 깨진 값은 실패 값이 되게 합니다. 모양이 바뀌는 판이면 옛 모양을 읽는 길이나 「새로 시작」 길을 둡니다. 비밀번호·개인정보는 이 저장소에 넣지 않습니다.

**Q10. 화면은 저장소를 직접 부르지 않는다**

- 왜: 화면이 `SharedPreferences`(4단계부터는 Firestore)를 직접 부르면 그 화면만 상태 흉내(`?state=`)가 안 먹고, 4단계에서 저장소를 바꿀 때 그 화면만 따로 고쳐야 합니다.
- 찾는 법: `grep -rn 'SharedPreferences' lib/features/*/screens lib/features/*/widgets lib/shared`(2-1·3단계 문서와 같은 명령).
- 고치는 법: 그 흐름의 `data/`로 옮기고 provider로 꺼냅니다.

**Q11. 바깥 객체는 생성자로 받는다**

- 왜: 저장·조회 코드가 저장소나 Firebase 객체를 안에서 직접 꺼내면(`.instance`·`getInstance()`), 테스트에서 가짜를 넣을 수 없고 개발용·실서비스용 프로젝트가 섞일 틈이 생깁니다.
- 찾는 법: `data/`·`lib/shared`에서 `.instance`·`getInstance(` 호출(디자인 규칙 검사 14번이 Firebase 쪽을 함께 잡습니다).
- 고치는 법: provider가 만든 객체를 생성자로 받습니다(앱 뼈대 틀 README 「코드 규칙 둘」).

**Q12. 상태 흉내는 저장·조회 코드 맨 앞 한 곳에서만 읽는다**

- 왜: 화면이 상태 흉내 값을 직접 읽으면, 캔버스에서 본 상태 화면이 실제 처리 경로와 다르게 그려집니다.
- 찾는 법: `devStateProvider`·`devGuestProvider`를 `lib/features/*/screens`·`widgets`에서 읽는 곳.
- 고치는 법: 저장·조회 함수 맨 앞의 `devStateAnswer`로 옮깁니다.

### 1.4 상태 관리와 화면 이동

**Q13. `build` 안에서는 `ref.watch`, 단추를 눌렀을 때는 `ref.read`**

- 왜: `build` 안에서 `ref.read`를 쓰면 값이 바뀌어도 화면이 안 바뀌고, 단추 처리 안에서 `ref.watch`를 쓰면 쓸데없이 다시 그려집니다.
- 찾는 법: `build(` 안의 `ref.read(`, `onPressed`·`onTap` 안의 `ref.watch(`. `riverpod_lint` 안내.
- 고치는 법: 위 원칙대로 바꿉니다.

**Q14. 화면을 떠나면 필요 없는 provider는 버려진다**

- 왜: 한 화면에서만 쓰는 불러오기 provider가 계속 살아 있으면, 다시 들어왔을 때 옛 값이 보이고 메모리를 붙잡습니다.
- 찾는 법: 코드 생성 provider 중 `keepAlive: true`인 것, 손으로 만든 provider 중 화면 전용인데 자동 버리기가 아닌 것.
- 고치는 법: 앱 전체가 쓰는 것(로그인 상태 등)만 오래 살리고, 나머지는 기본(자동 버리기)으로 둡니다.

**Q15. 경로는 경로 모음에서 꺼낸다**

- 왜: 화면마다 `'/meetings/…'`를 글자로 쓰면, 경로를 바꿀 때 한 곳이 빠져 죽은 이동이 생깁니다.
- 찾는 법: `context.go('`·`context.push('`·`GoRoute(path: '` 중 `lib/app/paths.dart` 밖에서 글자로 쓴 경로.
- 고치는 법: `paths.dart`의 이름으로 바꿉니다.

### 1.5 글자와 문구

**Q16. 글자 배율에 견딘다**

- 왜: 폰 설정에서 글자를 키운 사람에게 글자가 잘리거나 겹칩니다. 이전 앱에서 확인한 교훈: 넘치는 곳은 거의 늘 세 자리였습니다.
- 찾는 법: ① 높이를 숫자로 고정한 상자 안의 `Text`(디자인 규칙 검사 12번) ② `Row` 안의 `Text`가 `Expanded`·`Flexible` 없이 있는 곳 ③ `GridView`의 `childAspectRatio`. 그리고 화면마다 글자 배율 2.0 위젯 테스트가 있는지.
- 고치는 법: ① 최소 높이만 둡니다 ② `Expanded`·`Flexible`로 감싸거나 줄바꿈을 허용하고, `maxLines`를 쓰면 `overflow: TextOverflow.ellipsis`를 같이 ③ 비율을 글자 배율에 맞춰 바꾸거나 내용 높이를 따르는 배치로. 빠진 화면에는 배율 2.0 테스트를 더합니다(design-system 스킬 bootstrap-project.md §1.7의 도우미). 앱 전체에서 글자 배율을 막는 코드는 넣지 않습니다.

**Q17. 화면 글자는 문구 파일에서 꺼낸다**

- 왜: 화면 코드에 글자를 직접 쓰면 문구 검사(검사 ③)가 놓치고, 나중에 언어를 더할 때 화면을 다 뒤져야 합니다.
- 찾는 법: 디자인 규칙 검사 16번, 그리고 `SnackBar(content: Text(`·`hintText: '`·`labelText: '`·`tooltip: '`·`semanticLabel: '`처럼 `Text(` 밖에서 글자를 직접 쓴 곳.
- 고치는 법: `.arb` 문구 파일에 키를 더하고 그 키로 꺼냅니다. 문구 내용은 바꾸지 않고 옮기기만 합니다 — 고치는 것은 검사 ③ 몫입니다.

**Q18. 디버그 출력이 남지 않는다**

- 왜: `print`는 실서비스 앱의 기기 기록에도 남아, 개인정보가 섞이면 새어 나갑니다.
- 찾는 법: `print(`(`flutter analyze`의 `avoid_print`).
- 고치는 법: 지우거나 `debugPrint`로 바꿉니다. 개인정보·토큰은 어느 쪽으로도 찍지 않습니다.

### 1.6 Firebase (4단계부터)

**Q19. 실시간 구독은 화면이 사라지면 끊는다**

- 왜: Firestore 실시간 구독(`snapshots()`)을 끊지 않으면, 닫힌 화면 몫까지 읽기가 계속 쌓여 요금과 배터리를 씁니다.
- 찾는 법: `.snapshots()`·`.listen(`이 있는 `data/` 코드와 그것을 쓰는 provider.
- 고치는 법: `StreamProvider`(자동 버리기)로 두거나 `ref.onDispose`에서 `cancel()`합니다.

**Q20. 목록 항목마다 따로 읽지 않는다**

- 왜: 목록을 그리며 항목마다 다른 문서를 하나씩 읽으면(작성자 이름 등) 목록 한 번에 읽기가 항목 수만큼 늘어 요금이 커지고 느려집니다.
- 찾는 법: 목록 항목 위젯이나 항목마다 부르는 provider 안의 `.doc(…).get()`.
- 고치는 법: 목록에 필요한 값은 문서에 함께 담거나(작성자 이름 복사), 한 번에 묶어 읽습니다. 묶는 방식은 4-1 문서의 규칙을 따릅니다.

### 1.7 패키지

**Q21. 관리가 끊긴 패키지를 들이지 않는다 — 메인이 직접**

- 왜: 이전 앱에서 확인한 교훈: 관리가 끊긴 아이콘 패키지 하나 때문에 Flutter 판을 올리자 컴파일이 깨졌습니다.
- 찾는 법: `fvm flutter pub outdated`, 그리고 2·3단계에 새로 들인 패키지마다 pub.dev 페이지의 최근 발행일·지원 플랫폼(안드로이드·iOS)·관리 주체.
