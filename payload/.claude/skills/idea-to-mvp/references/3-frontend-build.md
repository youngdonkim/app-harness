이 단계는 **관문이 아닙니다** — 거르기는 마지막 단계(MvpLaunch)의 광고 실측에서 한 번만 합니다(SKILL.md §1.1). 이 단계는 광고 앞에 내놓을 물건의 앞면(화면)을 완성하는 자리입니다.

**이 단계 이름이 프런트엔드 구현(FrontendBuild)인 이유** — 여기서 하는 일이 딱 그것입니다. 2단계 코드에 남은 화면을 더하고, 빠진 화면이 없는지 대조하고, 움직임을 입히고, 폰에 깔리는 판으로 내보냅니다. **새로 짓지 않고 이어서 짓습니다** — 2단계에서 만든 Flutter 코드가 곧 앱의 화면이고, 이 단계는 그 코드 위에 남은 화면과 상태 화면을 더합니다. **이 앱 코드는 버리는 물건이 아닙니다** — 4단계(BackendBuild)가 같은 코드에 Firebase를 얹어 실서비스로 완성합니다. 처음부터 끝까지 앱은 하나입니다.

**용어 세 개를 섞지 않습니다.**

- **목업 캔버스** — 만든 화면들을 보통 폰(아이폰 16 폭)·작은 폰(갤럭시 S 폭) 크기 창으로 흐름 순서대로 펼쳐 iPad 시뮬레이터(맥 안의 가상 아이패드)에 띄우는 개발용 앱입니다. 진입점(앱이 시작하는 첫 파일) `lib/main_canvas.dart`로만 빌드되므로 실서비스 앱에는 들어가지 않습니다. 사람이 모든 화면을 한눈에 보는 도구이지 산출물이 아닙니다. 쓰는 법은 틀 `.claude/templates/mockup-canvas/README.md`가 정본입니다.
- **워킹 프로토타입(working prototype)** — 기기 안 저장소로 데이터가 도는 앱. 이 단계 끝의 **앱 상태를 가리키는 말**이지 단계 이름이 아닙니다. 백엔드가 아직 없다는 뜻일 뿐, 이 코드를 나중에 버린다는 뜻이 아닙니다. 「프로토타입」은 문서에서 늘 수식어를 달고 씁니다.
- **내부 테스트** — 구글 플레이 콘솔의 시험 트랙(같은 앱을 정해진 사람에게만 먼저 내보내는 통로) 가운데, 이메일 목록에 든 사람만 받는 가장 가벼운 트랙입니다. 이 단계의 「배포」는 여기에 올리는 일입니다.

## 1. 단계 목표

이 단계의 목표는 **2단계 코드에 남은 화면을 더해 화면 목록을 다 채우고, 움직임을 입혀 플레이 내부 테스트에 올려 실제 폰에 깔리는 앱을 만드는 것**입니다. 네 스텝으로 갑니다.

1. **남은 화면 만들기** (§2.2) — 공통 부품을 먼저 만들고, 화면 목록에서 `만드는 때 = 3단계`인 화면과 상태 표의 `O` 칸 중 아직 없는 상태 화면을 2단계 코드에 더합니다. 이미 있는 화면은 다시 만들지 않습니다. **화면 + 기기 안 저장소까지**입니다(백엔드 없음).
2. **대조·사람 확인** (§2.3) — 화면 ID마다 경로와 상태 화면이 코드에 있는지 대조하고, `feature-list.md` 머리에 `화면 대조 끝:`을 적고, 고르지 않은 비교안을 지운 뒤 사람이 목업 캔버스와 폰에서 앱을 봅니다.
3. **움직임 + 배포 전 검사 + 코드 정리** (§2.4·§2.5) — 화면에 움직임을 입히고, 화면 밖 검사와 배포 전 검사 세 가지(디자인 규칙 · 코드 품질 · 화면 문구)를 통과한 뒤, 2·3단계 코드를 한 번 정리합니다.
4. **배포** (§2.6) — main에 합친 커밋으로 앱 번들을 만들어 플레이 내부 테스트에 올립니다. 지인·팀 동료는 참가 링크로 받아 씁니다.

산출물은 **프로젝트 루트의 앱 코드 + 내부 테스트에 올린 판** 둘입니다. **앱 코드가 본 산출물이고, 4단계가 그대로 이어받습니다** — 백엔드가 없을 뿐 실서비스가 될 코드 그 자체입니다. 그래서 이 단계는 「나중에 다시 짤 거니까 대충」이 통하지 않습니다(§4). 목표를 이뤘는지는 §3 완료 체크리스트로 판정합니다.

**입력은 넷이고 맡은 역할이 다릅니다.**

- **`feature-list.md` 6~10절 — 빠짐 없음 담당.** 어떤 화면을 몇 개 만들지, 빈 상태·오류 같은 상태 화면까지 무엇을 빠뜨리지 않을지가 여기서 나옵니다. **화면 목록과 상태 표가 곧 빠짐 점검표입니다** — `MVP 포함 = O` 화면이 전부 「주소」(go_router 경로)를 갖고, 상태 표의 `O` 칸이 전부 `?state=` 값을 가져야 이 단계 앞부분이 끝납니다. 메뉴 구조(8절)가 메뉴 형태의 정본입니다.
- **2단계 코드 — 생김새의 본보기이자 이어 지을 바탕.** 2단계가 만들고 2-2가 다듬고 2-3이 개성을 입힌 화면, 1·2층 토큰(브랜드 면 `AppBrand`·제목 서체 포함), 셸, 감싸개 부품, 공통 부품, 저장·조회 코드, 가짜 저장소가 이미 있습니다. 이 단계가 더할 화면은 이 코드를 그대로 쓰고 같은 모양으로 만듭니다. 2-2 비교안의 빈 상태·로딩 화면이 상태 화면의 본보기입니다. 빈 상태 화면의 그림 자리는 2-3 비교안의 빈 상태가 본보기입니다(2-3을 건너뛰었으면 해당 없음). 2-4 머무는 공간을 썼으면 공간 부품(`lib/shared/components/{수단}/{공간_id}/`)과 그 내용 판(아래에서 올라오는 판)도 여기 든다.
- **`design-brief.md` — 말투·고정 문구·화면 규칙의 정본.** 확정 브랜드 자산·보이스 앤 톤·「문자 그대로」 고정 문구·UI 패턴 지정·모션·접근성 바닥선·가치 우선순위·「12. 화면 규칙」·「13. 개성」(고른 판·조작 방식·은유 행 포함. 2-3을 건너뛰었으면 `건너뜀` 한 줄)·「14. 머무는 공간」(상태·공간 움직임·누른 뒤·진동·소리 — 공간 지시서 `mvp/spaces/{공간 id}.md`를 가리킵니다)이 전부 여기 있습니다. 참고 자료가 아니라 **지시**입니다.
- **`intent.md` — 화면 순서·원하는 것 자료.** 사람이 어떤 순서로 어떤 화면을 거치는지(「5. 유저 플로우」), 무엇을 원하고 그래서 어디에 힘을 줄지(「3. 원하는 것」), 함께 정한 화면 모양(「6. 함께 정한 것」)이 여기서 나옵니다. 플로우 표의 핵심 행동은 그 화면에 **어떤 요소가 있어야 하는지**로 읽을 자료이지 문구·배치의 스펙이 아닙니다.

하나라도 빠지면 안 됩니다. 화면 목록만 보면 생김새가 제각각이 되고, 이미 있는 코드만 보면 상태 화면이 빠지고, 브리프가 빠지면 문구와 규칙이 흔들리고, `intent.md`가 빠지면 어디에 힘을 줄지가 흐려집니다.

**무엇이 정본인가** — 화면 생김새·흐름·상태·디자인 값의 정본은 2단계에서 화면을 만든 순간부터 Flutter 코드입니다. 화면 문구는 `lib/l10n/`의 `.arb` 문구 파일(다국어 문구를 언어별로 모아 두는 파일)이 정본입니다. 브리프는 코드에 실을 수 없는 다섯 가지(말투, 「문자 그대로」 고정 문구, 「11. 이 서비스만의 사실」, 왜 그렇게 정했는지, 모션 방향)의 정본으로 끝까지 남습니다. `feature-list.md`는 「어떤 화면을 만들어야 하나」 할 일 목록으로, 이 단계의 대조(§2.3)를 마치면 갱신하지 않는 기록이 됩니다(SKILL.md §2.2). 그래서 `화면 대조 끝:`을 적기 전까지 이 단계는 화면 목록의 「주소」 칸과 상태 표의 `?state=` 괄호를 채우고, 만들다 발견한 빠진 화면을 근거 한 줄과 함께 더할 수 있습니다. 화면이 크게 늘거나 흐름이 바뀌면 여기서 더하지 말고 2-1로 돌아가 화면 목록을 다시 엽니다.

**여기서 안 하는 것 (의도적)**

- ❌ **개발환경 구성** — 스택·Flutter 판·flavor(같은 코드로 설정만 다른 앱 두 벌을 빌드하는 장치)·디자인 시스템 첫 세팅·목업 캔버스는 2단계 개발환경 준비(`2-0-dev-setup.md`)가 이미 했습니다. 스택은 고정이라 이 단계에서 다시 고르지 않습니다.
- ❌ **백엔드** — Firestore 컬렉션·보안 규칙·로그인·서버 함수는 전부 4단계 몫입니다. 이 단계 데이터는 기기 안 저장소(`shared_preferences` — 폰 안에 이름=값으로 저장하는 패키지)에 JSON으로 담깁니다. 예외는 하나 — 플레이 콘솔이 개인정보처리방침 웹 주소를 요구해서, 실서비스 Firebase 프로젝트와 Hosting(웹 페이지 호스팅)만 배포 전에 먼저 만듭니다(§2.6.2). 앱은 여전히 Firebase에 붙지 않습니다.
- ❌ **퍼널 계측·실결제** — 4단계.
- ❌ **다크모드·한국어 밖 언어·성능 튜닝** — 실서비스 영역입니다. 단 문구는 처음부터 `.arb` 파일에 두고, 작은 폰과 큰 글자 배율은 챙깁니다.

| §2.6.2·§2.6.4 플레이 콘솔 작업 | — | **사람 몫.** 계정·약관·신고 답·첫 업로드는 사람이 콘솔에서. AI는 초안과 앱 번들을 만들어 줍니다 |
| §2.6.5 폰에서 확인 | — | **사람 몫.** AI가 자동 도구로 대신 판정하지 않습니다 |

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여 주고, 이번 단계가 할 일을 안내합니다

이전 단계(Mockup)가 남긴 산출물과 코드를 읽고 짧게 요약해 보여 주는 것으로 시작합니다.

- **만들 화면 개수** — 화면 목록에서 `MVP 포함 = O`인 화면이 몇 개인지(전체 몇 개 중), 그중 2단계에서 만든 것과 이번에 만들 것(`만드는 때 = 3단계`)이 각각 몇 개인지, 상태 표의 `O` 칸 중 아직 `?state=` 값이 없는 상태 화면이 몇 개인지.
- **빠짐 점검 결과** — 10절의 고아 화면·막다른 골목이 0건인지, 일곱 갈래 점검에서 근거 없는 X가 남아 있는지.
- **화면 규칙** — 브리프 「12. 화면 규칙」이 채워졌는지, 건너뜀 한 줄인지.
- **개성** — 브리프 「13. 개성」이 채워졌는지, 건너뜀 한 줄인지. 채워졌으면 로고·브랜드 색 면 전용 부품·제목 서체·사진 톤 부품(혁신판·파격판이면 조작 부품·은유 부품도)이 본 코드에 이미 있으니 다시 만들지 않고 쓴다. 「고른 판」 행이 없는 옛 「13」은 대담판과 같게(조작·은유 바꾸지 않음) 읽는다.
- **머무는 공간** — 브리프 「14」 「상태」가 `나중에`면 시작 안내 끝에 한 줄을 붙인다: 「{공간 화면}을 둘러보는 공간으로 따로 깊게 만드는 일은 미뤄 두셨습니다. 3단계 도중에도 「공간 만들자」 하시면 그 단계(2-4)로 갑니다.」 `적용`이면 공간 화면은 다시 만들지 않는다고 한 줄.

빠짐 점검이 비어 있거나 0건이 아닌 항목·근거 없는 X가 보이면 화면부터 만들지 말고 **2-1로 잠깐 돌아가 화면 목록을 먼저 채우자고** 안내합니다(`2-1-mockup.md`의 「빠짐 점검」). 화면 목록이 곧 만들 화면의 전체 목록이라, 목록에 없는 화면은 코드에도 안 생깁니다.

이어서 `mvp/intent.md`의 **서비스 한 줄 정의**와 `mvp/design-brief.md`의 **관점·브랜드 인상 한 줄·확정 브랜드 자산**도 한 줄씩 보여 줍니다 — 이번 화면의 말투와 미감 기준입니다.

그다음 **남은 화면을 같은 코드에 더해 화면 목록을 다 채우고, 사람이 본 뒤 플레이 내부 테스트에 올리는 단계**라는 것을 설명합니다. 설명 골자 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전합니다.

> 2단계에서 화면 목록을 다 적었고, 그중 주요 화면은 실제 앱 코드로 만들어 다듬었습니다. 이번에는 남은 화면 — 설정·비밀번호 찾기·삭제 확인 같은 화면과, 데이터가 없을 때·불러오는 중·오류가 났을 때의 화면 — 을 같은 코드에 더하겠습니다. 이미 만든 화면은 그대로 두고, 2단계에서 정한 화면 규칙대로 만듭니다. 다 만들면 화면 목록과 하나하나 맞춰 본 뒤, 목업 캔버스와 폰에서 보실 수 있게 띄워 드리겠습니다. 괜찮다고 하시면 화면에 움직임을 입히고, 구글 플레이의 내부 테스트에 올려 폰에서 받아 써 보실 수 있게 하겠습니다. 데이터는 아직 서버가 아니라 폰 안에 저장되는 수준입니다. 진짜 DB(데이터를 모아 두는 저장소)는 4단계에 붙입니다.

**사람이 미리 시작해야 하는 일을 이 자리에서 알립니다** — 플레이 콘솔의 사업자(조직) 계정은 처음 쓸 때 확인할 것이 많고 며칠 걸릴 수 있어서, 화면을 만드는 동안 사람이 나란히 진행해야 배포 때 막히지 않습니다. 목록은 §2.6.2 표의 「[사람]」 줄 가운데 ①·②입니다 — 사업자등록번호·통신판매업 신고번호(없으면 신고부터), 조직 확인 서류, 플레이 콘솔 개발자 계정. 이미 끝났으면 넘어갑니다.

**끝나면 같이 볼 사람이 있는지 미리 한 번 짚어 둡니다** — 비의무입니다(§2.7). 내부 테스트는 이메일 목록으로 받으니, 볼 사람의 구글 계정 이메일을 그때 받습니다.

**브랜치는 새로 열지 않습니다** — 2단계 브랜치 그대로 이어 갑니다(이미 feature 브랜치면 그대로. SKILL.md 「2·3단계는 한 브랜치로 간다」). 이 브랜치는 §2.6에서 처음 main에 합칩니다.

이미 `feature-list.md` 머리에 `화면 대조 끝:`이 있으면(스킬 중간 재실행 등) §2.4부터 이어 가고, §3 체크리스트로 검증해 부족한 부분만 보완합니다 — 처음부터 다시 만들지 않습니다.

**`이전 결론 → 이번 결론` 섹션은 이 단계엔 없습니다**(SKILL.md §2.2) — 그 체인은 6단계 `launch-plan.md`에서 처음 시작합니다. 진행 중 아이디어·가설이 뒤집히면 그 결과를 코드에 그대로 반영하고, 문장으로 확정하는 건 6단계에서 합니다.

### 2.2 남은 화면 만들기 — 2단계 코드에 「만드는 때 = 3단계」 화면과 상태 화면을 더합니다

이 절차는 SKILL.md §1.5 **초안 모드**입니다 — AI가 문서와 이미 있는 코드를 스펙 삼아 끝까지 만든 뒤 완성본으로 리뷰받습니다. 중간에 화면 하나하나 승인받지 않습니다.

**범위** — 화면 목록에서 `만드는 때 = 3단계`인 화면, 그리고 상태 표의 `O` 칸 중 아직 `?state=`로 뜨지 않는 상태 화면입니다. 상태 화면은 상태 표의 `O` 옆 한 줄 문구를 그대로 지시로 씁니다. 이미 있는 화면은 다시 만들지 않습니다.

**상태 화면은 `?state=`로 뜨게 합니다** — 경로 끝에 `?state=empty|loading|error|forbidden`(로그인 전 모습은 `?as=guest`)을 붙이면 그 상태가 뜹니다. 화면 코드는 이 값을 읽지 않습니다. 저장·조회 코드(각 흐름의 `data/` 폴더)가 함수 맨 앞에서 상태 흉내 도우미 `devStateAnswer`를 불러, 값이 있으면 빈 결과·끝나지 않는 응답·실패 값을 돌려줍니다. 화면은 그 답을 실제 처리 경로대로 그립니다. 그래서 상태 화면이 뜨면 실제 빈 결과·오류 처리 경로가 돈다는 뜻이기도 합니다. 값을 넣는 길은 둘입니다 — 목업 캔버스는 창마다 provider(앱 어디서나 꺼내 쓰는 공급자 — Riverpod의 기본 단위) 덮어쓰기로, 개발용 앱(`main_dev.dart`)은 라우터가 경로 뒤 질의를 읽어서. 실서비스 진입점에서는 늘 꺼져 있습니다. 자세한 모양은 목업 캔버스 틀 README 「상태 흉내와 가짜 저장소」가 정본입니다.

**지도가 처음 생기는 화면은 같은 틀을 씁니다** — 3단계에서 지도 화면이 처음 생기면(2단계에 지도 화면이 없어 지도 부품이 아직 없을 때) `2-1-mockup.md` 「견본 지도」와 틀 `.claude/templates/sample-map/`의 `README.md`대로 만듭니다. 이미 있으면 그 부품을 씁니다.

**약관·개인정보처리방침은 앱 안에서 웹 주소로 엽니다** — 3단계에는 앱 안에 「받는 정보 목록·보관 기간·문의처」 세 항목 뼈대 화면이나, Hosting에 올릴 웹 페이지(§2.6.2 ④)로 가는 줄만 둡니다. 내용은 사람이 채웁니다. 아직 비어 있는 항목에는 개발 메모를 두지 않고, 사용자가 봐도 되는 말(예: 「정식 출시 전에 안내합니다」)을 둡니다.

**만든 화면은 목업 캔버스 목록 파일에 오릅니다** — 메인은 에이전트 보고의 「화면 ID ↔ 경로」 표로 화면 목록의 「주소」 칸을 채우고, 상태 값 괄호는 손으로 세지 않고 상태 칸 채우기 스크립트로 적은 뒤, 목록 만들기 스크립트를 돌립니다. 스크립트가 화면 목록·상태 표에서 `lib/dev/canvas/screens.generated.dart`를 다시 만듭니다 — 손으로 적지 않습니다. 화면 목록을 고칠 때마다 다시 돌립니다(목업 캔버스 틀 README 「목록 파일」).

```bash
fvm dart run tool/state_fill.dart <상태값 파일>   # 한 줄에 「S-07 empty error」 꼴
fvm dart run tool/canvas_list.dart
```

만드는 일은 **서브 에이전트에 위임합니다** — 화면이 많으면 출력이 크고, 메인이 직접 하면 뒤따르는 대조(§2.3)와 검수에 써야 할 맥락이 그 출력으로 덮입니다. 화면이 많으면 §2.2.1대로 공통 부품을 먼저 만든 뒤 묶음으로 나눠 여러 에이전트에 맡깁니다.

**모델은 sonnet입니다** — 공통 부품·남은 화면·상태 화면 모두. 생김새와 짓는 규칙은 2단계가 이미 정했고, 이 단계는 정해진 부품과 화면을 따라 만드는 일이라서입니다. 처음 정하는 일은 opus, 따라 하는 일은 sonnet이 하네스의 기본 원칙입니다(SKILL.md §3.2).

1. **시작 전 확인 (메인)** — `feature-list.md`의 빠짐 점검(10절)이 비어 있거나 X가 근거 없이 남아 있으면 만들지 말고 2-1로 돌아가 채웁니다(§2.1).
2. **공통 부품·경로·저장·조회 코드 (서브 에이전트 하나, sonnet)** — §2.2.1.
3. **남은 화면 (서브 에이전트 sonnet, 묶음이면 여럿)** — 지시서에 `2-1-mockup.md` 「주요 화면 만들기」 절의 **화면 작업 지시서에 꼭 넣을 문장 전부**를 넣고, 3단계 몫 한 문장을 더합니다.
   - 3단계 몫 한 문장: 「화면 목록의 `만드는 때 = 3단계` 행과 상태 표의 `O` 칸 중 아직 없는 것만 만들어라. 이미 있는 화면은 고치지 마라. 공통 부품은 `lib/shared/components/common/`의 것을, 경로는 `lib/app/paths.dart`의 것을 쓰고, 공통으로 쓸 만한 부품이나 새 경로 모음을 따로 만들지 말고 보고하라.」
4. **화면 밖 검사 (메인)** — 묶음이 다 끝난 뒤 §2.5.1의 「매번」 줄(형식·분석·테스트·생성 코드)을 돌립니다. 화면은 보지 않습니다(`AGENTS.md` 검증 원칙).

**화면 요소 → 부품 대응과 짓는 규칙은 2단계 그대로입니다** — 버튼·확인 창·입력칸 같은 화면 요소를 어느 감싸개 부품(Material 부품을 감싸 토큰을 입힌 `AppButton` 같은 부품)의 어느 variant로 만드는지, 처음부터 피할 모양은 `2-1-mockup.md` 「주요 화면 만들기」 절의 「화면 요소 → 부품」 표를 따릅니다. 이 규칙은 스킬 밖 문서에만 있어 에이전트가 알 길이 없으니, 메인이 표와 프로젝트 `AGENTS.md` 디자인 시스템 연결 정보의 「적용 규칙 요약」을 `<constraints>`에 걸러 넣고 이 꼭 넣을 문장을 더합니다.

> 요소마다 「화면 요소 → 부품」 표로 부품·variant를 정하고, 대응 없는 요소는 전용 부품으로 만들어 부품 목록(`docs/components.md`)에 등록하며, 보고에 「화면 요소 → 부품」 표를 남겨라.

메인은 diff 검수 때 이 표를 봅니다 — 표에 없는 요소가 화면에 있거나, 같은 요소가 화면마다 다른 부품으로 만들어졌으면 거기서 잡습니다.

**design-system 스킬의 규칙 가운데 화면을 지을 때 매번 걸리는 것** — 메인이 스킬을 한 번 읽고 아래를 `<constraints>`에 몇 줄로 넣습니다. 에이전트에게 스킬을 읽으라고 시키지 않습니다(`AGENTS.md` 위임 절).

- 값은 `context.colors`·`context.space`·`context.radius`·`context.text`·`context.motion` 이름으로만 꺼낸다. `Color(0x…)`·`Colors.*`·숫자 간격·`fontSize:`·`Duration(…)`·`Curves.*`·`Theme.of(context).colorScheme`을 화면에 쓰지 않는다.
- 화면 글자는 `.arb` 문구 파일에서 꺼낸다. `Text('…')`에 글자를 직접 쓰지 않는다.
- 글자 배율에 견딘다 — 글자가 든 상자의 높이를 숫자로 고정하지 않고, `Row` 안의 긴 글자는 `Expanded`·`Flexible`로 감싸고, `GridView`의 가로세로 비율을 고정하지 않는다. 새 화면마다 글자 배율 2.0에서 넘침이 없는지 보는 위젯 테스트를 하나씩 더한다(도우미 자리는 design-system 스킬 bootstrap-project.md §1.7).
- 화면 전체 폭(`MediaQuery.sizeOf`)은 셸만 읽고, 부품은 `LayoutBuilder`로 받은 자리의 폭을 읽는다.
- 주 버튼(`AppButtonVariant.primary`)은 화면마다 화면 목록 「주 행동」 칸의 행동 하나에만 쓴다.

**이미지·아이콘 자산** — 브리프 「이미지·영상 계획」 표의 장면은 실물이 있으면 이때 코드에 넣습니다(`assets/` 아래, `pubspec.yaml`에 등록). 자산을 더하면 앱을 다시 빌드해야 보인다는 것을 사람에게 알립니다(`AGENTS.md` 반영 표). 브리프는 고치지 않습니다 — 이미지가 어디 있는지는 코드가 정본입니다. 없으면 장면 설명을 적은 자리 표시를 그대로 두고, 늦어도 6단계 광고 전에 실물로 바꿉니다(`1-design-brief-template.md` 「4.」).

#### 2.2.1 공통 부품 먼저

**화면이 많아 여러 에이전트에 묶음으로 나눠 맡길 때는, 나누기 전에 공통 부품·경로·저장·조회 코드부터 만듭니다.** 첫 에이전트가 넷을 먼저 해 둔 뒤에 묶음 에이전트를 띄웁니다.

1. **공통 부품** — 어느 흐름에서나 나오는 부품 중 아직 없는 것을 `lib/shared/components/common/`에 만듭니다: 불러오기 실패 패널(「다시 시도」), 권한없음 패널, 로딩 뼈대(목록·글·입력 화면 모양), 입력 칸 묶음(이름·칸·도움말·오류 문구 — 화면 읽기 도구가 함께 읽게 묶음), 되돌리기 어려운 확인 창(진행 표시·창 안 오류·「다시 시도」), 위치 줄(돌아가기), 알림 띠 띄우기 도우미(`SnackBar`를 한곳에서 띄움), 로그인 필요 행동 막기(로그인·가입 마무리로 보내기)와 데이터 오류 갈래(없음·권한없음·로그인 필요 — `AppError` 갈래와 짝). 확인 창에 화면 ID를 주었으면 그 경로는 「여는 화면 경로 + `?confirm=<이름>`」입니다 — 공통 확인 창 부품이 그 질의를 읽어 열리고, 목업 캔버스도 이 경로로 띄웁니다. 2단계에서 이미 만든 부품은 다시 만들지 않고, 2-2 비교안의 빈 상태·로딩 화면을 본보기로 모양을 맞춥니다.
2. **경로** — 이번에 더할 화면의 경로를 전부 `lib/app/paths.dart`(경로를 한곳에 모은 상수 파일)와 라우터에 먼저 적습니다. 묶음마다 경로를 따로 모으면 같은 경로가 여러 파일에 생깁니다.
3. **저장·조회 코드** — 이번에 더할 화면이 쓸 저장·조회 함수(목록·상세·만들기·고치기·지우기)를 각 흐름의 `data/`에 먼저 만듭니다(§2.2.4).
4. **가짜 저장소** — 새 저장·조회 provider마다 `lib/dev/fakes/fake_<흐름>_repository.dart`를 만들고 `lib/dev/fakes/canvas_overrides.dart`에 한 줄씩 등록합니다. 등록하지 않으면 캔버스의 그 화면이 진짜 저장소를 불러 상태 창이 갈리지 않습니다(목업 캔버스 틀 README 「상태 흉내와 가짜 저장소」).

묶음 에이전트에게는 이 부품·경로·저장·조회 코드·가짜 저장소를 쓰고, 공통으로 쓸 만한 부품이나 새 경로 모음을 따로 만들지 말고, `data/`·`lib/dev/fakes/`·`paths.dart`·라우터·부품 목록(`docs/components.md`)·`.arb` 문구 파일을 고치지 말고 보고하라고 지시합니다. 새 문구는 보고에 「키 이름 = 문구」 목록으로 남기게 하고, 메인(또는 다음 에이전트 하나)이 묶음이 다 끝난 뒤 `.arb`에 한 번에 넣습니다 — 두 묶음이 같은 파일을 동시에 고치면 한쪽이 덮이기 때문입니다. 묶음 에이전트는 빌드를 돌리지 않습니다 — 분석(`fvm flutter analyze`)과 자기 화면의 테스트까지만 하고, 빌드와 전체 테스트는 메인이 묶음이 다 끝난 뒤 한 번 돌립니다. 빌드 둘을 동시에 돌리면 같은 빌드 폴더를 서로 덮습니다. 묶음마다 공통 부품·경로를 따로 만들면 3단계 끝 코드 정리(§2.5.5)가 그것을 합치느라 커집니다 — 먼저 한곳에 모아 두는 것이 정리를 작게 하는 가장 싼 방법입니다.

화면이 적어 에이전트 하나가 끝까지 만들면 이 차례를 따로 떼지 않습니다 — 같은 에이전트가 공통 부품부터 만들고 화면으로 갑니다.

#### 2.2.2 입력 — 문서 세 개와 이미 있는 코드

**에이전트가** `mvp/feature-list.md` · `mvp/intent.md` · `mvp/design-brief.md` **셋을 전문 그대로 읽고**, 이미 있는 화면·공통 부품·저장·조회 코드를 읽습니다 — 작업의 입력(대상)이라 에이전트가 읽습니다. `AGENTS.md`가 메인이 읽으라고 하는 「규칙 자료」와 다릅니다. 요약해서 넘기지 않습니다 — 화면 목록이 길어서 요약하면 잘린 만큼 화면이 빠집니다.

#### 2.2.3 지시 골자

화면 에이전트에 넘길 지시 골자입니다 — `AGENTS.md` 태그 규칙대로 `<direction>`·`<constraints>`에 나눠 담습니다. 2단계 지시 골자(`2-1-mockup.md` 「주요 화면 만들기」 절)의 문구·데이터·브리프·가독성 줄은 그대로 가져오고, 아래가 이 단계의 몫입니다.

> **입력 세 개와 이미 있는 코드의 역할이 다르다.**
>
> - `feature-list.md` 6~10절 — **만들 화면의 전체 목록과 구조(정본).** 6절 화면 목록에서 `만드는 때 = 3단계`인 화면을 **ID 순서대로 하나도 빠짐없이** 만들고, 7절 상태 표에서 `O`인데 `?state=` 값이 안 붙은 상태 화면(빈 상태·로딩·오류·권한없음)도 **각각 `?state=`로 뜨게** 만든다. 상태 표의 `O*`(단추를 눌러야 생기는 상태)는 `?state=`로 띄우지 않는다 — 그 상태를 띄우려고 화면을 열 때 저장·조회 함수를 부르는 읽기를 더하지 마라. 그런 상태는 단추를 눌렀을 때의 처리 경로에서만 나온다. `O` 옆에 적힌 한 줄이 그 상태 화면에 보여 줄 것이다. 반대편 역할(공급자·운영자)의 화면도 같은 기준으로 전부 만든다. 화면 목록에 없는 화면은 만들지 마라. `MVP 포함 = X`인 화면으로 가는 버튼도 만들지 마라 — 눌러도 갈 곳이 없는 죽은 버튼이 된다. 어느 버튼인지는 9절 「미룬 화면을 가리키는 버튼」 표에 있다. **홈 첫 화면은 화면 목록 홈 행에 적힌 결정(유형·최상단 차례·로그인 전후 분리)을 제약으로 따른다** — 유형별 관례보다 이 기록이 우선이다.
> - **이미 있는 코드** — 2단계 화면과 공통 부품이 생김새의 본보기다. 같은 토큰·셸·부품으로, 2-2 비교안의 빈 상태·로딩 화면과 같은 모양으로 상태 화면을 만든다. 데이터는 이미 있는 저장·조회 코드를 거친다. 기존 화면에는 손대지 마라.
> - `design-brief.md` — **시각 디자인과 화면 문구의 정본. 참고 자료가 아니라 지시다.** 특히 「12. 화면 규칙」(글자 단계·간격 단계·색 쓰는 자리·버튼 종류·부품 상태·아이콘·이미지 비율·작은 폰 배치 규칙)을 그대로 따른다. 「13. 개성」이 채워졌으면 그것도 따른다 — 브랜드 색 면(`context.brand.surface`·`onSurface`)은 프로젝트 `AGENTS.md` 연결 정보 `BRAND_PARTS:` 줄의 전용 부품 파일에서만 쓰고 화면 코드에서 직접 꺼내지 않는다. 화면 폭 전체 띠는 소개 화면 한 곳뿐이고, 브랜드 색 면은 화면당 하나이며, 버튼·칩·태그·아이콘·제목 글자에는 칠하지 않는다. 제목 서체는 정한 글자 이름이 알아서 쓰니 화면에서 `fontFamily`를 따로 주지 않는다. 「13」이 `건너뜀`이면 이 줄을 빼고, 브랜드 색 면을 쓰지 마라. 나머지는 2단계 지시 골자와 같다.
> - (「13」의 「고른 판」이 혁신판이면 위에 더한다.) 핵심 행동은 「13」 「조작 방식」의 조작 부품(`lib/shared/components/`)을 그대로 쓰고, 대체 경로(버튼·목록)를 빼지 마라. 조작이 실패하는 경로(손을 일찍 뗌·엉뚱한 곳에 놓음·말을 못 알아들음·권한 거부 등)의 안내와 상태 화면도 만들어라.
> - (「고른 판」이 파격판이면 위에 더한다.) 「13」 「은유」를 따르는 화면은 `lib/shared/components/{수단}/`의 은유 부품을 쓰고, 고른 수단이 안 될 때의 대체 화면(권한 거부 → 직접 입력, 지도 못 불러옴 → 목록, 인식 실패 → 글 입력)도 함께 만들어라. 무거운 패키지는 `HEAVY_PARTS:`에 적힌 부품 안에서만 불러라.
> - (「13」이 `건너뜀`이거나 「고른 판」이 없거나 대담판이면 위 두 줄은 넣지 않는다.)
> - (「14」 「상태」가 `적용`이면 위에 더한다.) 「14」 「공간 화면」은 다시 만들지 마라. 공간이 여는 상세 화면은 공간의 내용 판 부품(`lib/shared/components/{수단}/{공간_id}/`)을 그대로 써서 만들어라 — 공간 안 내용 판과 상세 화면이 따로 놀지 않게. 공간 팔레트(`lib/core/design/stay/{수단}_palette.dart`)는 `STAY_PARTS:`에 적힌 부품 안에서만 `import`하라.
> - `intent.md` — **화면 순서와 사용자가 원하는 것을 읽는 자료.** 플로우 표의 화면 이름과 핵심 행동은 그 화면에 어떤 요소가 있어야 하는지를 보여 주는 **단서**이지 문구·배치의 스펙이 아니다.
>
> **메뉴**: `feature-list.md` 8절 「메뉴 구조」가 정본이다 — 거기 적힌 메뉴(하단 탭 등) 그대로만 만들고, 그 절에 없는 메뉴는 새로 지어내지 마라. 메뉴가 안 적혀 있으면 임의로 만들지 말고 먼저 물어봐라.
>
> **AI 대화**(AI와 대화하는 기능이 있는 서비스만): AI의 대답은 저장·조회 코드가 미리 써 둔 견본 대본에서 골라 돌려준다. AI 제공사 패키지를 깔거나 AI 키를 요구하거나 실제로 부르지 마라 — 진짜 연결은 4단계 몫이다. 「대답을 쓰는 중」「대답을 받지 못함 + 다시 받기」 상태를 같은 처리 경로에서 나오게 만든다.
>
> **기기 기능**: 카메라·사진첩·위치·알림처럼 폰 권한이 필요한 기능은 이 단계에서 권한을 요청하지 않는다 — 견본 값으로 흉내 낸다(§2.2.4). 권한 요청과 네이티브 설정은 4단계에서 실제 기능과 함께 붙인다.
>
> **보고**: 만든 화면의 화면 ID(상태 화면은 ID와 `?state=` 값)와 경로를 짝지은 표, 「화면 요소 → 부품」 표, 새 문구의 「키 이름 = 문구」 목록, 없어서 만들지 못한 부품, 임시로 정한 것, 「사실 확인 필요」 목록, 분석·테스트 결과.
>
> **전제가 다르면 멈추고 보고하라** — 화면 목록과 `intent.md`·브리프가 서로 어긋나면 임의로 고르지 말고 무엇이 어긋나는지 적어 돌려보내라. 만들다가 화면 목록에 없는 화면이 꼭 필요해 보이면 만들지 말고 근거 한 줄과 함께 보고하라.

- **메뉴 형태는 지시에 적지 않습니다** — 8절을 정본으로 가리키고 「그 절에 없는 메뉴는 새로 만들지 마라」는 금지만 둡니다. 지시에 메뉴 형태를 직접 적으면 8절과 지시가 두 갈래가 됩니다.
- **브리프 「12」와 공통 부품은 메인이 걸러 넣지 않아도 됩니다** — 「12」는 에이전트가 브리프 전문을 읽으며 보고, 공통 부품은 코드에 이미 있습니다. 다만 design-system 스킬의 `visual-polish.md` 항목 중 이번 화면에 닿는 것은 부를 때만 들어오는 규칙 자료라 메인이 읽고 지시서에 걸러 넣습니다(`AGENTS.md` 위임 절).
- **프로젝트 얘기를 지시에 덧붙이지 않습니다** — 무엇을 만들지는 세 파일과 이미 있는 코드가 다 말해 줍니다. 특히 색·서체·문구는 브리프가 정본이라 지시에 다시 적으면 두 갈래가 됩니다.

#### 2.2.4 데이터 — 저장·조회 코드 완성

저장·조회 코드의 짓는 규칙 — 흐름마다 `data/` 한 곳, provider로 꺼냄, 함수는 처음부터 `Future<Result<T>>`(나중에 오는 「성공 또는 실패」) 반환, 상태 흉내 도우미를 맨 앞에서 부름, 소유자 주석, 가짜 로그인 상태 — 은 `2-1-mockup.md` 「주요 화면 만들기」 절 그대로입니다. 이 단계는 남은 화면까지 그 규칙 안에서 **완성할 책임**을 집니다.

- 저장·조회·수정·삭제가 실제로 돌아야 합니다 — 앱을 껐다 켜도 데이터가 남는 수준. 화면만 전환되는 껍데기는 이 단계 완료가 아닙니다.
- 실패는 예외로 던지지 않고 `Result`의 실패 값(`AppError`의 네 갈래 — 네트워크·권한 없음·찾을 수 없음·알 수 없음)으로 돌려줍니다. 그래야 화면의 오류 상태가 상태 표와 한 줄씩 맞습니다. 저장된 JSON이 깨져 읽히지 않을 때도 앱이 멈추지 않고 실패 값이 됩니다(`Result.guard`로 감쌈).
- 새로 더한 데이터도 엔티티마다 소유자 주석 한 줄이 있습니다(`// 소유자: 이 항목을 만든 사용자` 같은). 결제·구독·횟수처럼 **사용자가 직접 바꾸면 안 되는 값**에는 「보호 필드」 주석을 답니다. 둘 다 4단계 보안 규칙의 근거가 됩니다.
- 화면에서 기기 안 저장소를 직접 부르는 곳이 0건입니다 — 반드시 저장·조회 코드를 거칩니다. 한 화면이라도 옆길로 새면 그 화면만 4단계에서 따로 찾아 고쳐야 하고, `?state=`로 상태 화면도 뜨지 않습니다. 프로젝트 맨 위에서:

```bash
grep -rn 'SharedPreferences' lib/features/*/screens lib/features/*/widgets lib/shared
```

- 통과: 0건. 걸린 줄은 저장·조회 코드로 옮깁니다.
- 비밀번호·개인정보를 기기 안 저장소에 넣지 않습니다 — 암호화되지 않은 공간입니다.
- **올리기 화면은 「올린 척」입니다** — 「사진 고르기」를 누르면 실제 사진첩을 열지 않고 견본 이미지 하나를 「방금 올린 것」으로 저장·조회 코드에 넣습니다. 사진첩·카메라를 여는 패키지는 폰 권한 설정이 따라와, 실제 파일 올리기와 함께 4단계에서 붙입니다. 사람 확인(§2.3.3) 때 「올린 사진이 그대로 보이지는 않는다」를 미리 알리고, ADR에 한 줄 적습니다.
- AI 대화 화면은 견본 대본으로 흉내 냅니다 — 2단계 규칙(`2-1-mockup.md` 「AI 대화」) 그대로입니다. 상태 표의 「대답을 쓰는 중」「대답을 받지 못함 + 다시 받기」가 보내기를 눌렀을 때 실제로 나와야 합니다.
- 영상·사진이 들어가는 화면은 견본 이미지 규칙(`1-design-brief-template.md` 「4.」 「이미지·영상 계획」) 그대로입니다 — 영상 자리는 견본 이미지 썸네일 + 재생 표시(▶ 아이콘·길이), 견본은 `assets/samples/`.
- **견본 데이터로 첫 화면을 채웁니다** — 내부 테스트로 받은 사람의 폰은 빈 저장소에서 시작합니다. 그래서 2단계와 같은 규칙으로, 기기 안 저장소가 비어 있으면 처음 한 번 견본 목록을 넣습니다(`2-1-mockup.md` 「예시 데이터」). 견본 목록은 `lib/features/<흐름>/data/`에 둡니다 — `lib/dev/`에 두면 실서비스 진입점이 그것을 부르게 되어 디자인 규칙 검사 13번에 걸리고, 내부 테스트 판(실서비스 진입점으로 빌드)에 견본이 안 들어갑니다. 가짜 저장소도 같은 목록을 씁니다. 새로 더하는 견본은 적게 만듭니다 — 빈 상태·몇 개·많은 개수처럼 화면이 보여 줘야 할 상태만 확인되면 충분하고, 수십 명·수백 건을 지어내 봐야 4단계에서 Firestore용으로 다시 만들며 버려집니다. 이 첫 실행 견본 넣기는 4단계에서 저장소를 바꿀 때 걷어냅니다.

#### 2.2.5 범위와 에스컬레이션

- **범위**: 화면 목록의 `MVP 포함 = O` 화면 전부 + 상태 표에 `O`로 적힌 상태 화면. `MVP 포함 = X`인 화면으로 가는 버튼은 만들지 않습니다.
- **에스컬레이션**: 화면 코드와 브리프가 서로 어긋날 때(→ 말투·고정 문구·규칙 결정은 브리프, 생김새·값은 코드가 기준. 어긋난 지점은 보고), 화면 목록에 있는데 코드에 없고 문서만으로는 모양을 정할 수 없는 화면을 발견했을 때, 바깥 서비스나 새 패키지가 필요할 때는 멈추고 배치로 질문합니다. 그 외 애매함은 합리적 가정 + `추후 결정:` 표시 후 계속합니다.
- **새 패키지**: 들이기 전에 pub.dev(Flutter 패키지 저장소)에서 최근 발행일·지원 플랫폼·관리 주체를 봅니다. 1년 넘게 발행이 없거나 안드로이드·iOS 중 하나를 지원하지 않으면 들이지 않습니다(`3-flutter-quality.md` 「패키지」).
- **정지 조건**: 같은 산출물의 자율 재작업은 최대 2회입니다(SKILL.md §1.5).

### 2.3 빠진 화면 대조와 사람 확인

남은 화면을 다 만들면 움직임으로 가기 전에 세 가지를 차례로 합니다 — ① 빠진 화면 대조 → ② `화면 대조 끝:` 표시와 비교안 정리 → ③ 사람이 목업 캔버스와 폰에서 앱을 봅니다.

#### 2.3.1 빠진 화면 대조 — 화면 ID마다

메인이 화면 ID마다 확인합니다. 눈대중으로 「대충 다 있네」 하고 넘어가지 않습니다 — 여기가 빠진 화면을 잡는 마지막 자리입니다.

1. `MVP 포함 = O`인 모든 화면이 「주소」를 가졌고 목업 캔버스 목록에 있는가 — 2단계 화면과 이번에 더한 화면 모두.
2. 상태 표 `O` 칸(`O*` 제외)이 모두 `?state=` 값을 가졌는가.
3. 화면 목록의 경로가 라우터에 실제로 있는가 — 「주소」 칸에만 적고 라우터에 없으면 캔버스 창에 「없는 주소」 화면이 뜹니다.
4. **반대편 역할(공급자·운영자) 화면**이 빠지지 않았는가 — 플로우 표의 대표 일 쪽만 만들어지기 쉬운 자리입니다.
5. `MVP 포함 = X`인 화면으로 가는 **죽은 버튼**이 코드에 없는가(9절 표 기준 — 표의 버튼 문구로 `.arb` 파일을 찾고, 그 키를 부르는 화면을 찾습니다).
6. **홈 첫 화면**이 화면 목록 홈 행에 적힌 **유형·최상단 차례·로그인 전후 결정**과 맞는가. 유형별 관례(design-system 스킬 `common-patterns.md` §1)가 아니라 **홈 행 기록**과 대조합니다 — 사용자가 관례와 다르게 정해 둔 것을 관례로 되돌리지 않습니다. 로그인 전후를 가르기로 했으면 두 화면이 다 있어야 합니다.
7. **`만드는 때`가 `3단계 — 은유 따라 다시`인 행**(2-3 파격판이 바꾼 화면)도 1~6번 대조에 듭니다 — 경로·상태 화면·은유 부품 사용이 모두 있어야 합니다.

1~3번은 기계로 맞댑니다. 프로젝트 맨 위에서 돌립니다. 먼저 목록 만들기와 상태 점검을 돌리고, 이어서 화면 목록과 캔버스 목록 파일의 ID를 맞댑니다. 맞대기는 2-1 끝의 대조와 같은 방식 — 칸을 번호가 아니라 머리줄의 칸 이름(「ID」·「화면 이름」·「MVP 포함」·「주소」)으로 찾습니다 — 이고, 대상만 `만드는 때 = 2단계`에서 `MVP 포함 = O` 전체로 넓힙니다.

```bash
fvm dart run tool/canvas_list.dart          # 끝에 「주소가 없어 뺀 화면 ID」를 알린다
fvm dart run tool/state_fill.dart --check   # 「O인데 값이 없는 칸」·「O가 아닌데 값이 있는 칸」을 찍는다

F=mvp/feature-list.md
C=lib/dev/canvas
T="$(mktemp -d)"
# 화면 목록 표: 「주소」 칸이 빈 MVP 화면을 찍고, MVP 화면 ID를 모은다
awk -F'|' -v out="$T/list-ids.txt" '
  !h && /ID/ && /화면 이름/ && /MVP 포함/ && /주소/ { for (i = 1; i <= NF; i++) { n = $i; gsub(/^[ \t]+|[ \t]+$|\*/, "", n); c[n] = i }; h = 1; next }
  h && !/^\|/ { exit }
  h { id = $c["ID"]; gsub(/[ \t]/, "", id)
      m = $c["MVP 포함"]; gsub(/[ \t]/, "", m)
      if (id !~ /^S-[0-9]/ || m !~ /^O/) next
      a = $c["주소"]; gsub(/[ \t]/, "", a)
      if (a == "") print "주소 없음: " id
      print id > out }
' "$F"
sort -u -o "$T/list-ids.txt" "$T/list-ids.txt"
# MVP 화면 중 목업 캔버스 목록 파일(자동·손 부분)에 없는 ID
grep -hoE "[\"']S-[0-9]+[A-Za-z0-9-]*[\"']" "$C/screens.generated.dart" "$C/screens.dart" | tr -d "\"'" | sort -u > "$T/canvas-ids.txt"
comm -23 "$T/list-ids.txt" "$T/canvas-ids.txt" | sed 's/^/목록 파일에 없음: /'
rm -rf "$T"

fvm flutter test test/app/router_test.dart  # 3번 — 아래 「경로 테스트」를 둔 파일
```

- 통과: 목록 만들기가 「주소가 없어 뺀 화면」을 0개로 알리고, 상태 점검과 맞대기가 아무것도 찍지 않고, 경로 테스트가 통과합니다. 맞대기의 awk는 칸 이름이 바뀌면 그 이름만 고칩니다 — 2-1의 대조 명령과 함께 고칩니다.
- 목록 만들기는 화면 목록의 칸을 번호가 아니라 머리줄의 칸 이름으로 찾습니다. 필요한 칸이 없으면 쓰지 않고 멈춥니다 — 칸 이름을 바꿨으면 `tool/feature_list.dart` 맨 위 이름을 같이 바꿉니다(목업 캔버스 틀 README 「목록 파일」).
- **경로 테스트** — 「화면 목록의 경로마다 라우터가 맞는 길을 찾는다」를 보는 테스트는 앱 뼈대 틀이 `test/app/router_test.dart`에 이미 넣어 둡니다. 3단계에서는 그 파일 위쪽 `screenPaths` 목록에 화면 목록의 「주소」 칸 경로를 채웁니다(`:id` 자리는 견본 값). 틀이 없던 프로젝트면 `.claude/templates/firebase/app/test/app/router_test.dart.template`을 복사해 경로를 채웁니다. 테스트는 화면을 판정하지 않고 「길이 있다」만 봅니다.

빠진 게 있으면 그 ID를 그대로 짚어 더 만들게 합니다(§2.2 지시서 그대로). 다 채워야 다음으로 갑니다. 화면이 너무 많이 늘거나 흐름이 통째로 바뀌면 이 단계에서 더하지 말고 2-1로 돌아가 화면 목록을 다시 엽니다.

#### 2.3.2 화면 대조 끝 표시와 비교안 정리

대조가 끝나면 메인이 둘을 합니다.

1. **`feature-list.md` 머리에 `화면 대조 끝: YYYY-MM-DD`를 적습니다.** 이 표시는 진행 상황 표시일 뿐입니다 — 문서를 고정한다는 뜻이 아닙니다. 다만 `feature-list.md`는 이 대조로 할 일 목록의 역할을 마쳤으므로, 그 뒤로는 화면이 늘거나 빠져도 갱신하지 않는 기록이 됩니다(코드에만 반영합니다). `/idea-to-mvp`가 지금 몇 단계인지 알아낼 때 이 표시를 「3단계 앞부분이 끝났다」는 단서로 씁니다(SKILL.md §1.2).
2. **고르지 않은 비교안을 지웁니다.** git에는 남습니다. 2-2·2-3에서 고른 판은 이미 본 화면 자리로 옮겨졌으니 남은 것은 고르지 않은 판뿐입니다. 지울 자리는 아홉입니다 — ① 비교안 판 토큰 `lib/core/design/drafts.dart`의 고르지 않은 판 값(2-3을 거쳤으면 판 토큰 파일 `lib/core/design/drafts/{판}.dart`와 `drafts.dart`의 그 `export` 줄, 판 접두 확장도), ② 그 판의 골든 그림(`test/goldens/canvas/`에서 창 열쇠에 `draft-`가 든 그림 — 2-3 비교안의 열쇠 `draft-bold`·`draft-innov`·`draft-leap`도 `draft-`로 시작하니 같이 걸립니다), ③ 비교안 화면 폴더 `lib/dev/drafts/`의 고르지 않은 화면(2-3은 판 폴더 `lib/dev/drafts/{판}/` 통째), ④ 목록 손 부분 `lib/dev/canvas/screens.dart`의 `canvasOverrides`에 든 `drafts:` 항목, 그리고 2-3을 거쳤으면 ⑤ 고르지 않은 후보 제목 서체의 파일(`assets/fonts/`)과 `pubspec.yaml`의 등록 줄과 `FoundationType`의 후보 이름 상수, ⑥ 고르지 않은 비교안 로고 SVG(`assets/brand/`)와 그 등록 줄(고른 로고와 앱 아이콘 원본은 남깁니다), ⑦ 디자인 시스템 페이지의 「브랜드」 껍데기(`lib/dev/drafts/{판}/brand_panel.dart`)와 그 판 자리, ⑧ `main_dev.dart`·`main_canvas.dart`·셸 안 개발용 경로에 더한 줄(`devBranchRoutes` 등)과 점검 테스트 `test/draft_checks/{판}_check_test.dart`, ⑨ 고르지 않은 판만 쓰던 패키지(`flutter pub remove`와 `adr.md` 한 줄). 고른 판의 판 접두 상수는 접두를 떼고 1층(`foundation.dart`)으로 옮겨졌는지 봅니다. 서체 파일은 MB 단위라 안 지우면 앱 크기가 불어납니다. 2-4에서 「쓰지 않음」으로 정한 공간 비교안도 같이 지웁니다 — 공간 폴더 `lib/dev/drafts/stay/`, 판 토큰 파일 `lib/core/design/drafts/stay.dart`와 `drafts.dart`의 그 `export` 줄, 디자인 시스템 페이지 「머무는 공간」 껍데기와 등록, 목업 캔버스 목록의 공간·가까이·많을 때 줄과 그 골든 그림(열쇠에 `draft-stay`), 점검 테스트 `test/draft_checks/stay_check_test.dart`, 공간만 쓰던 패키지(소리 재생 패키지 등 — `flutter pub remove`와 `adr.md` 한 줄). 자기 점검 그림(`.draft-checks/`)은 git에 올라가지 않으니 지우지 않아도 됩니다(`2-3-personality.md` §4.5). 지우기 전에 본 코드가 비교안을 불러오는 곳이 0건인지 확인합니다.

```bash
grep -rnE 'dev/drafts|design/drafts' lib --include='*.dart' | grep -vE '^lib/dev/|^lib/main_dev\.dart|^lib/main_canvas\.dart'
```

- 통과: 0건. 걸리면 그 부품을 본 코드 쪽(`lib/shared/components/` 또는 그 흐름의 `widgets/`)으로 옮긴 뒤 지웁니다.
- 지운 뒤 분석·테스트를 다시 돌립니다. 목록에서 빠진 창의 골든 그림은 저절로 지워지지 않으니 ②에서 손으로 지웁니다.
- 마지막으로 프로젝트 `AGENTS.md`의 연결 정보에 비교안 이름이 남아 있지 않은지 봅니다 — `grep -n 'draft' AGENTS.md`가 0건이어야 합니다(`draft`가 든 이름이 있으면 지웁니다). 2-3의 `BRAND_PARTS:`·`HEAVY_PARTS:` 줄에는 본 부품 경로만 있어야 합니다(`HEAVY_PARTS:`에 `lib/dev/drafts/…` 경로가 남았으면 위 `draft` 확인에 걸립니다).

#### 2.3.3 사람이 목업 캔버스와 폰에서 앱을 봅니다

**여기서는 사람이 봅니다.** AI는 화면을 보지 않습니다 — 시뮬레이터를 조작해 대신 열어 보고 「확인 완료」라고 결론 내지 않습니다(`AGENTS.md` 검증 원칙). 사용자가 명시적으로 시킬 때만 조작합니다.

1. **미리보기 그림을 다시 찍습니다** — 골든 테스트로 캔버스 창마다 그림을 새로 찍습니다(`.claude/scripts/build-lock.sh fvm flutter test --tags golden --update-goldens test/goldens/canvas_golden_test.dart`). 판을 줄여 봤을 때 이 그림이 뜹니다. 그림이 맞는지는 사람이 봅니다.
2. **두 곳에 띄웁니다** — 사람이 `r`·`R`을 누를 수 있게, 사용자가 쓰는 터미널에서 띄우고 명령을 함께 알립니다. 이미 떠 있으면 그것을 씁니다.
   - **목업 캔버스(이 프로젝트 전용 iPad 시뮬레이터 `<폴더 이름> 캔버스`)** — 코멘트 서버(`fvm dart run tool/canvas_server.dart` — 빈 포트를 찾아 뜨고 번호를 `.dart_tool/canvas_server.port`에 적음)를 먼저 켜고, 캔버스(`fvm flutter run --flavor dev -t lib/main_canvas.dart -d "$(basename "$PWD") 캔버스" --dart-define=CANVAS_SERVER=http://127.0.0.1:$(cat .dart_tool/canvas_server.port)`)를 띄웁니다. 시뮬레이터가 꺼져 있으면 먼저 켭니다(`2-1-mockup.md` §2.6.5 4번, 틀 README 「띄우기」). 다른 프로젝트 이름의 시뮬레이터에는 띄우지 않습니다. 모든 화면과 상태가 처음 다 모이는 순간이라 전체를 한 번에 볼 자리입니다.
   - **USB로 연결한 안드로이드폰** — 개발용 앱을 직접 실행합니다(`fvm flutter run --flavor dev -t lib/main_dev.dart -d <폰 이름>`). 폰은 한 번에 한 세션만 씁니다 — 다른 세션이 쓰는 중이면 사람에게 물어 정하고, 그동안은 전용 아이폰 시뮬레이터(`-d "$(basename "$PWD") 폰"`)로 띄웁니다. 움직임·키보드·뒤로 가기·실제 손맛은 캔버스가 아니라 폰에서 봅니다. 상태 화면은 개발용 앱에서도 경로 뒤 `?state=`로 뜹니다.
3. **대조 결과를 한 줄로 덧붙입니다** — 「화면 목록 O 화면 23개(2단계 14개 + 이번 9개) + 상태 화면 9개, 캔버스 목록과 전부 맞습니다」. 다 만든 뒤에 보여 줍니다 — 일부만 만든 상태로 확인받지 않습니다.
4. **사용자가 고칠 곳을 알리면 코드를 고치고 다시 보여 줍니다** — 알리는 길(말·코멘트 핀)과 「코멘트 반영해줘」를 들었을 때의 차례는 `2-1-mockup.md`의 「코멘트 반영」이 정합니다 — 쓰는 법을 처음 알린 적이 없으면 그 문서의 쓰는 법 안내를 붙입니다. 고친 뒤에는 무엇을 누르면 보이는지(`r`·`R`·다시 실행)를 `AGENTS.md` 반영 표대로 알립니다. 문구 한 줄·색 하나 같은 작은 손질은 메인이 직접, 여러 화면은 §2.2 지시서대로 위임합니다. 말투·고정 문구·규칙 결정이 바뀌면 브리프도 고칩니다. 괜찮다고 하면 움직임으로 넘어갑니다.

### 2.4 움직임 다듬기

모션(motion)은 화면 속 움직임이고, 마이크로 인터랙션(micro-interaction)은 버튼을 눌렀을 때 퍼지는 물결처럼 **동작 하나에 붙는 작은 움직임**입니다. 이 절에서 둘을 함께 코드에 입힙니다.

**왜 여기인가** — 2단계 화면은 움직임 없이 만들었습니다. 브리프 「8. 모션·인터랙션 방향」에는 원칙만 있습니다. 그대로 두면 화면을 만드는 에이전트가 제멋대로 넣습니다. 화면이 바뀌는 중에 움직임을 입히면 화면을 고칠 때마다 움직임도 다시 뜯게 되니, **남은 화면 대조와 사람 확인(§2.3) 직후가 자리입니다.** 4단계 전에 하는 건, 내부 테스트 판에서 사람이 화면과 움직임을 한 번에 보고 확정하려는 것입니다.

**작업 모드** — 입구의 「참고 받기」만 인터뷰 모드입니다(사용자에게 한 번 묻습니다). 분석·브리프 기록·코드 적용은 초안 모드로 AI가 완주합니다.

**기본 세트 넷 — 바닥선, 항상 넣습니다**

사용자에게 묻지 않고 넣습니다. 브리프 「8. 모션·인터랙션 방향」의 「완전성」 행과 같은 목록입니다.

| 자리 | 무엇을 | Flutter에서 |
|---|---|---|
| 눌렀을 때 반응 | 버튼·목록 행·탭처럼 누르는 요소 전부에 눌렸다는 표시 | Material 물결 효과(`InkWell`) — 감싸개 부품이 이미 갖고 있는지 보고, 직접 만든 누르는 요소에도 겁니다 |
| 화면 진입·전환 | 화면이 열리거나 바뀔 때 갑자기 튀지 않게 | 테마의 화면 넘김 설정 한 곳, 또는 라우터의 화면 넘김 페이지 한 곳에서 `context.motion` 길이로 |
| 목록 항목 추가·삭제 | 항목이 생기거나 사라질 때 | `AnimatedList`·`AnimatedSwitcher`·`AnimatedSize` |
| 로딩·완료 피드백 | 기다리는 동안과 끝났을 때 | 공통 로딩 뼈대, 공통 알림 띠 도우미(`SnackBar`) |

**장식 움직임(대표 움직임) — 선택, 사용자가 원할 때만**

대표 움직임(signature motion)은 서비스를 기억나게 하는 눈에 띄는 장식용 움직임입니다(예: 첫 화면 그림이 스크롤에 따라 바뀜). **브리프 「8」의 「대표 움직임: <어디서>」 행에 `사용자 확정`으로 적혀 있을 때만 넣습니다.** 그 행이 「없음」이면 넣지 않습니다 — AI가 멋을 내려고 끼워 넣지 않습니다. 장식도 같은 표의 「정서」·「금지」 행과 아래 동작 줄이기 규칙을 그대로 따릅니다.

**2-4에서 정한 공간 움직임** — 브리프 「14」 「상태」가 `적용`이면 공간의 늘 도는 작은 움직임·다가가기는 2-4가 정한 것이다(「14」 「공간 움직임」 행 — 「8」이 아니라 「14」에만 있다). 다시 묻지 않고 길이·곡선만 `context.motion` 값에 맞춘다. 숫자는 `lib/shared/components/{수단}/{수단}_values.dart`에 있다. 물건을 고를 때의 진동도 「14」 「진동·소리」 행대로 둔다.

**2-3에서 고른 대표 움직임** — 2-3에서 사용자가 판을 고르면 「대표 움직임: <어디서>」 행이 움직임마다 이미 `사용자 확정`입니다(대표 장면마다 2~3개까지). 그러면 다시 묻지 않고 받아서 코드에 입힙니다. 2-3 비교안은 `context.motion`의 길이·곡선 이름으로만 움직임을 만들었으니, 이 절이 기본 세트 넷과 함께 길이·곡선 값(1층)을 정할 때 대표 움직임도 같은 값에 맞춥니다. 고른 판에 따라 다릅니다.

- **대담판** — 애니메이션 패키지(`flutter_animate`·`lottie`·`rive` 등)가 필요한 움직임이면 이 절이 들일지 정합니다(필요할 때만 들이고 `adr.md`에 한 줄) — 2-3이 패키지를 먼저 깔지 않았습니다.
- **혁신판·파격판** — 움직임은 Flutter 기본 애니메이션(암묵 애니메이션 위젯·`AnimationController`·물리 시뮬레이션)과 `context.motion`만으로 만들었으니 패키지를 들이지 않고, 길이·곡선 값을 `context.motion` 이름에 맞춥니다. 「조작에 붙는 움직임」 행(끄는 동안 놓을 자리가 열림 등)도 같은 방식으로 따릅니다. 끝없이 도는 움직임(`AnimationController.repeat`)은 동작 줄이기 설정이면 시작하지 않는지 봅니다.

**참고 받기 — 이 절 입구에서 사용자에게 묻습니다**

디자인 스타일을 참고 앱으로 정하듯(「토스처럼」), 움직임도 「이 앱처럼」 식으로 받습니다. 브리프 「8」의 「참고 사이트」 행이 「없음」이 아니면 그걸로 시작하고, 더할 게 있는지만 묻습니다. 안내 골자 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전합니다.

> 이제 화면에 움직임을 입힐 차례입니다. 아래 넷은 기본으로 넣겠습니다 — 버튼 눌렀을 때 반응, 화면 열리고 바뀔 때 부드럽게, 목록에 항목이 생기고 사라질 때, 로딩 중·완료 표시.
>
> 그 위에 「이런 느낌으로 움직였으면 좋겠다」 하는 참고가 있으면 알려 주세요. 받은 참고는 제가 「어디서·무엇이·얼마나 길게·어떤 속도 변화로·어떤 순서로」 움직이는지 나눠서 디자인 브리프에 적고, 앱 전체 움직임의 기준으로 쓰겠습니다. 아래 네 가지 중 편한 것으로 주세요.
>
> **1. 앱 이름이나 사이트 주소** — 「이 앱처럼」 하고 이름이나 주소만 주세요. 움직임은 그림으로 잘 안 잡히니, **어느 요소가 언제 어떻게 움직이는지** 한두 줄을 같이 적어 주세요. 예: 「목록을 내리면 위 제목이 작아지면서 막대에 붙음」.
>
> **2. 화면 녹화(영상)** — 마음에 드는 앱을 직접 찍어서 올려 주세요.
> - **아이폰**: 화면 오른쪽 위에서 아래로 쓸어내려 제어 센터를 열고, 화면 기록 단추(동그라미 안에 점)를 누르세요. 3초 뒤 기록이 시작되고, 끝낼 때는 화면 위쪽의 빨간 표시를 눌러 멈추세요. 파일은 사진 앱에 저장됩니다. 단추가 안 보이면 제어 센터 편집에서 「화면 기록」을 추가하시면 됩니다.
> - **안드로이드폰**: 화면 위에서 아래로 두 번 쓸어내려 빠른 설정을 열고 「화면 녹화」를 누르세요. 끝낼 때는 알림에서 멈춤을 누르면 됩니다. 기종마다 이름이 조금 다를 수 있습니다.
> - 제가 영상을 직접 못 볼 수도 있습니다. 그래서 **몇 초쯤에 무엇이 움직이는지** 말로 같이 적어 주세요. 예: 「2초쯤 카드 세 장이 아래에서 하나씩 올라옴」.
>
> **3. 말로 묘사** — 느낌을 그냥 말로 적어 주세요. 예: 「버튼 누르면 살짝 눌리는 느낌」, 「카드가 아래에서 순서대로 올라옴」, 「화면이 바뀔 때 옆으로 밀리듯 넘어감」.
>
> **4. 프리셋 중 고르기**
> - **절제** — 페이드(서서히 나타나고 사라지는 효과)만. 조용하고 믿음직한 인상(돈·건강·업무 도구)에 맞습니다.
> - **부드러움** — 페이드에 살짝 밀기를 더함. 친근하고 편안한 인상(생활 서비스·커뮤니티)에 맞습니다.
> - **생동감** — 끝에서 살짝 튀는 움직임에 하나씩 순서대로 등장. 발랄하고 재밌는 인상(놀이·소셜·젊은 사용자)에 맞습니다.
> - **스크롤 따라 드러남** — 내려갈수록 내용이 하나씩 나타남. 이야기를 풀어 주는 소개 화면에 맞습니다.
>
> 잘 모르겠으면 「모르겠어」라고 하셔도 됩니다. 브랜드 인상 한 줄을 보고 「절제」나 「부드러움」 중에 제가 골라서 진행하겠습니다. 「생동감」이나 「스크롤 따라 드러남」이 더 어울려 보이면, 그것은 눈에 띄는 장식이라 쓰기 전에 한 번 여쭙겠습니다. 폰에서 보시고 바꾸시면 됩니다.

받은 입력별로 AI가 하는 일은 이렇습니다.

- **앱 이름·사이트 주소** — 사이트 주소면 브라우저 도구로 열어 봅니다. 우리 화면을 판정하는 게 아니라 참고를 읽는 일이라 「화면 검증은 사람 몫」 원칙과 부딪히지 않습니다. 바깥 사이트를 여는 일이니 같은 실패 2회면 멈추고, 401·403·404는 다시 시도하지 않습니다 — 그때는 사용자 묘사만으로 분석합니다. 앱 이름이면 사용자 묘사를 근거로 삼습니다.
- **화면 녹화** — 파일을 읽어 봅니다. 못 읽으면 사용자가 적은 「몇 초쯤 무엇이」 묘사를 근거로 삼습니다.
- **말로 묘사·프리셋** — 그대로 아래 분석표로 옮깁니다.
- **「모르겠어」** — 브리프 「1. 브랜드 인상과 관점」의 브랜드 인상 한 줄을 보고 프리셋 하나를 추천합니다. AI가 추천해 바로 진행하는 프리셋은 「절제」·「부드러움」 둘뿐이고, 지위는 `가정`입니다. 「생동감」·「스크롤 따라 드러남」은 그 자리에서 사용자 확인을 받아야 쓰고, 받으면 「대표 움직임: <어디서>」 행에 `사용자 확정`으로 적습니다.
- **「참고 없음」** — 기본 세트 넷만 넣고, 「정서」 행을 따라 길이·곡선을 정합니다.

**분석 항목표 — 참고를 이 다섯 항목으로 나눕니다**

| 항목 | 무엇을 적나 | 예 |
|---|---|---|
| 어디서 | 진입 · 스크롤 · 화면 전환 · 피드백(누름·로딩·완료) · 사라질 때(지우기·닫기) 중 언제 | 첫 화면 진입 |
| 무엇이 | 페이드 · 밀기 · 확대 · 순서대로 등장 중 어떤 움직임으로 | 아래에서 밀며 페이드 |
| 길이 | 빠름 · 보통 · 느림 중 어느 단계 | 보통 |
| 가속 곡선 | 가속 곡선(easing — 움직임이 처음과 끝에서 빨라지고 느려지는 모양) | 끝에서 부드럽게 멈춤 / 끝에서 살짝 튀었다 멈춤 |
| 순서 | 여러 개가 같이 움직일 때 누가 먼저, 얼마 간격으로 | 제목 → 본문 → 버튼, 짧은 간격 |

분석 결과는 브리프 「8. 모션·인터랙션 방향」 표에 **움직임 하나당 한 행**으로 적습니다 — 항목 열에 「움직임: <어디서>」, 내용 열에 나머지 네 항목을 한 줄로, 지위는 `가정`. **적는 건 말로 된 방향이지 밀리초 값이나 코드가 아닙니다** — 값은 1층 토큰에만 있습니다(SKILL.md §2.1). 사용자가 폰에서 보고 괜찮다고 하면 `사용자 확정`과 확정일로 바꿉니다(§2.6.5). 참고 사이트·앱을 받았으면 「참고 사이트」 행에 그것과 닮을 움직임을 적고 `사용자 확정`으로 둡니다 — 사용자가 직접 준 것이라서입니다. 사용자가 장식 움직임을 원하면 「대표 움직임: <어디서>」 행도 바로 `사용자 확정`으로 채웁니다.

값이 전달되는 경로를 사용자에게 한 번 설명합니다 — 말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전합니다.

> 움직임 값은 이렇게 쓰입니다. 주신 참고를 제가 나눠서 디자인 브리프의 「8. 모션·인터랙션 방향」에 한 줄씩 적고 → 거기 적힌 길이와 속도 변화를 디자인 시스템 맨 아래층(1층)에 「빠름·보통·느림」 같은 값 몇 개로 넣고 → 화면 코드는 그 이름만 불러 씁니다. 그래서 나중에 「전체적으로 좀 느려」라고 하시면 화면을 하나하나 고치는 것이 아니라 1층 값 하나만 바꾸면 앱 전체가 같이 바뀝니다.

**값은 토큰으로**

- 길이 세 단계(빠름·보통·느림)와 곡선 둘은 1층 `foundation.dart`에만 두고, 화면은 `context.motion.fast/base/slow`·`context.motion.standard/emphasis`로만 꺼냅니다. 자리와 모양은 design-system 스킬 bootstrap-project.md §1.4가 정합니다.
- **화면·부품에 `Duration(milliseconds: …)`·`Curves.*`·`Cubic(…)`을 적지 않습니다.** 디자인 규칙 검사 9번이 잡습니다.
- 이렇게 하는 이유 — 브리프 「정서」(예: 조용한 브랜드면 절제된 페이드)가 **값 몇 개로 앱 전체에 먹게** 하려는 것입니다. 화면마다 숫자를 적으면 화면마다 속도가 달라지고, 고칠 때도 전부 찾아다녀야 합니다.

**구현 도구**

- **기본 세트는 Flutter에 든 움직임 위젯으로 합니다** — `AnimatedOpacity`·`AnimatedSwitcher`·`AnimatedList`·`AnimatedSize`·`TweenAnimationBuilder` 같은 것들입니다. 새로 깔 것이 없습니다.
- **목록에서 지운 항목이 사라지는 움직임**은 `AnimatedList`의 「지우기」에 사라지는 모양을 넘겨 만듭니다. 데이터에서 먼저 빼고 목록에는 사라지는 모양만 잠깐 그리는 방식이라, 동작 줄이기로 길이가 0이 되면 바로 사라집니다.
- **장식·스크롤 연동이 필요할 때만 움직임 패키지를 들입니다.** 들이기 전에 최근 발행일·관리 주체를 확인하고(§2.2.5), 판은 그때 최신 stable을 쓰고 `mvp/adr.md`에 이유를 적습니다. 그 패키지에도 값은 `context.motion`으로 넘깁니다.

**접근성 — 동작 줄이기면 움직임을 끕니다, 예외 없음**

폰 설정의 「동작 줄이기」(어지럼증 등으로 움직임을 줄여 달라고 켜 두는 설정 — 안드로이드는 「애니메이션 삭제」, iOS는 「동작 줄이기」)가 켜져 있으면 **움직임을 끕니다. 장식 움직임도 예외가 아닙니다.** 화면마다 분기하지 않습니다 — `context.motion`이 시스템 설정을 읽어 길이를 0으로 돌려주는 **한 곳**에서 처리합니다(디자인 규칙 검사 8번). 그래서 화면이 `context.motion`만 쓰면 따로 할 일이 없습니다. Material 부품 자체의 움직임(화면 넘김·물결 효과)이 그 설정을 따르는지는 판마다 다를 수 있어, 2-0 도입 때 실측한 결과(design-system 스킬 bootstrap-project.md §1.4)를 따릅니다.

**검증 — 보는 건 사람, AI 몫은 화면 밖 검사까지**

움직임은 화면을 열어 봐야 판단됩니다. 그래서 **사람이 폰에서 봅니다** — 개발용 앱으로 먼저 보고, 내부 테스트 판으로 다시 봅니다(§2.6.5). AI가 시뮬레이터를 조작해 보고 「움직임 확인 완료」라고 결론 내지 않습니다. AI 몫은 분석·테스트 통과와 디자인 규칙 검사 8·9번(`bash .claude/scripts/design-check.sh --only 8,9`)까지입니다.

**이 절을 위임할 때 지시서에 넣을 것** — 이 절의 규칙은 자동으로 주입되지 않는 자료(이 문서·브리프·design-system 스킬)에만 있어 에이전트가 알 길이 없습니다. 메인이 걸러서 `<constraints>`에 넣습니다: 기본 세트 넷과 Flutter 쪽 수단, 「대표 움직임」 행(혁신·파격판이면 「조작에 붙는 움직임」 행도)의 지위(`사용자 확정`이 아니면 넣지 않음), 분석표 결과, 값은 `context.motion` 이름만 쓰기, 도구 선택(기본은 Flutter 내장 위젯), 동작 줄이기는 `context.motion` 한 곳, 그리고 「재위임 금지」 줄. 보고에는 공통 알림 띠 도우미를 부르는 곳의 수를 에이전트가 코드에서 직접 세어 적게 합니다 — 「몇 군데에 넣었다」는 말만 믿지 않고 메인이 그 수를 코드와 맞춰 봅니다.

### 2.5 배포 전 검사

남은 화면을 다 만들고 움직임까지 입혔다고(§2.4) 바로 내보내지 않습니다. **화면 밖 검사 목록**(§2.5.1)과 **배포 전 검사 세 가지** — ① 디자인 규칙 검사 ② 코드 품질 검사 ③ 화면 문구 검사 — 를 먼저 통과합니다. 초안 모드로 중간 확인 없이 끝까지 달린 코드에는 화면을 눌러 봐선 안 드러나는 위반이 쌓이기 마련이라, 내보내기 전에 기계로 한 번 훑습니다.

**실행 순서**

```
화면 대조·사람 확인(§2.3) → 움직임(§2.4) → 화면 밖 검사 → 검사 ① → 검사 ② → 검사 ③ → 수정 반영 → 코드 정리 → 화면 밖 검사 다시 → 머지·내부 테스트에 올리기(§2.6) → 사람이 폰에서 확인
```

검사 ②와 ③은 같은 파일을 고칠 수 있습니다. 그래서 **동시에 띄우지 않고 차례로 돌립니다** — ②가 끝나 반영된 뒤에 ③을 띄웁니다. 한꺼번에 띄우면 한쪽이 고친 줄을 다른 쪽이 덮습니다.

**배포 전 검사는 한 번으로 끝나지 않습니다** — 화면 밖 검사와 검사 ①②는 코드가 바뀔 때마다, ③은 사용자에게 보이는 문구가 바뀐 라운드마다 내보내기 전에 다시 돌립니다. 남은 화면을 다 만든 직후의 1차 실행으로 기준선을 잡고, 그 뒤 디자인 바꾸기 라운드나 피드백 반영(§2.7)으로 코드가 바뀔 때마다 다시 돌립니다. 검사 없이 변경만 쌓으면 위반과 잔재(아무도 안 쓰는 토큰·부품)가 라운드마다 쌓여, 나중엔 어느 라운드에서 들어온 건지 추적하는 비용이 고치는 비용보다 커집니다. 검사 ①은 grep 기반이라 **반복 비용이 쌉니다.**

**합치기 전 코드 정리와는 보는 곳이 다릅니다** — 검사 ①은 디자인 규칙, ②는 Flutter에서 실제로 잘 터지는 결함, ③은 사용자에게 보이는 문구, 코드 정리(`code-cleanup`)는 코드 구조·중복을 봅니다. 넷이 서로 다른 곳을 보는 상호 보완이라, 하나를 했다고 다른 것을 건너뛰지 않습니다.

#### 2.5.1 화면 밖 검사 목록

「화면은 사람이 보고, AI는 화면 밖 검사까지」입니다. 이 단계에서 돌리는 목록입니다. 모두 프로젝트 맨 위 폴더에서 돌립니다.

| 검사 | 명령 | 언제 |
|---|---|---|
| 형식 | `fvm dart format --output=none --set-exit-if-changed .` | 매번 |
| 정적 분석(린트·타입) | `fvm flutter analyze` | 매번 |
| 단위·위젯 테스트 (글자 배율 2.0 넘침·대비 테스트 포함) | `fvm flutter test --exclude-tags golden` | 매번. 대비 테스트는 `AppTokens.light.contrastPairs`를 읽습니다 — 브랜드 색을 들이기 전(`AppBrand.none`)에는 브랜드 짝이 목록에서 빠지고, 들인 뒤에는 브랜드 면 대비 세 줄이 함께 돕니다 |

| 디자인 규칙 검사 | `bash .claude/scripts/design-check.sh --allowed "<허용 space 이름>"` | 매번(§2.5.2) |

- **`flutter test`만으로 「통과」라고 하지 않습니다** — 테스트가 불러오지 않은 파일의 오류를 못 잡습니다. 분석과 테스트를 언제나 함께 돌리고, 둘 중 하나만 통과한 것을 통과로 보고하지 않습니다.
- **빌드 둘을 동시에 돌리지 않습니다** — 안드로이드 빌드와 테스트가 같은 빌드 폴더를 씁니다.
- 결과는 「무엇을 돌렸고 몇 건이 걸렸나」로 사용자에게 한 줄씩 보고합니다. 화면이 맞는지는 이 목록이 답하지 않습니다.
- `pub outdated`에서 판이 크게 뒤처진 패키지가 나오면 올리지 말고 목록만 보고합니다 — 판 올리기는 화면이 굳은 뒤 따로 합니다.

#### 2.5.2 검사 ① 디자인 규칙 검사

`design-system` 스킬의 철칙과 「디자인 규칙 검사가 잡는 것」 표가 기준입니다. 기준 항목을 이 문서에 베껴 두지 않는 이유는, 스킬이 바뀌면 검사 기준도 따라가야 하기 때문입니다. **이 문서는 걸린 줄을 어떻게 판정하는지의 정본입니다** — 스크립트는 명령만 돌리고 늘 exit 0으로 끝나며, 판정은 아래 표대로 메인이 합니다.

**돌리는 법** — `bash .claude/scripts/design-check.sh`를 프로젝트 맨 위에서 돌립니다. `--only 1,2,7`로 골라 돌리고, `--allowed`에는 프로젝트 `AGENTS.md` 디자인 시스템 연결 정보 「적용 규칙 요약」 ③의 허용 `context.space` 이름을 넘깁니다(없으면 11번을 건너뜁니다). 경로가 기본형과 다르면 스크립트 맨 위 주석의 환경변수로 덮습니다. 명령을 손으로 옮겨 돌리지 않습니다 — 셸마다 다르게 돌아 빈 결과가 통과처럼 보입니다.

**검사 대상** — 제품 코드(`lib/features`·`lib/shared/components`·`lib/app`)와 비교안·디자인 시스템 페이지(`lib/dev/drafts`·`lib/dev/design_system`)입니다. `lib/core/design/`(토큰을 정의하는 자리)과 목업 캔버스 껍데기(`lib/dev/canvas` — 프로젝트 디자인과 상관없는 개발 도구)는 빠집니다. 감싸개 폴더 `ui/`는 검사마다 넣고 빼는 것이 다르고, 스크립트 맨 위 주석에 적혀 있습니다.

#### 2.5.3 검사 ② 코드 품질 검사

하네스가 가진 점검표 `3-flutter-quality.md`(이 문서와 같은 폴더)로 **sonnet 에이전트 하나**가 앱 코드 전체를 리뷰하고 고칩니다. 사용자에게 「코드 품질 검사를 sonnet 에이전트 하나에 맡깁니다」라고 알립니다. 점검표는 부를 때만 들어오는 자료라 메인이 읽고, 「점검표」 절을 지시서의 `<data>`에 그대로 붙입니다. 지시서에 넣을 것은 이렇습니다.

1. 「`<data>`의 점검표 항목마다 앱 코드(`lib/`, 생성 파일 제외)를 보고 위반을 고쳐라. 화면 겉모습·문구·디자인 값은 바꾸지 마라 — 바꿔야 고쳐지는 것은 고치지 말고 보고하라.」
2. 「고친 뒤 `fvm flutter analyze`와 `fvm flutter test --exclude-tags golden`을 돌리고 결과를 보고하라. 둘 중 하나만 통과면 통과가 아니다.」
3. 「보고: 항목별 고친 곳 수, 고치지 않고 남긴 것과 이유.」
4. 「재위임 금지: 다른 에이전트를 띄우지 말고, 필요해 보이면 멈추고 보고하라.」

점검표 중 「패키지」 항목은 메인이 직접 합니다 — `fvm flutter pub outdated`를 돌리고, 2·3단계에 새로 들인 패키지의 최근 발행일을 pub.dev에서 봐 사용자에게 보고합니다. 웹을 조회하는 일이니 같은 실패 2회면 멈추고, 401·403·404는 다시 시도하지 않습니다. 문제가 있는 패키지를 남기기로 하면 이유를 ADR(SKILL.md §3.1)에 한 줄 적습니다.

#### 2.5.4 검사 ③ 화면 문구 검사

`ux-writing-reviewer` 에이전트(정의에 모델이 정해져 있습니다)에 사용자에게 보이는 문구를 감사·교정받습니다. 기준은 에이전트 정의에 든 글쓰기 원칙과 브리프의 보이스 앤 톤·「문자 그대로」 고정 문구 표입니다 — 브리프는 에이전트가 스스로 읽으니, 지시서엔 파일 목록과 「재위임 금지」 한 줄이면 됩니다. 초안 모드로 수십 개 화면의 문구를 한 번에 지은 직후가 이 검사가 가장 값어치 있는 자리입니다 — 사람이 폰에서 눌러 볼 땐 흐름을 보느라 문구 위반이 눈에 잘 안 들어옵니다.

**고치는 대상은 문구 파일입니다** — 화면 글자는 `lib/l10n/`의 `.arb` 문구 파일에 모여 있습니다(디자인 규칙 검사 16번). 그래서 에이전트는 `.arb` 파일을 고치고, 화면 파일은 그 문구가 어디에 어떻게 뜨는지 읽는 맥락으로만 받습니다. 이 에이전트에는 명령을 돌리는 도구가 없어 바뀐 파일을 스스로 찾지 못하므로, 메인이 프로젝트 맨 위에서 뽑아 지시서의 `<data>`에 붙입니다.

```bash
ls lib/l10n/*.arb
{ git diff --name-only main...HEAD -- lib; git ls-files --others --exclude-standard -- lib; } \
  | grep -E '\.dart$' | grep -vE '^lib/(dev|l10n)/|\.g\.dart$|\.freezed\.dart$' | sort -u
```

- 첫째 줄이 고칠 파일, 둘째 줄이 맥락으로 읽을 화면·부품 파일입니다. 지시서에 「`.arb` 파일만 고치고, 화면 파일은 읽기만 하라. 키 이름은 바꾸지 마라」를 넣습니다.
- **나눠 맡길 때는 차례로 돌립니다** — 묶음마다 같은 `.arb` 파일을 고치므로 동시에 띄우지 않습니다. 맥락 파일이 20개 안팎을 넘으면 폴더(흐름)대로 잘라 묶음마다 「이번에 볼 키」를 그 흐름의 키로 좁힙니다. 메인은 묶음 보고를 합칠 때 같은 문구(버튼 이름 등)를 묶음마다 다르게 고쳤는지 봅니다. 에이전트가 「못 한 파일」을 보고하면 그것만 다음 묶음으로 맡깁니다.
- 남은 화면을 다 만든 직후 1차는 반드시 돌립니다. 이후 라운드는 **사용자에게 보이는 문구가 바뀐 라운드에만** 다시 돌립니다.
- 에이전트가 `판단 필요:`로 돌려준 항목(고정 문구·톤 미확정·뜻이 바뀔 수 있는 문구)은 임의로 정하지 말고 사용자에게 물어 정리합니다.
- 고친 뒤 메인이 `fvm flutter gen-l10n`(또는 빌드)로 문구 클래스를 다시 만들고 분석·테스트를 돌립니다.

#### 2.5.5 검사 뒤 — 코드 정리

검사 ①②③의 수정을 반영했으면, 내보내기 전에 코드를 정리합니다. **2·3단계를 통틀어 한 번뿐인 정리입니다** — 2단계를 따로 합치지 않았으니(SKILL.md 「2·3단계는 한 브랜치로 간다」) 지난 정리의 기준점이 main이고, 2·3단계 코드 전체가 대상입니다. 그래서 바뀐 파일이 많아 묶음 나누기가 기본입니다(나누는 법은 `code-cleanup`). 재사용(같은 일을 하는 코드가 두 곳에 있나)·단순화·효율·깊이(한 부품이 너무 많은 일을 하나)를 봅니다. 절차와 「지난 정리」를 찾는 법은 `code-cleanup` 스킬이 정합니다 — 메인이 Skill 도구로 부르고, 이 문서에 절차를 다시 적지 않습니다. 3단계는 남은 화면을 여러 묶음이 동시에 만들어 같은 일을 하는 코드가 생기기 쉬운 자리라, 내보내기 전에 한 번 거릅니다. 정리로 코드가 바뀌었으면 화면 밖 검사(§2.5.1)와 검사 ①을 다시 돌립니다.

### 2.6 배포 — 플레이 내부 테스트

**지금 내보내는 건 백엔드 없는 워킹 프로토타입입니다.** 데이터는 서버가 아니라 폰 안에 있습니다. **그래도 내보내는 데 아무 문제가 없습니다** — 서버가 할 일이 없을 뿐입니다. 「백엔드부터 붙여야 내보낼 수 있다」는 건 오해입니다.

**그래서 얻는 것은 「폰에 깔리는 진짜 앱」입니다.** 웹은 링크 하나로 누구나 바로 열지만, 앱은 **안드로이드폰을 가진 사람이, 참가 링크를 눌러 플레이 스토어에서 받아야** 씁니다. 쓰임은 두 가지입니다 — (가) 지인·팀 동료가 자기 폰에 깔아 직접 만져 보게 하기(§2.7), (나) 멀리 있는 사람에게 참가 링크를 보내 반응 받기.

**어디서 만들고 누가 올리나** — 실서비스에 나가는 것은 언제나 main의 커밋에서 만듭니다(`AGENTS.md` 「머지와 출시」). 그래서 차례는 이렇습니다.

1. 코드 정리까지 끝난 이 브랜치에서 첫 버전 번호를 적습니다(§2.6.3).
2. 사용자에게 「폰과 캔버스로 화면을 확인하셨다면 main에 합쳐도 되겠습니까?」라고 묻고, 「보내줘」를 들으면 `/done-task`로 합칩니다. 합쳐도 아무 데도 나가지 않습니다. Hosting 페이지(`hosting/`)도 이때 함께 들어갑니다.
3. main에서 `backend-release`로 Hosting만 올려 개인정보처리방침 주소를 엽니다(웹 페이지 틀 README §3의 8번 — §2.6.2 ④).
4. main에서 `store-release` 스킬의 「번들만 만들기」 갈래로 앱 번들을 만들고 서명을 확인합니다. 첫 판은 콘솔에서 사람이 올립니다(§2.6.4).

#### 2.6.1 미리 알릴 것

보여 주기 전에 받을 사람에게 한 줄씩 미리 알립니다. 미리 말해 두지 않으면 상대가 이걸 버그로 읽고, 정작 받아야 할 화면·흐름 반응이 그 얘기에 묻힙니다.

- **안드로이드폰만 됩니다** — 아이폰용은 아직 없습니다.
- **참가 링크로 받습니다** — 플레이 스토어에서 검색해서는 안 나옵니다. 받으려면 받을 사람의 구글 계정 이메일이 시험 참가자 목록에 들어 있어야 합니다.
- **데이터는 그 폰 안에만 있습니다** — 로그인도 서버 저장도 아직 없어, 앱을 지우거나 폰을 바꾸면 넣어 둔 데이터가 사라지고, 다른 사람과 데이터가 이어지지 않습니다.
- **처음 올린 판은 한동안 임시 이름으로 보일 수 있습니다** — 플레이가 처음 올린 앱을 검토하기 전에는 앱 이름·스토어 정보가 임시로 뜰 수 있습니다(공식 도움말 기준 최대 이틀).

#### 2.6.3 버전 번호와 첫 앱 번들

**버전 번호 꼴** — `pubspec.yaml`의 `version: x.y.z+N`입니다. `+` 뒤 숫자 N이 빌드 번호(안드로이드 versionCode)이고, **플레이에 올릴 때마다 반드시 커져야 하며 같은 번호는 두 번 못 올립니다.** 앞의 `x.y.z`는 사람이 보는 판 이름입니다 — 3단계는 `0.x`, 6단계 정식 출시 때 `1.0.0`입니다.

- **첫 판은 이 브랜치에서 적습니다** — 합치기 전에 `version: 0.1.0+1`(이미 다른 값이면 그 값)로 맞춰 커밋합니다. 그래서 첫 판은 번호 올리기 커밋을 따로 만들지 않습니다.
- **그 뒤 판은 `store-release`가 올립니다** — 번호를 올리는 커밋은 작업 브랜치 → PR로 넣고, 합친 커밋에 `v<x.y.z>+<N>` 태그를 남깁니다(`store-release` 스킬).

**첫 앱 번들 만들기** — 합친 뒤 main에서 `store-release` 스킬을 「번들만 만들기」 갈래로 부릅니다 — 올리기 없이 번들을 만들고 서명을 확인해 파일 경로를 알려 주는 갈래입니다. 요점은 셋입니다.

1. 업로드 키 `key.properties`를 빌드하는 동안만 프로젝트에 연결하고, 끝나면 지웁니다.
2. `.claude/scripts/build-lock.sh fvm flutter build appbundle --release --flavor prod -t lib/main_prod.dart`로 앱 번들(AAB — 구글이 기기마다 알맞게 쪼개 주는 묶음 파일)을 만듭니다.
3. 번들의 서명이 업로드 키인지 확인합니다 — debug 서명으로 만든 번들을 올리는 실수를 막습니다.

#### 2.6.4 콘솔에서 올리기 — 사람 몫

**첫 판은 손으로 올립니다.** 이전 앱에서 확인한 교훈입니다 — 한 번도 검토를 통과해 출시된 적 없는 앱(Draft App, 「초안 앱」)에는 명령 도구로 「완료」 상태 릴리스나 스토어 정보를 올릴 수 없습니다(`Only releases with status draft may be created on draft app` 오류). 그래서 이 상태가 풀리는 4단계 비공개 테스트 통과 전까지는 콘솔에서 손으로 올리고, 명령 도구(fastlane)는 6단계 앞에서 켭니다.

AI는 아래를 사람에게 그대로 건넵니다 — 올릴 파일의 경로(`build/app/outputs/bundle/prodRelease/app-prod-release.aab`), 버전 이름, 변경 내역 문구(한국어, 몇 줄). 사람이 하는 일은 이 차례입니다.

1. 콘솔 → 그 앱 → 「테스트 → 내부 테스트」 → 「새 버전 만들기」.
2. 처음이면 **플레이 앱 서명**을 켭니다 — 진짜 서명 키는 구글이 보관하고, 우리는 업로드 키만 갖습니다.
3. 앱 번들 파일을 올리고, 변경 내역을 붙여 넣고, 검토 → 출시를 누릅니다.
4. 「테스터」 탭에서 참가 링크를 복사해 볼 사람에게 보냅니다.

올린 뒤 사람이 콘솔의 경고·오류를 그대로 옮겨 주면 AI가 무엇을 고칠지 정리합니다. 올리는 동작 자체를 AI가 브라우저로 대신 누르지 않습니다 — 결과가 바깥으로 나가는 일이라 사람이 직접 합니다.

#### 2.6.5 사람이 폰에서 확인합니다

사람이 참가 링크로 받은 앱을 자기 안드로이드폰에서 직접 써 봅니다(SKILL.md §1.5 사람 몫 — AI가 자동 도구로 대신 판정하지 않습니다). 볼 것은 이렇습니다.

- 화면 목록의 핵심 흐름이 끝까지 돌아가는지.
- 데이터를 넣고 **앱을 완전히 껐다 켜도 남아 있는지**(기기 안 저장소 동작).
- 폰 설정에서 **글자 크기를 크게** 해도 글자가 잘리거나 겹치지 않는지.
- 폰 설정에서 **애니메이션 삭제(동작 줄이기)** 를 켜면 움직임이 꺼지는지.
- 뒤로 가기(안드로이드 뒤로 버튼·쓸어 넘기기)가 기대대로 움직이는지.
- 움직임(§2.4)이 어색하지 않고 브랜드 인상에 맞는지. 괜찮다고 하면 AI가 브리프 「8」의 `가정` 행을 `사용자 확정`과 확정일로 바꿉니다.

발견된 문제는 §2.7의 차례(고치기 → 검사 → 합치기 → `store-release`로 더 높은 빌드 번호로 다시 올리기)로 고칩니다.

### 2.7 피드백 반영 (지인·팀 동료와 본 뒤)

**이 절은 건너뛰어도 됩니다.** 워킹 프로토타입이 폰에 깔렸으면 지인이나 팀 동료와 함께 한 번 보는 걸 권합니다 — 보고 나온 수정거리를 반영하고, 고칠 게 없으면 그냥 다음 단계로 넘어갑니다. **관문이 아니고 산출물도 없습니다** — 사람을 새로 구하러 다닐 필요도 없습니다. 마땅한 사람이 없으면 이 절을 통째로 건너뜁니다.

**지인에게는 참가 링크를 보냅니다** — 받을 사람의 이메일을 먼저 시험 참가자 목록에 넣어야 링크가 열립니다(§2.6.2 ⑩).

**화면 목록은 갱신하지 않습니다** — `화면 대조 끝:`을 적은 시점에 할 일 목록의 역할이 끝났습니다(§2.3.2). 화면이 늘거나 빠져도 코드에만 반영합니다. 화면 구조가 통째로 뒤집히는 대규모 개편(화면 절반을 새로 짜는 수준)이라면 이건 피드백 반영이 아니라 **피봇**입니다 — 2-1로 되돌아가 화면 목록을 다시 여는 재실행으로 다룹니다(SKILL.md §2.2).

**피드백을 목업 캔버스에 코멘트 핀으로 남겨 받을 수도 있습니다** — 사용자가 받은 피드백을 캔버스의 「코멘트 달기」로 옮겨 적고 「코멘트 반영해줘」라고 하면, 아래 2번의 코드 고치기를 `2-1-mockup.md`의 「코멘트 반영」 차례로 합니다.

절차는 이렇습니다.

1. **새 브랜치를 엽니다** — 3단계 브랜치는 §2.6에서 이미 합쳤으니, main에 서 있으면 `/new-task`로 작업 브랜치를 엽니다.
2. **코드를 고칩니다** (초안 모드). 무엇을 왜 바꾸는지 **화면 ID로** 정리해서 시작합니다(예: 「S-04(카드 정보 입력)를 첫 안내에서 빼고 S-03 다음에 바로 S-05로 — 이유: 본 사람 대부분이 그 화면에서 멈췄다」). 화면을 새로 만들 땐 design-system 스킬의 이름과 기존 부품을 그대로 쓰고, 화면 목록 대신 목록 손 부분(`screens.dart`의 `canvasExtraScreens`)으로 캔버스에 올립니다. 움직임 피드백(「전체적으로 느려」·「너무 튀어」)은 화면마다 고치지 않고 1층 모션 값을 고쳐 앱 전체에 먹입니다 — 코드 수정은 위임해도 됩니다. 브리프 「8」의 해당 행은 메인이 직접 고칩니다(SKILL.md §3) — 행에는 값이 아니라 바뀐 방향만 적습니다(§2.4).
3. **화면을 더하거나 고칠 땐 상태 화면도 같이 만들었는지 코드에서 확인합니다** — 빈 상태·오류·로딩이 `?state=`로 뜨는지, 가짜 저장소가 등록됐는지. 상태 표는 `화면 대조 끝:` 뒤 갱신하지 않는 기록이라, 이 점검은 코드 수정 절차가 맡습니다.
4. **배포 전 검사를 다시 돌립니다** (§2.5 — 재실행 기준은 거기).
5. **사람이 폰과 캔버스로 확인하고 「보내줘」라고 하면** `/done-task`로 합치고, `store-release`로 더 높은 빌드 번호를 붙여 내부 테스트에 다시 올립니다. 앱이 아직 Draft 상태면 「번들만 만들기」 갈래로 번들을 받아 §2.6.4처럼 콘솔에서 손으로 올립니다.
6. **사람이 폰에서 다시 확인합니다** (§2.6.5).

더 고칠 게 없으면 이 단계는 끝입니다. 코드는 그대로 4단계로 넘어가 백엔드가 얹힙니다 — 파일을 확정해 고정하는 게 아니라, 지금 화면으로 다음으로 간다는 뜻입니다.

## 4. 산출물 스펙

이 단계의 산출물은 둘입니다.

**① 앱 코드 (본 산출물)**

- **위치**: 프로젝트 루트(`pubspec.yaml`·`lib/`·`test/`·`android/`·`ios/` 등).
- **스택**: 2단계에서 고정한 스택 — Flutter(Dart)·Material 3·Riverpod·go_router·flavor 두 벌(`dev`·`prod`). 판은 `.fvmrc`·`pubspec.lock`이 기록하고, 이유는 `mvp/adr.md`에 있습니다.
- **범위**: 화면 목록 `MVP 포함 = O` 화면 전부 + 상태 화면(`?state=`로 뜸). **데이터는 기기 안 저장소** — Firebase 앱 연결은 4단계 준비(4-0)에서 계정을 확정한 뒤에 합니다. 실서비스 Firebase 프로젝트와 Hosting은 개인정보처리방침 페이지 때문에 먼저 있을 수 있습니다.
- **성격**: 2단계에서 화면을 만든 순간부터 **화면 생김새·흐름·상태·디자인 값의 정본**이고, 화면 문구는 `.arb` 문구 파일이 정본입니다. 피드백을 반영할 때도 4단계에서도 이 코드를 고칩니다. **버리는 시제품이 아니라 실서비스가 될 본체입니다.**

**② 내부 테스트에 올린 판**

- main의 커밋으로 만든 앱 번들이 플레이 내부 테스트 트랙에 올라가 있고, 참가 링크로 받을 수 있습니다. 판마다 `v<x.y.z>+<N>` 태그가 남습니다(첫 판 뒤부터는 `store-release`가 남김).
- 코드를 고쳐 합칠 때마다 더 높은 빌드 번호로 다시 올려, 참가자의 폰에 늘 최신 판이 가게 합니다.

**함께 생기는 기록** — `mvp/store-listing.md`(스토어 등록정보 초안과 앱 콘텐츠 신고 답 초안). 6단계 앞에서 확정 문구가 fastlane 스토어 정보 폴더로 옮겨가면, 이 파일에는 파일로 옮길 수 없는 것(카테고리·연락처·신고 답과 이유)만 남습니다.

**산출물이 아닌 것 — 목업 캔버스.** 목업 캔버스와 디자인 시스템 페이지는 사람이 화면을 보는 개발용 도구입니다. 앱 코드 안(`lib/dev/`)에 있지만 캔버스·개발용 진입점에서만 불리고, 실서비스 진입점은 부르지 않습니다(디자인 규칙 검사 13번). 4단계에도 남겨 둡니다 — 백엔드를 붙인 뒤에도 전 화면을 훑는 데 씁니다.

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3을 따릅니다 — `AGENTS.md` 응답 톤(~입니다 체)·친근·짧게.
- **진입 안내**: 「화면 목록과 화면 규칙이 다 나왔으니 이제 진짜 돌아가는 앱을 마저 채울 차례입니다 — 남은 화면을 지금 코드에 더하고, 화면 목록과 하나하나 맞춰 본 뒤 목업 캔버스와 폰에 띄워 드리겠습니다. 보시고 괜찮다고 하시면 움직임을 입히고 구글 플레이 내부 테스트에 올려 드리겠습니다. 그사이 플레이 콘솔의 사업자 정보는 며칠 걸릴 수 있으니 미리 시작해 주세요.」
- **화면을 보는 건 사용자 몫이라고 분명히 말합니다** — 「제가 열어서 확인해 봤습니다」라고 하지 않습니다. 띄우는 명령과 결과만 알리고 본 결과를 기다립니다(§2.3.3). 대신 화면 목록 ID 대조 결과는 AI가 세어서 같이 보고합니다(§2.3.1).
- **고친 뒤엔 무엇을 누르면 보이는지 함께 말합니다** — `r`(핫 리로드)·`R`(핫 리스타트)·다시 실행 중 무엇인지(`AGENTS.md` 반영 표).
- **화면 품질 불만**: 「화면이 별로다」 하면 다시 만들어 달라고만 던지지 말고, §2.2.3 지시를 더 구체화(빠진 화면 ID·상태 화면 짚기, 어느 화면 어디가 이상한지)해서 보완하자고 안내합니다. 전체 생김새가 문제면 화면을 하나하나 다시 만들지 않고 토큰·공통 부품을 고쳐 앱 전체에 먹입니다.
- **화면이 너무 많다고 할 때**: **`화면 대조 끝:` 전이면** 화면 목록에서 임의로 화면을 빼지 말고, 2-1로 돌아가 `MVP 포함` 열을 다시 정하자고 안내합니다. **대조 뒤라면** 코드에서 그 화면을 바로 빼면 됩니다 — 화면 목록은 그 시점엔 이미 갱신하지 않는 기록입니다(§2.3.2).
