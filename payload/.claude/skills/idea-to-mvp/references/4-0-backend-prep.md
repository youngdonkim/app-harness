4단계는 코드만 짜는 단계가 아닙니다. 클라우드 DB·로그인·서버 함수가 **밖의 계정에 묶이는 순간**이라, 어느 계정으로 무엇을 만들지가 코드보다 먼저 정해져 있어야 합니다. 이걸 뒤로 미루면 실제로 이런 일이 납니다 — 백엔드를 다 붙인 뒤에 「회사 이메일 계정으로 만들어졌네」를 발견해서, 프로젝트를 새로 만들고 앱 등록·설정 파일·서명 지문·로그인 설정·비밀값을 전부 다시 잇습니다. 이전 앱에서 확인한 교훈입니다 — 4단계를 끝낸 뒤 백엔드 프로젝트가 다른 소유의 조직에 만들어진 것을 발견해, 프로젝트를 새로 만들고 연결을 처음부터 다시 했습니다.

이 문서는 **사람이 브라우저에서 해야 하는 일**을 모아 둔 자리입니다. AI는 터미널 명령(CLI)으로 할 수 있는 일은 하지만, 계정 만들기·로그인·결제 등록·콘솔의 약관 동의는 못 합니다. 순서는 이렇습니다 — **AI가 이 체크리스트를 보여 줍니다 → 사람이 계정·로그인 쪽을 끝냅니다 → AI가 명령 쪽을 잇습니다 → 4-1로 갑니다.**

> ⚠ 여기 적힌 외부 서비스의 화면 위치·명령·요금제 조건은 이 글을 쓴 시점 기준입니다. 따라 하기 전에 공식 문서로 지금도 맞는지 확인하고, 달라졌으면 공식 문서를 따르고 이 문서를 고쳐야 한다고 사용자에게 보고합니다. 반대로 「계정을 먼저 정한다」·「비밀번호는 보이는 순간 저장한다」 같은 우리 규칙과 이전 앱에서 확인한 교훈은 그대로 지킵니다.

## 1. 이 하위 단계가 하는 일

- 4단계가 만들 것들이 묶일 계정을 정하고, 그 계정으로 외부 서비스 로그인·등록을 끝냅니다.
- Firebase(구글이 운영하는, 로그인·DB·파일 저장·서버 함수를 한데 묶은 서비스) 프로젝트 **둘**을 만듭니다 — 개발 기기의 앱이 붙는 **개발용**과, 플레이에서 받은 앱이 붙는 **실서비스용**입니다. 왜 둘인지는 `4-1-backend-db.md` §2.4에 있습니다.
- 앱 뼈대 틀의 backend 묶음(`.claude/templates/firebase/`)을 넣어, 앱이 두 프로젝트에 붙을 준비까지 마칩니다.
- 리드타임(lead time — 신청해서 끝날 때까지 기다리는 시간)이 긴 것(소셜 로그인 앱 등록·검수, 결제 심사)을 지금 시작해서 4-2·4-3에서 기다리지 않게 합니다.
- 비밀값이 어디 저장돼 있는지 장부로 남깁니다(값 자체는 이 저장소에 들어가지 않습니다).

**여기서 안 하는 것**: 컬렉션·보안 규칙·서버 함수 내용 — 그건 4-1부터입니다. 이 문서는 「만들 준비」지 「만들기」가 아닙니다.

## 2. 0번 — 어느 계정으로 할지부터

체크리스트를 보기 전에 한 줄로 먼저 답합니다 — **이 서비스는 누구 소유인가(개인/회사/조직)?** 이 답이 아래 §3의 계정 전부를 정합니다.

**프로젝트 `AGENTS.md`에 「소유와 계정」 표가 있으면 소유 답은 이미 받아 둔 것입니다.** 그 경우 이 절의 확인은 「지금 로그인된 계정이 표의 계정과 같은가」의 **대조**로 좁혀집니다 — **여기서 `docs/account-check.md`를 읽고**, 아래 표의 명령으로 실제 계정을 꺼내 표와 맞춰 봅니다. 다르면 아래 표 「계정이 다르면」 행대로 맞춥니다. 항목이 `(확인 필요)`면 아래대로 처음부터 확인하고, 이번에 확정된 계정은 표에 채웁니다.

| 확인할 것 | 어떻게 |
|---|---|
| 지금 로그인된 계정이 소유자인가 | 각 콘솔(Firebase·구글 클라우드·플레이)의 오른쪽 위 프로필에서 **이메일**을 봅니다. 아이디만 보고 판단하지 않습니다 — 아이디는 개인 것 같은데 이메일만 회사인 경우가 흔합니다. 플레이 콘솔은 왼쪽 위의 개발자 계정 이름도 봅니다 |
| CLI가 어느 계정인가 | 먼저 `.claude/scripts/with-owner.sh --check`(소유·장부·키 이름·Firebase 계정·gh 계정 — 키 값은 안 나옵니다), 그다음 `.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npx firebase login:list`로 이 컴퓨터에 등록된 구글 계정을 봅니다. 브라우저에 로그인된 계정과 CLI 계정이 다른 경우가 있습니다 |
| 계정이 다르면 | gh는 소유자 계정의 발급 토큰을, Firebase CLI는 소유자 계정 이메일을 이 컴퓨터의 계정 장부(`~/.config/harness/<소유>.env` — 소유는 `.claude/owner`)에 두고 실행기로 넘깁니다(gh는 `GH_TOKEN`, Firebase는 `FIREBASE_ACCOUNT`). 전역 로그인 전환·활성 계정 바꾸기는 소유가 다른 프로젝트를 조용히 망가뜨립니다(`docs/account-check.md` 원칙 ②) |
| 서비스 간 연결(앱 연결·저장소 연결·광고 연결)이면 | **양쪽을 대조합니다** — 연결에 붙는 것은 상대 서비스의 지금 세션입니다. 상대 쪽 로그인 계정도 표와 맞춘 뒤 연결하고, 끝나면 화면의 연결 계정을 표와 다시 대조합니다 |
| 브라우저 작업 프로필이 정해져 있고 로그인돼 있는가 | 표의 「브라우저 작업 프로필」 항목을 봅니다. 비어 있으면 사용자에게 묻고 채웁니다. 그 프로필로 이 소유의 서비스들에 실제로 로그인돼 있어야 합니다 — 로그인 폼이 뜨면 아직 준비가 안 된 것입니다 |

화면 작업 프로필 규칙은 `AGENTS.md` 「소유와 계정」 그대로입니다 — 여기선 위 표 마지막 행으로 대조만 합니다.

**계정에 묶이는 쓰기 작업 직전마다, 같은 걸음에서 계정을 다시 확인합니다.** 쓰기 작업은 프로젝트·앱 만들기, 키 발급, 비밀값 넣기, PR 생성·머지, 브라우저 콘솔 작업입니다. 작업 시작 때 한 번 확인한 것을 여러 걸음 뒤에 믿지 않습니다. 콘솔은 마지막에 쓴 구글 계정으로 열리고, 브라우저 에이전트도 마지막 로그인 계정으로 열립니다.

**AI는 서비스마다 「회사 계정입니까, 개인 계정입니까」를 사용자에게 명시적으로 확인받습니다.** 위 명령으로 나온 이메일·조직 이름을 서비스별로 보여 주며 하나씩 판정을 받습니다. 이메일 도메인만 보고 AI가 단정하지 않습니다 — 회사 도메인을 개인 용도로 쓰는 경우도, 개인 지메일이 회사 계정인 경우도 있습니다. 이전 앱에서 확인한 교훈: 아이디는 개인 것처럼 보였는데 이메일만 회사 것이었습니다.

**AI는 이 답을 받기 전에는 어떤 외부 리소스도 만들지 않습니다.** 답이 없으면 묻고 멈춥니다 — 되돌리기 비싼 갈림길이라 SKILL.md §1.5 에스컬레이션 기준 (c)에 해당합니다.

**잘못된 계정에 이미 생긴 리소스는 — ID·키가 따라가면 옮기고, 아니면 새로 만듭니다.** Firebase 프로젝트는 아직 앱 등록·서명 지문·로그인 설정이 적을 때 새로 만드는 쪽이 대개 쌉니다. 옮긴 뒤엔 옛 계정에 남는 권한(구성원·로그인 연결)을 걷습니다.

**사용자가 들어온 뒤에 소유를 통째로 옮겨야 하면 `/transfer-ownership` 스킬을 씁니다.** 4-0 시점처럼 아직 실사용자가 없으면 그 절차는 과합니다 — 위 판단대로 그 자리에서 옮기거나 새로 만듭니다.

## 3. 준비 체크리스트

각 항목에 **[사람]**(계정 만들기·결제·약관 동의·일회용 코드(OTP)·패스키처럼 사람만 되는 일), **[Aside]**(브라우저 에이전트가 콘솔에서 하는 일), **[AI]**(터미널 명령으로 하는 일)를 표시했습니다. 같은 항목 안에서는 **앞 몫이 끝나야 다음 몫으로 넘어갑니다.**

- **[Aside] 몫은 콘솔에서만 되는 일입니다** — 앱 등록, 서명 지문 등록, 디버그 토큰 등록, 구성원 초대. **로그인·재로그인도 Aside가 합니다.** 사람은 OTP·패스키 입력만 맡고, **이메일 인증 코드는 Aside가 메일함에서 읽어 넣습니다.**
- **[Aside]가 비밀값을 받는 절차는 넷입니다** — 화면에서 읽어 **파일로만 저장**(대화에 값을 남기지 않습니다) → 그 값이 유효한지 한 번 확인 → §4.1 표대로 제자리에 설치 → 파일 삭제. **저장에 실패했으면 값 모르는 키를 살려 두지 않고 즉시 폐기한 뒤 다시 발급합니다.**
- **예외 — 자동화를 붙이면 계정이 제재되는 서비스는 [사람]입니다.** 카카오(계정·카카오 디벨로퍼스 콘솔)가 그렇습니다(`docs/account-check.md` 「서비스별 함정」의 카카오 항목). AI는 사람이 건네준 키를 설정에 넣는 일만 합니다.
- **발급 토큰은 계정 단위입니다** — 소유 계정당 하나를 만들고, 그 소유의 프로젝트들이 **계정 장부 파일 하나를 나눠 씁니다.** 같은 소유 장부에 이미 살아 있는 토큰이 있으면 다시 발급하지 않습니다. **이름은 프로젝트가 아니라 용도·기기로 짓습니다**(계정 단위 토큰에 프로젝트 이름을 붙이면 그 프로젝트가 끝났을 때 남들이 쓰는 토큰을 지우게 됩니다). 예외는 §3.4의 개발용 관리자 키처럼 **프로젝트 하나에 묶인 키**입니다 — 이건 프로젝트 ID로 이름을 짓습니다.

### 3.1 GitHub

- **[Aside]** 저장소가 소유자 계정 아래에 있는지 확인합니다. 아니면 저장소 설정의 Transfer(소유권 이전) 기능으로 지금 옮깁니다 — CI·비밀값을 다 붙인 뒤에 옮기면 전부 다시 연결해야 합니다.
- **[AI]** gh CLI 인증(계정 장부의 발급 토큰 `GH_TOKEN`)은 `github-connect`에서 이미 끝나 있습니다. 여기서는 토큰이 살아 있고 표의 계정 것인지 `.claude/scripts/with-owner.sh gh api user --jq .login`으로 확인만 합니다. 없거나 죽었으면 `github-connect`를 돌립니다.
- **GitHub에 넣는 비밀값은 없습니다.** 보안 규칙 테스트는 CI에서 `demo-`로 시작하는 가짜 프로젝트로 돌아 실제 Firebase 자격 증명이 필요 없고, 실서비스 배포는 CI가 아니라 이 맥에서 메인이 합니다.

### 3.2 Firebase 프로젝트 만들기

**이 절은 따로 불러도 됩니다.** 플레이 콘솔의 앱 콘텐츠 신고에 개인정보처리방침 웹 주소가 필요해서, 3단계 배포 전에 실서비스 프로젝트와 Hosting(Firebase의 웹 페이지 호스팅)만 먼저 만들 수 있습니다. 그때는 이 절만 하고 앱은 아직 Firebase에 붙이지 않습니다. 4-0에서 다시 오면 이미 있는 것은 확인만 하고 넘어갑니다.

**① 계정과 자리를 먼저 대조합니다** — **[사람]** 콘솔 오른쪽 위 이메일이 계정 표의 소유 계정인지 봅니다. 두 프로젝트를 같은 자리(조직이 있으면 같은 구글 클라우드 조직, 개인 계정이면 같은 계정 아래)에 둡니다. 소유 이전이나 요금 정리를 할 때 한곳에서 보이게 하려는 것입니다.

**② 두 프로젝트를 만듭니다** — **[사람]** Firebase 콘솔에서 만듭니다.

| | 개발용 | 실서비스용 |
|---|---|---|
| 프로젝트 ID | `<이름>-dev` (예: `example-dev`) | `<이름>-prod` (예: `example-prod`) |
| 별칭(`.firebaserc`) | `dev` | `prod` |

- 프로젝트 ID는 전 세계에서 하나라 이미 쓰이면 끝에 숫자가 붙습니다. **만든 뒤 실제 ID를 계정 표에 적습니다.** 이 ID가 `.firebaserc`·설정 파일·실행기의 키 파일 이름으로 이어집니다.
- 만들 때 묻는 Google Analytics(앱 이용 통계) 연결은 **켭니다** — 퍼널 계측의 원천입니다. 연결할 Analytics 계정도 소유 계정의 것인지 봅니다.

**③ 리전을 정합니다 — 한 번 정하면 못 바꿉니다** — **[사람]** Firestore(Firebase의 DB)를 처음 만들 때 고르는 위치는 바꿀 수 없습니다. **두 프로젝트를 같은 리전**으로 만듭니다. 한국 서비스면 서울(`asia-northeast3`)이 기본입니다. 서버 함수의 리전 상수도 같은 값으로 맞춥니다(§3.3의 틀 넣기가 넣습니다). Storage(파일 저장소)의 기본 버킷도 같은 위치로 만듭니다.

**④ 요금제를 Blaze로 바꾸고 예산 알림을 겁니다** — **[사람]** Blaze(쓴 만큼 내는 요금제)는 서버 함수·예약 백업·Secret Manager(서버 함수 비밀값 금고)에 필요합니다. 결제 수단 등록은 사람 몫입니다.

- **예산 알림** — 구글 클라우드 콘솔의 「결제 → 예산 및 알림」에서 프로젝트마다 겁니다. 개발용은 **월 1만 원 수준**으로, 실서비스는 6단계 광고 예산과 따로 정합니다(그때까지는 개발용과 같은 수준으로 걸어 둡니다).
- **예산 알림은 돈을 막지 않습니다.** 정해 둔 금액에 닿으면 메일을 보낼 뿐, 서비스를 멈추지 않습니다(공식 문서에 적힌 동작). 그래서 알림 메일이 소유자가 실제로 읽는 메일함으로 가는지 확인합니다. 알림 비율(50%·90%·100% 등)은 그 화면의 기본값을 씁니다.
- 실수로 비용이 크게 나는 대표적인 길은 「컬렉션 전체 읽기」와 「무한히 도는 트리거」입니다. 4-1 §8.4가 그 규칙입니다.

**⑤ Hosting을 켭니다(3단계에서 앞당겨 부를 때는 여기까지)** — **[AI]** 실서비스 프로젝트의 Hosting에 개인정보처리방침·계정 삭제 요청 페이지를 올리는 일은 웹 페이지 틀(`templates/hosting-site/`)과 실서비스 배포 절차를 따릅니다. 주소는 기본 주소(`<프로젝트 ID>.web.app`)로 시작하고, 자기 도메인은 6단계 전에 검토합니다.

### 3.3 앱 등록과 backend 틀 넣기

**넣는 순서의 정본은 `.claude/templates/firebase/README.md` §4입니다.** 여기서는 그 앞뒤에 사람이 할 일과, 틀 README에 없는 확인만 적습니다.

1. **[AI]** backend 묶음을 넣습니다(README §4 ①) — `.firebaserc`에 §3.2에서 확정한 두 프로젝트 ID가 들어갑니다.
2. **[AI]** Firebase 패키지와 Node 쪽 도구를 들입니다(README §4 ②③). Firebase CLI는 저장소 최상위 `package.json`의 개발 의존성입니다.
3. **[AI]** FlutterFire CLI(앱에 Firebase 설정 파일을 만들어 주는 도구)로 flavor(같은 코드로 설정만 다른 앱 두 벌을 빌드하는 장치)마다 설정 파일을 만듭니다(README §4 ④). 이 명령이 두 프로젝트에 안드로이드 앱(`<패키지 이름>.dev`·`<패키지 이름>`)과 iOS 앱을 **등록**합니다. 실행기를 앞에 붙여 부르므로 §3.4의 Firebase CLI 로그인이 먼저 끝나 있어야 합니다.
4. **[AI]** iOS flavor 스크립트를 다시 돌리고, 안드로이드 빌드 설정을 확인하고, 만들고 검사합니다(README §4 ⑤~⑧).
5. **[Aside]** 개발용 프로젝트의 안드로이드 앱(`<패키지 이름>.dev`)에 **이 맥의 디버그 키 서명 지문(SHA-1)**을 등록합니다. 지문은 AI가 `keytool -list -v -alias androiddebugkey -keystore ~/.android/debug.keystore -storepass android`로 뽑아 건넵니다(디버그 키 비밀번호는 모두에게 같은 공개값입니다). 실서비스 앱의 지문은 §3.7에서 플레이 콘솔을 본 뒤 등록합니다.
6. **[AI]** 지문을 더한 뒤에는 그 flavor의 설정 파일을 **다시 받습니다**(같은 `flutterfire configure` 명령을 한 번 더). 안드로이드 설정 파일(`google-services.json`)에 지문에 맞는 로그인 클라이언트가 들어가기 때문입니다. 이전 앱에서 확인한 교훈: 지문만 넣고 설정 파일을 다시 받지 않아 구글 로그인이 실패했습니다.

**설정 파일은 git에 올립니다.** 안의 값(API 키 등)은 「이 앱이 어느 프로젝트에 붙나」를 가리키는 공개 식별값이고, 막는 일은 보안 규칙과 App Check가 합니다. 대신 **[Aside]** 구글 클라우드 콘솔의 「API 및 서비스 → 사용자 인증 정보」에서 안드로이드 API 키를 「이 패키지 이름 + 서명 지문」으로만 쓰이게 제한합니다(실서비스는 §3.7의 지문까지 넣은 뒤).

### 3.4 Firebase CLI 로그인과 개발용 관리자 키

**Firebase CLI는 로그인 세션을 씁니다.** 여러 구글 계정을 이 컴퓨터에 등록해 두고 명령마다 고르는 방식이라, 전역 전환이 없습니다(`docs/account-check.md` 원칙 ②).

- **[사람]** `fnm exec --using=.nvmrc -- npx firebase login`(이미 다른 계정이 있으면 `login:add`)을 사람이 자기 터미널에서 칩니다. 브라우저 창에서 구글 계정을 고르는 일이라 AI가 대신하지 않습니다.
- **[AI]** 계정 장부에 `FIREBASE_ACCOUNT=<그 이메일>` 한 줄을 둡니다(값이 아니라 이름표라 화면에 내도 됩니다). 실행기가 `firebase`·`flutterfire` 명령마다 `--account <이메일>`을 붙입니다.
- **[AI]** `.claude/scripts/with-owner.sh --check`가 그 이메일을 답하고, `… npx firebase projects:list`에 두 프로젝트가 보이는지 확인합니다.

**개발용 관리자 키 — 시드·정리 스크립트가 쓰는 자격 증명**

4-1의 시드 스크립트(개발용 프로젝트에 견본 데이터를 넣는 스크립트)와 정리 스크립트는 관리자 SDK(Admin SDK — 보안 규칙을 거치지 않고 DB·계정을 다루는 서버용 도구)로 돕니다. 관리자 SDK는 Firebase CLI의 로그인을 쓰지 못하고, 따로 자격 증명이 필요합니다.

**어떻게 넘기나요?** 개발용 프로젝트 **전용** 서비스 계정(사람 대신 API를 부르는 계정)의 키 파일을 장부 폴더에 두고, 실행기가 **개발용 대상 명령일 때만** 그 파일을 넘깁니다.

```bash
.claude/scripts/with-owner.sh fnm exec --using=.nvmrc -- npm --prefix functions run seed -- --project dev
```

1. 실행기가 명령에서 `--project dev`(`--project=dev`·`-P dev`도 같음)를 찾습니다.
2. `.firebaserc`에서 `dev` 별칭의 프로젝트 ID를 읽고, 장부의 `FIREBASE_SA_DIR` 폴더에서 `<그 ID>.json`을 찾습니다.
3. 키 파일 안의 프로젝트 ID가 개발용 ID와 같으면 `GOOGLE_APPLICATION_CREDENTIALS`(관리자 SDK가 키 파일 자리를 읽는 환경변수)로 넘깁니다.

`--project prod`이거나, 대상이 없거나, `dev`와 `prod`가 섞였으면 **아무것도 붙이지 않습니다.** 개발용 대상인데 키 파일이 없거나 다른 프로젝트의 키면 **실행하지 않고 멈춥니다** — 컴퓨터에 남은 다른 자격 증명으로 조용히 도는 일을 막으려는 것입니다. `firebase`·`flutterfire` 명령에는 붙이지 않습니다(그쪽은 `--account`를 씁니다). 실행기는 Node 스크립트(`npm`·`npx`·`node`·`tsx`·`ts-node`)에만 붙입니다.

**실서비스용 키 파일은 만들지 않습니다.** 실서비스 자격 증명이 시드·정리 스크립트에 닿을 길 자체를 없애려는 것입니다. 실서비스에 견본 데이터가 꼭 필요하면 4-1 §11대로 사람이 확인한 뒤 메인이 따로 합니다.

키 파일 만드는 순서:

1. **[사람]** 구글 클라우드 콘솔에서 **개발용 프로젝트**를 고른 것을 화면 위쪽 프로젝트 선택기로 확인합니다(실서비스 프로젝트에서 만들면 이 절의 뜻이 통째로 사라집니다).
2. **[사람]** 「IAM 및 관리자 → 서비스 계정」에서 서비스 계정을 하나 만듭니다(이름 예: `seed-runner`). 역할은 시드가 하는 일만 줍니다 — Firestore 읽기·쓰기, Storage 객체 관리, Firebase 인증 사용자 관리. 정확한 역할 이름은 그때 구글 클라우드 IAM 문서로 확인합니다. 「소유자」·「편집자」 같은 넓은 역할은 주지 않습니다.
3. **[사람]** 그 서비스 계정의 「키 → 키 추가 → 새 키 만들기 → JSON」으로 키 파일을 내려받습니다. **키 파일은 이때 한 번만 받을 수 있습니다** — 잃으면 새 키를 만들고 옛 키를 지웁니다.
4. **[AI]** 내려받은 파일을 `~/.config/harness/keys/<개발용 프로젝트 ID>.json`으로 옮기고(내려받기 폴더에 남기지 않습니다), 파일 권한을 600, `keys/` 폴더 권한을 700으로 둡니다. 파일 내용은 화면에 내지 않습니다.
5. **[AI]** 장부에 `FIREBASE_SA_DIR=~/.config/harness/keys` 한 줄을 둡니다(이미 있으면 그대로). `.claude/scripts/with-owner.sh --check`가 「개발용 관리자 키: 있음」을 답하면 끝입니다.

**키 만들기가 막히면 멈추고 사람에게 넘깁니다.** 구글 클라우드 **조직** 아래 프로젝트는 조직 정책(조직 전체에 거는 보안 규칙)이 서비스 계정 키 만들기를 막아 둘 수 있습니다 — 최근에 만든 조직은 이 막음이 기본으로 켜져 있습니다(공식 문서의 「기본적으로 보안이 적용된 조직」). 화면에 정책 때문에 만들 수 없다는 문구가 뜨면, 우회하지 않고 사용자에게 알립니다. 조직 관리자가 **개발용 프로젝트에만** 그 정책의 예외를 열어야 합니다(공식 문서는 태그로 프로젝트 하나만 빼는 방법을 안내합니다). 조직 없이 개인 구글 계정 아래 만든 프로젝트는 이 정책이 없습니다.

### 3.5 App Check 등록과 디버그 토큰

App Check는 「이 요청이 진짜 우리 앱에서 왔나」를 확인하는 Firebase 기능입니다. 켜는 차례는 `security-baseline.md` 2부(앱에서는 처음부터 켜고, 서버 쪽 강제는 숫자를 본 뒤 단계적으로)가 정본이고, 여기서는 콘솔 준비만 합니다.

- **[Aside]** 두 프로젝트의 「App Check → 앱」에서 안드로이드 앱을 Play Integrity(플레이가 「정품 앱·정상 기기」를 확인해 주는 기능)로 등록합니다. Play Integrity는 플레이 콘솔의 앱과 구글 클라우드 프로젝트를 잇는 설정이 필요할 수 있습니다 — 그때 공식 문서와 콘솔 안내를 따릅니다. iOS 앱(App Attest)은 iOS를 낼 때 합니다.
- **개발용 앱은 디버그 공급자를 씁니다.** 개발 기기의 개발용 앱은 플레이에서 받은 앱이 아니라 Play Integrity를 통과하지 못하기 때문입니다.
  1. **[AI]** 개발용 앱을 기기에서 처음 실행하면 로그에 디버그 토큰이 한 줄 뜹니다 — 안드로이드는 `DebugAppCheckProvider`가 남기는 줄, iOS 시뮬레이터는 「App Check debug token」 줄입니다(iOS는 Xcode scheme 실행 인자에 `-FIRDebugEnabled`가 있어야 보입니다).
  2. **[Aside]** **개발용 프로젝트** 콘솔의 「App Check → 앱 → 점 세 개 메뉴 → 디버그 토큰 관리」에 그 토큰을 등록합니다. 기기마다(안드로이드폰·iOS 시뮬레이터) 따로입니다.
  3. 디버그 토큰은 「확인 없이 백엔드에 닿는 열쇠」라 비밀값으로 다룹니다 — git·문서·대화에 값을 적지 않고, 실서비스 프로젝트에는 등록하지 않습니다. 새어 나갔으면 그 자리에서 콘솔에서 지웁니다.
  4. 앱을 지웠다 다시 깔거나 시뮬레이터를 초기화하면 새 토큰이 나옵니다 — 그때 다시 등록합니다.

### 3.6 소셜 로그인 준비(구글·카카오)

로그인 흐름 자체는 `4-2-backend-auth.md`가 다룹니다. 여기서는 콘솔 쪽 준비만 하고, 검수처럼 오래 걸리는 것은 지금 시작합니다.

**콘솔에서 무엇을 만들기 전에, 오른쪽 위 프로필 이메일을 「소유와 계정」 표와 먼저 대조합니다.** 이전 앱에서 확인한 교훈: 브라우저 에이전트가 다른 소유의 계정으로 열린 콘솔에 구글 클라우드 프로젝트를 만들었습니다.

**소유권 이전이 안 되는 제공사의 앱은 소유 계정이 확정된 뒤에 만듭니다.** 앱을 새로 만들면 제공사가 주는 사용자 아이디가 바뀌어 **이미 가입한 사람이 같은 계정으로 못 들어옵니다** — 되돌릴 수 없는 결정입니다. 카카오가 그쪽이니, 소유가 확정되기 전에 만들지 않습니다.

**구글 로그인**

- **[Aside]** 두 프로젝트의 「Authentication → 로그인 방법」에서 Google을 켭니다. 이때 각 프로젝트에 OAuth 동의 화면(로그인 창에 뜨는 앱 이름·지원 메일)이 만들어집니다. 앱 이름은 「<앱 이름>」, 개발용은 「<앱 이름> 개발」로 둡니다.
- **안드로이드 구글 로그인은 서명 지문(SHA-1)으로 앱을 알아봅니다.** 등록해야 하는 지문은 셋입니다.

  | 프로젝트·앱 | 등록할 지문 | 어디서 |
  |---|---|---|
  | 개발용(`<패키지 이름>.dev`) | 이 맥의 디버그 키 | §3.3의 5번 |
  | 실서비스(`<패키지 이름>`) | **플레이 앱 서명 키** | 플레이 콘솔(§3.7) |
  | 실서비스(`<패키지 이름>`) | 업로드 키 | `keytool -list -v -keystore ~/.config/harness/keys/<패키지 이름>-upload.jks` — 비밀번호는 같은 폴더의 `<패키지 이름>-upload.properties`에 있습니다. AI가 값을 화면에 내지 않고 지문 줄만 뽑습니다 |

  실서비스 flavor를 이 맥에서 돌려 볼 일이 있으면 디버그 키 지문도 실서비스 앱에 더합니다. **하나만 넣으면 「내 폰에선 되는데 스토어 판에선 안 되는」 사고가 납니다** — 플레이는 올린 앱을 구글이 보관한 앱 서명 키로 다시 서명해 내보내기 때문입니다(공식 문서: 플레이 앱 서명을 쓰면 지문을 로컬 키가 아니라 플레이 콘솔에서 가져옵니다). 지문을 더한 뒤에는 설정 파일을 다시 받습니다(§3.3의 6번).
- iOS 시뮬레이터에서 구글 로그인을 하려면 iOS 설정 파일의 「역방향 클라이언트 ID」를 URL 스킴으로 등록해야 합니다 — 4-2에서 앱 코드와 함께 합니다.
- **[사람]** OAuth 동의 화면이 「테스트」 상태면 등록한 테스트 사용자만 로그인됩니다. 실서비스 프로젝트는 4단계 베타 공유 전에 「프로덕션」으로 바꿉니다. 이름·이메일·프로필 사진 같은 기본 정보만 받으면 대개 구글 검수가 필요 없지만, 지금 요건은 콘솔 안내로 확인합니다.

**카카오 로그인**

- **[사람]** 카카오 계정·카카오 디벨로퍼스 콘솔은 사람이 직접 엽니다(브라우저 에이전트를 붙이면 계정이 제재됩니다 — §3 도입부 예외).
- **[사람]** 앱을 **하나** 만들고 「카카오 로그인」을 켭니다. 플랫폼에 안드로이드를 등록하며 패키지 이름 둘(`<패키지 이름>.dev`·`<패키지 이름>`)과 **키 해시**(카카오가 서명 지문을 적는 꼴)를 넣습니다. 키 해시도 구글과 같은 셋 — 디버그 키·플레이 앱 서명 키·업로드 키 — 입니다. 키 해시는 지문과 적는 꼴이 다르니, AI가 카카오 공식 문서의 방법으로 바꿔 건넵니다.
- **[사람]** 동의 항목 중 `profile_nickname`·`profile_image`를 켭니다(안 켜면 이름·사진이 안 넘어옵니다). `account_email` 같은 항목은 검수·서류가 붙을 수 있습니다 — 필요하면 그 시점의 공식 절차를 확인해 따르고, 필요 없으면 켜지 않습니다.
- **[사람]** 「앱 키」의 **네이티브 앱 키**와 **REST API 키**를 사용자가 AI에게 건넵니다. 네이티브 앱 키는 앱에 들어가는 공개값이라 `env/dev.json`·`env/prod.json`에 넣고(개발용과 실서비스가 같은 앱이면 같은 값), REST API 키는 서버 함수가 쓸 때만 서버 함수 비밀값에 넣습니다.
- **카카오는 Firebase가 기본으로 지원하는 로그인 수단이 아닙니다.** 그래서 서버 함수가 카카오 토큰을 카카오에 확인한 뒤 Firebase 로그인 토큰을 만들어 줍니다 — 흐름과 그 함수는 4-2 §11.2입니다. 이 함수가 Firebase 로그인 토큰을 만들려면 서버 함수의 서비스 계정에 「토큰 서명」 권한이 있어야 할 수 있습니다(4-2 §11.2에서 확인).

### 3.7 구글 플레이 콘솔 — 사업자 정보와 앱 서명 키 지문

- **[사람] 사업자 정보를 확인합니다.** 플레이 콘솔의 개발자 계정은 사업자(조직) 계정입니다. 한국 사업자는 콘솔에 **사업자등록번호와 통신판매업 신고번호**를 넣어야 합니다(이전 앱에서 확인). 원래 3단계 배포 전에 끝나 있어야 하는 일이라, 여기서는 「계정 세부정보」에 두 번호가 들어가 있고 확인 대기로 막힌 것이 없는지만 봅니다. 신고번호가 아직 없으면 그것부터 신고합니다 — 며칠 걸립니다.
- **[사람] 플레이 앱 서명이 켜져 있는지 봅니다.** 진짜 앱 서명 키는 구글이 보관하고, 우리는 업로드 키만 갖습니다. 3단계 첫 판을 올리며 켜졌을 것입니다.
- **[Aside] 앱 서명 키 지문을 가져옵니다.** 플레이 콘솔의 그 앱 → 「출시 → 설정 → 앱 무결성」(화면 이름은 바뀔 수 있습니다)에서 **앱 서명 키 인증서**의 SHA-1을 읽습니다. 같은 화면의 **업로드 키 인증서** 지문은 우리 업로드 키와 같아야 합니다 — 다르면 엉뚱한 키로 올렸다는 뜻이라 멈추고 보고합니다.
- **[Aside]** 그 지문을 실서비스 프로젝트의 안드로이드 앱(§3.6 표)과 카카오 키 해시에 넣습니다.

### 3.8 AppsFlyer(설치 출처 측정)

광고를 여러 매체에 걸 때 「누가 어느 매체를 보고 설치했나」를 한 곳에서 가르는 MMP(설치 출처 측정 서비스)로 AppsFlyer를 씁니다. SDK를 앱에 넣고 이벤트를 잇는 일은 4-3의 계측 절 몫이고, 여기서는 계정만 준비합니다.

- **[사람]** 소유 계정의 이메일로 AppsFlyer 계정을 만들고, 요금제(Growth)와 무료 범위를 공식 요금 안내로 확인합니다. 결제 수단 입력은 사람이 합니다.
- **[Aside]** 실서비스 앱(`<패키지 이름>`)을 AppsFlyer에 등록하고, **개발 키(dev key — SDK가 AppsFlyer에 자기를 알리는 값)**를 받습니다. 이 값은 앱에 들어가는 공개값이라 `env/prod.json`에만 둡니다. **개발용 앱은 AppsFlyer에 보내지 않습니다** — 개발용 flavor에서는 SDK를 켜지 않고, 개발용 앱(`<패키지 이름>.dev`)을 AppsFlyer에 따로 등록하지도 않습니다. 개발 기기의 설치가 매체별 설치 숫자에 섞이면 6단계 판정 숫자가 오염되기 때문입니다(`4-3-backend-deploy.md` §2.3.2).
- 계정 이메일을 「소유와 계정」 표의 MMP 행에 적습니다.

### 3.9 AI 제공사 키

- **[사람]** 쓰는 AI 제공사마다 소유자 계정으로 키를 만들고, 결제 수단과 **월 지출 상한**을 같이 겁니다. **개발용과 실서비스용 키를 따로** 만들고, 개발용은 상한을 더 낮게 둡니다. 다른 소유의 키가 섞여 있으면 지금 교체합니다 — 안 그러면 청구서가 엉뚱한 곳으로 갑니다.
- **[AI]** 키는 **앱에 넣지 않습니다.** 서버 함수 비밀값(Secret Manager)에 프로젝트마다 넣습니다 — 개발용은 지금, 실서비스용은 `backend-release` 절차로 main에서 넣습니다(넣는 꼴은 4-1 §8.3). 값을 대화에 붙여 받지 않습니다 — 사용자가 직접 넣는 명령을 치거나, 값을 파일로 받아 넣은 뒤 지웁니다.

### 3.10 로컬 도구

2단계 개발환경 준비에서 Flutter·Xcode·Android Studio·Node·fnm은 이미 깔려 있습니다. 4단계에서 더하거나 다시 확인하는 것만 적습니다.

- **[사람이 정함] Xcode를 최신 판으로 올립니다 — 4-0 맨 앞에서.** Firebase iOS SDK의 새 판은 최신 Xcode를 요구합니다. Xcode가 오래되면 iOS 빌드가 「firebase-ios-sdk … contains incompatible tools version」 같은 오류로 멈추고, 그때 가서 올리면 수십 GB를 받는 동안 iOS 시뮬레이터 개발이 통째로 멈춥니다. 그래서 순서는 이렇습니다.
  1. **[AI]** 지금 판(`xcodebuild -version`)과, Firebase 공식 문서(Apple 플랫폼 설정 페이지·Apple SDK 출시 노트)가 요구하는 최소 Xcode 판을 확인해 사용자에게 보여 줍니다. 판 숫자는 이 문서에 적지 않습니다 — 그때그때 확인합니다.
  2. **[사람]** 모자라면 앱 스토어에서 Xcode를 업데이트합니다. 용량이 크고 앱 스토어 계정이 필요해 사람 몫입니다. 다 깔린 뒤 Xcode를 한 번 열어 추가 구성 요소 설치와 약관 동의를 누릅니다.
  3. **[AI]** iOS 시뮬레이터 런타임이 새 Xcode와 맞는지 보고, 모자라면 받습니다. 그다음 README §3 ⑩의 iOS 빌드 두 줄로 확인합니다.
- **[AI]** Firebase CLI는 §3.3에서 저장소 개발 의존성으로 깔립니다. 전역에 깔지 않고 `npx firebase`로 부릅니다.
- **[AI]** FlutterFire CLI가 없으면 `fvm dart pub global activate flutterfire_cli`로 깝니다. iOS flavor 스크립트가 쓰는 `xcodeproj`(Xcode 프로젝트 파일을 고치는 Ruby 도구)가 없으면 `gem install xcodeproj`.
- **[AI]** 서버 함수의 Node 판이 Cloud Functions가 지원하는 판인지 공식 문서로 확인하고, `.nvmrc`와 맞춥니다. 고른 판 숫자는 이 문서가 아니라 `mvp/backend-build.md`와 ADR에 적습니다.
- **에뮬레이터는 깔지 않습니다** — 개발에는 쓰지 않고, 보안 규칙 테스트만 CI 안에서 잠깐 띄웁니다(`4-1-backend-db.md` §3.3).
- **[AI]** `gh`·`firebase` 인증이 표의 계정 것인지 §2 방식대로 다시 확인합니다.

> **참고 — 쓴 시점 실측 (규칙이 아닙니다. 어긋나면 공식 문서를 따르고 이 줄을 고쳐야 한다고 보고합니다.)**
>
> - gh는 등록된 계정이 둘이면 **전역 활성 계정이 저절로 바뀌는 일이 있습니다** — 그래서 활성 계정이 아니라 장부의 토큰(`GH_TOKEN`)으로 고정합니다.
> - 맥 키체인에서 CLI 토큰을 꺼내는 조회 명령은 허용 창이 떠서 무한 대기합니다 — 계정 확인은 CLI 자체의 조회 명령으로 하고, 무한 대기 가능성이 있는 명령은 시간 상한을 걸어 부릅니다.
>
> 더 긴 목록은 `transfer-ownership` 스킬 §10.

## 4. 비밀값 장부

값 자체는 적지 않고, **어디에 있는지만** 적습니다. 아래 표를 채워서 `backend-build.md`의 「배포 정보」 아래에 옮겨 둡니다. 정본은 이 서식을 채워 옮긴 `mvp/backend-build.md`이고, 여기 표는 서식입니다.

**「프로젝트」 칸이 있습니다.** 서버 함수 비밀값처럼 프로젝트마다 따로 넣는 값은, 이름이 같아도 개발용·실서비스용 행을 둘로 씁니다. 한쪽만 바꾸고 다른 쪽을 잊는 일을 표에서 보이게 하려는 것입니다.

| 비밀값 | 프로젝트 | 만든 곳 | 저장된 곳 | 다시 볼 수 있나 | 만료일 | 갱신 시 같이 바꿀 곳 |
|---|---|---|---|---|---|---|
| gh 발급 토큰(`GH_TOKEN`) | 해당 없음 | GitHub 설정 | 이 컴퓨터의 계정 장부 | 아니오 — 재발급 | (발급 화면에서 확인) | 계정 장부 ↔ 같은 소유 장부를 쓰는 다른 프로젝트 |
| 개발용 관리자 키 파일 | 개발용 | 구글 클라우드 콘솔(서비스 계정) | 장부 폴더 `keys/<개발용 ID>.json` (장부에는 폴더 경로 `FIREBASE_SA_DIR`만) | 아니오 — 새 키 발급 | 없음(조직 정책이 만료를 걸 수 있음 — 콘솔에서 확인) | 키 파일 교체 뒤 옛 키를 콘솔에서 삭제 |
| App Check 디버그 토큰 | 개발용 | 기기 첫 실행 로그 | 개발용 프로젝트 콘솔(기기마다) | 예 — 콘솔 | 없음 | 앱을 다시 깔면 새로 등록, 옛 토큰 삭제 |
| `<비밀값 이름>`(예: AI 제공사 키) | 개발용 | 제공사 콘솔(개발용 키) | 서버 함수 비밀값 + 비밀번호 관리자 | 대부분 한 번만 | (콘솔에서 확인) | 비밀값 다시 넣기 → 그 비밀값을 쓰는 함수 다시 배포 |
| `<비밀값 이름>` | 실서비스 | 제공사 콘솔(실서비스 키 — 개발용과 다른 키) | 〃 | 〃 | 〃 | 〃 (`backend-release`로) |
| 카카오 REST API 키 | 실서비스·개발용 | 카카오 콘솔 | 서버 함수 비밀값(쓸 때만) | 예 — 콘솔 | 없음 | 두 프로젝트의 비밀값 ↔ 함수 다시 배포 |
| 업로드 키 파일·비밀번호 | 해당 없음 | `keytool` | 장부 폴더 `keys/`의 `<패키지 이름>-upload.jks`·`.properties`(앱마다 따로) + 비밀번호 관리자 | 비밀번호는 비밀번호 관리자 | 없음 | 잃으면 구글에 업로드 키 재설정 요청(며칠) → 지문이 바뀌므로 실서비스 앱·카카오 키 해시도 교체 |
| 플레이 올리기용 서비스 계정 키 | 해당 없음 | 구글 클라우드 콘솔 | 장부 폴더 `keys/`(장부에는 경로만) | 아니오 — 새 키 발급 | 없음 | 6단계 앞 `store-release` 준비에서 만듦 |

공개값(Firebase 설정 파일, 카카오 네이티브 앱 키, AppsFlyer 개발 키)은 비밀값이 아니라 이 표에 넣지 않습니다. 자리는 §4.1 표에 있습니다.

**「갱신 시 같이 바꿀 곳」은 짝으로 적습니다.** 같은 값이 두 곳 이상에 들어가면 한 곳만 바꿨을 때 나머지가 옛 값으로 남아 **특정 기능만 조용히 실패합니다.**

**폐기 규칙 — 지우기 전에 묻습니다.** 토큰·키를 지우기 전에 **같은 계정의 다른 프로젝트가 그 값을 쓰는지 먼저 확인하고 사용자에게 묻습니다.** 발급 토큰은 계정당 하나를 여러 프로젝트가 나눠 쓰는 게 기본이라, 이 프로젝트만 보고 지우면 남의 프로젝트가 멈춥니다. **프로젝트가 다른 소유로 옮겨 갔다는 이유만으로 옛 계정의 토큰을 폐기하지 않습니다.**

**규칙: 한 번만 보여 주는 값은 보이는 그 순간 비밀번호 관리자에 옮깁니다.** 「나중에 옮겨야지」가 사고의 시작입니다. **에이전트가 만든 토큰·키도 같습니다** — 값을 그 자리에서 확보하고, 못 확보했으면 값 모르는 채로 살려 두지 않고 바로 폐기한 뒤 다시 만듭니다. 키 파일(JSON·`.jks`)은 비밀번호 관리자 대신 장부 폴더 `keys/`가 자리이고, 잃었을 때 다시 만드는 길을 장부에 적어 둡니다.

### 4.1 같은 값을 어디어디에 넣나

한 값이 여러 곳에 들어가는 것들입니다. 한 곳만 넣으면 그 자리를 쓰는 기능만 조용히 실패합니다.

| 값 | 원천 | 개발용에 넣는 곳 | 실서비스에 넣는 곳 |
|---|---|---|---|
| 서명 지문(SHA-1) | `keytool`(디버그·업로드 키), 플레이 콘솔(앱 서명 키) | 개발용 프로젝트의 `<패키지 이름>.dev` 앱 ← 디버그 키 | 실서비스 프로젝트의 `<패키지 이름>` 앱 ← 앱 서명 키 + 업로드 키(+ 필요하면 디버그 키) |
| 카카오 키 해시 | 위 지문을 카카오 꼴로 바꾼 값 | 카카오 앱의 안드로이드 플랫폼(패키지 둘에 공통) ← 디버그 키 | 같은 자리 ← 앱 서명 키 + 업로드 키 |
| Firebase 설정 파일 | `flutterfire configure` | `lib/core/firebase/firebase_options_dev.dart`·`android/app/src/dev/google-services.json`·`ios/config/dev/GoogleService-Info.plist` | 같은 세 자리의 `prod` |
| 카카오 네이티브 앱 키 | 카카오 콘솔 | `env/dev.json` | `env/prod.json` |
| 카카오 REST API 키(서버 함수가 쓸 때만) | 카카오 콘솔 | 개발용 서버 함수 비밀값 | 실서비스 서버 함수 비밀값 |
| AppsFlyer 개발 키 | AppsFlyer 콘솔 | 넣지 않음 — 개발용 flavor는 SDK를 켜지 않음(`env/dev.json`에 이름도 두지 않음) | `env/prod.json` |
| AI 제공사 키 | 제공사 콘솔 | 개발용 서버 함수 비밀값 ← 개발용 키 | 실서비스 서버 함수 비밀값 ← 실서비스 키 |
| App Check 디버그 토큰 | 기기 로그 | 개발용 프로젝트 콘솔 | 넣지 않음 |

⚠ **지문을 더하거나 바꾸면 그 flavor의 설정 파일을 다시 받습니다.** 안드로이드 설정 파일 안의 로그인 클라이언트가 지문에 따라 달라지기 때문입니다.

⚠ **비밀값을 새로 넣으면 그 값을 쓰는 서버 함수를 다시 배포합니다.** 이미 떠 있는 함수는 옛 값을 계속 씁니다(공식 문서에 적힌 동작).

**같은 기능이 개발용에서는 되고 실서비스에서는 안 되면, 코드보다 이 표의 실서비스 칸을 먼저 의심합니다.** 지문·키 해시·비밀값 중 실서비스 자리에 빠진 것이 있는지부터 봅니다.

## 5. AI의 진행 방식

0. **「나중에 — 4단계 백엔드 구현 때」 기능부터 다시 묻습니다** — `mvp/feature-list.md` 1절 「더할 기능」 표에서 범위가 `나중에 — 4단계 백엔드 구현 때`인 줄을 꺼내 보기 창(AskUserQuestion, 여러 개 고르기)으로 묻습니다. 질문 하나에 보기 3개까지 + 「이번에도 미룸」 — 줄이 더 많으면 질문을 나눕니다. 보기 설명은 「[{흔한 / 변형 / 실험} · {크기}] {사용자가 하면 → 얻는 것}」. 메시지 첫 줄은 「목업 화면을 만들 때 「나중에 — 4단계 백엔드 구현 때」로 미뤄 두신 기능이 N개 있습니다. 로그인·Firestore 저장·서버 함수·푸시 알림을 붙이는 지금이 만들 수 있는 때입니다」 뜻으로 씁니다. 고른 것은 범위를 `만든다 (4단계 백엔드 구현 때 채택, YYYY-MM-DD)`로 고치고 4-1 컬렉션·보안 규칙 설계와 아래 체크리스트(계정·키·권한이 더 필요한지 — 푸시 알림이면 FCM과 알림 권한, 서버 함수면 Blaze 요금제)에 넣습니다 — 화면이 늘면 화면 목록이 아니라 코드에 더합니다. 「이번에도 미룸」은 `나중에 — 6단계 출시 검증 뒤`로 옮깁니다(다시 꺼낼 자리가 남게). 그런 줄이 없거나 표가 없으면 건너뜁니다. 고른 기능이 계정·키를 더 부르면(메일 발송·AI 제공사 등) 이 체크리스트를 보여 주기 전에 고르므로 함께 들어갑니다.
1. 4단계에 들어서면 4-1보다 먼저 §2·§3을 한 화면 체크리스트로 만들어 보여 줍니다 — 그 프로젝트의 말로 풀어서, 배치 질문(SKILL.md §1.4 — 한 번에 묶어 묻기)으로 묻습니다. **Xcode 업데이트(§3.10)는 받는 데 오래 걸리니 맨 앞에 둡니다.**
2. 사람이 자기 몫을 끝냈다고 답하면, **AI가 명령으로 실제로 확인합니다** — `with-owner.sh --check`, `firebase projects:list`, `xcodebuild -version`, 설정 파일 대조 스크립트 등. 말만 믿고 넘어가지 않습니다.
3. AI 몫 중 결과가 밖으로 나가는 일(키 설치·비밀값 넣기·콘솔 설정)은 **위임하지 않고 메인이 직접 합니다**(`AGENTS.md`의 배포 위임 금지 원칙과 같은 이유입니다). 틀 넣기와 빌드 확인처럼 파일만 바꾸는 일은 위임해도 됩니다.
4. 리드타임이 긴 것(카카오 검수, OAuth 동의 화면 프로덕션 전환, 통신판매업 신고, 조직 정책 예외)은 시작만 시켜 두고 4-1로 넘어갑니다 — 완료를 기다리지 않습니다.
5. 장애나 권한 부족으로 막히면 막힌 항목만 사용자에게 넘기고, 나머지 4-1 작업은 계속합니다. 같은 실패가 2번 나면 멈추고 무엇이 실패했는지 알립니다. 로그인·가입 실패는 1번에 사람에게 넘깁니다(`docs/account-check.md` 원칙 ⑥).
