로그인은 버튼 하나 붙이는 일로 끝나지 않습니다. **어떤 정보를 받느냐**에 따라 동의를 받는 방식과 필요한 화면 수가 통째로 갈리고, 받고 난 뒤에는 그 상태를 유지·확인·강제하는 코드가 따로 필요합니다.

**이 문서는 두 덩이입니다.**

| | 앞부분 (§1~9) | 뒷부분 (§10~14) |
|---|---|---|
| 묻는 것 | **무엇을 받고 언제 동의받나** | 받은 뒤 그 상태를 **어떻게 유지·확인·강제하나** |
| 성격 | 법·흐름 설계 | 기술 표준 |
| 산출 | 온보딩 화면 구조 | 로그인·권한·세션 코드 |

앞부분이 정한 흐름(소셜 로그인 버튼 → 인증 → 신규만 온보딩) 위에 「로그인을 어떻게 붙이고, 권한을 어디서 막나」를 얹는 것이 뒷부분입니다. 그래서 앞에서 뒤로 순서대로 읽습니다.

> ⚠ **앞부분은 법률 자문이 아닙니다.** 한국에서 서비스하는 경우를 기준으로 정리한 실무 메모입니다. **정식 출시 전에는 사람이 법률 검토를 받아야 합니다.** 여기엔 법 조문 번호를 적지 않습니다 — 취지만 담았습니다.

> **뒷부분의 전제: Flutter 앱 + Firebase 고정 스택.** 다른 스택은 다루지 않습니다.
> **권한 규칙 자체는 `.claude/rules/security-baseline.md` 2부에 있습니다** — 기본 전부 거부, 규칙 모양, 권한 이름으로 묻기, 보호 필드, 서버 함수 안 권한 확인, 하지 말 것. 보안 규칙·서버 함수·`lib/core/firebase/` 코드를 만지면 자동으로 읽히니(정확한 목록은 그 파일의 `paths`) 여기 다시 옮겨 적지 않습니다. 뒷부분은 **한 번 밟는 절차**만 담습니다.

뒷부분의 각 항목 옆 표시는 근거 등급입니다 — **[공식]** 공급자 문서가 시킨 것 · **[우리 결정]** 우리가 골라 정한 것 · **[이전 앱에서 확인한 교훈]** 실제로 겪어서 아는 것.

> ⚠ **여기 적힌 외부 도구(Firebase·FlutterFire·카카오 SDK 등)의 패키지 이름·명령·화면 위치·동작은 이 글을 쓴 시점 기준입니다.** `AGENTS.md` 「규칙이 낡았을 때」대로 하되, 따라 하기 *전에* 확인합니다. **[공식] 표시가 붙은 것일수록 더 그렇습니다** — 남의 결정이라 우리 사정과 무관하게 바뀝니다. 반대로 **[우리 결정]**·**[이전 앱에서 확인한 교훈]**은 공식 문서에 없는 우리 몫이라 그대로 지킵니다.

## 1. 먼저 가를 것 — 선택 정보를 받나

로그인을 붙이기 전에 이것부터 답합니다. 답에 따라 흐름이 통째로 갈립니다.

판별 기준은 질문 하나입니다 — **이 정보가 없으면 서비스의 핵심 기능을 제공할 수 없나?**

| 구분 | 뜻 | 예 |
|---|---|---|
| 필수 | 없으면 서비스 이용 자체가 안 됨 | 로그인 계정 식별자, 메일, 결제 정보, 배송 서비스의 주소 |
| 선택 | 없어도 서비스는 돌아감 — 부가 기능·맞춤용 | 성별, 나이, 직업, 관심사, 마케팅 수신, 추천인 코드 |

**서비스 목적에 따라 달라집니다** — 성인 인증이 필요한 서비스면 나이가 필수가 됩니다. 고정 목록으로 외우지 말고 위 질문으로 매번 가릅니다.

**갈림길 — 여기서 읽을 곳이 갈립니다**:

| 답 | 읽을 절 |
|---|---|
| 필수만 받는다 | **2번 → 9번**. 3~8번은 안 읽어도 됩니다 |
| 선택도 받는다 | 2번부터 9번까지 전부 |

어느 쪽이든 9번을 지나면 뒷부분(10번부터)으로 이어서 갑니다.

## 2. 필수 정보만 받는 경우 — 고지문 한 줄로 끝

서비스 제공에 꼭 필요한 정보는 **계약을 이행하려고 받는 것**이라 별도 동의 절차 없이 받을 수 있습니다. 적용된다는 사실만 알리면 됩니다 — 로그인 버튼 아래 한 줄이면 충분합니다.

> 가입 또는 로그인 시 이용약관과 개인정보처리방침이 적용됩니다.

**동의를 간주하는 표현은 쓰지 않습니다** — 「계속하면 동의하는 것으로 봅니다」 같은 문장. 한국 개인정보 보호법이 인정하지 않는 방식이라 위반 소지가 됩니다.

여기까지면 화면이 늘지 않습니다. **9번(약관·개인정보처리방침 페이지)만 마저 하면 끝입니다.** 화면에 실제로 뜨는 문구의 말투는 `mvp/design-brief.md`의 「보이스 앤 톤」이 정본입니다 — 위 문장은 내용의 본보기입니다.

## 3. 선택 정보를 받는 경우 — 지켜야 할 것 셋

| # | 지킬 것 | 어기면 |
|---|---|---|
| 1 | 필수 동의와 선택 동의를 하나로 묶지 않습니다 — [전체 동의] 하나로 퉁칠 수 없습니다. 체크박스를 따로 둡니다 | 동의를 제대로 받은 게 아니게 됩니다 |
| 2 | 선택 동의를 거부해도 가입을 막지 않습니다 | 과태료 대상 |
| 3 | 데이터 클래스와 보안 규칙에서 선택 정보 필드는 **없어도 되게** 만듭니다 — 앱의 데이터 클래스는 빈 값을 받고, 규칙은 그 필드가 없어도 통과시킵니다 | 2번을 코드가 못 지킵니다 |

3번이 **법 요구가 데이터 모양으로 내려오는 자리**입니다. 동의 항목(필수/선택·동의 시각·약관 판)은 사용자 문서에 함께 담고, 보안 규칙과 규칙 테스트에 반영합니다(`4-1-backend-db.md` §5·§6).

## 4. 소셜 로그인은 가입과 로그인을 구분하지 못합니다

버튼 하나가 둘 다 처리합니다. 처음 온 사람인지 다시 온 사람인지는 **소셜 로그인 서비스에 갔다 와야** 압니다.

그래서 로그인 버튼 *앞*에 동의 체크박스를 두면 **다시 온 사람이 로그인할 때마다 매번 체크**하게 됩니다. (실제 사례: 체크 상태가 화면 안에만 있어서 화면을 열 때마다 풀렸습니다.)

즉 선택 동의를 받으려면 **가입과 로그인을 내부에서 갈라야 합니다** — 3번이 5번으로 이어지는 고리가 여기입니다.

## 5. 그래서 이 구조를 씁니다 — 인증 뒤 신규만 온보딩으로

```
소셜 로그인 버튼(구글·카카오)
  → 인증 완료
  → 사용자 문서(users/{uid})가 있고 필수 동의가 끝났는지 조회
      ├ 기존 회원 → 바로 들어감 (아무것도 안 물어봄)
      └ 신규      → 온보딩 화면
                     (필수) 약관·처리방침 동의
                     (선택) 마케팅 수신, 추가 정보
                     → 사용자 문서 만들기 → 가입 완료
```

다시 온 사람은 아무것도 안 걸립니다.

- **온보딩 화면이 새로 필요해집니다** — 다른 화면과 같은 방법으로 만듭니다. `design-system` 스킬 방법론을 따릅니다(토큰 이름으로만 색·간격·글자를 고르고, 값을 직접 쓰지 않습니다).
- **신규 판별의 기준은 「사용자 문서와 필수 동의가 있나」입니다** — 로그인 수단이 알려 주는 「처음 로그인」 표시에 기대지 않습니다(§11.3).
- **로그인은 클라우드에서만 확인됩니다** — 에뮬레이터를 쓰지 않으니, 개발용 프로젝트에 붙은 개발용 앱으로 확인합니다.

## 6. 체크박스를 로그인 앞에 두려 한다면 — 막다른 길 둘

「한 번 동의한 걸 어디에 기억하나」를 정해야 하는데, 이 단계에서는 둘 다 막힙니다.

| 기억할 자리 후보 | 왜 막히나 |
|---|---|
| 기기 안 저장소 | 동의는 오래 남아야 하는 기록인데, 앱을 지우거나 기기를 바꾸면 사라집니다. 이 단계는 기기 안에 데이터를 쌓던 경로를 걷어냅니다 |
| Firestore | 로그인해야 쓸 수 있는데 동의는 로그인 전에 받아야 합니다. 순서가 꼬입니다 |

그래서 5번 구조가 답입니다.

## 7. 소셜 로그인 창에서 선택 동의를 받는 방법 — 기록은 우리 몫

카카오처럼 일부 소셜 로그인은 개발자 콘솔에서 받을 항목을 필수/선택으로 나눠 두면 **그쪽 로그인 화면에서 대신 동의를 받아** 결과를 함께 넘겨줍니다.

그래도 **「언제 무엇에 동의했는지」 기록을 우리 DB에 남길 책임은 우리에게 있습니다.** 신규 가입 시점에 기록을 남기는 절차(5번 온보딩)는 그대로 필요합니다.

## 8. 가입 때 자동으로 도는 함수가 있으면 동의 전에 가입이 끝납니다

계정이 만들어지는 순간 사용자 문서를 자동으로 만드는 서버 함수(Firebase Auth의 「사용자 생성」 트리거나 차단 함수)를 붙이는 경우가 많습니다. 카카오 로그인처럼 서버 함수가 계정을 만드는 경우도 같습니다. 그러면 **동의를 받기 전에 계정이 이미 있습니다.**

1번에서 가른 답을 그대로 따릅니다.

| 1번의 답 | 할 일 |
|---|---|
| 선택도 받는다(동의 기록이 필요하다) | 자동으로 만드는 사용자 문서에는 동의 필드를 비워 두고, 「필수 동의 시각이 없으면 신규」로 판별합니다(§11.3). 동의 시각·약관 판 필드는 데이터 모양을 정할 때 미리 잡습니다 |
| 필수만 받는다 | 미리 넣을 필요 없습니다. 나중에 필드를 더하는 비용도 크지 않습니다 |

**동의 시각은 서버 시간으로 넣고, 앱이 고칠 수 없게 합니다** — 사용자가 동의 기록을 뒤로 고치면 기록의 뜻이 없어집니다. 처음 쓸 때만 허락하고 그 뒤로는 바꾸지 못하게 규칙을 겁니다.

## 9. 약관·개인정보처리방침 페이지가 필요해집니다

링크만 걸고 페이지가 없으면 죽은 링크입니다. **로그인을 붙이는 이 단계에서 두 페이지도 함께 갖춥니다.** 플레이도 개인정보처리방침 **웹 주소**를 요구하고, 계정을 만드는 앱이면 **앱 밖에서 계정 삭제를 요청할 수 있는 웹 주소**와 앱 안 삭제 기능도 요구합니다(§11.4). 웹 페이지는 실서비스 프로젝트의 Firebase Hosting에 둡니다 — 3단계 배포 전에 개인정보처리방침만 먼저 올렸으면 여기서 내용을 실제 수집 항목에 맞게 고칩니다.

| 지킬 것 | 왜 |
|---|---|
| 앱 안에서 언제든 찾아볼 수 있는 자리에 링크를 둡니다(예: 설정 화면) | 로그인 화면에만 두면 이미 로그인한 사람은 찾을 길이 없습니다 |
| 내용은 실제로 받고 저장하는 것만 사실대로 적습니다 | 안 받는 정보를 적어 두는 것도 사실과 다른 말입니다 |
| 처리를 맡기는 곳(Firebase 등)과 해외로 가는 데이터를 적습니다 | 서버가 해외에 있으면 국외 이전 고지가 필요합니다 |
| 세게 들리는 면책 조항을 지어내지 않습니다 | 근거 없이 지어낸 문장은 효력도 없고 위험만 남습니다 |
| AI가 쓴 초안이고 법률 검토가 필요하다는 표시를 페이지에도 남깁니다 | 출시 전 사람의 검토를 빠뜨리지 않게 |

## 10. 손대기 전에 로그인 쪽 공식 문서를 받아 읽습니다

**받아 읽는 절차는 `4-1-backend-db.md` §4와 같습니다** — 기억으로 짜지 않고 실제로 받아 읽고, 우리 틀과 맞춰 보고, 공식과 다르게 간 줄에만 `// 공식은 X, 우린 Y, 이유는 Z` 주석을 남깁니다. 여기서는 로그인 쪽에서 받아 읽을 것만 적습니다. **[공식 + 우리 결정]**

| 무엇을 쓰기 전에 | 받아 읽을 것 |
|---|---|
| 앱의 로그인 상태 다루기 | FlutterFire 문서의 Authentication 시작하기·로그인 상태 지켜보기, `firebase_auth` 패키지 예제 |
| 구글 로그인 | FlutterFire 문서의 소셜 로그인(구글) 절, `google_sign_in` 패키지의 설명과 판올림 안내(판이 크게 바뀔 때 부르는 방법이 바뀐 적이 있습니다), 구글의 안드로이드 클라이언트 인증(서명 지문) 문서 |
| 카카오 로그인(앱) | 카카오 디벨로퍼스의 Flutter SDK 문서 — 카카오톡으로 로그인·카카오 계정으로 로그인, 키 해시 등록 |
| 카카오 토큰 확인(서버 함수) | 카카오 디벨로퍼스의 REST API 문서 — 토큰 정보 보기, 사용자 정보 가져오기 |
| 커스텀 토큰 | Firebase 문서의 「커스텀 토큰 만들기」(관리자 SDK)와 FlutterFire의 커스텀 토큰 로그인 |
| 역할 | Firebase 문서의 「사용자 정의 클레임으로 접근 제어」 |
| 권한 테스트 | Firebase 문서의 보안 규칙 단위 테스트(로그인한 사용자 흉내에 클레임 넣기) |

> 패키지 이름·페이지 이름은 바뀔 수 있습니다. 없으면 공식 문서에서 지금 자리를 찾고, 이 문서를 고쳐야 한다고 보고합니다.

## 11. 로그인 붙이기

로그인은 Firebase Authentication(Firebase의 로그인 기능)이 맡습니다. 앱은 어느 로그인 수단을 쓰든 마지막에 **Firebase에 로그인한 사용자 하나**(`uid`)를 얻고, 보안 규칙과 서버 함수는 그 `uid`만 봅니다. 콘솔 쪽 준비(지문·키 해시·동의 화면)는 4-0 §3.6에서 끝나 있어야 합니다.

**로그인 코드의 자리** — 로그인 수단마다 「소셜 로그인 → Firebase 로그인」을 하는 코드는 로그인 기능 폴더의 저장·조회 코드(repository) 한 곳에 둡니다. 화면은 그 코드를 부르기만 하고, `FirebaseAuth.instance`를 직접 부르지 않습니다(틀의 `firebase_providers.dart`가 공급합니다). 실패는 `Result`로 돌려줘 화면이 오류 상태를 고릅니다 — 「사용자가 로그인 창을 닫음」은 오류가 아니라 취소로 다룹니다.

### 11.1 구글 로그인

1. 앱이 `google_sign_in`으로 기기 안 구글 로그인 창을 띄워 구글 토큰을 받습니다. **[공식]**
2. 그 토큰으로 Firebase 로그인 자격 증명을 만들어 Firebase에 로그인합니다. **[공식]**
3. 안드로이드는 **서명 지문**으로 앱을 알아봅니다. 지문 셋(개발용 앱의 디버그 키, 실서비스 앱의 플레이 앱 서명 키 + 업로드 키)이 4-0 §4.1 표대로 들어가 있고, 그 뒤 설정 파일을 다시 받았는지 확인합니다. **하나라도 빠지면 「내 폰에서는 되는데 스토어 판에서는 안 되는」 사고가 납니다** — 플레이는 올린 앱을 구글이 보관한 키로 다시 서명해 내보내기 때문입니다. **[공식 + 이전 앱에서 확인한 교훈]**
4. iOS 시뮬레이터에서도 구글 로그인을 하려면 iOS 설정 파일(`GoogleService-Info.plist`)의 「역방향 클라이언트 ID」를 앱의 URL 스킴으로 등록합니다. flavor마다 설정 파일이 다르니 값도 flavor마다 다릅니다 — 빌드 설정 값으로 갈라 넣습니다. **[공식]**
5. **확인** — 개발용 앱으로 개발 기기에서 사람이 눌러 봅니다. 실서비스 쪽 지문은 4단계 베타 공유(플레이 시험 트랙에서 받은 앱)에서 처음 확인됩니다 — 그때 안 되면 지문부터 봅니다.

### 11.2 카카오 로그인 — 서버 함수가 커스텀 토큰을 만듭니다

**카카오는 Firebase가 기본으로 지원하는 로그인 수단이 아닙니다.** 그래서 이렇게 잇습니다. **[우리 결정]**

```
① 앱: 카카오 SDK로 로그인 → 카카오 액세스 토큰을 받음
② 앱: 호출형 서버 함수에 카카오 액세스 토큰을 보냄
③ 서버 함수: 그 토큰을 카카오에 직접 물어 확인
     - 토큰 정보 보기 → 이 토큰이 「우리 카카오 앱」에서 발급됐는지(app_id) 확인
     - 사용자 정보 가져오기 → 카카오 회원번호(id)와 동의한 항목(닉네임·사진)
④ 서버 함수: uid = "kakao:<카카오 회원번호>"로 Firebase 커스텀 토큰을 만들어 돌려줌
     (그 uid의 Firebase 계정이 없으면 만들고, 표시 이름·사진을 넣음)
⑤ 앱: 그 커스텀 토큰으로 Firebase에 로그인
```

**지킬 것**

- **서버 함수는 앱이 보낸 회원번호를 믿지 않습니다.** 카카오 토큰만 받아, 회원번호는 카카오에 물어서 얻습니다. 앱이 회원번호를 보내게 하면 남의 번호를 넣어 남의 계정으로 들어옵니다. **[우리 결정]**
- **토큰이 우리 앱 것인지 봅니다** — 토큰 정보의 `app_id`가 우리 카카오 앱 ID와 같아야 합니다. 다른 카카오 앱에서 받은 토큰을 들고 와도 회원번호는 나오기 때문입니다. 우리 앱 ID는 서버 함수 설정 값으로 둡니다. **[공식 + 우리 결정]**
- **카카오가 일시 오류를 내면 로그인 실패로 처리하고 다시 시도하게 합니다** — 토큰 정보 보기는 「일시적 플랫폼 오류」와 「토큰이 틀림·만료」를 다른 코드로 돌려줍니다. 앞의 것을 「틀린 토큰」으로 다루지 않습니다. 정확한 코드는 카카오 문서로 확인합니다. **[공식]**
- **uid에 앞머리를 붙입니다**(`kakao:`) — 나중에 다른 로그인 수단을 더해도 번호가 겹치지 않습니다. **[우리 결정]**
- **커스텀 토큰은 한 시간 안에 써야 합니다** — 앱은 받자마자 로그인하고, 저장해 두지 않습니다. **[공식]**
- **이 함수에 App Check를 붙입니다** — 로그인 함수는 로그인 전에 불리므로 `request.auth`로 막을 수 없습니다. 「진짜 우리 앱」 확인이 유일한 문입니다. 강제는 `security-baseline.md` 2부의 단계대로 켭니다. **[우리 결정]**
- **커스텀 토큰을 만들려면 서명 권한이 필요할 수 있습니다** — 서버 함수 안의 관리자 SDK는 기본 서비스 계정으로 토큰에 서명하는데, 그 계정에 서명 권한(`iam.serviceAccounts.signBlob` — 보통 「서비스 계정 토큰 생성자」 역할로 줌)이 없으면 실패합니다. 개발용에서 처음 실패하면 그 권한부터 봅니다. 실서비스에도 같은 권한을 `backend-release` 전에 맞춥니다. **[공식]**
- **카카오 REST API 키는 이 흐름에 필요 없습니다** — 사용자 토큰으로 묻기 때문입니다. 연결 끊기처럼 관리자 키가 필요한 일을 할 때만 서버 함수 비밀값으로 넣습니다(§11.4).
- **함수 이름·코드 자리** — `functions/src/auth/` 기능 폴더에 둡니다. 「토큰 정보 응답이 이러면 허락·거부」 같은 판단은 Firebase 없이 도는 순수 함수로 떼어 단위 테스트를 둡니다(`4-1-backend-db.md` §8.2·§10.2).

**다른 길 — OIDC 연결** — 카카오는 OpenID Connect(OIDC — 로그인 결과를 서명된 신분 토큰으로 주는 표준)를 지원하고, Firebase도 OIDC 로그인 수단을 받을 수 있습니다. 이 길이면 서버 함수가 없어집니다. 대신 Firebase Authentication을 **Identity Platform으로 올려야** 하고, OIDC 수단은 요금 구간이 기본 로그인 수단과 다를 수 있으며, 카카오는 앱 키와 웹 키가 갈려 수단을 따로 등록해야 한다는 보고가 있습니다. 그래서 기본안은 커스텀 토큰이고, OIDC로 가려면 그때 Identity Platform 요금 안내와 FlutterFire의 OIDC 로그인 문서를 확인해 사용자에게 비교를 보여 주고 정합니다(ADR에 남깁니다).

**페이스북 로그인은 MVP에서 쓰지 않습니다.** 이전 앱에서 확인한 교훈: 소셜 로그인 플러그인, 특히 페이스북 것은 iOS를 붙일 때 호환 문제가 컸습니다.

### 11.3 첫 로그인과 신규 판별

- **신규 판별은 사용자 문서로 합니다** — 로그인한 뒤 `users/{uid}` 문서를 읽어, 없거나 필수 동의 시각이 비어 있으면 온보딩으로 보냅니다(§5). 로그인 결과에 붙는 「처음 로그인」 표시는 쓰지 않습니다 — 온보딩 중간에 앱을 끄고 다시 열면 그 표시는 이미 「처음 아님」이라, 동의 없이 들어가게 됩니다. **[우리 결정]**
- **사용자 문서는 본인만 만들고, 소유자 필드는 `uid`와 같아야 합니다** — 규칙 모양은 `security-baseline.md` 2부, 동의 시각을 서버 시간으로 한 번만 쓰는 것은 §8.
- **소셜 쪽 이름을 그대로 공개 이름으로 쓰지 않습니다** — 구글은 실명을, 카카오는 닉네임을 줍니다. 공개되는 작성자 이름이 있으면 온보딩에서 한 번 확인받습니다. 사진도 같습니다.

### 11.4 로그아웃과 탈퇴

- **로그아웃** — Firebase에서 로그아웃하고, 그 사용자가 쓴 로그인 수단(구글·카카오)의 기기 안 로그인도 함께 끊습니다. 안 끊으면 다음 로그인 때 계정 고르기 창 없이 같은 계정으로 바로 들어가, 「다른 계정으로 로그인」이 안 됩니다.
- **탈퇴(계정 삭제)는 앱 안에 있어야 합니다** — 플레이가 계정을 만드는 앱에 요구합니다. 탈퇴는 서버 함수가 합니다 — 사용자 문서·사용자가 올린 파일·Firebase 계정을 지우고, 카카오면 카카오 연결 끊기를 부릅니다. 지우는 범위(남기는 기록이 있으면 무엇을 왜)는 개인정보처리방침과 맞춥니다.
- **앱 밖 삭제 요청** — 웹 페이지(Hosting)의 삭제 요청 폼은 HTTP 서버 함수(`deletionRequest`)가 받아 클라이언트 읽기·쓰기가 막힌 컬렉션에 쌓고, 처리는 사람이 하거나 서버 함수가 합니다(`4-1-backend-db.md` §7.3).
- 탈퇴처럼 민감한 일은 Firebase가 「최근 로그인」을 요구할 수 있습니다. 그 오류가 오면 다시 로그인시킨 뒤 이어서 합니다. **[공식]**

## 12. 역할은 사용자 정의 클레임에, 판정은 권한 이름으로

**근거는 「모든 프로젝트에 역할이 둘 이상 필요하다」가 아닙니다.** 그건 확인된 게 아닙니다. 근거는 **추가 부담이 작다**는 것입니다 — 실제 부담은 규칙 규율(기본 전부 거부·동작 나눠 쓰기·규칙 테스트)인데, 그건 역할을 나누든 안 나누든 지켜야 합니다. 그 위에 역할 구조를 얹는 비용은 판정 함수 하나와 클레임을 붙이는 스크립트 하나뿐입니다. **[우리 결정]**

**역할을 담는 자리 — 사용자 정의 클레임** — 사용자 정의 클레임(custom claims)은 서버가 로그인 토큰에 붙이는 값입니다. 보안 규칙과 호출형 서버 함수 모두 `request.auth.token.<이름>`으로 읽습니다. **관리자 SDK로만 붙일 수 있어서 사용자가 고칠 수 없습니다.** 사용자가 쓸 수 있는 문서 필드로 권한을 판단하지 않는 이유가 이것입니다(`security-baseline.md` 2부). **[공식]**

### 12.1 규칙 넷

**규칙 1 — 역할은 클레임의 목록 하나(`roles`)에 담습니다.** 「운영자인가」 같은 예·아니오 클레임(`isOperator: true`)으로 시작하지 않습니다. 예·아니오는 셋째 역할이 생기면 클레임을 또 만들어야 하고, 한 사람이 여러 역할을 갖는 것도 따로 다뤄야 합니다. 목록이면 값 하나를 더하면 끝입니다. **[우리 결정]**

**규칙 2 — 일반 회원에게는 클레임을 붙이지 않습니다.** 클레임에는 **특별한 역할만** 담습니다. 「로그인한 사람」은 `request.auth != null`이 이미 거릅니다. 회원 전원에게 `member`를 붙이는 것은 같은 말의 반복이고, 붙이는 일을 빠뜨린 사람만 조용히 막힙니다. **[우리 결정]**

**규칙 3 — 규칙과 서버 함수는 신분이 아니라 권한 이름으로 묻습니다.** ← **넷 중 제일 중요합니다** **[우리 결정]**

원칙과 이유는 `security-baseline.md` 2부에 있습니다. 여기선 우리가 정한 모양만 적습니다 — **판정 함수는 역할 이름이 아니라 권한 이름을 받아 예/아니오를 돌려줍니다**(`can('reports.resolve')`). 「어느 권한을 어느 역할이 갖나」는 함수 안에만 둡니다.

```
// firestore.rules — 판정 함수
function rolesWith(permission) {
  return {
    'reports.resolve': ['operator'],
    'posts.hide':      ['operator', 'moderator']
  }.get(permission, []);
}
function can(permission) {
  return request.auth != null
    && request.auth.token.get('roles', []).hasAny(rolesWith(permission));
}

match /reports/{id} {
  allow update: if can('reports.resolve') && /* 바꿀 수 있는 필드 제한 */ true;
}
```

(위 권한·역할 이름은 예시입니다. 그 프로젝트의 것으로 채웁니다. 규칙 언어의 함수 이름은 그때 공식 문서로 확인합니다.)

**서버 함수에도 같은 판정 함수를 둡니다** — 서버 함수는 보안 규칙을 거치지 않으니, 권한이 필요한 함수는 함수 안에서 `can(request.auth, 'reports.resolve')`로 직접 묻습니다. 판정 함수는 `functions/src/auth/permissions.ts` 한 곳에 두고, 권한↔역할 표는 규칙의 것과 **같은 내용**이어야 합니다. 두 곳이라 어긋날 수 있으므로, **두 표는 같은 커밋에서 함께 고치고** 같은 경우를 규칙 테스트와 함수 단위 테스트가 함께 고정합니다(§13).

**규칙 4 — 표는 함수 안에서 시작하고, 관리가 필요해지면 옮깁니다.** 역할이 적을 때는 함수 안 표가 가장 단순합니다. 규칙 3을 지켰으면 표를 옮기거나 키워도 `allow` 줄은 한 줄도 안 바뀝니다. **[우리 결정]**

**바깥 모양(`can('권한')`)은 처음부터 고정하고, 안쪽 표는 자라게 둡니다** — 이게 규칙 3·4의 요지입니다.

### 12.2 미루는 것 셋

| 미루는 것 | 왜 |
|---|---|
| 역할 부여 화면 | 4단계 범위 밖입니다. 부여는 메인이 스크립트로 합니다(§12.3 ①) |
| 권한↔역할 표를 DB로 옮기기 | 규칙이 표를 읽으려면 문서 읽기가 매 요청 더 듭니다. 역할이 적을 땐 함수 안 표가 싸고 단순합니다 |
| 문서마다 다른 권한(이 게시판의 운영자만 등) | 클레임은 모든 문서에 같은 역할을 줍니다. 문서별 권한이 정말 필요해지면 그때 보호 필드(서버 함수만 쓰는 필드)로 따로 설계합니다 |

### 12.3 클레임을 쓸 때 같이 정해 둘 것

**① 역할을 붙이고 떼는 길은 하나입니다.** 관리자 SDK로 클레임을 쓰는 스크립트(`functions/scripts/` 아래)를 두고, 메인이 사람의 확인을 받은 뒤 돌립니다. 개발용은 개발용 관리자 키로(4-0 §3.4의 실행 꼴), 실서비스는 실서비스 키 파일을 만들지 않으므로 권한을 가진 서버 함수를 거쳐 main에서 메인이 합니다. 앱에서 역할을 붙이는 길은 만들지 않습니다. **[우리 결정]**

**② 클레임은 바로 반영되지 않습니다.** 클레임은 로그인 토큰에 실려 가는데, 토큰은 정해진 주기로만 새로 받습니다(공식 문서 기준 최대 한 시간). **[공식]** 그래서:

- 역할을 **붙였으면** — 그 사용자의 앱이 토큰을 새로 받아야 보입니다. 앱에 「토큰 새로 받기」(`getIdToken(true)`)를 부르는 자리를 하나 둡니다(예: 앱이 앞으로 올 때).
- 역할을 **뗐으면** — 옛 토큰이 남은 동안은 권한이 살아 있습니다. 운영자 권한을 급히 거둬야 하면 클레임을 지운 뒤 그 사용자의 갱신 토큰을 폐기해(관리자 SDK의 갱신 토큰 폐기) 다시 로그인시킵니다. 이 차이를 사용자에게 미리 말해 둡니다.

**③ 클레임은 작게 둡니다.** 클레임 전체 크기에 상한이 있고, 토큰이 모든 요청에 실려 갑니다. 역할 이름 목록만 담고, 프로필 같은 데이터는 문서에 둡니다. 정확한 상한은 공식 문서로 확인합니다. **[공식]**

**④ 권한 이름은 `컬렉션.동작` 꼴로 통일합니다**(`reports.resolve`). 규칙에서 쓰는 이름과 서버 함수에서 쓰는 이름을 따로 지으면 **존재하지 않는 권한을 부르게 됩니다** — 그 경우 판정은 언제나 「아니오」라 조용히 막힙니다. 실제로 쓸 것만 만듭니다. **[우리 결정]**

**⑤ ⚠ 문서 필드로 역할을 판단하던 코드에서 옮겨 오면, 기존 값을 클레임으로 옮기는 일을 같은 작업에 넣습니다.** 판정만 클레임으로 바꾸고 기존 운영자에게 클레임을 안 붙이면 **권한이 통째로 사라지는데 오류가 안 납니다.** 옮기는 스크립트를 개발용에서 먼저 돌리고, 실서비스는 대상 목록을 사람에게 보여 확인받은 뒤 메인이 돌립니다. **[우리 결정]**

## 13. 권한은 테스트로 고정합니다

보안 규칙 테스트(`rules-test/`, 공식 도구 `@firebase/rules-unit-testing`)는 로그인한 사용자를 흉내 낼 때 **토큰에 클레임을 함께 넣을 수 있습니다** — 「운영자인 척」·「일반 회원인 척」·「로그인 안 한 척」을 같은 규칙에 차례로 대 봅니다. 규칙 테스트는 CI에서만 돕니다(`4-1-backend-db.md` §10.1). **[공식]**

**① 최소 셋은 반드시 씁니다.** 다 쓰면 유지가 안 되니 범위를 셋으로 고정합니다.

1. 공개여야 하는 것이 **로그인 안 한 사람에게 보이는가**
2. 남의 것이 **안 보이는가**(본인 문서만 읽는 컬렉션)
3. 권한이 필요한 일이 **일반 회원에게 막히고, 그 권한을 가진 역할에게만 열리는가** — `can()`을 쓰는 `allow` 줄마다

**② 클레임이 없는 사람, 엉뚱한 역할을 가진 사람을 꼭 넣습니다.** 「운영자는 된다」만 시험하면, 판정 함수가 아무에게나 「예」를 돌려줘도 통과합니다. 거부되어야 하는 경우(`assertFails`)를 허락되는 경우(`assertSucceeds`)보다 많이 둡니다. **[우리 결정]**

**③ 서버 함수의 판정 함수도 같은 경우로 단위 테스트를 둡니다.** 규칙의 표와 함수의 표가 어긋나면 둘 중 하나의 테스트가 깨지게, 같은 권한·역할 짝을 양쪽에 씁니다(§12.1 규칙 3). **[우리 결정]**

**④ 문서에 「이 컬렉션은 공개」라고 적지 않습니다 — 테스트가 그 기록입니다.** **[우리 결정]** 글로 적으면 코드와 어긋나는 날이 옵니다. 테스트로 적어 두면 실수로 닫았을 때 깨지고, 실수로 열어도 「공개 아님」 테스트가 깨집니다.

**⑤ 로그인 흐름 자체는 기기에서 사람이 봅니다.** 구글·카카오 로그인 창은 규칙 테스트로 흉내 낼 수 없습니다. 개발용 앱으로 개발 기기에서 사람이 눌러 확인하고, 카카오 서버 함수의 판단 부분만 단위 테스트로 고정합니다.

## 14. 세션 층 — Firebase Auth가 기기에 저장·갱신합니다

**① Firebase Auth가 이미 해 주는 것** **[공식]**: 로그인 상태를 기기에 저장해 앱을 다시 열어도 로그인돼 있게 하고, 짧게 사는 로그인 토큰을 만료 전에 알아서 새로 받고, 상태가 바뀌면(로그인·로그아웃·토큰 갱신) 알림 흐름(`authStateChanges`·`idTokenChanges`)으로 알려 줍니다. 구체적인 주기와 이름은 패키지 판에 따라 달라질 수 있으니, 그 값에 기대는 코드를 쓸 거면 공식 문서로 지금 값을 확인합니다. 여기서 중요한 건 숫자가 아니라 「이미 해 준다」는 사실입니다.

**② 그래서 세션을 앱이 따로 저장하지 않습니다.** 로그인 여부·`uid`·토큰을 기기 안 저장소나 별도 provider 상태에 복사해 두지 않고, 언제나 Firebase Auth의 알림 흐름에서 읽습니다. 없어도 될 복사본이 **「로그인이 풀렸는데 화면은 로그인한 것처럼 보이는」** 버그를 낳습니다. **[우리 결정]**

**③ 「로그인했나」로 화면을 가르는 곳은 한 곳입니다 — go_router의 로그인 문지기.** 화면 이동 표(`lib/app/router.dart`)의 이동 전 확인(redirect) 한 곳이 Firebase Auth 상태를 보고 로그인 화면·온보딩·원래 가려던 화면 중 하나로 보냅니다. 화면마다 「로그인 안 했으면 돌려보내기」를 따로 넣지 않습니다 — 흩어지면 어느 화면 하나가 빠집니다. **[우리 결정]**

**④ 로그인 뒤 돌아갈 화면** — 문지기가 로그인 화면으로 보낼 때 원래 가려던 주소를 함께 넘기고(예: `/login?from=/posts/42`), 로그인이 끝나면 그 주소로 보냅니다. 넘어온 값은 **앱 안 주소(`/`로 시작)인지 확인**하고, 아니면 첫 화면으로 보냅니다 — 딥링크(앱 밖에서 앱의 특정 화면을 여는 링크)로 엉뚱한 값이 들어올 수 있습니다(`security-baseline.md` 1부). **[우리 결정]**

**⑤ 로그인 전에 받은 입력은 한 곳에서 맡았다가 한 곳에서 돌려줍니다.** 카카오톡으로 로그인하면 앱이 카카오톡으로 잠시 넘어갑니다. 그동안 안드로이드가 메모리를 아끼려고 우리 앱을 끌 수 있어서, 화면 안에만 있던 입력은 사라질 수 있습니다. 그래서 로그인 전 입력을 지켜야 하면 기기 안 저장소에 맡기고, 로그인 문지기를 지난 뒤 **한 지점에서만** 꺼내 지웁니다. 맡기는 곳과 꺼내는 곳이 둘 이상으로 흩어지면 이 방식은 반드시 깨집니다. **[우리 결정]**

**⑥ 남는 인증 오류는 다시 시도로 해결되지 않습니다.** 토큰 갱신을 Firebase Auth가 하므로, 서버가 「로그인 정보가 없다·틀렸다」를 돌려주는 경우는 대개 계정이 지워졌거나·갱신 토큰이 폐기됐거나(§12.3 ②)·App Check에 막힌 경우입니다. 같은 요청을 되풀이하지 않고, 로그아웃시켜 로그인 화면으로 보내거나 오류 상태를 보여 줍니다. **[우리 결정]**

**로그인 상태가 필요한 흐름을 개발 중에 되풀이해 확인할 때**는, 매번 실제 소셜 로그인을 거치지 않아도 되게 4-1의 시드 스크립트가 **개발용 프로젝트에만** 고정 ID 테스트 계정(`seed-` 머리말)을 만듭니다. 기기 통합 테스트가 그 계정으로 로그인하는 방법은 4-3의 스모크 테스트 절이 정합니다. 실제 소셜 로그인 왕복은 로그인 자체를 확인할 때만 사람이 합니다.
