이 문서는 2단계의 맨 앞 하위 단계입니다. 2단계는 **`2-0-dev-setup.md`(개발환경 준비) → `2-1-mockup.md`(기능·화면 목록과 주요 화면) → `2-2-mockup-design-upgrade.md`(전문가 수준 디자인 개선) → `2-3-personality.md`(개성 입히기)** 순서로 갑니다. 단계 번호는 하나라 대화가 끊기지 않고 이어집니다.

**왜 맨 앞인가** — 2단계는 화면을 그림이 아니라 실제 앱과 같은 Flutter 코드로 바로 만듭니다. 그러려면 그 바닥 — 앱 뼈대, 고정한 판, 디자인 토큰, 셸, 목업 캔버스 — 이 먼저 있어야 합니다. 여기서 만든 코드는 버리는 물건이 아닙니다. 2-1이 그 위에 주요 화면을 짓고, 3단계가 남은 화면을 더해 플레이 내부 테스트로 내고, 4단계가 Firebase를 붙입니다. 처음부터 끝까지 앱은 하나입니다.

**들어오는 때** — 1단계가 끝나 `mvp/intent.md`와 `mvp/design-brief.md`가 있고, 루트에 앱 코드(`pubspec.yaml`)가 아직 없을 때입니다 (SKILL.md §1.2). 2단계에 처음 들어오면 이 문서와 `2-1-mockup.md`를 함께 읽습니다. 2단계 시작 안내(`2-1-mockup.md` §2.1)에 이 문서의 도구 점검표와 이름 확인 질문(§2.1)을 얹어 한 메시지로 냅니다.

**이 문서는 2-1과 나란히 돕니다** — 이름 확인 답이 오면 §2.2~§2.6은 서브 에이전트 하나가 끝까지 하고, 그동안 메인은 2-1의 기능 목록·화면 목록(`2-1-mockup.md` §2.3~§2.5)을 씁니다. 둘은 서로 기다리지 않습니다. 셸의 메뉴만 화면 목록 8절(메뉴 구조)이 나온 뒤 한 번 맞춥니다(§2.5 4번). 2-1의 주요 화면 만들기(`2-1-mockup.md` §2.6)는 이 문서가 끝난 뒤에 시작합니다.

## 1. 단계 목표

이 문서의 목표는 **2-1이 주요 화면을 Flutter로 바로 만들 수 있는 바닥을 까는 것**입니다. 끝나면 아래가 있습니다.

- **루트 앱 코드 뼈대** — 고정 스택으로 만든 Flutter 앱(안드로이드·iOS, 폰만). 개발용(`dev`)·실서비스용(`prod`) 두 벌 빌드(flavor — 같은 코드로 설정만 다른 앱 두 벌을 빌드하는 장치)와 진입점 둘, 안드로이드 서명 자리, 다국어 문구 파일 구조가 들어 있습니다. Firebase는 아직 붙지 않고, 앱은 Firebase 없이 돕니다.
- **고정한 판** — Flutter 판은 `.fvmrc`, Node 주 판은 `.nvmrc`에 적혀 있고, 이 맥·CI가 같은 판을 씁니다. 패키지 판은 `pubspec.lock`에 남습니다. 이 맥에 없던 도구는 AI가 깔았거나, 사람 몫이면 사람이 마쳤습니다.
- **기술 결정 기록** — `mvp/adr.md`(ADR — 왜 그 기술·판을 골랐는지 적어 두는 문서)에 서비스 이름·패키지 이름, 판 조합, 안드로이드 빌드 도구 판.
- **디자인 시스템 첫 세팅** — `lib/core/design/`의 토큰 세 층과 테마, 앱에 넣은 한글 서체, 모든 화면에 씌우는 셸, 감싸개 부품, 부품 목록 문서(`docs/components.md`), `AGENTS.md`의 「디자인 시스템 연결 정보」 절.
- **목업 캔버스 뼈대** — iPad 시뮬레이터(맥 안에서 도는 가상 아이패드)에 띄우는 캔버스 진입점(`lib/main_canvas.dart`), 「[서비스 이름] 디자인 시스템」 페이지, 목록 파일, 상태 흉내, 코멘트 서버, 골든 테스트 준비.

**여기서 안 하는 것 (의도적)**:

- ❌ **화면** — 주요 화면은 2-1 §2.6이 만듭니다. 이 문서는 셸까지입니다.
- ❌ **Firebase** — 프로젝트 만들기·설정 파일·패키지는 4단계 준비(`4-0-backend-prep.md`)에서 계정을 확정한 뒤에 합니다. 2·3단계 데이터는 기기 안 저장소(`shared_preferences`)에 담깁니다. 화면이 굳기 전에 데이터 구조를 먼저 짜 두면, 화면 구조가 뒤집힐 때 그 작업이 통째로 버려지기 때문입니다.
- ❌ **플레이 콘솔·업로드 키** — 3단계 배포 절(`3-frontend-build.md`)이 합니다. 여기서는 서명을 빌드 설정에 잇는 자리만 둡니다(§2.3).
- ❌ **프로젝트 전용 variant**(부품의 모양 종류 — 버튼의 주 버튼·보조 버튼 같은 것)와 브리프 「12. 화면 규칙」의 코드 반영 — 2-2가 규칙을 정한 뒤에 합니다 (`2-2-mockup-design-upgrade.md`). 지금 1층에 들어가는 값은 대부분 브리프 「4」의 출발값(`가정`)이라, 2-2가 바꿀 것을 미리 굳히지 않습니다.

## 2. 진행 절차

### 2.1 시작 — 도구 점검과 이름 확인

**도구 점검표 — 2-0을 시작할 때 한 번에 봅니다.** 메인이 이름 확인 질문을 내기 전에 아래 확인 명령을 실제로 돌리고, 결과를 한 표로 같은 메시지에 붙입니다. 빠진 도구를 처음에 한 번에 알려야 단계 중간에 하나씩 멈추지 않습니다. 특히 사람 몫(Xcode 설치, Android Studio 첫 설정, 폰의 USB 디버깅)은 시간이 걸리니, 개발환경 준비가 뒤에서 도는 동안 사람이 함께 하도록 맨 앞에 알립니다.

**누가 까나 — 세 갈래입니다.**

- **AI가 묻지 않고 깝니다** — 2단계에 꼭 필요하고 가벼운 도구입니다. 깐 뒤 결과만 표로 알립니다.
- **AI가 묻고 깝니다** — 용량이 커서(수 GB) 사용자가 정해야 하는 도구입니다. Android Studio가 여기 듭니다.
- **사람이 합니다** — 앱 스토어 로그인, 약관 동의, 관리자 암호, 폰 설정처럼 AI가 대신할 수 없는 일입니다. AI는 화면 이름 그대로 한 단계씩 안내합니다.

**지금(2단계) 필요한 도구**

| 도구 | 하는 일 | 확인 명령 | 없으면 |
|---|---|---|---|
| git·gh·jq | 코드 변경 이력, GitHub 명령 도구, 하네스 훅(명령 전후에 저절로 도는 검사 스크립트)이 쓰는 JSON 읽기 도구 | `git --version`, `command gh --version`, `jq --version` | git·gh는 프로젝트를 처음 만들 때 `github-connect` ①②가 확인했습니다. jq가 없으면 메인이 점검 때 `github-connect` ③대로 바로 깝니다 — 없으면 main으로 바로 올리기를 막는 훅이 `git push`를 전부 막습니다 |
| fvm | 프로젝트마다 Flutter 판을 골라 쓰게 해 주는 도구 | `fvm --version` | AI가 깝니다(§2.2) |
| Flutter SDK | 앱을 만드는 도구 본체(수백 MB) | `fvm flutter --version` | fvm이 `.fvmrc`에 적힌 판을 받습니다(§2.2). Homebrew로 깔린 Flutter가 따로 있어도 그대로 두고 쓰지 않습니다 |
| Xcode + iOS 시뮬레이터 | iOS 빌드 도구와 가상 아이폰·아이패드. **개발 기기이자 목업 캔버스 자리**입니다 | `xcodebuild -version`, `xcrun simctl list devices available` | **사람 몫** — 아래 「Xcode 준비」 |
| CocoaPods(없을 수 있음) | 옛 방식의 iOS 플러그인 묶음 도구. 최신 Firebase Apple SDK는 CocoaPods 배포를 끝내고 Swift Package Manager(Xcode의 패키지 관리 도구)로만 나오며, Flutter도 SPM이 기본입니다. SPM을 지원하지 않는 플러그인이 생겼을 때만 필요합니다 | `pod --version` | 지금은 깔지 않습니다. 그런 플러그인이 생겼을 때 AI가 `brew install cocoapods`로 깝니다 |
| xcodeproj(Ruby 도구) | Xcode 프로젝트 파일을 고치는 도구. 앱 뼈대 틀의 iOS flavor 스크립트가 씁니다 | `ruby -e 'require "xcodeproj"; puts Xcodeproj::VERSION'` | AI가 `gem install --user-install xcodeproj`로 깝니다 — 사용자 폴더에 깔아 관리자 암호가 필요 없습니다 |
| Android Studio + Android SDK | 안드로이드 빌드 도구. Android Studio 안에 자바 실행기(JDK)도 들어 있습니다 | `fvm flutter doctor` | **AI가 묻고 깝니다**(수 GB) — 허락하면 `brew install --cask android-studio`. 첫 설정과 약관은 **사람 몫** — 아래 「Android Studio 준비」 |
| JDK(자바) | 안드로이드 빌드 도구(Gradle)가 씁니다. 지도 패키지가 높은 판을 요구해서, CI(`.github/workflows/ci.yml`의 `java-version`)와 같은 판 이상이어야 합니다 | `fvm flutter doctor -v`의 Java 줄 | Android Studio에 든 것을 씁니다. 판이 낮으면 Android Studio를 최신으로 올립니다 |
| 실제 안드로이드폰 | 개발 기기. USB로 연결합니다 | `fvm flutter devices`에 보이는지 | **사람 몫** — 아래 「안드로이드폰 준비」 |
| Node.js(fnm) | 4단계의 서버 함수·Firebase CLI·보안 규칙 테스트가 이 위에서 돕니다. 앱 코드와는 상관없습니다 | `fnm --version`, `fnm exec --using=.nvmrc -- node -v` | 가벼워서 지금 AI가 깔아 둡니다(§2.2) — 4단계 준비가 기다리지 않게 하려는 것입니다 |
| Aside(견본 이미지 검색용 브라우저) | 화면을 채울 견본 이미지를 무료 사진 사이트(Pexels·Unsplash·Pixabay)에서 검색합니다. 이 세 사이트는 명령(curl)으로는 검색이 막히고 Aside로는 열립니다 | `command -v aside` | **있으면 아무것도 깔지 않습니다.** 없으면 명령줄 도구를 공식 설치 명령(`curl -fsSL https://releases.aside.com/install.sh \| bash`)으로 AI가 깔고, 브라우저 앱은 「aside.com/download에서 받아 설치해 주세요」라고 안내합니다. 미루거나 실패해도 멈추지 않습니다 — 견본 이미지는 Burst로 채웁니다 |

**나중 단계에서 깔 도구** — 지금 깔지 않고, 점검표에도 넣지 않습니다. 그 단계 문서가 깝니다.

| 도구 | 하는 일 | 언제 |
|---|---|---|
| Firebase CLI | Firebase 배포·프로젝트 관리 명령 도구. 저장소 최상위 `package.json`의 개발 의존성으로 판을 고정합니다 | 4단계 준비(`4-0-backend-prep.md`) |
| FlutterFire CLI | 앱에 Firebase 설정 파일을 만들어 주는 도구 | 4단계 준비 |
| fastlane | 스토어 정보·앱 번들을 플레이에 올리는 도구 | 6단계 앞 |

**Xcode 준비 (사람 몫)** — Xcode가 없거나 낡았을 때만 안내합니다.

1. 맥의 App Store에서 Xcode를 받거나 업데이트합니다. 용량이 커서(수십 GB) 시간이 걸립니다.
2. 터미널에서 아래 두 줄을 차례로 칩니다. 관리자 암호를 묻고, 두 번째 줄은 약관을 보여 줍니다(`agree` 입력).

   ```bash
   sudo sh -c 'xcode-select -s /Applications/Xcode.app/Contents/Developer && xcodebuild -runFirstLaunch'
   sudo xcodebuild -license
   ```

3. 끝나면 「됐어」라고 알려 주시면 됩니다. 그다음 iOS 시뮬레이터 받기(`xcodebuild -downloadPlatform iOS`)는 AI가 합니다.

**Xcode가 4단계에 필요한 판보다 낮으면 지금 알립니다.** Firebase iOS SDK 최신 판은 최신 Xcode가 있어야 빌드됩니다. Xcode가 낡으면 4단계에서 iOS 빌드가 「firebase-ios-sdk … contains incompatible tools version」으로 멈춥니다. 2단계에는 Firebase가 없어 지금 Xcode로도 되니, 점검표의 「이어서 하는 일」 칸에 「4단계 전에 App Store에서 Xcode를 최신으로 업데이트해 주세요(용량이 큽니다)」라고 적어 둡니다. 판단 근거는 Firebase iOS SDK 공식 저장소의 요구 Xcode 판과 지금 `xcodebuild -version`입니다.

**Android Studio 준비 (사람 몫)** — AI가 Android Studio를 깐 뒤에 안내합니다.

1. Android Studio를 한 번 엽니다. 첫 화면의 설정 마법사(Setup Wizard)에서 「Standard」를 고르고 끝까지 진행합니다. Android SDK를 내려받는 단계와 약관 동의가 여기 있습니다.
2. 첫 화면 「More Actions → SDK Manager」 → 「SDK Tools」 탭에서 「Android SDK Command-line Tools」에 체크하고 「Apply」를 누릅니다. 이 도구가 있어야 다음 약관 명령이 돕니다.
3. 터미널에서 프로젝트 폴더로 가 `fvm flutter doctor --android-licenses`를 치고, 나오는 약관마다 `y`를 누릅니다. 「All SDK package licenses accepted」가 나오면 됩니다.

**안드로이드폰 준비 (사람 몫)** — 폰 화면 이름은 제조사마다 조금 다릅니다. 안내할 때 「삼성이면 이 이름」처럼 사용자의 폰에 맞춰 바꿔 말합니다.

1. 폰의 「설정 → 휴대전화 정보 → 소프트웨어 정보」에서 「빌드 번호」를 일곱 번 누릅니다. 「개발자 모드를 켰습니다」가 뜹니다.
2. 「설정 → 개발자 옵션」에서 「USB 디버깅」을 켭니다.
3. 폰을 USB로 맥에 연결하면 폰에 「USB 디버깅을 허용하시겠습니까?」가 뜹니다. 「이 컴퓨터에서 항상 허용」에 체크하고 「허용」을 누릅니다.

AI는 `fvm flutter devices`로 폰이 보이는지 확인합니다. 폰 준비는 2-1에서 화면을 직접 만져 볼 때 필요하니, 지금 안 돼도 이 문서는 멈추지 않습니다.

**점검표를 보여 주는 문안** — 판 숫자는 그때 확인한 값을 넣습니다. 골자:

> 시작하기 전에 이 맥에 필요한 도구가 있는지 봤습니다.
>
> | 도구 | 상태 | 이어서 하는 일 |
> |---|---|---|
> | git·gh·jq | 있음 | 없음 |
> | fvm·Flutter | 없음 | 제가 깔고, 이 프로젝트에 쓸 Flutter 판을 정하겠습니다 |
> | Xcode | [판]판 있음 | [없음 / 4단계 전에 App Store에서 최신으로 업데이트해 주세요(용량이 큽니다)] |
> | Android Studio | 없음 | 수 GB라 여쭙니다 — 깔아도 될까요? 깔고 나면 첫 설정과 약관 동의를 한 단계씩 안내하겠습니다 |
> | 안드로이드폰 | 연결 안 됨 | 폰에서 USB 디버깅을 켜 주세요(아래 안내). 2-1에서 화면을 만져 볼 때 필요합니다 |
> | Node.js | 있음([판]판) | 4단계 서버 함수용 판을 정해 제가 따로 받아 두겠습니다. 원래 있던 판은 그대로 둡니다 |
> | Aside(견본 이미지 검색용 브라우저) | [있음 / 없어서 제가 깔겠습니다] | [없음 / 앱 설치가 필요하면 안내하겠습니다] |

다 있으면 표 대신 「필요한 도구는 다 있습니다」 한 줄로 줄입니다. 사람 몫이 있으면 표 아래에 위 「준비」 단계 중 해당하는 것만 붙입니다.

**깐 것을 알리는 문안** — 개발환경 준비 서브 에이전트의 보고가 오면, 메인이 그다음 응답에 이 맥에 깐 것을 결과 표로 붙입니다. 깐 것이 없으면 내지 않습니다. 골자(판 숫자와 방법은 보고 그대로):

> 개발환경을 준비하며 이 맥에 깐 것입니다.
>
> | 도구 | 한 일 |
> |---|---|
> | fvm(Flutter 판 관리 도구) | Homebrew(맥용 프로그램 설치 도구)로 깔았습니다 |
> | Flutter [판]판 | fvm으로 이 프로젝트용으로 받았습니다. 원래 있던 Flutter는 그대로 두었습니다 |
> | fnm(Node 판 관리 도구)·Node.js [판]판 | 4단계 서버 함수용으로 받았습니다. 원래 있던 Node는 그대로 두었습니다 |
> | xcodeproj | iOS 빌드 설정을 고치는 도구라 깔았습니다 |

표 행은 실제로 한 일만 남깁니다. 사람 몫이 남았으면 표 아래에 한 줄로 적고, 그 일이 꼭 지금 필요한지도 함께 적습니다.

**이름 확인 — 인터뷰 모드입니다** (SKILL.md §1.5 에스컬레이션 기준 (c) "결과를 되돌리기 비싼 갈림길"). 앱을 만들기 전에 서비스 이름과 패키지 이름을 확인받습니다.

**왜 앱을 만들기 전인가** — 패키지 이름(`app.example` 같은 앱의 고유 이름. iOS에서는 번들 ID)은 앱을 만드는 명령(`flutter create`)에 들어가 안드로이드·iOS 설정 수십 곳에 박힙니다. 그리고 플레이에 한 번 올리면 바꿀 수 없습니다 — 바꾸면 스토어에서 완전히 다른 앱이 됩니다. 나중에 바꾸면 옛 이름이 설정 구석구석에 남습니다. 이전 앱에서 확인한 교훈입니다. 그래서 첫 명령 전에 한 번 못 박습니다.

**무엇을 확인하나** — 1단계 끝에서 정한 서비스 이름과 패키지 이름(`1-intent.md`가 적어 두는 자리)을 그대로 보여 주고 확인만 받습니다. 1단계에서 정하지 못했으면 여기서 정합니다.

| 값 | 뜻 | 예 |
|---|---|---|
| 서비스 이름 | 홈 화면에 뜨는 앱 이름 | 예시앱 |
| 패키지 이름 | 앱의 고유 이름. 보통 가진 도메인을 거꾸로 씁니다(`example.app` → `app.example`). 개발용 앱은 끝에 `.dev`가 붙습니다 | `app.example`(개발용 `app.example.dev`) |
| Dart 패키지 이름 | 코드 안에서 쓰는 이름. 패키지 이름의 마지막 조각입니다(영문 소문자·숫자·`_`) | `example` |

질문 골자:

> 앱을 만들기 전에 이름 하나만 확인하겠습니다. 앱 이름은 **[서비스 이름]**, 앱의 고유 이름(패키지 이름)은 **`[패키지 이름]`** 으로 만들겠습니다. 패키지 이름은 플레이에 한 번 올리면 바꿀 수 없어서, 지금 맞는지 꼭 봐 주세요.
>
> 예시 답변: 「그대로 가 주세요」 / 「도메인을 바꿀 거라 `com.예시`로 해 주세요」

**답이 오면** 확정 값을 `mvp/adr.md`에 한 항목으로 적고(「ADR-NNNN: 서비스 이름·패키지 이름 — 플레이에 올리면 못 바꿈」), 확정한 패키지 이름을 `AGENTS.md` 「이 프로젝트가 쓰는 도구」 첫 문단의 「앱 패키지 이름」 줄에 적습니다(예: 「앱 패키지 이름은 `app.example`(개발용 앱은 `app.example.dev`)이다.」). 처음에는 그 줄이 「(2-0 개발환경 준비에서 채움)」으로 비어 있고, 이미 값이 있으면 확정 값과 같은지 보고 다르면 고칩니다. 그다음 바로 §2.2부터 위임합니다.

**스택은 묻지 않습니다** — Flutter + Firebase로 고정이고, 지원 기기는 폰뿐입니다(§2.2). 이미 루트에 `pubspec.yaml`이 있으면(스킬 중간 재실행 등) 묻지 않고 §3 체크리스트로 검증해 빠진 것만 보완합니다 — 처음부터 다시 만들지 않습니다.

### 2.2 판 맞추기 — Flutter·Node·안드로이드 빌드 도구

**고정 스택 — 후보 제시·사용자 선택 없음.** idea-to-mvp 앱은 무조건 이 조합으로 빌드합니다.

| 영역 | 고정 |
|---|---|
| 언어·SDK | Flutter stable + Dart, fvm으로 판 고정 |
| 지원 기기 | 폰만(안드로이드·iOS). 태블릿은 지원하지 않습니다 — 목업 캔버스 빌드만 예외로 아이패드에 뜹니다(§2.6) |
| 부품 바탕 | Material 3 |
| 상태 관리 | Riverpod 3 + `riverpod_generator`(코드 생성) + `riverpod_lint`(Riverpod 전용 린트) |
| 화면 이동 | go_router — 화면 하나 = 경로 하나 |
| 2·3단계 저장 | `shared_preferences`(기기 안 이름=값 저장소)에 JSON으로 |
| 백엔드 | FlutterFire(Firebase 공식 Flutter 플러그인 모음) — 4단계에서 붙입니다 |
| 오류 모양 | `Result<T>` + `AppError` — 앱 뼈대 틀이 깝니다 |
| 다국어 | Flutter 공식 다국어(`flutter_localizations` + `.arb` 문구 파일). 문구 파일 구조는 처음부터 두고, 넣는 말은 한국어뿐입니다 |
| 린트 | `flutter_lints` + `riverpod_lint` |
| 테스트 | `flutter_test`(내장) + 골든 테스트 도우미 하나 + `integration_test` |

**왜 고정** — 2단계에서 만든 화면 코드가 그대로 실서비스 화면이 되려면 처음부터 실서비스와 같은 바닥 위에서 지어야 합니다. 그리고 빌드가 싼 시대엔 *뭘 쓸지*를 매번 고르는 일을 없애고 *뭘 만들지*에 집중합니다. 고정 스택 밖의 패키지(지도·아이콘 등)는 검증 가설에 필요할 때만 더합니다. 2-3(개성 입히기)이 고른 판과 수단에 따라 수단 패키지(지도·음성·카메라·센서 등)를 들이는 것도 이 규칙 안의 추가입니다 — 판을 고정하고 `adr.md`에 기록합니다. 스택에서 빼거나 다른 것으로 갈아타지 않습니다.

**판 숫자는 이 문서에 적지 않습니다** — 판은 빨리 바뀝니다. 그때 조사해 `mvp/adr.md`에 적고, 3·4단계는 그 기록을 참조만 합니다. 조사는 공식 문서·pub.dev(Flutter 패키지 저장소)·npm registry로 하고, 학습 시점 이후의 판은 기억으로 적지 않습니다.

**Flutter 판부터 정합니다.**

1. **fvm 깔기** — `fvm --version`이 되면 건너뜁니다. 없으면 묻지 않고 공식 설치 방법으로 깝니다.
   - Homebrew가 있으면: `brew tap btwld/fvm && brew install btwld/fvm/fvm`
   - Homebrew가 없거나 위 명령이 실패하면: `curl -fsSL https://fvm.app/install.sh | bash`
   - 공식 설치 스크립트로 깔았으면 `~/fvm/bin`에 생기고 명령 경로(PATH)에는 없습니다. 셸 설정 파일은 고치지 않으니, 이 프로젝트의 flutter·dart 명령은 `~/fvm/bin/fvm`처럼 전체 경로로 부르거나 명령 앞에 `PATH=$HOME/fvm/bin:$PATH`를 붙입니다. 이 사실을 `AGENTS.md` 「이 프로젝트가 쓰는 도구」의 fvm 줄과 이후 지시서에 한 줄로 넘깁니다. 빌드 잠금 스크립트(`build-lock.sh`)는 `fvm`이 명령 경로에 없으면 `~/fvm/bin/fvm`을 스스로 찾아 씁니다. 사람에게는 `~/.zshrc`에 `export PATH="$HOME/fvm/bin:$PATH"`를 넣으면 터미널에서도 `fvm`이 된다고 안내합니다.
   - 같은 실패가 두 번이면 멈추고 무엇이 실패했는지 보고합니다.
2. **고를 판** — 지금의 Flutter stable 최신입니다. Flutter 공식 릴리스 목록으로 확인합니다.

   ```bash
   curl -s https://storage.googleapis.com/flutter_infra_release/releases/releases_macos.json \
     | jq -r '.current_release.stable as $h | .releases[] | select(.hash == $h) | .version'
   ```

   Xcode·Android 빌드 도구가 그 판을 받는지는 아래 5번의 빌드와 `fvm flutter doctor`로 확인합니다. 막히면 바로 앞 stable로 한 단계 물러서고 ADR에 이유를 적습니다.
3. **판 고정** — 저장소 최상위 폴더에서 `fvm install <판>` → `fvm use <판> --force`. `.fvmrc`(Flutter 판 한 줄이 든 JSON — 정본)와 `.fvm/` 폴더가 생깁니다. `--force`는 아직 `pubspec.yaml`이 없어 fvm이 묻는 확인을 건너뛰게 합니다. `.fvm/`은 무시 목록(`.gitignore`)에 들어가야 합니다 — fvm이 스스로 더하지만, 들어갔는지 확인합니다. `.fvmrc`는 git에 올립니다.
4. **부르는 법** — 이 프로젝트의 flutter·dart 명령은 언제나 `fvm flutter …`·`fvm dart …`로, 저장소 최상위 폴더에서 부릅니다. fvm이 그 폴더의 `.fvmrc`를 읽어 판을 고르므로 셸 설정 파일을 고칠 필요가 없습니다. 이 맥에 Homebrew로 깔린 Flutter는 지우지도 바꾸지도 않습니다 — 사용자의 다른 프로젝트가 쓸 수 있어서입니다.
5. **확인** — `fvm flutter --version`의 판이 `.fvmrc`와 같은지, `fvm flutter doctor`가 무엇을 빠졌다고 하는지 봅니다. 사람 몫(Xcode·Android SDK·약관)으로 빠진 것은 보고에 남기고 이어 갑니다.

**판을 맞춰야 하는 자리**

| 자리 | 맞추는 법 |
|---|---|
| 이 맥 | `.fvmrc` + `fvm flutter …`(위 3·4번) |
| `pubspec.yaml`의 `environment` | Dart `sdk`와 `flutter` 하한을 고른 판에 맞춥니다 |
| CI | `.github/workflows/ci.yml`이 `.fvmrc`를 읽어 같은 판을 깝니다 — 따로 고칠 것이 없습니다. CI의 Flutter를 「stable 최신」으로 바꾸지 않습니다. 이전 앱에서 확인한 교훈: CI만 판이 앞서가 빌드가 어긋났습니다 |
| 안드로이드 빌드 도구 | `flutter create`가 넣은 Gradle·안드로이드 Gradle 플러그인·Kotlin 판과 JVM 타깃(자바 바이트코드 판)을 ADR에 적어 둡니다. **Flutter 판을 올릴 때마다 이 넷을 함께 확인합니다** — 이전 앱에서 확인한 교훈: Flutter를 올리자 안드로이드 JVM 타깃이 어긋나 빌드가 깨졌습니다 |
| `.nvmrc` | Node 주 판(아래) |

**Node 주 판을 정합니다** — Node.js(자바스크립트 실행기)는 앱이 아니라 4단계의 서버 함수(Cloud Functions, TypeScript)·Firebase CLI·보안 규칙 테스트가 씁니다. 가벼우니 지금 받아 두어 4단계 준비가 기다리지 않게 합니다.

1. **고를 주 판** — 아래 셋을 모두 만족하는 것 중 가장 새 것입니다.
   - ① Cloud Functions for Firebase가 지원합니다 — Firebase 공식 문서 「Node.js 버전 설정」의 지원 목록으로 확인합니다. 4단계에서 서버 함수 실행 판이 이 값을 그대로 씁니다.
   - ② Firebase CLI가 받습니다 — `curl -s https://registry.npmjs.org/firebase-tools/latest | jq -r .engines.node`
   - ③ LTS(장기 지원판 — 오래 보안 수정을 받는 판)입니다. Node.js 공식 릴리스 일정으로 확인합니다.

     ```bash
     curl -s https://raw.githubusercontent.com/nodejs/Release/main/schedule.json \
       | jq -r --arg t "$(date +%F)" 'to_entries[] | select(.value.lts != null and .value.lts <= $t and .value."end" > $t) | "\(.key) LTS 시작 \(.value.lts) 지원 끝 \(.value."end")"'
     ```

2. **`.nvmrc`** — 루트에 주 판 숫자 한 줄을 적어 git에 올립니다. CI의 Node 단계가 이 파일을 읽습니다. `package.json`은 지금 만들지 않습니다 — 4단계 준비에서 앱 뼈대 틀의 backend 묶음이 넣습니다.
3. **fnm으로 받기 — 묻지 않고 합니다.** fnm(Node 판 관리 도구 — 여러 판을 깔아 두고 명령마다 골라 쓰게 해 주는 프로그램)으로 이 프로젝트의 판만 받습니다. 원래 있던 Node·Homebrew는 지우지도 바꾸지도 않습니다.
   - **fnm 깔기** — `fnm --version`(또는 `~/.local/share/fnm/fnm --version`)이 되면 건너뜁니다. Homebrew가 있으면 `brew install fnm`. 그것이 실패하거나 Homebrew가 없으면 fnm 공식 GitHub 릴리스의 실행 파일을 사용자 폴더에 풉니다(관리자 암호 창이 뜨지 않습니다).

     ```bash
     tmp="$(mktemp -d)" && mkdir -p ~/.local/share/fnm \
       && curl -fsSL -o "$tmp/fnm-macos.zip" https://github.com/Schniz/fnm/releases/latest/download/fnm-macos.zip \
       && unzip -o "$tmp/fnm-macos.zip" -d ~/.local/share/fnm && chmod +x ~/.local/share/fnm/fnm && rm -rf "$tmp"
     ```

   - **판 받기** — `fnm install <주 판>` 뒤 `fnm exec --using=.nvmrc -- node -v`로 주 판을 확인합니다.
   - **부르는 법** — 이 프로젝트의 node·npm·npx 명령은 언제나 `fnm exec --using=.nvmrc --`를 앞에 붙여 저장소 최상위 폴더에서 부릅니다. fnm이 명령 경로에 없으면 `~/.local/share/fnm/fnm`처럼 전체 경로로 부릅니다.
   - **하지 않는 것** — 셸 설정 파일(`~/.zshrc` 등)에 fnm을 넣지 않습니다. `fnm env`·`fnm use`·`fnm default`는 셸 설정이 있어야 듣는 명령이라 쓰지 않습니다. AI의 명령은 부를 때마다 새 셸에서 돌아 앞 명령의 상태가 이어지지 않으니, 명령마다 판을 붙이는 방식이 맞습니다.
   - **실패하면** — 같은 실패가 두 번이면 멈추고 알립니다. Node는 4단계에야 쓰므로, 이 문서의 나머지는 이어 갑니다.

**패키지를 들이기 전에 확인합니다** — 고정 스택 밖의 패키지를 더할 때마다(이 문서에서든 뒤 단계에서든) pub.dev에서 「최근 발행일·지원 플랫폼·관리 주체」를 봅니다. 1년 넘게 새 판이 없거나 안드로이드·iOS 중 하나를 지원하지 않으면 들이지 않고 다른 길을 찾습니다. 이전 앱에서 확인한 교훈: 관리가 끊긴 패키지 하나 때문에 Flutter를 올리자 컴파일이 깨졌습니다. 들인 패키지와 확인 결과는 ADR에 한 줄씩 적습니다.

**ADR에 적는 것** — 고른 Flutter 판과 그 근거, Dart 하한, Node 주 판과 ①②③을 무엇으로 확인했는지, 안드로이드 빌드 도구 넷의 판, 고정 스택 밖으로 들인 패키지. 패키지의 정확한 판은 `pubspec.lock`이 기록하니 ADR에 옮겨 적지 않습니다. 이 맥에 무엇을 깔았는지는 컴퓨터마다 다른 일이라 ADR이 아니라 보고와 「깐 것을 알리는 문안」에 적습니다.

### 2.3 앱 뼈대 — flavor 둘과 서명

**하네스가 틀을 줍니다** — 앱 뼈대는 `.claude/templates/firebase/`(app 묶음), 서명은 `.claude/templates/android-signing/`에 있습니다. 넣는 순서·파일·채울 자리는 두 폴더의 `README.md`가 정본이고, 여기 다시 적지 않습니다. 이 절은 그 순서를 돌리며 지킬 것만 적습니다.

**차례** (앱 뼈대 틀 `README.md` §3의 ①~⑪):

1. **앱을 만듭니다** — `fvm flutter create --org <패키지 앞부분> --project-name <Dart 패키지 이름> --platforms android,ios .` 값은 §2.1에서 확정한 것입니다. 예를 들어 패키지 이름이 `app.example`이면 `--org app --project-name example`입니다.
2. **견본 둘 지우기 → app 묶음 복사(`apply.sh app`) → 패키지 들이기** — 패키지는 판 숫자를 적지 않고 `pub add`가 고르게 둡니다. 틀이 정한 목록에 더해 고정 스택의 나머지 셋을 함께 들입니다.

   ```bash
   fvm flutter pub add shared_preferences
   fvm flutter pub add dev:riverpod_lint
   ```

   `riverpod_lint`를 켜는 법(분석기에 붙이는 설정)은 판마다 바뀌어 왔으니 Riverpod 공식 문서(riverpod.dev)의 설치 안내대로 합니다. 안내대로 `analysis_options.yaml`의 `plugins:`에 붙이면 그 린트는 `fvm flutter analyze`에서는 돌지 않고 `fvm dart analyze`에서만 돕니다(2026-10 실측, Flutter 3.47) — 그래서 이 하네스의 모든 분석 자리는 두 명령을 함께 돌립니다. 두 명령 말고 따로 돌려야 하는 명령이 또 생기면 ADR과 보고에 적습니다. `flutter_lints`는 `flutter create`가 이미 넣습니다.
3. **상태 흉내 파일 → `pubspec.yaml`·`analysis_options.yaml` → 안드로이드 flavor → 안드로이드 서명** — 서명은 서명 틀 `README.md`의 「넣는 순서」입니다. 업로드 키는 지금 만들지 않습니다 — 키가 없으면 개발용 서명으로 빌드되고, 3단계 배포 전에 만듭니다.
4. **iOS flavor** — `ruby tool/ios_flavors.rb <패키지 이름> <서비스 이름>`. xcodeproj가 없으면 §2.1 표대로 깝니다.
5. **만들고 검사합니다** — 틀 `README.md` §3 ⑩의 명령 전부. iOS 빌드는 Xcode가, 안드로이드 빌드는 Android SDK가 있어야 하니, 없으면 그 빌드만 「남은 빌드」로 보고합니다.
6. **라우터·테마 연결(⑪)** — 테마는 §2.5가 디자인 시스템을 들인 뒤 잇습니다. 첫 화면 자리는 2-1이 첫 화면을 만들 때 바꿉니다.

**루트에 이미 있는 파일을 덮지 않습니다** — 루트에는 `AGENTS.md`·`CLAUDE.md`·`README.md`·`mvp/`·`docs/`·`.claude/`·`.github/`·`.gitignore`가 이미 있습니다. `flutter create`는 이미 있는 파일을 덮지 않고 건너뜁니다. 그래서 Flutter가 넣으려던 무시 목록 줄이 빠집니다. 같은 명령을 임시 폴더에서 한 번 더 돌려 만든 `.gitignore`의 줄을 루트 `.gitignore`에 합칩니다(이미 있는 줄은 그대로 둡니다). 그 밖에 겹치는 파일을 덮어야 할 것 같으면 멈추고 보고합니다.

**Firebase 없이 돕니다** — app 묶음의 백엔드 준비 자리(`lib/core/firebase/backend_init.dart`)는 아무것도 하지 않는 빈 판입니다. 4단계 준비가 backend 묶음으로 바꿔 넣습니다. 설정 파일 대조 스크립트도 Firebase 설정 파일이 없으면 그 부분을 건너뛰어 통과합니다.

**CI가 이때부터 돕니다** — CI(저장소에 올릴 때마다 자동으로 도는 검사)는 `pubspec.yaml`이 생기면 Flutter 검사를 돌리기 시작합니다. 그래서 위 5번이 모두 통과해야 합니다. 생성 파일(`*.g.dart`)과 `pubspec.lock`은 git에 올립니다 — CI가 「다시 만들었더니 달라졌다」를 잡습니다.

### 2.4 개발 기기 연결 — iOS 시뮬레이터와 안드로이드폰

개발 기기는 둘입니다. **iOS 시뮬레이터**(맥 안의 가상 아이폰)와 **USB로 연결한 실제 안드로이드폰**입니다. 개발에 Firebase 에뮬레이터(내 컴퓨터에서 Firebase를 흉내 내는 도구)는 쓰지 않습니다.

1. **iOS 시뮬레이터 — 이 프로젝트 전용 둘을 만듭니다** — Xcode가 준비됐으면 AI가 `xcodebuild -downloadPlatform iOS`로 시뮬레이터 런타임을 받습니다. 그다음 프로젝트 폴더 이름(저장소 최상위 폴더의 이름)을 붙인 시뮬레이터 둘을 `xcrun simctl create`로 만듭니다.
   - `<폴더 이름> 캔버스` — 목업 캔버스 자리입니다. 판이 넓게 보이도록 가장 큰 아이패드 기종으로 만듭니다.
   - `<폴더 이름> 폰` — 개발용 앱을 아이폰으로 보는 자리입니다. 보통 크기 아이폰 기종(예: iPhone 16)으로 만듭니다.

   ```bash
   xcrun simctl list devicetypes | grep -E "iPad|iPhone"   # 기종 이름 보기 — 아이패드는 화면이 가장 큰 것(13-inch 등)을 고른다
   NAME=$(basename "$PWD")
   xcrun simctl list devices | grep -qF "$NAME 캔버스 (" || xcrun simctl create "$NAME 캔버스" "<가장 큰 아이패드 기종 이름>"
   xcrun simctl list devices | grep -qF "$NAME 폰 (" || xcrun simctl create "$NAME 폰" "<아이폰 기종 이름>"
   ```

   - **왜 전용으로 만드나요?** — 한 맥에서 여러 프로젝트를 동시에 돌리면, 기종 이름(「iPad Pro 13-inch」 같은)으로 고른 시뮬레이터 하나에 두 프로젝트의 캔버스가 함께 뜹니다. 화면에는 나중에 띄운 것만 보여 사람이 어느 프로젝트를 보는지 헷갈립니다. 이름에 폴더 이름이 들어 있으면 시뮬레이터 창 제목만 보고 어느 프로젝트인지 압니다.
   - **이미 같은 이름이 있으면 새로 만들지 않고 그것을 씁니다** — 위 명령이 이름을 먼저 찾아봅니다. 같은 이름이 둘 이상 생기면 `flutter run -d`가 하나를 고르지 못하니, 하나만 남기도록 사람에게 알립니다(AI가 지우지 않습니다).
   - **이후 모든 실행 명령은 이 이름으로 기기를 부릅니다** — `flutter run -d "<폴더 이름> 캔버스"`처럼 씁니다. 사용자가 시킨 일로 iOS 시뮬레이터 조작 도구를 쓸 때도 이 이름을 기기 이름(`device`)으로 넘깁니다. 기기를 안 정하면 도구가 다른 프로젝트의 시뮬레이터를 고를 수 있습니다.
   - **꺼진 시뮬레이터는 `flutter run`이 찾지 못합니다** — 띄우기 전에 켭니다: `xcrun simctl boot "$NAME 캔버스" 2>/dev/null; open -a Simulator`(이미 켜져 있으면 첫 명령은 아무 일도 하지 않습니다).
   - **다른 프로젝트 이름의 시뮬레이터는 건드리지 않습니다** — 켜기·끄기·지우기·앱 깔기 모두입니다(`AGENTS.md` 「검증」).
2. **안드로이드폰** — 사람이 §2.1 「안드로이드폰 준비」를 마쳤으면 `fvm flutter devices`에 폰이 보입니다. 보이지 않으면 케이블(충전 전용 케이블이 아닌지)과 폰의 허용 창을 다시 보도록 안내합니다.
3. **실행 명령을 정해 둡니다** — 사람이 앱을 직접 띄울 때 쓰는 명령입니다. 2-1이 화면을 만든 뒤 보고에 그대로 붙입니다.

   ```bash
   fvm flutter run --flavor dev -t lib/main_dev.dart -d "$(basename "$PWD") 폰"   # 이 프로젝트 전용 아이폰 시뮬레이터
   fvm flutter run --flavor dev -t lib/main_dev.dart -d <폰 이름 또는 ID>         # USB로 연결한 안드로이드폰
   ```

   폰 이름·ID는 `fvm flutter devices`의 둘째 칸입니다. **안드로이드폰은 한 번에 한 세션만 씁니다** — 한 맥에서 여러 프로젝트 세션이 돌면 사람이 「지금 폰은 어느 세션이 쓴다」고 정하고, 다른 세션은 시뮬레이터로만 봅니다(`AGENTS.md` 「검증」).
4. **고친 것이 화면에 들어가는 길** — 코드를 고치면 반영하는 방법이 종류마다 다릅니다(핫 리로드 `r`, 핫 리스타트 `R`, 다시 빌드). 그 표는 `AGENTS.md` 「검증」 절에 있고, AI는 작업을 끝낼 때마다 그 표대로 「이제 무엇을 누르면 보이는지」 알립니다.

**이 절에서 화면을 보여 주지 않습니다** — 볼 화면이 아직 없습니다. AI는 기기에 앱을 띄워 판정하지 않습니다(`AGENTS.md` 「검증」).

### 2.5 디자인 시스템 첫 세팅

같은 하네스의 `design-system` 스킬 방법론대로, 그 스킬의 `bootstrap-project.md` §1~§4 순서로 갑니다. 메인이 그 절차를 한 번 읽고 작업에 닿는 제약을 지시서에 걸러 넣습니다 (§1 「위임 지시서에 꼭 넣을 것」). 파일 이름·클래스 이름·`context.*` 이름은 스킬이 정한 그대로 씁니다 — 디자인 규칙 검사·목업 캔버스·앱 뼈대 틀이 그 이름을 읽습니다.

1. **1층과 서체** (`lib/core/design/foundation.dart` — 숫자·색 값을 쓰는 유일한 파일) — 브리프 「4. 확정 브랜드 자산」의 「우리가 쓰는 값」 표로 채웁니다. 옮기는 법은 design-system `reference-analysis.md` §5입니다. 흰 바탕 대비 때문에 브리프 「4」의 값보다 한 단계 진한 단계에 이었으면(예: 위험색·성공색) 어느 색을 어느 단계로 이었는지 보고에 적고, 메인이 브리프 「4」 그 색 행에 「코드는 한 단계 진하게 — 대비」를 붙입니다.
   - **서체는 지금 앱에 넣습니다** — 표에 적힌 무료 한글 서체(유료면 대체 서체) 파일을 `assets/fonts/`에 두고 `pubspec.yaml`에 등록합니다. 방법은 design-system `font-loading.md`입니다. 실행 중에 인터넷으로 서체를 받는 패키지(`google_fonts`)는 쓰지 않습니다.
   - 서체를 지금 넣는 까닭이 하나 더 있습니다. 골든 테스트(§2.6) 안에는 폰의 기본 한글 서체가 없어서, 테마가 앱에 넣은 서체를 가리키지 않으면 한글이 네모 상자로 찍힙니다.
   - 움직임 기본 값도 1층에 자리만 잡습니다. 값은 3단계 모션 다듬기 절이 브리프 「8」로 정합니다.
2. **2층** (`semantic.dart` — 역할 이름) — Material `ColorScheme` 이름과 우리 확장 일곱 개를 1층 상수로 채웁니다.
3. **테마 조립과 접근 확장** (`theme.dart`·`tokens.dart`·`design.dart`) — 2층으로 `ThemeData`를 만들고, 화면이 값을 꺼내는 길을 `context.colors`·`context.space`·`context.text` 같은 이름 하나로 만듭니다. 그다음 앱 뼈대의 `lib/app/app.dart`에 `theme: buildAppTheme(AppTokens.light)`를 잇습니다(§2.3 6번). `test/app/router_test.dart`의 `_testApp`에 주석으로 둔 `theme:` 줄도 함께 풉니다 — 셸이 테마를 읽기 시작해도 라우터 테스트가 깨지지 않게 하려는 것입니다.
4. **셸** (`lib/app/shell.dart` — 모든 화면에 공통으로 씌우는 상단 바·하단 탭·바탕 틀) — `feature-list.md` 8절 「메뉴 구조」대로 만듭니다. 아직 없으면 브리프 「6. 주 사용 맥락」에 맞는 기본 메뉴로 만들고, 메인이 8절을 쓴 뒤 한 번 맞춥니다(메인이 직접 고치거나 같은 에이전트에 이어 맡깁니다). 셸은 상단·본문·하단 세 영역으로 시작하고, 안전 영역(`SafeArea` — 상태 표시줄·홈 표시줄 자리)을 셸이 맡습니다. 폰만 지원하니 화면 폭으로 메뉴를 바꾸는 갈래는 없습니다. 하단 탭이 있으면 go_router의 셸 경로가 이 셸을 감쌉니다. 탭의 경로는 아직 화면 목록이 없으니 임시 경로로 두고, 2-1 첫 화면 에이전트가 주소 모음 파일(`lib/app/paths.dart`)을 만들 때 셸이 그 파일을 쓰게 바꿉니다. 2-0이 경로를 지어 정하지 않습니다.
5. **감싸개 부품·대비 테스트·글자 배율 도우미** — 2-1의 주요 화면에 꼭 필요한 감싸개(`AppButton`·`AppTextField` 등 — Material 부품을 감싸 variant와 누르는 크기를 정한 우리 부품)만 `lib/shared/components/ui/`에 만듭니다.
   - **누르는 영역은 브리프 「9. 접근성 바닥선」의 값(48dp 이상)을 감싸개와 테마에 처음부터 넣습니다.** 화면 코드에서 덮어써 맞추지 않습니다. 브리프 「4」의 「부품 모양」 행이 그보다 작은 크기를 적었으면 「9」가 이기고, 그 어긋남을 보고에 적습니다.
   - 새 variant는 만들지 않습니다(§1). 「부품 모양」 행(버튼·카드·입력칸·상단 바의 생김새)은 테마로 먼저 풀고, 감싸개에서 Material 기본 모양을 바꿨으면 연결 정보의 「고친 Material 감싸개 목록」에 적습니다.
   - 대비 도우미(`contrast.dart`)와 2층 색 짝 대비 테스트, 글자 배율 2.0 검사 도우미(`test/helpers/text_scale.dart`)를 둡니다. 비교안 자리(`drafts.dart`)는 머리 주석만 둔 빈 파일로 만듭니다.
6. **부품 목록 문서** (`docs/components.md`) — 만든 감싸개와 셸 부품을 등록합니다. 형식은 design-system `component-taxonomy.md` §6이고, 문서 끝의 「## 전체 부품 색인」(부품 파일 경로 한 줄씩)까지 만듭니다 — 3단계 배포 전 검사가 이 색인과 실제 부품 파일을 대조합니다. 색인은 손으로 쓰지 않고 `component-taxonomy.md` §6.1이 정한 명령으로 만듭니다.
7. **연결 정보** (`AGENTS.md`의 「디자인 시스템 연결 정보」 절) — 그 절이 나열한 항목을 채웁니다. 토큰 파일 경로와 Dart 패키지 이름, 감싸개 부품 목록, 부품 목록 위치, 고친 Material 감싸개 목록, 철칙 요약, 적용 규칙 요약입니다. 「12」가 아직 `추후 결정`이라 간격 허용 목록은 비워 두고 2-2가 채웁니다. 브리프 「4」의 「서체 — 제목」이 이미 채워져 있어 1층에 제목 서체(`FoundationType.titleFamily`)를 넣었으면, 연결 정보에 그 서체 이름과 제목 서체를 쓰는 글자 이름(`AppTextStyles`의 어느 이름인지)도 한 줄 적습니다. 2-3이 이 줄을 읽습니다.

**이후 모든 화면·부품 코드는 `context.*` 이름으로만 값을 꺼냅니다** — 색·간격·글자 크기 숫자, `Colors.`, `Color(0x…)`를 화면에 적지 않습니다(스킬 철칙). 그래야 2-2가 1·2층 값을 바꿀 때 화면을 다시 만들지 않고도 따라옵니다.

**값은 대부분 `가정`입니다** — 브리프 「4」의 값 중 지위가 `가정`인 것은 그대로 1층에 넣되, 보고에 「`가정` 값으로 채운 1층 항목」으로 적습니다. 2-1이 화면을 보여 줄 때 사용자가 확인하고(`2-1-mockup.md` §2.6.5), 2-2가 다듬습니다. 사용자가 2-1 도중에 값을 바꾸면 1층과 브리프 「우리가 쓰는 값」 표를 함께 고칩니다 (`2-1-mockup.md` §2.7).

### 2.6 목업 캔버스 뼈대 넣기

**목업 캔버스**는 만든 화면을 모두 한 판에 펼쳐 보는 개발용 앱입니다. iPad 시뮬레이터에 띄우고, 화면을 흐름 순서로 늘어놓되 화면마다 보통 폰(아이폰 16 폭) 크기 창을 하나씩 둡니다. 멀리서는 미리 찍어 둔 그림(골든 그림)을, 확대하면 실제 화면을 보여 줍니다. 고칠 곳에 메모를 꽂을(코멘트 핀) 수 있고, 맨 끝 창에는 실제 토큰·부품으로 글자 단계·색 역할·간격·둥글기·부품 상태를 보여 주는 「[서비스 이름] 디자인 시스템」 페이지가 있습니다. 왼쪽 사이드바의 「흐름 묶음 / 단계」 전환으로, 지난 단계의 화면까지 단계마다 한 줄씩 펼쳐 비교해 볼 수도 있습니다. 사람이 2단계 내내 모든 화면을 한눈에 보는 자리입니다.

**하네스가 틀을 줍니다** — 뼈대 코드는 `.claude/templates/mockup-canvas/`에 있습니다. 파일 이름, 넣는 자리, 넣는 차례, 띄우는 법은 그 폴더의 `README.md`가 정본이고, 여기 다시 적지 않습니다.

**차례**:

1. **틀 넣기** — 틀 `README.md` §3 「프로젝트에 넣는 차례」 ①~⑦을 그대로 합니다. 상태 흉내 파일(`lib/core/dev_state/dev_state.dart`)은 §2.3에서 이미 넣었으니 건너뜁니다. 앱 뼈대가 flavor를 쓰므로 아이패드 지원 설정(⑥)은 기본 `Debug.xcconfig`·`Release.xcconfig` 두 파일에만 줄을 더합니다 — flavor 설정 파일은 앱 뼈대 틀이 이미 그 줄을 넣었습니다.
2. **서비스 이름 채우기** — 디자인 시스템 페이지(`lib/dev/design_system/design_system_page.dart`, design-system `bootstrap-project.md` §6)를 만들고 제목을 「[서비스 이름] 디자인 시스템」으로 둡니다(예: 「예시앱 디자인 시스템」). 「규칙 페이지」라고 부르지 않습니다. **페이지의 설명 글에 숫자 값을 쓰지 않습니다** — 값은 실제 테마에서 읽어 보여 줍니다. 글에 적은 숫자는 토큰이 바뀌어도 따라오지 못하고, 디자인 규칙 검사에도 걸립니다.
3. **목록 파일** — 자동 부분(`lib/dev/canvas/screens.generated.dart`)은 틀 그대로 빈 목록으로 둡니다. 지금은 화면이 없기 때문입니다. 2-1이 화면을 만들고 화면 목록 「주소」 칸을 채운 뒤 `fvm dart run tool/canvas_list.dart`로 만듭니다 (`2-1-mockup.md` §2.6.2). 손 부분(`screens.dart`)에는 디자인 시스템 페이지 창만 둡니다.
4. **가짜 저장소 자리** — `lib/dev/fakes/canvas_overrides.dart`는 틀 그대로(개발용 flavor 값 한 줄) 둡니다. 저장·조회 코드는 아직 없으니, 흐름마다 저장·조회 코드와 가짜 저장소는 2-1이 화면을 만들며 함께 만듭니다(틀 `README.md` §6).
5. **검사** — 틀 `README.md` §3 ⑧의 검사 중 화면을 열지 않는 것을 돌립니다. 분석, 골든을 뺀 테스트, 골든 그림 찍기(`--update-goldens` — 지금은 디자인 시스템 페이지 창뿐), 캔버스 진입점 빌드와 지원 기기 값 확인(캔버스는 `1 2`, 개발용 진입점은 `1`)입니다. 캔버스를 시뮬레이터에 띄워 보는 일은 사람 몫입니다.

**원칙**:

- **틀을 다시 짓지 않습니다** — 복사하고 이름만 채웁니다. 매번 새로 지으면 토큰이 들고 프로젝트마다 목업 캔버스가 달라집니다.
- **틀이 판과 안 맞으면 틀 고칠 문안을 냅니다** — 이 판의 Flutter·패키지 API가 틀과 다르면, 프로젝트에 복사한 파일만 고치고, `.claude/templates/`의 틀에 고칠 내용은 `[하네스 제안]` 문안으로 보고에 담습니다. 틀은 하네스 사본이라 여기서 고치면 다음 동기화 때 사라지고, 문안이 하네스 저장소에 반영돼야 다음 프로젝트가 같은 문제를 다시 만나지 않습니다.
- **실서비스 앱에는 캔버스가 없습니다** — 캔버스는 진입점(`lib/main_canvas.dart`)이 따로라 실서비스 빌드에 아예 들어가지 않습니다. `lib/main_prod.dart`가 `lib/dev/`를 불러오지 않는 것을 앱 뼈대의 검사 스크립트와 디자인 규칙 검사가 확인합니다.
- **캔버스는 Firebase를 켜지 않습니다** — 4단계 뒤에도 가짜 저장소로만 돕니다.
- **목업 캔버스는 사람이 보는 도구입니다** — AI는 캔버스를 띄워 보고 판정하지 않습니다 (`AGENTS.md` 「검증」). 골든 그림도 AI가 화면이 맞는지 판정하는 수단이 아닙니다.
- **4단계에도 남겨 둡니다** — 실서비스에 들어가지 않으니 해가 없고, 백엔드를 붙인 뒤에도 전 화면을 훑는 데 씁니다.

이 문서가 끝나도 사용자에게 화면을 따로 보여 주지 않습니다 — 볼 화면이 아직 없습니다. 2-1이 주요 화면을 만든 뒤 캔버스 띄우는 법과 함께 한 번에 보여 줍니다 (`2-1-mockup.md` §2.6.5). 대화창에는 「개발환경 준비가 끝났습니다」 한 줄과, 남은 사람 몫(있으면)만 알립니다.

### 2.7 Dart·Flutter 공식 플러그인 (선택)

Dart·Flutter 팀이 낸 클로드 코드 플러그인이 있습니다. 안에 Dart·Flutter 공식 MCP 서버(AI가 분석기 진단·기호 찾기·테스트 실행·실행 중인 앱 살펴보기를 직접 부르는 도구)가 들어 있습니다. 없어도 이 하네스의 절차는 막히지 않습니다 — 분석·테스트는 `fvm` 명령으로 돕니다. 그래서 **선택**이고, 이름 확인 질문(§2.1)과 같은 메시지에 한 줄로만 알립니다.

- **설치** (터미널에서):

  ```bash
  claude plugin marketplace add flutter/agent-plugins
  claude plugin install dart-flutter@dart-flutter
  ```

- **설치 범위는 사용자 전역을 권합니다** — 프로젝트마다 다시 깔지 않아도 됩니다.
- 설치는 사용자 설정을 바꾸는 일이라 AI가 대신 하지 않습니다. 명령과 이름은 바뀔 수 있으니, 안내하기 전에 Flutter 공식 문서의 AI 도구 안내 페이지로 다시 확인합니다.

## 3. 완료 체크리스트

2단계 전체의 완료 체크리스트는 `2-3-personality.md` §3입니다. 아래는 이 문서 몫입니다.

- [ ] **도구 점검표** (§2.1) — 지금 필요한 도구의 확인 결과를 한 표로 보여 줬습니다. AI가 깔 수 있는 것은 묻지 않고 깔았고, Android Studio는 묻고 깔았고, 깐 것을 결과 표로 알렸습니다. 사람 몫(Xcode, Android Studio 첫 설정과 약관, 폰의 USB 디버깅)을 한 단계씩 안내했습니다. Xcode가 4단계에 필요한 판보다 낮으면 「4단계 전에 업데이트」를 알렸습니다.

## 4. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — `AGENTS.md` 응답 톤(~입니다 체)·친근·짧게.
- **가벼운 설치는 묻지 않고 결과로 알립니다** — 「깔아도 될까요?」라고 묻지 않고, 무엇을 어떤 방법으로 깔았는지 결과 표로 알립니다(§2.1 「깐 것을 알리는 문안」). 원래 있던 Flutter·Node를 그대로 뒀으면 왜 그랬는지 한 줄(다른 프로젝트가 그 판을 쓸 수 있습니다)을 붙입니다.
- **큰 설치는 크기와 용도를 알리고 묻습니다** — Android Studio는 「수 GB이고, 안드로이드 앱을 빌드하는 데 필요합니다」처럼 알리고 답을 기다립니다.
- **사람 몫은 화면 이름 그대로, 한 단계씩** — 「설정 → 개발자 옵션 → USB 디버깅」처럼 사용자가 화면에서 보는 이름으로 적습니다. 관리자 암호가 필요한 명령은 그대로 복사해 칠 수 있게 코드 블록으로 줍니다. 끝나면 「됐어」라고만 알려 달라고 합니다.
- **도구 점검표는 표 하나로 끝냅니다** — 확인한 결과와 이어서 할 일만 적습니다. 다 있으면 한 줄로 줄입니다.
- **이름 질문은 짧게 한 번** — 왜 지금 못 박는지(플레이에 올리면 못 바꿉니다) 한 줄만 붙입니다. 판 숫자·패키지 이름 같은 조사 내용은 묻지 않습니다 — AI가 조사해 정하고 ADR에 남깁니다.
